### 1. WHAT IS IT?

A periodic snapshot from which training can restart *exactly*: model weights, **optimizer state** (AdamW moments; weights alone are not enough), step counter, LR-schedule position, **data-loader position / RNG state** and the config.

### 2. WHY DOES IT EXIST?

Long runs *will* crash (hardware faults, preemption, divergence). Checkpoints bound lost work to one interval and let you roll back past a bad region.

### 3. DETAILED EXPLANATION

Practices (all implemented in `lab/pretrain.py` at toy scale):

- **Atomic writes:** write `tmp`, then `os.replace`, so a crash mid-write never corrupts `latest.pt`.
- **Exact resume:** batches are a pure function of `(seed, step)` (`get_batch`), so no sampler state is needed and resumed == uninterrupted (`test_resume_matches_uninterrupted_run` checks identical loss and weights).
- **Keep several:** a rolling `latest` plus periodic permanent snapshots (`step_000200.pt`) to roll back further.
- **Metrics + provenance** next to the weights: config, parameter count, tokens seen, 6ND FLOPs, data fingerprint, torch/python versions, tokens/sec, full loss/LR/grad-norm history ([9.9](09.09-data-provenance.md)).
- **At scale:** sharded/async checkpoints (each rank writes its shard while training continues), checkpoint size ≈ 12-16 bytes per parameter with fp32 optimizer state ([9.23](09.23-distributed-pretraining.md)), and a *tested restore*: a checkpoint you never restored is a hope, not a backup.

![Resume](../figures/08_checkpoint_resume.png)

*Figure 8 — A 120-step run (thick blue) and a run stopped at step 60 and resumed from its checkpoint (thin orange) overlap exactly; the title reports the maximum difference measured in this lab.*

**Reproducibility checklist.** Seed everything (`seed_everything`), pin library versions (recorded in metrics), use deterministic algorithms (`torch.use_deterministic_algorithms`), log the dataset fingerprint, never depend on dict/set ordering or Python's randomised `hash()`. Bit-exact reproducibility across *different hardware or GPU counts* is generally **not** achievable; aim for statistical reproducibility there (`REVIEW_REQUIRED`).

### 4. HOW DOES IT WORK?

1. Every `ckpt_every` steps gather model, optimizer, step, config, history. 2. Write to a temp file. 3. Atomically rename to `latest.pt`. 4. Periodically keep a numbered copy. 5. On restart load `latest.pt`, restore model and optimizer, continue from `step` (the learning rate and batch are functions of step and seed). 6. Verify by comparing a resumed vs uninterrupted run.

### 5. SIMPLE EXAMPLE

A save-game in a video game: position, inventory and quest log, not just the character's face.

### 6. TECHNICAL EXAMPLE

Stop a lab run at step 60, call `train(..., resume=True)`; the loss curve and final weights equal those of the uninterrupted 120-step run to about 1e-6, because Adam moments, step and data order were all restored.

### 7. CODE

```python
# Run from lab/: stop at step 30, resume, and compare with an uninterrupted run (about 10 s).
import tempfile, numpy as np
import run_lab
from model import ModelConfig
from pretrain import TrainConfig, train

tok, tr, va, _ = run_lab.prepare()
mk = lambda: TrainConfig(steps=60, eval_every=30, ckpt_every=30, model=ModelConfig(vocab_size=tok.vocab_size))
a, b = tempfile.mkdtemp(), tempfile.mkdtemp()
full = train(mk(), tr, va, a)
train(mk(), tr, va, b, stop_at=30)
res = train(mk(), tr, va, b, resume=True)
la = [h["loss"] for h in full["history"]["train"]]; lb = [h["loss"] for h in res["history"]["train"]]
print("max loss diff:", np.max(np.abs(np.array(la) - np.array(lb))))
```

Source: [`../lab/pretrain.py`](../lab/pretrain.py) (`save_checkpoint`, `load_checkpoint`, `train`).

### 8. INPUT → PROCESS → OUTPUT

```
training state (weights, optimizer, step, RNG/data position, config) -> tmp write -> atomic rename -> latest.pt (+ numbered snapshots, metrics.json)
```

### 9. ENTERPRISE USE CASE

Cluster jobs are preempted or fail; automatic restart from the most recent *validated* checkpoint is a platform requirement, along with retention policy, encryption at rest and a manifest linking checkpoint, dataset version and code commit.

### 10. AI ENGINEERING CONNECTION

Released base models are checkpoints; fine-tuning ([Tier 10](../../tier-10-fine-tuning-alignment/README.md)) starts from one, and intermediate checkpoints enable continued pretraining ([9.29](09.29-continued-pretraining.md)), evaluation over training time and model merging.

### 11. ADVANTAGES

- Bounded loss of work on failure; ability to roll back before a bad region.
- Enables continued pretraining, branching experiments and auditing.

### 12. LIMITATIONS

- Large (12-16 bytes per parameter with optimizer state) and slow to write at scale.
- Restores can fail silently if never tested; bit-exact resume across different hardware or parallelism is not generally guaranteed.

### 13. TRADE-OFFS

Frequent checkpoints: less lost work, more I/O overhead. Rare checkpoints: cheap, but a crash costs hours. Sync vs async writes; local fast storage vs durable remote storage.

### 14. COMMON MISTAKES

- Saving weights only (resume silently changes the optimisation).
- Non-atomic writes leaving a corrupt `latest`.
- Never testing a restore.
- Restarting from the *last* checkpoint when the bad region began earlier.

### 15. PERFORMANCE / COST CONSIDERATIONS

Write time subtracts from MFU unless async/sharded; choose the interval so expected lost work (half an interval per failure) balances write overhead. Retain few full snapshots to control storage cost.

### 16. SECURITY CONSIDERATIONS

Loading a checkpoint via `pickle` (`torch.load(weights_only=False)`, as the lab does for its own files) can **execute arbitrary code**: load only checkpoints you created or trust, prefer safe tensor formats such as safetensors for sharing, and sign/verify artefacts. Encrypt checkpoints at rest: weights can leak memorised training data.

### 17. INTERVIEW EXPLANATION

"A pretraining checkpoint is a save-game: weights plus optimizer state, step and schedule position, data-loader position or RNG, and the config. I'd write atomically, keep rolling and permanent snapshots, record the data fingerprint, and test restore. If batches are a pure function of seed and step, resume is exact — and I'd verify that rather than assume it."

### 18. RAPID-FIRE ANSWER

Weights + optimizer + step + data position + RNG + config, written atomically and restore-tested.
