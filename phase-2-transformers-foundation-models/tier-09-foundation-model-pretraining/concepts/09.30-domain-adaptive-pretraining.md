### 1. WHAT IS IT?

Continued pretraining on a **domain corpus** (legal, biomedical, code, an enterprise's own documents) before task-specific fine-tuning.

### 2. WHY DOES IT EXIST?

Vocabulary, style, notation and facts of a specialised domain are absorbed with far more tokens than a fine-tune would use, which helps when the domain's language is far from general web text.

### 3. DETAILED EXPLANATION

Costs: compute, curation effort, forgetting general skills, and **data-governance risk**: private documents baked into weights cannot be selectively deleted. Often *RAG (Tier 20) or fine-tuning ([Tier 10](../../tier-10-fine-tuning-alignment/README.md)) is cheaper and safer*.

Decision rule of thumb (`REVIEW_REQUIRED` as guidance, not law): use RAG for **knowledge that changes or must be cited/deleted**; fine-tune for **behaviour/format**; use domain-adaptive pretraining when the **language of the domain itself** is far from web text *and* you have lots of clean in-domain text.

```
Does the knowledge change often or must it be cited/deleted per document?   -> RAG (Tier 20)
Is the need mainly style / format / task behaviour?                          -> fine-tuning (Tier 10)
Is the domain's language far from web text AND you own lots of clean text?   -> domain-adaptive pretraining (this tier)
                                                                                + replay + regression evals ([9.29](09.29-continued-pretraining.md))
```

### 4. HOW DOES IT WORK?

1. Collect, clean, dedup and license-check the domain corpus ([9.3](09.03-data-cleaning.md)-[9.10](09.10-data-licensing.md)). 2. Choose a mixture of domain data plus general replay. 3. Run continued pretraining with a gentle schedule ([9.29](09.29-continued-pretraining.md)). 4. Evaluate domain and general capabilities (per-domain loss and downstream evals). 5. Fine-tune for the task.

### 5. SIMPLE EXAMPLE

A generalist doctor spends a year immersed in oncology literature before starting oncology residency tasks, while still keeping up basic medicine.

### 6. TECHNICAL EXAMPLE

A biomedical model is continued-pretrained on 50B tokens of papers with 20% general replay; per-domain validation loss on biomedical text falls substantially while general loss rises slightly; downstream biomedical QA benefits (illustrative; `REVIEW_REQUIRED` for any quantified claim).

### 7. CODE

```python
# Mixture with replay for a domain-adaptive run, using the lab's mixer (domain = "code" here; 20% general replay).
from collections import Counter
import data_prep as dp

docs = dp.make_synthetic_crawl(0, 400)
weights = {"code": 0.8, "wiki": 0.1, "web": 0.05, "chat": 0.05}      # domain-heavy with a general replay slice
mixed = dp.mix_sources(docs, weights, total_docs=len(docs), seed=0)
print({k: round(v / len(mixed), 2) for k, v in Counter(d["source"] for d in mixed).items()})
```

### 8. INPUT → PROCESS → OUTPUT

```
domain corpus (+ general replay) -> cleaned, deduped, licensed -> continued pretraining -> domain-adapted base -> fine-tune
```

### 9. ENTERPRISE USE CASE

A firm with a large, clean, owned archive of domain documents and a need for strong jargon handling (e.g. claims, clinical, engineering notation) may justify it; a firm whose knowledge changes weekly should use RAG.

### 10. AI ENGINEERING CONNECTION

It is one option in the adaptation ladder: prompting, RAG, fine-tuning, domain-adaptive pretraining, full pretraining. Choose the lowest rung that meets the requirements; evaluation (Tier 15, with Tier 30 for production) decides.

### 11. ADVANTAGES

- Deep absorption of domain vocabulary and style.
- Better base for downstream fine-tuning in that domain.

### 12. LIMITATIONS

- Costly; forgetting risk; knowledge frozen at training time.
- Private data in weights cannot be deleted per document.

### 13. TRADE-OFFS

Specialisation vs generality; compute and curation cost vs RAG/fine-tune simplicity; control (own the weights) vs maintainability.

### 14. COMMON MISTAKES

- Doing it to inject facts that change or must be cited (use RAG).
- No replay data and no regression evals.
- Skipping access-control and PII scrubbing on internal documents.

### 15. PERFORMANCE / COST CONSIDERATIONS

Compute `6 N D_domain` plus data curation and evaluation; usually orders of magnitude less than pretraining from scratch but far more than a LoRA fine-tune.

### 16. SECURITY CONSIDERATIONS

Anything in the adaptation corpus can be memorised and regurgitated: apply access-control-aware filtering (a user must not extract documents they could not read), PII/secret scrubbing and membership-inference review before training.

### 17. INTERVIEW EXPLANATION

"I'd do domain-adaptive pretraining instead of RAG only when the domain's text distribution is genuinely different — notation, jargon, code dialect — I have a large clean corpus, knowledge doesn't need to be deletable or cited per document, and I can afford the compute. Otherwise RAG for changing or citable knowledge and fine-tuning for behaviour."

### 18. RAPID-FIRE ANSWER

Continued pretraining on a domain corpus; justified only when the domain language is far from web text and governance allows baking data into weights.
