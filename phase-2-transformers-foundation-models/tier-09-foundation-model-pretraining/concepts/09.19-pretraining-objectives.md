### 1. WHAT IS IT?

The family of training objectives beyond plain next-token and masked prediction: **span corruption / denoising** (T5/BART style), **prefix-LM**, **fill-in-the-middle (FIM)**, **multi-token prediction** and **auxiliary losses** (MoE balancing loss, router z-loss).

### 2. WHY DOES IT EXIST?

Different objectives give different capabilities: infilling for code editors, encoder-decoder behaviour for translation/summarisation, extra signal per token from multiple-token heads, and regularisers that keep sparse models stable.

### 3. DETAILED EXPLANATION

- **Span corruption / denoising:** replace spans with sentinels; the model reconstructs them (definitions in Tier 8).
- **Prefix-LM:** bidirectional attention over a prefix, causal over the suffix; loss on the suffix.
- **Fill-in-the-middle:** rearrange a document into `prefix, suffix, middle` with sentinel tokens and train left-to-right so the model learns to infill (`REVIEW_REQUIRED` for exact recipes).
- **Multi-token prediction:** extra heads predict several future tokens (active research, `REVIEW_REQUIRED`).
- **Auxiliary losses:** the MoE balancing loss ([9.27](09.27-load-balancing.md)), z-loss on logits or router ([9.28](09.28-training-stability.md)).

Choosing the objective chooses the model family; the data pipeline and scaling reasoning in this tier are the same for all of them.

### 4. HOW DOES IT WORK?

Each objective is a recipe for (a) transforming the token stream into inputs and targets, (b) a choice of attention mask, and (c) which positions are scored. Total loss = main loss + weighted auxiliary losses.

### 5. SIMPLE EXAMPLE

Autocomplete for the end of a sentence (next-token) vs autocomplete for a blank in the middle of a paragraph (FIM) — the second needs the text after the blank as well.

### 6. TECHNICAL EXAMPLE

A code model trained with FIM can complete a function body given the signature (prefix) and the return statement (suffix); the same model still does ordinary left-to-right completion.

### 7. CODE

```python
# Fill-in-the-middle transform (PSM format) — standalone sketch; sentinel names are placeholders (REVIEW_REQUIRED).
import random

def fim_transform(text: str, rng: random.Random, pre="<PRE>", suf="<SUF>", mid="<MID>") -> str:
    a, b = sorted(rng.sample(range(len(text) + 1), 2))      # cut the document at two points
    prefix, middle, suffix = text[:a], text[a:b], text[b:]
    return f"{pre}{prefix}{suf}{suffix}{mid}{middle}"        # train left-to-right on this string

print(fim_transform("def add(a, b):\n    return a + b\n", random.Random(0)))
```

### 8. INPUT → PROCESS → OUTPUT

```
document -> objective-specific transform + mask -> model -> scored positions only -> main loss + auxiliary losses
```

### 9. ENTERPRISE USE CASE

Internal code assistants benefit from FIM-capable base models; document-understanding systems may prefer encoder-decoder denoising models.

### 10. AI ENGINEERING CONNECTION

Model cards list objective variants (FIM support, long-context phases, multi-token heads); they determine which inference modes (infilling, speculative decoding with extra heads, [Tier 11](../../tier-11-llm-inference-optimization/README.md)) a model supports.

### 11. ADVANTAGES

- Adds capabilities (infilling) or training signal at little cost.
- Auxiliary losses stabilise sparse models.

### 12. LIMITATIONS

- More recipe complexity; benefits are model- and data-specific.
- Transformed text changes the data distribution (sentinel tokens) and the evaluation protocol.

### 13. TRADE-OFFS

Extra objectives can slightly lower plain left-to-right quality or complicate evaluation; they buy specific capabilities.

### 14. COMMON MISTAKES

- Comparing losses across objectives.
- Forgetting to add sentinel tokens to the tokenizer ([Tier 6](../../tier-06-tokenization-embeddings/README.md)).
- Mis-weighting auxiliary losses so they dominate the main loss.

### 15. PERFORMANCE / COST CONSIDERATIONS

Multi-token heads add parameters and compute; FIM changes only the data transform (nearly free); denoising adds encoder-decoder cost.

### 16. SECURITY CONSIDERATIONS

FIM-trained code models can be prompted to infill secrets from surrounding context; the same scrubbing requirements apply.

### 17. INTERVIEW EXPLANATION

"Beyond plain next-token loss there are variants: span corruption for encoder-decoder models, prefix-LM, fill-in-the-middle so code models can infill, multi-token prediction heads, and auxiliary losses like the MoE balancing loss. The objective picks the model family; the data pipeline and scaling reasoning stay the same."

### 18. RAPID-FIRE ANSWER

Variants (denoising, prefix-LM, FIM, multi-token, auxiliary losses) that trade simplicity for capabilities or stability.
