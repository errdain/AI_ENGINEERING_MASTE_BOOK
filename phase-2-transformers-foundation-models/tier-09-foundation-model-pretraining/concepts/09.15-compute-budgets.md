### 1. WHAT IS IT?

Estimating training cost: **FLOPs ≈ 6·N·D**, converted to GPU-time and money using hardware peak throughput and utilisation (MFU).

### 2. WHY DOES IT EXIST?

Pretraining costs are large and mostly committed up front. You need a first-order estimate before launching, to compare plans and to detect whether a run is behaving as expected.

### 3. DETAILED EXPLANATION

**The 6ND rule.** For a dense Transformer, training FLOPs ≈ `6 · N · D`: ≈ `2ND` for the forward pass (one multiply-add per parameter per token) plus ≈ `4ND` for the backward pass. It ignores attention's sequence-length term, embeddings and overheads, so it is a first-order estimate.

**From FLOPs to time and money.** `GPU-seconds = 6ND / (peak FLOP/s x MFU)`. **MFU** (model-FLOPs utilisation) is the fraction of hardware peak you really achieve; large-scale runs commonly land well below 100% (figures like 30-50% are often quoted; `REVIEW_REQUIRED`). Cost = GPU-hours x price per GPU-hour, **plus** failed runs, restarts, ablations, data processing, storage, evaluation and people, often a multiple of the headline.

### 4. HOW DOES IT WORK?

1. Pick N (active parameters for MoE) and D. 2. `C = 6ND`. 3. Choose hardware: peak FLOP/s per GPU, number of GPUs, expected MFU. 4. `T = C / (GPUs x peak x MFU)`. 5. Multiply by price. 6. Add overhead for restarts/ablations/people.

### 5. SIMPLE EXAMPLE

A road trip: distance (FLOPs) divided by effective speed (peak x MFU) gives time; fuel price gives cost; detours and breakdowns add more.

### 6. TECHNICAL EXAMPLE

7B parameters and 1T tokens: `6ND = 4.2e22` FLOPs. At 400 TFLOP/s peak, 40% MFU, 2,048 GPUs: `4.2e22 / (400e12 x 0.4 x 2048)` ≈ 1.28e5 s ≈ **1.5 days** of pure compute (hardware figures here are illustrative; `REVIEW_REQUIRED`). The lab: 128,512 parameters x 204,800 tokens x 6 ≈ 1.6e11 FLOPs (`flops_6nd`, `test_6nd_rule`).

### 7. CODE

```python
# Run from lab/: the 6ND rule and a GPU-time estimate.
from pretrain import flops_6nd

def gpu_days(n_params: float, n_tokens: float, peak_tflops: float, mfu: float, n_gpus: int) -> float:
    seconds = flops_6nd(n_params, n_tokens) / (peak_tflops * 1e12 * mfu * n_gpus)
    return seconds / 86400

print(flops_6nd(7e9, 1e12))                          # 4.2e22
print(gpu_days(7e9, 1e12, 400, 0.40, 2048))          # about 1.5 days
```

Source: [`../lab/pretrain.py`](../lab/pretrain.py).

### 8. INPUT → PROCESS → OUTPUT

```
N, D -> C = 6ND -> / (GPUs x peak x MFU) -> wall-clock time -> x $/GPU-hour -> headline cost (+ overheads)
```

### 9. ENTERPRISE USE CASE

Business cases for custom or continued pretraining start here: GPU-hours, reserved vs on-demand pricing, and a risk multiplier for restarts and ablations, compared against RAG or fine-tuning alternatives.

### 10. AI ENGINEERING CONNECTION

The same `2N` FLOPs per token (forward only) underlies inference-cost reasoning ([Tier 11](../../tier-11-llm-inference-optimization/README.md)); active vs total parameters matters for MoE ([9.25](09.25-mixture-of-experts-pretraining.md)).

### 11. ADVANTAGES

- Simple, surprisingly predictive first-order estimate.
- Lets you compare plans in minutes.

### 12. LIMITATIONS

- Ignores attention's O(T²) term (matters for long context), embeddings, activation recomputation, and communication overhead.
- MFU is an assumption; real values depend on hardware, software and parallelism.

### 13. TRADE-OFFS

Faster time-to-train (more GPUs) vs lower efficiency (communication overhead, lower MFU) and higher failure exposure.

### 14. COMMON MISTAKES

- Using total instead of active parameters for MoE.
- Assuming 100% MFU.
- Quoting only compute cost, forgetting ablations, restarts, data and people.

### 15. PERFORMANCE / COST CONSIDERATIONS

Track MFU during the run as a health metric; a sudden drop signals a straggler, data-loader stall or hardware fault. Include checkpointing and evaluation overhead in plans.

### 16. SECURITY CONSIDERATIONS

Large GPU allocations are valuable targets (credential theft, cryptomining); use least-privilege access, audit logs and budget alerts.

### 17. INTERVIEW EXPLANATION

"Training FLOPs for a dense Transformer are about six times parameters times tokens — two for the forward pass, four for the backward. Divide by peak FLOP/s times MFU times number of GPUs for time, multiply by price for cost, and then add a realistic multiplier for failed runs and ablations. It's first-order, but it's what I'd use to compare plans."

### 18. RAPID-FIRE ANSWER

`FLOPs ≈ 6ND`; time = FLOPs / (GPUs x peak x MFU).
