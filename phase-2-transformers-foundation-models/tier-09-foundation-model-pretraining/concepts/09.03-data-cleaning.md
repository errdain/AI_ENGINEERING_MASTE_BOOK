### 1. WHAT IS IT?

Deterministic repair and removal of artefacts in raw text: HTML/script stripping, navigation and cookie boilerplate removal, Unicode normalisation, removal of control and zero-width characters, whitespace collapsing, mojibake repair, and dropping obviously truncated documents.

### 2. WHY DOES IT EXIST?

Models learn whatever is in the stream, including markup junk, invisible characters and boilerplate. Cleaning removes that noise cheaply, before the costlier filters and before training.

### 3. DETAILED EXPLANATION

Cleaning is *repair*; quality filtering ([9.4](09.04-quality-filtering.md)) is *selection*. Log what changed, and preserve content that is meaningful in some domains (code indentation, table structure, non-ASCII scripts). Apply the same normalisation (e.g. NFC) that the tokenizer assumes ([Tier 6](../../tier-06-tokenization-embeddings/README.md)), and the same cleaning at training and serving time where the model sees user text.

![Funnel](../figures/01_data_pipeline_funnel.png)

*Figure 1 — The "cleaned" bar barely drops documents (it repairs text); the big drops come from the filters after it.*

### 4. HOW DOES IT WORK?

`clean_text` in the lab: (1) NFC-normalise; (2) remove `<script>`, `<style>` and tags; (3) remove cookie-banner boilerplate; (4) delete control and zero-width characters; (5) collapse runs of spaces/tabs and 3+ newlines; (6) strip. Newlines are kept, but note the **known limitation** (found while verifying this chapter): the step that collapses runs of spaces/tabs to one space also shrinks code indentation (a 4-space indent becomes 1 space). The module docstring claims indentation is kept; the code does not do that. For a toy corpus it is harmless, for real code data it is exactly the over-cleaning bug listed below (`REVIEW_REQUIRED`: fix in `lab/data_prep.py` by collapsing only *inner* whitespace and preserving leading whitespace; see the exercise).

### 5. SIMPLE EXAMPLE

Scanning a book: remove the coffee stains and page numbers, but keep the paragraph breaks.

### 6. TECHNICAL EXAMPLE

A web page with `<div class='nav'>`, a cookie banner and a `<script>` tag is reduced to its single real sentence, which then faces the quality filter.

### 7. CODE

```python
# Run from lab/: HTML/NFC behaviour is covered by test_clean_text_strips_html_and_normalises; the second half shows the indentation limitation.
from data_prep import clean_text

assert clean_text("<p>Café ​ok</p><script>x=1</script>") == "Café ok"
code = "def f(x):\n    return x + 1\n"
print(repr(clean_text(code)))                    # 'def f(x):\n return x + 1'
assert clean_text(code) == "def f(x):\n return x + 1"   # newlines kept, but the 4-space indent collapsed to 1: the classic bug
print("ok")
```

### 8. INPUT → PROCESS → OUTPUT

```
raw HTML/text -> NFC -> strip markup/boilerplate -> drop control chars -> collapse whitespace -> clean text
```

### 9. ENTERPRISE USE CASE

Cleaning internal documents (PDF-to-text artefacts, email signatures, confidentiality footers) before training or RAG indexing.

### 10. AI ENGINEERING CONNECTION

The same cleaner feeds RAG ingestion and fine-tuning sets. A mismatch between cleaning at train time and at inference time quietly degrades quality.

### 11. ADVANTAGES

- Cheap, deterministic, explainable.
- Removes noise that would otherwise burn tokens (and parameters) on junk.

### 12. LIMITATIONS

- Rules are brittle; HTML extraction is imperfect (lost tables, merged columns).
- Cannot judge whether text is *good*, only well-formed.

### 13. TRADE-OFFS

Aggressive cleaning gives tidy text but risks deleting signal (code layout, rare scripts); light cleaning keeps signal but passes noise to later stages.

### 14. COMMON MISTAKES

- Over-cleaning **code** (collapsing indentation destroys Python); the lab's `clean_text` has exactly this flaw today.
- Cleaning that differs between training and serving.
- Throwing away non-English text because the cleaner assumed ASCII.

### 15. PERFORMANCE / COST CONSIDERATIONS

Embarrassingly parallel and cheap per document, but at trillions of tokens it is a distributed job; regex backtracking on pathological pages can be a hidden cost.

### 16. SECURITY CONSIDERATIONS

Hidden or zero-width text can carry injected instructions; stripping invisible characters is a (partial) defence. Do not execute or render scraped HTML.

### 17. INTERVIEW EXPLANATION

"Cleaning is the deterministic repair step: strip markup and boilerplate, normalise Unicode, remove control and zero-width characters, collapse whitespace. It's different from quality filtering, which decides whether a document is worth keeping. The classic bug is over-cleaning code or non-English text, and I'd test the cleaner on code explicitly."

### 18. RAPID-FIRE ANSWER

Repair artefacts deterministically (markup, boilerplate, bad characters) without deleting real signal.

### 19. INTERVIEW QUESTIONS

- **Basic:** What is the difference between cleaning and filtering?
- **Intermediate:** Why must Unicode normalisation match the tokenizer's?
- **Advanced:** How do you evaluate that a cleaner did not hurt code data?
- **Scenario:** Python completions lose indentation after a data refresh. Where do you look?
