### 1. WHAT IS IT?

The same idea as language balancing, along the *topic/genre* axis: web prose vs code vs math vs dialogue vs scientific text vs legal/medical text.

### 2. WHY DOES IT EXIST?

Domain mix shapes what the model is good at. More code tends to improve code and, often, structured reasoning (a widely reported effect; `REVIEW_REQUIRED`). An unbalanced mix gives a model that is fluent in whatever was cheapest to collect.

### 3. DETAILED EXPLANATION

Domains are tagged by source or by a classifier; the mixture machinery ([9.6](09.06-data-mixture-design.md)) sets shares. The essential discipline is **per-domain validation loss** ([9.31](09.31-pretraining-evaluation.md)): an improving average can hide one domain getting worse when you change shares.

![Mixture and epochs](../figures/03_mixture_epochs.png)

*Figure 3 — Domain shares and the epochs they imply. In the lab the sources `wiki`, `web`, `code`, `chat` play the role of domains; try the weights in [mixture_explorer.html](../interactive/mixture_explorer.html).*

### 4. HOW DOES IT WORK?

1. Tag documents by domain. 2. Set target shares from capability goals. 3. Check epochs per domain. 4. Train proxies; compare per-domain loss and downstream evals. 5. Adjust shares; re-check.

### 5. SIMPLE EXAMPLE

A cook who practises only soup becomes great at soup; adding baking lessons costs some soup practice time.

### 6. TECHNICAL EXAMPLE

Raising code from 10% to 20% typically lowers code-domain loss; you check that the web-prose and math domain losses did not regress and that the small code corpus is not repeated beyond a few epochs.

### 7. CODE

```python
# Per-domain validation loss from the lab's validation documents (sketch of the monitoring habit).
from collections import defaultdict
import data_prep as dp

docs = dp.make_synthetic_crawl(0, 300)
_, va = dp.split_train_val(docs)
by_domain = defaultdict(list)
for d in va:
    by_domain[d["source"]].append(d)
print({k: len(v) for k, v in by_domain.items()})   # evaluate the model on each group separately
```

### 8. INPUT → PROCESS → OUTPUT

```
domain tags + capability goals -> target shares -> proxy ablations -> per-domain loss table -> adjusted shares
```

### 9. ENTERPRISE USE CASE

A legal-tech firm balances general text against contracts and case law, tracking loss on each so general fluency does not degrade as legal share rises.

### 10. AI ENGINEERING CONNECTION

Domain share explains model strengths (code, math, medical) and informs whether domain-adaptive pretraining, fine-tuning or RAG is the right tool for a use case.

### 11. ADVANTAGES

- Steers capability profile directly.
- Per-domain monitoring catches regressions early.

### 12. LIMITATIONS

- Domain boundaries are fuzzy; tagging errors blur shares.
- Cross-domain transfer is hard to predict.

### 13. TRADE-OFFS

Specialist strength vs generalist breadth; more of a domain vs repetition of its limited data.

### 14. COMMON MISTAKES

- Watching only the average validation loss.
- Domain shares set by availability, not target capability.
- No domain-tagged validation sets.

### 15. PERFORMANCE / COST CONSIDERATIONS

Domain-tagged evaluation is cheap compared with training; the cost is building and maintaining clean per-domain validation sets.

### 16. SECURITY CONSIDERATIONS

Domains such as code and medical text carry domain-specific risks (secrets in code, patient data); scrub before up-weighting them.

### 17. INTERVIEW EXPLANATION

"Domain balancing is mixture design along the topic axis — prose, code, math, dialogue, specialist text. The mix shapes capabilities, so I'd set shares from target evals and always track per-domain validation loss, since the average can hide a regression in one domain."

### 18. RAPID-FIRE ANSWER

Choose topic/genre shares from capability goals and monitor per-domain loss.
