### 1. WHAT IS IT?

The vocabulary is the ordered table mapping each token (string or bytes) to an integer ID, plus the rules (merges, probabilities) needed to produce those tokens from text.

### 2. WHY DOES IT EXIST?

A model with fixed-size embedding and output layers needs a closed, finite set of symbols agreed between training and inference.

### 3. DETAILED EXPLANATION

The vocabulary has size V. That number sets the shape of the embedding matrix `V x d` ([6.18 Embedding matrix](06.18-embedding-matrix.md)) and of the output layer (V logits per position). It contains base symbols, learned pieces and special tokens ([6.8 UNK](06.08-unk.md)-[6.11 EOS](06.11-eos.md)).

Vocabulary and weights are inseparable: ID 5231 means row 5231 of *this* checkpoint's matrix. Examples of sizes (`REVIEW_REQUIRED`, verify per model card): GPT-2 about 50k, BERT-base about 30k, Llama 2 about 32k, newer Llama/GPT-4-class models roughly 100k-200k+.

### 4. HOW DOES IT WORK?

Training produces `token -> id` and often `id -> token` plus merges/probabilities; serialization writes them to files (`vocab.json`, `merges.txt`, `.model`, `tokenizer.json` depending on library, `REVIEW_REQUIRED`). The lab exposes `ByteBPE.vocab` and `vocab_size = 4 specials + 256 bytes + #merges`.

### 5. SIMPLE EXAMPLE

The legend of a map: everyone using the map must agree on what each symbol means.

### 6. TECHNICAL EXAMPLE

Adding 3 chat special tokens to a base model means resizing the embedding and output matrices (`V -> V+3`), initializing the new rows, and fine-tuning so they acquire meaning.

### 7. CODE

```python
# run inside lab/
from mini_bpe import ByteBPE
tok = ByteBPE.train("low lower lowest " * 20, num_merges=10)
print(tok.vocab_size == 4 + 256 + len(tok.merges))   # True (training may stop early if no pair repeats)
print(tok.vocab[tok.offset + 256])    # first learned merge as bytes
```

### 8. INPUT → PROCESS → OUTPUT

```
corpus ──train──► {token -> id} + merges ──► frozen artifact shipped with the weights
```

### 9. ENTERPRISE USE CASE

Model registries version tokenizer files together with checkpoints; a mismatched tokenizer is a classic deployment incident.

### 10. AI ENGINEERING CONNECTION

V determines embedding/softmax memory ([6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md)) and which strings are cheap or expensive in tokens.

### 11. ADVANTAGES

Closed finite alphabet enables fixed-size layers and fast lookup.

### 12. LIMITATIONS

Frozen after training; extending requires embedding surgery; different models are not interchangeable.

### 13. TRADE-OFFS

Large V: fewer tokens but bigger layers and rarer-token undertraining; small V: the opposite.

### 14. COMMON MISTAKES

- Loading a tokenizer from model A with weights from model B.
- Resizing the vocabulary without initializing/training new rows.
- Not versioning tokenizer files.

### 15. PERFORMANCE / COST CONSIDERATIONS

Embedding + output head cost O(V d) parameters/memory each; see the calculator in [explore: `vocab_tradeoff.html`](../interactive/vocab_tradeoff.html).

### 16. SECURITY CONSIDERATIONS

Treat tokenizer files as code-adjacent artifacts: verify checksums and avoid loading from untrusted sources (some formats may execute code when loaded; check your library, `REVIEW_REQUIRED`).

### 17. INTERVIEW EXPLANATION

*"The vocabulary is the fixed table of tokens and their IDs. Its size sets the embedding and output-layer shapes, and it must ship with the model weights because IDs index weight rows."*

### 18. RAPID-FIRE ANSWER

The frozen token-to-ID table; its size V sets the embedding shape.
