### 1. WHAT IS IT?

A realtime speech system lets users converse naturally with an AI by voice: streaming ASR, an LLM (or speech-to-speech model), and streaming TTS, wired through transport, endpointing and interruption handling (barge-in) to keep the response delay low.

### 2. WHY DOES IT EXIST?

Human conversation has gaps of a few hundred milliseconds; much more feels laggy and much less means interrupting. Voice products succeed or fail on this latency and turn-taking behaviour.

### 3. DETAILED EXPLANATION

**Cascaded architecture.** mic -> VAD/endpointing ([14.13](14.13-speech-segmentation.md)) -> streaming ASR ([14.18](14.18-streaming-speech.md)) -> LLM (streaming tokens) -> sentence chunker -> streaming TTS ([14.16](14.16-text-to-speech-tts.md)) -> speaker. Latency is the sum of stages (Figure 9, right: endpoint 400 ms + ASR 300 + LLM first token 500 + TTS first audio 250 + network 150 = 1.6 s with *illustrative* numbers; common rule-of-thumb targets are well under a second, `REVIEW_REQUIRED`).

**End-to-end speech-to-speech models.** Audio-in audio-out models (some full-duplex, listening while speaking) skip text and can respond faster and with richer prosody, at the price of control, tooling and evaluation maturity (`REVIEW_REQUIRED`).

**Turn-taking.** *Endpointing* (when has the user finished?), *barge-in* (user speaks over the agent: stop TTS immediately, flush buffers, cancel the LLM request), backchannels ('mm-hm'), and echo cancellation so the agent does not hear itself.

**Transport.** WebRTC (UDP, jitter buffers, Opus audio in ~20 ms frames) vs WebSocket (TCP, easier, head-of-line blocking) (`REVIEW_REQUIRED` for current practice).

**Latency tactics.** Overlap stages (start TTS on the first LLM sentence), speculative LLM start on stable partial transcripts, keep connections warm, co-locate services, smaller models for first response, filler phrases ('let me check...').

**Observability.** Per-turn timeline: end-of-speech time, ASR final, LLM first token, TTS first byte, first audio played. Track p50/p95 and interruption success rate.

```
user speech ─► [VAD+ASR streaming] ─► final text ─► LLM stream ─► sentence 1 ─► TTS stream ─► audio out
        ◄──────────── barge-in: stop TTS, cancel LLM, flush audio buffer ◄────────── user speaks again
```

### 5. SIMPLE EXAMPLE

A phone call with a very fast assistant: it must notice when you finish, answer promptly, and stop talking the instant you interrupt.

### 6. TECHNICAL EXAMPLE

A voice-agent server keeps one WebSocket per call, runs streaming ASR, calls an LLM with streaming enabled, splits output at sentence boundaries, streams TTS chunks back, and cancels all in-flight work on barge-in.

### 7. CODE

```python
# run inside lab/ -- latency-budget arithmetic and a barge-in-style endpoint rule
import numpy as np
from audio_core import energy_vad, tone, noise, streaming_latency

stages = {"endpoint": 0.40, "asr_final": 0.30, "llm_first_token": 0.50, "tts_first_audio": 0.25, "network": 0.15}
print(round(sum(stages.values()), 2), "s end-of-speech -> first audio (illustrative)")

sr = 8000                                           # endpointing: speech, then 0.6 s silence
x = np.concatenate([tone(300, 0.5, sr), noise(0.6, sr, 0.001)])
flags = energy_vad(x, sr, frame_ms=20, threshold_db=-30, hangover=2)
silence_frames = len(flags) - np.where(flags)[0].max() - 1
print("trailing silence after speech:", silence_frames * 20, "ms -> endpoint fires if >= 400 ms")
```

### 9. ENTERPRISE USE CASE

Customer-support voice agents, drive-through ordering, in-car assistants: they are judged on latency, interruption handling, containment rate and handoff to humans; compliance requires call recording consent and PII redaction.

### 10. AI ENGINEERING CONNECTION

This is where LLM serving ([Tier 11](../../tier-11-llm-inference-optimization/README.md): time to first token, streaming), tool use, and speech meet; agent frameworks add function calling during the call.

### 11. ADVANTAGES

Natural interaction, hands-free, accessible; cascaded designs are debuggable and swap-able.

### 12. LIMITATIONS

Latency stacking, interruptions, echo, noisy audio, accents; ASR errors propagate to the LLM; speech-to-speech models are harder to control and audit.

### 13. TRADE-OFFS

Cascaded (modular, controllable, slower) vs speech-to-speech (faster, more natural, less transparent); aggressive endpointing vs cutting users off; cost per minute vs quality.

### 14. COMMON MISTAKES

- Waiting for the full LLM answer before TTS.
- No barge-in cancel (agent talks over user).
- Measuring only average latency.
- No echo cancellation.
- Logging raw audio and PII unredacted.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost per minute = ASR + LLM tokens + TTS characters + telephony; concurrency limited by GPU/stream state. Autoscale on concurrent calls; keep warm pools to avoid cold starts.

### 16. SECURITY CONSIDERATIONS

Prompt injection by voice ('ignore previous instructions'), toll fraud, voice-clone impersonation of callers, recording-consent laws and PII; require authentication for sensitive actions beyond voice similarity, confirm irreversible actions, limit tools per call (`REVIEW_REQUIRED` legal).

### 17. INTERVIEW EXPLANATION

*"A realtime voice system chains streaming ASR, an LLM and streaming TTS, with endpointing and barge-in handling on top. Total delay is the sum of stages, so I overlap them: start TTS on the first sentence, keep streaming everywhere and cancel in-flight work when the user interrupts. The alternative is speech-to-speech models that are faster but less controllable."*

### 18. RAPID-FIRE ANSWER

Streaming ASR + LLM + streaming TTS with endpointing and barge-in, tuned for sub-second turn latency.
