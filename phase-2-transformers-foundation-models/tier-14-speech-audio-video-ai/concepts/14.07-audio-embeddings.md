### 1. WHAT IS IT?

An audio embedding is a vector (or sequence of vectors) produced by a neural encoder that summarises what an audio signal contains: phonetic content, speaker identity, or general sound semantics. Frame-level embeddings are a sequence `[T, d]`; clip-level embeddings pool them to one `[d]`.

### 2. WHY DOES IT EXIST?

Raw samples and mel frames are not semantically organised. Learned embeddings place similar sounds near each other, enabling classification, retrieval, speaker verification, clustering and conditioning of other models (for example an LLM listening to audio).

### 3. DETAILED EXPLANATION

**Kinds of audio embeddings.**
- *Self-supervised speech encoders* (wav2vec 2.0, HuBERT, w2v-BERT, WavLM): trained on unlabeled speech by masking and predicting latent or discrete targets; frame-level outputs are good starting points for ASR with little labelled data (`REVIEW_REQUIRED` for details).
- *Speaker embeddings* (i-vectors, d-vectors, x-vectors, ECAPA-TDNN): one vector per utterance that clusters by speaker; used for verification and diarization ([14.14](14.14-speaker-diarization.md)).
- *General audio / audio-text embeddings* (AudioSet-style classifiers, CLAP): clip vectors for sound events or aligned to text in a shared space, enabling text-to-audio retrieval.
- *ASR encoder outputs* ([14.11](14.11-encoder-decoder-asr.md)): the encoder of Whisper-style models is itself a strong embedding of content.

**Pooling.** Mean pooling over time, attentive statistics pooling (speaker models), or CLS-style tokens ([Tier 8](../../tier-08-transformer-architecture/README.md)).

**Similarity.** Cosine similarity, same as text embeddings ([Tier 6](../../tier-06-tokenization-embeddings/README.md)).

**Toy illustration in the lab.** `speaker_features` is a hand-made 20-D spectral-shape embedding (mean log-mel over loud frames, mean-subtracted) and `cluster_speakers` groups segments by cosine-ish distance via k-means. It is *not* a learned embedding, but it shows the interface: variable-length audio in, fixed vector out, geometry encodes similarity.

### 4. HOW DOES IT WORK?

1. Convert audio to log-mel frames ([14.5](14.05-mel-spectrograms.md)) or raw waveform to a CNN front-end.
2. Pass through the encoder (CNN/Transformer/Conformer) to get `[T', d]`.
3. Optionally pool over time to `[d]`.
4. Use with cosine similarity, a linear head (classification), or as a conditioning input.

```
audio ──► log-mel [T,80] ──► encoder (conv + transformer) ──► [T/2.., d] ──pool──► [d] ──► cosine / classifier / retrieval
```

### 5. SIMPLE EXAMPLE

Instead of describing a song by its raw sound, you describe it by a short fingerprint: songs that sound alike have fingerprints that are close.

### 6. TECHNICAL EXAMPLE

Voice-search systems compute an embedding for each spoken query and compare to embeddings of catalogue titles; speaker verification compares two utterance embeddings with a cosine threshold tuned to a target false-accept rate.

### 7. CODE

```python
# run inside lab/ -- toy 'embedding': spectral-shape vector, cosine similarity
import numpy as np
from audio_core import tone, noise, speaker_features

sr = 8000
def voice(f, seed): return tone(f, 0.4, sr) + 0.3 * tone(2 * f, 0.4, sr) + noise(0.4, sr, 0.01, seed=seed)
a1, a2, b = (speaker_features(voice(f, s), sr) for f, s in [(200, 0), (200, 1), (600, 2)])
cos = lambda u, v: float(u @ v / (np.linalg.norm(u) * np.linalg.norm(v)))
print(cos(a1, a2) > cos(a1, b))     # True: same 'speaker' is closer
```
Learned encoders (wav2vec 2.0, HuBERT, ECAPA) are used via libraries; **not run here, verify APIs (`REVIEW_REQUIRED`)**.
Code: [`lab/audio_core.py`](../lab/audio_core.py)

### 8. INPUT → PROCESS → OUTPUT

```
audio (variable length) ─► encoder ─► [T', d] ─► pooling ─► [d] ─► cosine / retrieval / classifier
```

### 9. ENTERPRISE USE CASE

Banks use voice biometrics (speaker embeddings) as one factor in call-centre authentication, with liveness checks and fallbacks; media companies embed their audio archive for text-to-sound search.

### 10. AI ENGINEERING CONNECTION

Embeddings are how audio plugs into LLM systems: an audio encoder's output can be projected into an LLM's token space for speech-aware chat (see [14.28](14.28-video-language-models.md) for the video analogue) or used for RAG over audio ([14.29](14.29-audio-video-text-alignment.md)).

### 11. ADVANTAGES

Semantic, compact, reusable across tasks, good with little labelled data.

### 12. LIMITATIONS

Encoders encode what they were trained for (content vs speaker vs events); domain and language shift hurt; embeddings can leak speaker identity.

### 13. TRADE-OFFS

Larger encoders: better quality, more latency/cost. Frame vs clip embeddings: detail vs size.

### 14. COMMON MISTAKES

- Using a content embedding for speaker tasks (or vice versa).
- Comparing embeddings from different models.
- Choosing a verification threshold on a tiny dev set.
- Ignoring that pooling over padding frames pollutes the mean.

### 15. PERFORMANCE / COST CONSIDERATIONS

Embedding a minute of audio costs an encoder forward pass (milliseconds to seconds on a GPU depending on size); store vectors in an index as in text RAG.

### 16. SECURITY CONSIDERATIONS

Speaker embeddings are biometric templates: protect, hash/encrypt, set retention limits. Replay and synthetic-voice attacks defeat naive verification; combine with anti-spoofing (`REVIEW_REQUIRED`).

### 17. INTERVIEW EXPLANATION

*"An audio embedding is a vector from a neural encoder that captures what matters about a clip: content, speaker, or sound type, depending on the training objective. Similar audio lands nearby, so I can do retrieval, clustering or verification with cosine similarity. The trade-off is that each encoder encodes one view, so pick the right one and never mix models."*

### 18. RAPID-FIRE ANSWER

A learned vector summarising an audio clip, so similar sounds or speakers are close in space.
