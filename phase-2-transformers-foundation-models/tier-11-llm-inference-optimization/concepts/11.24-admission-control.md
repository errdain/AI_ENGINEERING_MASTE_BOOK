### 1. WHAT IS IT?

**Admission control** decides whether to accept a new request at all, based on queue length, estimated KV need, per-tenant quota, priority and current load.

### 2. WHY DOES IT EXIST?

It protects the latency and KV memory of already-admitted work: accepting more than you can serve harms every user.

### 3. DETAILED EXPLANATION

- Inputs: estimated prompt tokens, requested `max_tokens`, tenant quotas (tokens per minute), priority, current queue depth and KV free space.
- Outputs: admit, queue, or reject (with a reason and `Retry-After`).
- The lab's `max_queue` rejects arrivals when the queue is full, and requests whose `prompt + max_output` can never fit are rejected; test `test_admission_control_sheds_load`.

### 4. HOW DOES IT WORK?

On arrival: validate size limits -> check tenant quota -> check queue/KV headroom -> admit/queue or reject.

### 5. SIMPLE EXAMPLE

A club bouncer counting heads against fire-code capacity.

### 6. TECHNICAL EXAMPLE

A shared gateway gives each team a token-per-minute quota and reserves capacity for interactive traffic.

### 7. CODE

```python
from dataclasses import dataclass

@dataclass
class Gate:
    max_queue: int
    max_tokens_cap: int = 2048
    tokens_per_min: int = 100_000

    def admit(self, queue_len: int, requested_max_tokens: int, used_this_min: int) -> tuple[bool, str]:
        if requested_max_tokens > self.max_tokens_cap: return False, "max_tokens too large"
        if used_this_min + requested_max_tokens > self.tokens_per_min: return False, "tenant quota"
        if queue_len >= self.max_queue: return False, "overloaded"
        return True, "ok"

g = Gate(max_queue=5)
print(g.admit(2, 512, 0), g.admit(5, 512, 0), g.admit(0, 4096, 0))
```

### 8. INPUT → PROCESS → OUTPUT

```
request -> size check -> quota check -> capacity check -> admit | queue | reject(429/503)
```

### 9. ENTERPRISE USE CASE

Per-team quotas and priority tiers on an enterprise LLM gateway.

### 10. AI ENGINEERING CONNECTION

Gateways (Tier 36) combine admission control with caching, routing and cost tracking.

### 11. ADVANTAGES

Predictable latency; protects memory; limits abuse.

### 12. LIMITATIONS

Estimates of output length are imperfect; strict limits reject legitimate bursts.

### 13. TRADE-OFFS

Utilisation vs headroom; strictness vs availability.

### 14. COMMON MISTAKES

Quotas in requests not tokens; no server-side `max_tokens` cap; admission that ignores KV state.

### 15. PERFORMANCE / COST CONSIDERATIONS

Prevents over-subscription that would trigger preemption and recompute.

### 16. SECURITY CONSIDERATIONS

Enforce authentication and per-tenant limits at admission; it is a primary denial-of-wallet defence.

### 17. INTERVIEW EXPLANATION

"Admission control is the front-door decision: do we take this request now? I check size limits, tenant token quotas and queue or KV headroom, then admit, queue or reject with a reason. It protects the latency of work already accepted."

### 18. RAPID-FIRE ANSWER
