### 1. WHAT IS IT?

**Continuous (in-flight) batching** schedules at *iteration* granularity: after every decode step, finished sequences leave the batch and waiting requests join immediately (their prefill runs, then they decode with everyone else).

### 2. WHY DOES IT EXIST?

Requests finish at different times. Waiting for the whole batch wastes GPU slots and keeps short requests hostage to long ones. Continuous batching keeps the batch full and cuts queueing delay.

### 3. DETAILED EXPLANATION

- The unit of scheduling is one decode iteration, not one request.
- It needs a KV allocator that can add and remove sequences on the fly ([11.21 PagedAttention](11.21-pagedattention.md)): contiguous max-length buffers waste memory, so engines pair it with paging.
- New requests' prefill steals compute from decoding; engines balance via chunked prefill or limits (REVIEW_REQUIRED).
- Admission decisions use KV capacity: the lab reserves `prompt + max_output` tokens (safe, no preemption) or optionally only the prompt (`reserve_full=False`, which would need preemption in a real engine).

### 4. HOW DOES IT WORK?

Every iteration:
1. Remove sequences that hit EOS/stop/length.
2. Admit queued requests while slots and KV capacity allow ([11.24 Admission control](11.24-admission-control.md)).
3. Prefill the newly admitted prompts (stalling or interleaving with decode).
4. Run one decode step for all running sequences.
5. Stream tokens; repeat.

### 5. SIMPLE EXAMPLE

A hotel breakfast table where a seat is refilled the moment a guest leaves, instead of seating a whole tour group together.

### 6. TECHNICAL EXAMPLE

Lab (24 requests, capacity 600 KV tokens, 8 slots): static makespan 269 ticks / mean TTFT 87 vs continuous 152 / 18 (`python lab/benchmark.py`; seed-dependent simulation).

### 7. CODE

```python
import random
from scheduler import Req, simulate, metrics

random.seed(1)
reqs = [Req(rid=i, arrival=0, prompt=20, out=random.choice([5, 10, 40, 80])) for i in range(16)]
for mode in ("static", "continuous"):
    f, r, log = simulate(reqs, 10_000, max_batch=4, mode=mode)
    m = metrics(f, log)
    print(mode, m["makespan"], round(m["mean_ttft"], 1))
# static 296 100.0 | continuous 221 61.9 for this seed
```

See [`../lab/scheduler.py`](../lab/scheduler.py) and tests `test_continuous_beats_static`, `test_scheduler_never_exceeds_capacity_and_finishes`.

### 8. INPUT → PROCESS → OUTPUT

```
queue -> admit while (slots & KV free) -> prefill -> decode ALL running -> finished leave -> loop each iteration
```

### 9. ENTERPRISE USE CASE

Used by modern LLM serving engines (vLLM and similar; REVIEW_REQUIRED for engine specifics) so a shared GPU serves chat traffic at high utilisation.

### 10. AI ENGINEERING CONNECTION

Foundation of high-throughput open-model hosting; interacts with prefix caching, speculative decoding and scheduling policies ([11.22 Request scheduling](11.22-request-scheduling.md)).

### 11. ADVANTAGES

High GPU utilisation; low queue wait; short requests not blocked by long ones.

### 12. LIMITATIONS

Scheduler complexity; prefill/decode interference; needs flexible memory management.

### 13. TRADE-OFFS

Throughput and TTFT vs ITL jitter from interleaved prefill; fairness vs efficiency.

### 14. COMMON MISTAKES

Assuming it speeds up one request (it raises capacity and reduces waiting); not bounding the queue ([11.23 Backpressure](11.23-backpressure.md)); ignoring KV exhaustion.

### 15. PERFORMANCE / COST CONSIDERATIONS

Higher utilisation directly cuts cost per token ([11.45 Inference cost](11.45-inference-cost.md)).

### 16. SECURITY CONSIDERATIONS

Mixed-tenant batches make performance isolation important: one tenant's long prompts can inflate others' latency; apply per-tenant limits.

### 17. INTERVIEW EXPLANATION

"Continuous batching schedules per decode iteration. As soon as a sequence finishes, its slot is given to a waiting request, so the batch stays full. Compared to static batching, short requests are not held hostage by long ones, utilisation rises and queue time falls. It relies on paged KV memory and needs admission control."

### 18. RAPID-FIRE ANSWER

Per-iteration scheduling: finished sequences leave and new ones join immediately; keeps GPU batch full.
