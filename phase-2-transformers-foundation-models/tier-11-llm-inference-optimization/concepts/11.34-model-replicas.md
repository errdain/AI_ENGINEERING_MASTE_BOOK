### 1. WHAT IS IT?

**Model replicas** are multiple identical copies of a serving instance behind a load balancer.

### 2. WHY DOES IT EXIST?

One instance has a throughput ceiling and is a single point of failure. Replicas add capacity and availability.

### 3. DETAILED EXPLANATION

- Scale **throughput and availability**, not single-request latency, and not model size (it does not help a model fit).
- Balancing: round-robin is poor for LLMs because requests differ hugely in length; prefer least-outstanding-tokens or queue-aware policies, and KV/prefix-aware routing so a conversation returns to the replica that has its prefix cached (`REVIEW_REQUIRED` per gateway).
- Replicas can combine with tensor parallelism: e.g. 4 replicas, each TP=2 on 8 GPUs.

### 4. HOW DOES IT WORK?

Gateway receives request ─► picks replica (health, load, affinity) ─► replica streams response; unhealthy replicas are drained and replaced.

### 5. SIMPLE EXAMPLE

Opening more checkout lanes: each customer still takes the same time, but more customers are served.

### 6. TECHNICAL EXAMPLE

Two replicas each sustaining 1,000 tok/s serve 2,000 tok/s total (illustrative), and one can fail without a full outage.

### 7. CODE

```python
# Least-outstanding-tokens routing (toy)
from dataclasses import dataclass

@dataclass
class Replica:
    name: str
    outstanding_tokens: int = 0
    healthy: bool = True

def pick(replicas: list[Replica]) -> Replica:
    ok = [r for r in replicas if r.healthy]
    if not ok:
        raise RuntimeError("no healthy replica")
    return min(ok, key=lambda r: r.outstanding_tokens)

rs = [Replica("a", 900), Replica("b", 120), Replica("c", 500, healthy=False)]
print(pick(rs).name)   # b
```

### 8. INPUT → PROCESS → OUTPUT

```
requests ─► load balancer/gateway ─► replica 1 / 2 / 3 (each: engine + GPUs) ─► tokens
```

### 9. ENTERPRISE USE CASE

Production LLM platforms run N replicas per model with zero-downtime rollouts and per-tenant limits.

### 10. AI ENGINEERING CONNECTION

Capacity and availability building block for every serving stack; autoscaling ([11.37 Serving autoscaling](11.37-serving-autoscaling.md)) adjusts N.

### 11. ADVANTAGES

- Linear-ish throughput scaling; fault tolerance; rolling deploys.

### 12. LIMITATIONS

- Does not reduce latency; more GPUs cost money; cache locality lost without affinity.

### 13. TRADE-OFFS

Cost vs headroom; spread (availability) vs locality (cache hit rate).

### 14. COMMON MISTAKES

- Round-robin on variable-length requests. - Believing replicas help fit a big model. - No spare capacity for failover.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost scales with N; keep N+1 headroom; weight loading time affects replace speed ([11.38 Cold starts](11.38-cold-starts.md)).

### 16. SECURITY CONSIDERATIONS

Same auth/TLS everywhere; weights replicated across nodes need access control and encryption at rest.

### 17. INTERVIEW EXPLANATION

"Replicas are identical serving instances behind a balancer. They raise throughput and availability but not single-request latency or model-fit; to fit a big model you shard with tensor or pipeline parallelism. I'd route by outstanding tokens and preserve cache affinity."

### 18. RAPID-FIRE ANSWER

Replicas scale throughput and availability, not latency or model size.
