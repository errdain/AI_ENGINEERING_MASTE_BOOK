### 1. WHAT IS IT?

**Prefill vs decode bottlenecks** contrasts the two phases of inference: prefill processes the whole prompt in parallel (usually compute-bound, drives TTFT); decode generates one token per step (usually memory-bound, drives ITL/TPS).

### 2. WHY DOES IT EXIST?

Optimizations target one phase or the other; applying the wrong one wastes effort.

### 3. DETAILED EXPLANATION

| | Prefill | Decode |
|---|---|---|
| Parallelism | all prompt tokens at once | one token per sequence per step |
| Typical bound | compute (FLOPs) | memory bandwidth (weights + KV reads) |
| Metric it drives | TTFT | ITL / TPS |
| Helped by | faster FLOPs, prefix caching, shorter prompts, tensor-parallel | quantization, more bandwidth, larger batch, GQA/KV quantization, speculative decoding |
| Interference | long prefills stall decode steps of other users (chunked prefill mitigates; some systems disaggregate prefill and decode onto different machines — `REVIEW_REQUIRED`) | |

### 4. HOW DOES IT WORK?

Request ─► prefill (compute-bound, builds KV) ─► first token ─► decode loop (memory-bound) ─► end. Scheduler may chunk prefill and interleave with decode to protect ITL.

### 5. SIMPLE EXAMPLE

Reading a long email (prefill: fast with parallel brain power) vs typing the reply word by word (decode: sequential).

### 6. TECHNICAL EXAMPLE

Workload A: 8k-token prompts, 100 output tokens → TTFT dominates, optimize prefill. Workload B: 100-token prompts, 1,000 output tokens → decode dominates, optimize bandwidth/batch/quantization.

### 7. CODE

```python
def phase_split(prompt_tokens, out_tokens, prefill_tok_s, decode_tok_s):
    """Seconds spent in each phase (single request, batch 1; rates are illustrative inputs)."""
    return prompt_tokens / prefill_tok_s, out_tokens / decode_tok_s

print(phase_split(8000, 100, 20000, 60))    # (0.4, 1.67)  -> decode dominates even with long prompt
print(phase_split(8000, 100, 2000, 60))     # slower prefill hardware: (4.0, 1.67)
```

### 8. INPUT → PROCESS → OUTPUT

```
prompt ─► [PREFILL: compute] ─► KV cache ─► [DECODE: bandwidth] ─► tokens
```

### 9. ENTERPRISE USE CASE

RAG apps have long prompts (prefill-heavy); chat has short prompts and long outputs (decode-heavy); sizing differs.

### 10. AI ENGINEERING CONNECTION

Guides prefix caching ([11.18 Prefix caching](11.18-prefix-caching.md)), chunked prefill, speculative decoding ([11.25 Speculative decoding](11.25-speculative-decoding.md)) choices.

### 11. ADVANTAGES

- Right lever for the right phase.

### 12. LIMITATIONS

- Phases interfere when co-scheduled.

### 13. TRADE-OFFS

Chunk size trade-off: smaller chunks protect ITL but slow TTFT.

### 14. COMMON MISTAKES

- Optimizing decode for a prefill-bound workload. - Ignoring prefill interference.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost per request ≈ prefill compute + decode bandwidth time × tokens.

### 16. SECURITY CONSIDERATIONS

Long-prompt abuse can monopolize prefill capacity; enforce input limits.

### 17. INTERVIEW EXPLANATION

"Prefill is parallel and compute-bound and sets time to first token; decode is sequential and memory-bound and sets inter-token latency. I measure which dominates my workload, then choose levers accordingly."

### 18. RAPID-FIRE ANSWER

Prefill: compute-bound, TTFT; decode: memory-bound, ITL.

### 19. INTERVIEW QUESTIONS

**Basic:** Which phase drives TTFT? **Intermediate:** Name two levers for each. **Advanced:** Chunked prefill vs disaggregation? **Scenario:** TTFT is bad only for long prompts — what do you do? (prefix cache, faster prefill, limits.)
