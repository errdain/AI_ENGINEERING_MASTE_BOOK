### 1. WHAT IS IT?

**Request scheduling** is the policy that decides which waiting request runs next (and which running request may be paused or evicted) in an LLM serving engine.

### 2. WHY DOES IT EXIST?

GPU slots and KV memory are limited; with more requests than capacity, the order of service determines fairness, tail latency and throughput.

### 3. DETAILED EXPLANATION

- **FCFS:** simple and fair, but suffers head-of-line blocking behind a huge request.
- **Shortest-job-first / priority:** lowers mean latency, but output length is unknown a priori (estimates, or max_tokens as a proxy); long jobs can starve.
- **Per-tenant fair queues / weighted fair queuing:** prevents one tenant from monopolising capacity.
- **Preemption:** evict a running request's KV and either recompute it later or swap it to CPU memory; needed when admission reserves only the prompt (`reserve_full=False`).
- **Reservation policy:** the lab reserves `prompt + max_output` KV tokens on admission (safe, conservative) or only the prompt.
- Policies trade **fairness, tail latency and throughput**; specifics differ per engine (REVIEW_REQUIRED).

[See the effect in the batching Gantt page](../interactive/batching_gantt.html) (arrival gap, length spread, slots).

### 4. HOW DOES IT WORK?

Each iteration: order the waiting queue by policy; admit while slots and KV allow; if memory is exhausted mid-flight, preempt according to policy; run one decode step.

### 5. SIMPLE EXAMPLE

A hospital emergency room triaging by urgency, not strictly by arrival time, while making sure no one waits forever.

### 6. TECHNICAL EXAMPLE

A shared internal gateway reserves capacity for interactive requests and runs batch jobs at lower priority so they cannot raise interactive TTFT.

### 7. CODE

```python
import heapq

class Scheduler:
    """Priority queue with FIFO tie-break. Lower priority number runs first."""
    def __init__(self): self.q, self.n = [], 0
    def submit(self, rid, priority=1):
        heapq.heappush(self.q, (priority, self.n, rid)); self.n += 1
    def next(self):
        return heapq.heappop(self.q)[2] if self.q else None

s = Scheduler()
s.submit("batch-job", priority=5); s.submit("chat-1", priority=0); s.submit("chat-2", priority=0)
print([s.next() for _ in range(3)])      # ['chat-1', 'chat-2', 'batch-job']
```

### 8. INPUT → PROCESS → OUTPUT

```
arrivals -> queue (ordered by policy) -> admit (slots & KV) -> run -> finish | preempt -> back to queue
```

### 9. ENTERPRISE USE CASE

Multi-tenant gateways with priority tiers and per-team token quotas.

### 10. AI ENGINEERING CONNECTION

Affects agents (bursty request multiplication) and RAG (variable prompt sizes); scheduling policy interacts with prefix caching.

### 11. ADVANTAGES

Controls tail latency, fairness and utilisation without more hardware.

### 12. LIMITATIONS

Output length is unknown; preemption costs recompute/swap time; policies need tuning.

### 13. TRADE-OFFS

Fairness vs throughput; mean vs tail latency; reservation safety vs utilisation.

### 14. COMMON MISTAKES

Sorting by prompt length only; no starvation protection; counting requests rather than tokens for fairness.

### 15. PERFORMANCE / COST CONSIDERATIONS

Better scheduling raises goodput (requests meeting their SLO) on the same GPUs.

### 16. SECURITY CONSIDERATIONS

Without per-tenant fairness a tenant can degrade others (noisy neighbour); enforce quotas.

### 17. INTERVIEW EXPLANATION

"The scheduler decides who runs next. FCFS is simple but suffers head-of-line blocking; priority or shortest-first lowers mean latency but needs length estimates and can starve; fair queues protect tenants. When memory runs out, preemption evicts a request's KV to recompute or swap later. It's always a trade-off between fairness, tail latency and throughput."

### 18. RAPID-FIRE ANSWER

The policy that orders and admits requests (FCFS, priority, fair queues) and handles preemption.
