### 1. WHAT IS IT?

**Time to first token (TTFT)** is the time from request arrival to receipt of the first output token: queueing + prefill (+ network).

### 2. WHY DOES IT EXIST?

It is what users perceive as "is it thinking?" and the primary responsiveness metric for streaming products.

### 3. DETAILED EXPLANATION

- Dominated by prompt length, queue depth and prefix-cache hits.
- Must be measured **including queue time**; define it as p50/p95/p99, not a mean.
- Rises sharply when the server is saturated (long queues) or when long prefills block others.
- Levers: shorter prompts, prefix caching ([11.18 Prefix caching](11.18-prefix-caching.md)), more compute for prefill, tensor parallelism ([11.35 Tensor-parallel inference](11.35-tensor-parallel-inference.md)), admission control ([11.24 Admission control](11.24-admission-control.md)), chunked prefill (REVIEW_REQUIRED).

### 4. HOW DOES IT WORK?

`TTFT = t_first_token_received - t_request_sent = queue_wait + prefill + first-sample + network`.

### 5. SIMPLE EXAMPLE

Time from pressing the elevator button to the doors opening, not to reaching your floor.

### 6. TECHNICAL EXAMPLE

An internal copilot SLO: p95 TTFT < 1 s at 4k-token prompts (illustrative target, not a recommendation).

### 7. CODE

```python
import time

def timed_stream(stream):
    """stream: any iterator that yields tokens as they arrive. Returns (ttft, total, n)."""
    t0, first, n = time.perf_counter(), None, 0
    for _ in stream:
        n += 1
        if first is None:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0, n

def fake_stream():
    time.sleep(0.05)               # queue + prefill
    for _ in range(5):
        time.sleep(0.01); yield "tok"

print(timed_stream(fake_stream()))
```

### 8. INPUT → PROCESS → OUTPUT

```
send -> [network] -> [queue] -> [prefill] -> first token -> [network] -> client sees it   (TTFT = whole span)
```

### 9. ENTERPRISE USE CASE

Dashboards show TTFT percentiles per route, tenant and prompt-length bucket.

### 10. AI ENGINEERING CONNECTION

RAG and agents inflate prompt length; reasoning models can make "first visible token" late if reasoning tokens are hidden (REVIEW_REQUIRED per product).

### 11. ADVANTAGES

Direct user-experience metric; easy to measure end-to-end.

### 12. LIMITATIONS

Mixes queueing and compute; sensitive to prompt-length mix; client-side measurement includes network.

### 13. TRADE-OFFS

Low TTFT usually costs capacity (spare prefill compute) or accuracy (shorter context).

### 14. COMMON MISTAKES

Reporting averages; measuring on the server only; omitting queue time; comparing TTFT across different prompt lengths.

### 15. PERFORMANCE / COST CONSIDERATIONS

Adding replicas/capacity lowers queueing TTFT; prefix caching lowers prefill TTFT.

### 16. SECURITY CONSIDERATIONS

Timing differences in TTFT can leak prefix-cache hits across tenants; scope caches per tenant when prompts are confidential.

### 17. INTERVIEW EXPLANATION

"TTFT is request arrival to the first token: queue time plus prefill plus network. It's what users feel as responsiveness, so I measure it as a percentile and split it into queue and prefill before deciding whether to cache, shorten prompts, or add capacity."

### 18. RAPID-FIRE ANSWER

TTFT = queue + prefill (+ network) until the first token; report percentiles.
