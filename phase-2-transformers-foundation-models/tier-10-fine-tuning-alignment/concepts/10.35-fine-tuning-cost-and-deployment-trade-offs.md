### 1. WHAT IS IT?

**Fine-tuning cost and deployment trade-offs** compare prompting/RAG, full fine-tuning, LoRA, QLoRA and DPO by training cost, serving shape and fit.

### 2. WHY DOES IT EXIST?

To choose the cheapest approach that meets the behaviour requirement.

### 3. DETAILED EXPLANATION

| Choice | Training cost | Serving | Best when |
|---|---|---|---|
| Prompting / RAG (Tier 17/20) | none | longer prompts | knowledge changes often; no behaviour change needed |
| Full FT | highest (16 B/param + activations) | one model per task | big behaviour shift, enough data/GPUs |
| LoRA | low | merge (free) or hot-swap | many tasks/tenants, one base |
| QLoRA | lowest memory | merge into fp16 then quantize | single small GPU |
| DPO on top | ~2x SFT per example | unchanged | style/safety preference with pairs |

Rule: *try prompting and RAG first; fine-tune for behaviour (format, tone, skills) rather than for facts that change.* Deployment: version adapters with their base hash; test merged vs unmerged outputs; plan rollback (keep the previous adapter).

![Memory](../figures/03_lora_params_and_memory.png)

*Figure: analytic memory for full FT vs LoRA vs QLoRA.* [Explore the calculator](../interactive/qlora_memory.html).

### 4. HOW DOES IT WORK?

Decision flow: can prompting/RAG meet the bar? If not, is it behaviour or facts? Behaviour -> SFT with LoRA/QLoRA; large shift -> full FT; relative quality -> DPO; then merge or hot-swap.

### 5. SIMPLE EXAMPLE

Rent, renovate, or rebuild: pick the cheapest that works.

### 6. TECHNICAL EXAMPLE

7B model: full FT ~112 GB (16 B/param, before activations); LoRA fp16 base ~14 GB + adapter state; QLoRA ~4 GB base + adapter state (memory calculator, analytic).

### 7. CODE

```python
from lora import finetune_memory_gb
for m in ("full_fp16_adam", "lora_fp16", "qlora_4bit"):
    print(m, round(finetune_memory_gb(7, m, r_params_m=20), 1))   # 112.0, 14.3, 4.3 GB
```

### 8. INPUT → PROCESS → OUTPUT

```
requirement --> prompting/RAG? --> else SFT(LoRA/QLoRA) --> DPO? --> evaluate --> merge or hot-swap --> version + rollback
```

### 9. ENTERPRISE USE CASE

Multi-tenant platforms run one base with many per-tenant adapters, versioned with the base hash.

### 10. AI ENGINEERING CONNECTION

Links training choices to serving design ([Tier 11](../../tier-11-llm-inference-optimization/README.md)) and cost engineering (Tier 36).

### 11. ADVANTAGES

A clear decision framework saves GPU spend.

### 12. LIMITATIONS

Numbers here ignore activations, KV cache and overheads; fine-tuning does not add reliable new facts.

### 13. TRADE-OFFS

Quality ceiling versus cost; operational simplicity versus flexibility.

### 14. COMMON MISTAKES

Fine-tuning for facts that change; skipping the prompting baseline; not versioning adapter+base; no rollback.

### 15. PERFORMANCE / COST CONSIDERATIONS

Dominated by GPU-hours; memory formula above; evaluation and data cost often exceed compute.

### 16. SECURITY CONSIDERATIONS

Adapter registry access control; signed artifacts; per-tenant isolation.

### 17. INTERVIEW EXPLANATION

I try prompting and RAG first, fine-tune for behaviour not changing facts, use LoRA or QLoRA to fit the hardware, full fine-tuning only for large shifts, and DPO when I have preference pairs. I merge for speed or hot-swap for multi-tenancy, version adapters with the base hash, and keep rollbacks.

### 18. RAPID-FIRE ANSWER

Prompt first, LoRA next, full FT last.
