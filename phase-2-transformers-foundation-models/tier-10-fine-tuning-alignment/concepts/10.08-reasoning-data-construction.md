### 1. WHAT IS IT?

**Reasoning-data construction** builds training examples that include intermediate steps (a chain of thought) before the final answer, and verified outcomes that can drive reinforcement learning.

### 2. WHY DOES IT EXIST?

Models answer multi-step problems better when trained to produce and check steps.

### 3. DETAILED EXPLANATION

Routes: human-written rationales; teacher-generated rationales filtered by **answer correctness** (*rejection sampling*); or sample many solutions and keep those a **verifier** accepts (unit tests, math checker). Verifiable rewards can then feed RL ([10.22](10.22-rlhf.md)). Reasoning-model architecture and training belong to Tier 12; this tier fixes only the data idea. **Pitfalls:** right answer with wrong reasoning, over-long rationales, leaking benchmark solutions.

### 4. HOW DOES IT WORK?

Sample k solutions per problem -> verify final answers -> keep correct ones (optionally also check step validity) -> SFT, or use the verifier as an RL reward.

### 5. SIMPLE EXAMPLE

Showing your work in math class and keeping only the worked solutions that got the right answer.

### 6. TECHNICAL EXAMPLE

Math problems with a checker: keep a sampled solution only if the final number matches. Not exercised in the lab (lab tasks are single-step); no measured result is claimed.

### 7. CODE

```python
def keep(solutions, check):            # rejection sampling with a verifier
    return [s for s in solutions if check(s)]
```

### 8. INPUT → PROCESS → OUTPUT

```
problem --> sample k solutions --> verifier --> kept (steps + answer) --> SFT / RL reward
```

### 9. ENTERPRISE USE CASE

Code assistants train on solutions that pass unit tests.

### 10. AI ENGINEERING CONNECTION

Underpins reasoning models and planning agents; verifiers double as reward functions.

### 11. ADVANTAGES

Verifiable signal without human labels.

### 12. LIMITATIONS

Only works where checking is possible; written reasoning may not reflect the real computation.

### 13. TRADE-OFFS

Verified-only quality versus coverage of open-ended tasks.

### 14. COMMON MISTAKES

Trusting final-answer-only filters; very long traces; benchmark leakage.

### 15. PERFORMANCE / COST CONSIDERATIONS

Sampling many solutions is expensive; verification is usually cheap.

### 16. SECURITY CONSIDERATIONS

Sandbox code execution; contamination controls.

### 17. INTERVIEW EXPLANATION

For reasoning I include intermediate steps in the target and keep only samples a verifier accepts, such as passing tests or a matching answer. That gives clean data and a programmatic reward for RL, with the caveat that a correct answer does not guarantee valid reasoning.

### 18. RAPID-FIRE ANSWER

Sample many, keep what a checker accepts.
