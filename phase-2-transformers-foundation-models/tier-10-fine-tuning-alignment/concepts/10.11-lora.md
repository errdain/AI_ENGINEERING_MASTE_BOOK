### 1. WHAT IS IT?

**LoRA (Low-Rank Adaptation)** freezes a weight matrix `W` and learns its update as a product of two thin matrices: `h = W x + (alpha / r) * B (A x)`, with `A` of shape `r x d_in` and `B` of shape `d_out x r`.

### 2. WHY DOES IT EXIST?

The update to a weight during fine-tuning is often well approximated by a low-rank matrix, so learning `delta W` (d_out x d_in) directly wastes parameters and optimizer memory.

### 3. DETAILED EXPLANATION

```
h = W x + (alpha / r) * B (A x)    W frozen (d_out x d_in);  A: r x d_in ;  B: d_out x r
init: A ~ random (Kaiming),  B = 0   =>  delta W = 0 at step 0  =>  adapted model == base model
```

![LoRA decomposition](../figures/02_lora_decomposition.png)

*Figure: a 16x16 weight (256 params) gets a rank-2 update with only 64 trainable parameters. B is tall-thin, A short-wide, and the product has repeated row/column structure.*

![Rank approximation](../figures/11_lora_rank_approximation.gif)

*Animation: the best rank-r approximation (truncated SVD) of a target update with a decaying spectrum. Watch the right-hand error curve: it falls fast then flattens, the intuition for why a small r often suffices. This is the Eckart-Young property, not a claim about any real fine-tuning update.*

**Trainable parameters** (formula, tested): for each adapted layer `r * (d_in + d_out)`. For a square `d x d` matrix that is `2rd` vs `d^2`, i.e. `200 r / d` percent. **Merging:** `W' = W + (alpha/r) B A` folds into the base: zero inference overhead, and `unmerge` restores the original (tested to 1e-5/1e-6).

**Gradient subtlety (tested).** At init `B = 0`, so `dL/dA = 0` and only `B` receives gradient on step one; `A` starts moving once `B != 0`.

[Explore LoRA](../interactive/lora_explorer.html): d, layers, rank, alpha, which matrices, B=0 toggle.

### 4. HOW DOES IT WORK?

1. Freeze `W`. 2. Add `A` (random) and `B` (zeros). 3. Forward: `W x + scale * B(A x)` with `scale = alpha/r`. 4. Backprop only to `A`, `B`. 5. Optionally merge. 6. Store only `A`, `B`.

### 5. SIMPLE EXAMPLE

Instead of rewriting a 1000x1000 table, store a 1000x4 and a 4x1000 "correction" whose product is added to it.

### 6. TECHNICAL EXAMPLE

Lab: LoRA on all six matrices (r=8) reached accuracy **0.55** at 200 steps with lr 1e-2 (hand-written `LoRALinear`); the same adapters work for SFT, DPO and reward models. Accuracy at 200 steps varied 0.45-0.85 across my seeds/edits, so no ranking against full FT is claimed. Numbers here come from the seeded lab run (`../lab/run_lab.py`, 64,512-parameter char model, one seed, CPU); they teach mechanics, not large-model behaviour.

### 7. CODE

```python
# ../lab/lora.py (excerpt)
class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=4, alpha=8.0):
        super().__init__()
        self.base, self.r, self.alpha = base, r, alpha
        for p in base.parameters(): p.requires_grad_(False)
        self.A = nn.Parameter(torch.empty(r, base.in_features)); nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))     # zero => identity at init
    def forward(self, x):
        return self.base(x) + (self.alpha / self.r) * ((x @ self.A.t()) @ self.B.t())
    @torch.no_grad()
    def merge(self): self.base.weight += (self.alpha / self.r) * (self.B @ self.A)
```
Files: [`../lab/lora.py`](../lab/lora.py); tests `test_lora_init_is_identity`, `test_lora_grads_at_init_only_B`, `test_merged_weights_equal_adapter_output` in [`../lab/test_tier10.py`](../lab/test_tier10.py). Framework equivalent: the Hugging Face PEFT library (`LoraConfig`/`get_peft_model`; verify current API, `REVIEW_REQUIRED`).

### 8. INPUT → PROCESS → OUTPUT

```
x --> W x ----------------------+--> h
 \--> A x --> B (.) --> * (alpha/r) -+
(train only A, B; after training: W' = W + (alpha/r) B A)
```

### 9. ENTERPRISE USE CASE

One 7B base plus dozens of 20-200 MB adapters per tenant/task, hot-swapped at serve time (`REVIEW_REQUIRED` sizes; Tier 35).

### 10. AI ENGINEERING CONNECTION

The standard PEFT for LLM SFT, DPO and reward models; basis of QLoRA ([10.15](10.15-qlora.md)) and adapter merging ([10.30](10.30-adapter-merging.md)).

### 11. ADVANTAGES

Cheap, mergeable (zero latency), starts exactly at the base, tiny artifacts.

### 12. LIMITATIONS

Possibly less capacity for large domain shifts or new knowledge (published comparisons mix; `REVIEW_REQUIRED`); hyper-parameters to tune.

### 13. TRADE-OFFS

Rank and targets (capacity) versus memory ([10.12](10.12-lora-rank.md), [10.14](10.14-lora-target-modules.md)); keep separate (swappable) versus merge (fast).

### 14. COMMON MISTAKES

Forgetting `requires_grad=False`; inconsistent merge/dropout; comparing runs with different learning rates (LoRA usually wants a *higher* LR than full FT; lab 1e-2 vs 1e-3).

### 15. PERFORMANCE / COST CONSIDERATIONS

No gradients/optimizer state for the base; activations unchanged; latency zero after merge, a small extra matmul if unmerged.

### 16. SECURITY CONSIDERATIONS

An adapter encodes training data; protect it like data. Merged weights cannot be un-merged from the file alone without the base.

### 17. INTERVIEW EXPLANATION

LoRA freezes W and learns a low-rank update BA with B initialised to zero, so training starts from the exact base model. It trains r(d_in+d_out) parameters per layer instead of d_in times d_out, and the update can be merged into W for free inference. Rank, alpha and which layers to target are the knobs.

### 18. RAPID-FIRE ANSWER

delta W = (alpha/r) B A, B = 0 at init, mergeable.

### 19. INTERVIEW QUESTIONS

**Basic:** What does LoRA train?

**Intermediate:** Derive the trainable parameter count. Why is B initialised to zero?

**Advanced:** Why do only B receive gradients at step one? When does LoRA fail to match full FT?

**Scenario:** Fine-tuned LoRA model is slower than expected at serving. Why and what to do? (Unmerged extra matmuls; merge, or batch adapters.)
