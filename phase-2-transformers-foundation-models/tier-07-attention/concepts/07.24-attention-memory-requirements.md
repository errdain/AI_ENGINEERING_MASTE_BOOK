### 1. WHAT IS IT?

Attention memory requirements: (1) the **score matrix** `B·H·n²·bytes` per layer when materialised; (2) the inference **KV cache** `2·L·H_kv·d_h·n·B·bytes`.

### 2. WHY DOES IT EXIST?

Out-of-memory errors in long-context training and serving come from these two terms; sizing them tells you which lever to pull.

### 3. DETAILED EXPLANATION

1. **Score matrix (activations).** At `n = 4096`, `H = 32`, fp16: 32·4096²·2 B = **1 GiB per layer per sequence**; at `n = 32768` it is 64× larger (**64 GiB**). Nobody should materialise this at long context ([7.25 FlashAttention](07.25-flashattention.md)).
2. **KV cache (inference).** Grows *linearly* in `n` and `B`, and is usually what limits concurrent users in serving.

**Cost levers** (each attacks a different term):

| Lever | Attacks | Effect |
|---|---|---|
| GQA/MQA | KV-cache size & bandwidth | cache ÷ (H/H_kv) |
| FlashAttention | score-matrix memory traffic | no n×n matrix stored; same exact result |
| Sliding window | pairs computed and cached | O(n·w) instead of O(n²) |
| Lower-precision KV cache (int8/fp8) | cache bytes | ÷2 or ÷4 at some quality risk (`REVIEW_REQUIRED`) |
| Shorter prompts / retrieval (Tiers 17, 20) | n itself | quadratic savings |

1. Pick shapes (L, H, H_kv, d_h, n, B, dtype).
2. Evaluate both formulas.
3. Compare with device memory minus weights.

### 5. SIMPLE EXAMPLE

Keeping a notebook of every earlier page (cache) versus keeping a table of every page-versus-page comparison (score matrix).

### 6. TECHNICAL EXAMPLE

Llama-style shapes (illustrative): L=32, H_kv=8, d_h=128, n=8192, fp16 ⇒ 1 GiB per sequence; 32 concurrent sequences ⇒ 32 GiB of cache.

### 7. CODE

```python
from attention_np import kv_cache_bytes, score_matrix_bytes
GiB = 2**30
print(kv_cache_bytes(layers=32, n_kv_heads=8, head_dim=128, seq_len=8192, batch=1) / GiB)   # 1.0
print(score_matrix_bytes(seq_len=4096, n_heads=32) / GiB)                                  # 1.0
```

### 8. INPUT → PROCESS → OUTPUT

```
(L, H_kv, d_h, n, B, dtype) ─► 2·L·H_kv·d_h·n·B·bytes ─► GiB of KV cache
(B, H, n, dtype)            ─► B·H·n²·bytes            ─► GiB of naive scores / layer
```

### 9. ENTERPRISE USE CASE

GPU-memory budgeting: weights + KV cache + activations must fit; concurrency = free memory / cache per request (Tier 11).

### 10. AI ENGINEERING CONNECTION

Drives max context, batch size and cost per request.

### 11. ADVANTAGES

Closed-form, easy to compute.

### 12. LIMITATIONS

Ignores allocator fragmentation and framework overhead.

### 13. TRADE-OFFS

Cache precision, H_kv, and window size versus quality.

### 14. COMMON MISTAKES

Using `H` instead of `H_kv`; forgetting both K and V (factor 2); forgetting batch; mixing bytes and bits.

### 15. PERFORMANCE / COST CONSIDERATIONS

KV cache is read every decode step: bandwidth cost ∝ cache size.

### 16. SECURITY CONSIDERATIONS

Per-request caches must be isolated and freed; oversized contexts enable denial of service.

### 17. INTERVIEW EXPLANATION

*"Two things scale with context: the naive score matrix, quadratic and avoidable with flash-style kernels, and the KV cache, linear in n and batch and sized as 2·L·H_kv·d_h·n·B·bytes. GQA shrinks the cache."*

### 18. RAPID-FIRE ANSWER

KV cache = 2·L·H_kv·d_h·n·B·bytes; scores = B·H·n²·bytes.
