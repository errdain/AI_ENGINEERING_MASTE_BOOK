### 1. WHAT IS IT?

Factuality is whether a model's claims agree with the world (or with an agreed reference). It is a property of claims, not of fluency.

### 2. WHY DOES IT EXIST?

LLMs produce fluent text whether or not it is true, and users trust fluent text. Factuality evaluation measures how often claims are supported.

### 3. DETAILED EXPLANATION

Methods:
1. **Closed-book QA**: compare short answers with references (exact match or normalised F1; ""[15.8 Task-specific evaluation](15.08-task-specific-evaluation.md)"").
2. **Claim decomposition**: split a long answer into atomic claims, verify each against a trusted source or retrieval, report the fraction supported (a 'factual precision'); optionally also coverage (recall of required facts).
3. **Adversarial sets** built around common misconceptions (for example TruthfulQA; details REVIEW_REQUIRED).
4. **Human verification** for a sample.
5. **Judge-assisted verification** with the limits in ""[15.28 LLM-as-judge concepts and limitations](15.28-llm-as-judge-concepts-and-limitations.md)"".

Separate factuality (world) from groundedness (""[15.14 Groundedness](15.14-groundedness.md)"": faithful to the *provided* context) and from hallucination (""[15.13 Hallucination](15.13-hallucination.md)"": the failure mode). Facts change over time: tag items with dates and refresh. Report per-topic: long-tail entities are worse.

### 4. HOW DOES IT WORK?

Collect prompts with verifiable answers -> extract claims -> check each against a source -> aggregate supported / contradicted / unverifiable -> slice by topic and popularity.

### 5. SIMPLE EXAMPLE

A fact-checker highlighting each sentence of an article as confirmed, wrong or unverifiable.

### 6. TECHNICAL EXAMPLE

Biography prompts: decompose each answer into claims such as 'born in 1950'; check against a curated table; report supported fraction per entity popularity bucket.

### 7. CODE

```python
# run inside lab/ -- a toy claim-level factuality scorer against a trusted fact table
FACTS = {("paris", "capital_of"): "france", ("water", "boils_at_c"): "100"}
claims = [(("paris", "capital_of"), "france"), (("water", "boils_at_c"), "90"), (("mars", "moons"), "2")]
supported = sum(FACTS.get(k) == v for k, v in claims if k in FACTS)
checkable = sum(k in FACTS for k, _ in claims)
print(f"supported {supported}/{checkable} checkable; {len(claims) - checkable} unverifiable")
```

### 8. INPUT → PROCESS → OUTPUT

```
answer -> atomic claims -> verify vs sources -> supported / contradicted / unverifiable -> factual precision
```

### 9. ENTERPRISE USE CASE

Knowledge-base assistants report claim-level factual precision on audited samples and block releases when it drops.

### 10. AI ENGINEERING CONNECTION

Factuality motivates RAG (Tier 20, later) and groundedness checks; this tier provides the measurement.

### 11. ADVANTAGES

- Claim-level scores are interpretable and sliceable.

### 12. LIMITATIONS

- Needs trusted sources; claim extraction errors; facts age; 'unverifiable' is a third category.

### 13. TRADE-OFFS

- Automatic verification speed vs reliability; strictness vs coverage.

### 14. COMMON MISTAKES

- Equating fluency with factuality.
- Ignoring unverifiable claims.
- Static fact sets that go stale.

### 15. PERFORMANCE / COST CONSIDERATIONS

Claim extraction and verification multiply cost per answer.

### 16. SECURITY CONSIDERATIONS

Poisoned or outdated sources corrupt both RAG and the evaluator; vet the reference set.

### 17. INTERVIEW EXPLANATION

Factuality measures whether claims match the world. I decompose answers into atomic claims, verify each against trusted sources, report supported/contradicted/unverifiable fractions by slice, and keep it separate from groundedness, which is about the given context.

### 18. RAPID-FIRE ANSWER

Claims, not sentences; supported vs contradicted vs unverifiable.

### 19. INTERVIEW QUESTIONS
