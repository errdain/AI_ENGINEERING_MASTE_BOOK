### 1. WHAT IS IT?

An evaluation gate is an automated pass/fail rule on evaluation results (minimum quality, maximum harm, no significant regression) that must hold before a change can proceed.

### 2. WHY DOES IT EXIST?

Without explicit gates, 'looks good' decides releases. Gates make criteria explicit, consistent and auditable, and block regressions automatically.

### 3. DETAILED EXPLANATION

Gate types (all in `evalharness.Gate` / `evaluate_gates`):
- **Absolute floor/ceiling**: `min`/`max` on a metric (for example accuracy lower-CI >= 0.80, harmful rate <= 1%). Using the **lower confidence bound** rather than the mean is conservative: a small benchmark must show a bigger margin.
- **Regression gate**: drop vs a baseline <= `max_regression`; optionally only fail if the paired bootstrap says the drop is significant (`require_significant`), to avoid blocking on noise ([15.33 Model comparison](15.33-model-comparison.md)).
- **Slice gates**: per-category thresholds (`slice:safety`) so averages cannot hide a failing slice.
- **Hard vs soft**: hard gates block; soft gates warn.
- **Fail closed**: a missing metric or missing baseline is a failure, with a reason.
- **Reasons**: every failure states metric, value and threshold; vague 'FAIL' is not acceptable.

Gate thresholds are policy: set from risk and cost; review periodically; log any override with an owner (REVIEW_REQUIRED per organisation). Try the dashboard to see one failure block a release.

### 4. HOW DOES IT WORK?

Collect metrics from the stored result -> evaluate each gate -> collect reasons -> pass only if no hard gate fails.

### 5. SIMPLE EXAMPLE

An airport safety checklist: one unchecked item grounds the plane, regardless of how many others pass.

### 6. TECHNICAL EXAMPLE

Candidate: accuracy 0.84 [lower 0.79], safety refusal 0.97 (min 0.99), ECE 0.04, regression 0.03: blocked, with two reasons listed (Figure 9; explorer).

### 7. CODE

```python
# run inside lab/
from evalharness import EvalResult, Gate, evaluate_gates
res = EvalResult("cand", "d", "v1", "exact_match", 0, "1.0", {"a": 1.0}, {"a": []},
                 {"mean": 0.84, "ci_low": 0.79, "slice:safety": 0.97, "n": 400})
gates = [Gate("accuracy LCB", "ci_low", min=0.78), Gate("safety refusal", "slice:safety", min=0.99),
         Gate("calibration", "ece", max=0.05)]
print(evaluate_gates(res, gates))        # FAIL: safety below minimum; calibration metric missing -> fail closed
```

Lab code: [`lab/evalharness.py`](../lab/evalharness.py).

```
result metrics + baseline + gate rules -> evaluate each -> reasons -> PASS / FAIL (block)
```

### 9. ENTERPRISE USE CASE

CI blocks merges or deployments when hard gates fail; overrides need a named approver and are logged.

### 10. AI ENGINEERING CONNECTION

The enforcement step for safety, quality and regression criteria in every LLM release.

### 11. ADVANTAGES

- Consistent, auditable, automatic.

### 12. LIMITATIONS

- Thresholds can be arbitrary; gates can be gamed or too strict.

### 13. TRADE-OFFS

- Strict gates slow shipping; loose gates ship regressions.

### 14. COMMON MISTAKES

- Mean instead of lower bound.
- No slice gates.
- Passing on missing data.
- Silent overrides.

### 15. PERFORMANCE / COST CONSIDERATIONS

Gate evaluation is negligible; the cost is in producing the metrics.

### 16. SECURITY CONSIDERATIONS

Protect gate configuration: changing thresholds is a privileged action.

### 17. INTERVIEW EXPLANATION

An evaluation gate is an explicit pass/fail rule on results: absolute floors, regression limits (optionally significance-aware), per-slice minimums, with hard and soft levels, fail-closed behaviour and stated reasons. I use lower confidence bounds, gate safety slices separately and audit overrides.

### 18. RAPID-FIRE ANSWER

Explicit thresholds, lower bounds, slices, fail closed, reasons.
