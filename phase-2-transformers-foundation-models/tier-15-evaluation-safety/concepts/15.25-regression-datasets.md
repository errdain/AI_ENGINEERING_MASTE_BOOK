### 1. WHAT IS IT?

A regression dataset is a growing set of test cases created from past failures (bugs, incidents, red-team successes, user complaints) so that fixed problems stay fixed.

### 2. WHY DOES IT EXIST?

Models and prompts change constantly; without a regression set, old failures silently return.

### 3. DETAILED EXPLANATION

Properties:
- Each case records **source** (incident id), **expected behaviour**, tags and date. `Dataset.add_regression` in the lab requires an id and source, and rejects duplicates.
- Cases are **small, specific, deterministic** to score; they are not a representative sample, so do not use their pass rate as an estimate of overall quality (that is the golden/benchmark set's job, [15.26 Golden datasets](15.26-golden-datasets.md)).
- Pass criterion is usually **zero failures** (or a tracked allowance), plus a check that new failures did not appear.
- Maintenance: dedupe, retire cases whose requirements changed (with review), version the set (content hash, [15.30 Evaluation versioning](15.30-evaluation-versioning.md)).
- Flaky cases (non-deterministic outputs) need seeded runs or tolerant scorers ([15.29 Evaluation reproducibility](15.29-evaluation-reproducibility.md)).

### 4. HOW DOES IT WORK?

Incident arrives -> minimise to a reproducing input -> write expected behaviour -> add with source -> CI runs the regression set on every change -> failures block merge.

### 5. SIMPLE EXAMPLE

A bug tracker whose every closed bug becomes an automated test.

### 6. TECHNICAL EXAMPLE

A model update starts producing wrong dates for 'next Friday'; the case is added; two releases later a prompt change reintroduces the bug and CI catches it.

### 7. CODE

```python
# run inside lab/ (see demo.py for a full run)
from evalharness import Dataset, Example, run_eval
ds = Dataset("regress", "regression", [])
ds.add_regression("inc-101", "what is 7+7?", "14", source="incident-101", tags=["math"])
model = lambda q: "14"
r = run_eval(model, "m", ds)
assert r.metrics["mean"] == 1.0, "a regression case failed"
print("regression set version", ds.version)
```

Lab code: [`lab/evalharness.py`](../lab/evalharness.py), [`lab/demo.py`](../lab/demo.py).

### 8. INPUT → PROCESS → OUTPUT

```
failure -> minimal reproducing case + expected output + source -> regression set -> CI run -> block on failure
```

### 9. ENTERPRISE USE CASE

Platform teams own the regression harness; feature teams add cases; any failing case blocks the release train.

### 10. AI ENGINEERING CONNECTION

Prompt, retrieval or model changes in any LLM app are guarded by regression suites; Tier 30 extends this to applications.

### 11. ADVANTAGES

- Cheap, fast, precise guard against repeat failures.

### 12. LIMITATIONS

- Biased toward past failures; can grow stale; not an estimate of overall quality.

### 13. TRADE-OFFS

- Size (run time) vs coverage.

### 14. COMMON MISTAKES

- Using regression pass rate as quality estimate.
- No source/provenance.
- Never retiring obsolete cases.

### 15. PERFORMANCE / COST CONSIDERATIONS

Small sets run in seconds; keep them in CI.

### 16. SECURITY CONSIDERATIONS

Cases derived from production logs may contain PII: sanitise first ([15.20 Privacy evaluation](15.20-privacy-evaluation.md)).

### 17. INTERVIEW EXPLANATION

A regression dataset turns each past failure into a permanent, deterministic test with a source and expected behaviour, run in CI on every change. It protects against repeat failures but is not representative, so I keep a separate golden set for quality estimation.

### 18. RAPID-FIRE ANSWER

Every fixed bug becomes a test; zero tolerance; versioned.
