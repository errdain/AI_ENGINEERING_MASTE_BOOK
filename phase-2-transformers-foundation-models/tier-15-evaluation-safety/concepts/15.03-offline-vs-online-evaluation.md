### 1. WHAT IS IT?

Offline evaluation scores a model on fixed datasets before release. Online evaluation measures behaviour on live traffic after (or during) release, via experiments or monitoring.

### 2. WHY DOES IT EXIST?

Offline is cheap, safe and repeatable but may not match real traffic. Online reflects real users and drift but is slower, riskier and noisier. Mature teams use both.

### 3. DETAILED EXPLANATION

| | Offline | Online |
|---|---|---|
| Data | fixed golden / regression / benchmark sets | live user traffic |
| Risk | none to users | users exposed |
| Speed | minutes to hours | days to weeks (need traffic) |
| Repeatability | high (seeded) | low (population changes) |
| Signals | accuracy, groundedness, refusal rate | task success, thumbs, escalation, retention |
| Typical use | gate before release | A/B test, canary, monitoring |

Offline results justify exposing a model to a small fraction of traffic; online results confirm (or refute) that offline gains transfer. Disagreement between them is a signal that the offline set is unrepresentative ([15.17 Distribution-shift evaluation](15.17-distribution-shift-evaluation.md)).

### 4. HOW DOES IT WORK?

Offline gate -> canary on a small traffic share -> staged ramp with guardrail metrics -> full release, rolling back automatically on guardrail breach. Tier 30 owns A/B testing and monitoring details.

### 5. SIMPLE EXAMPLE

A restaurant tests a recipe in the kitchen (offline) before putting it on the menu for a few tables (online).

### 6. TECHNICAL EXAMPLE

Candidate model scores +2 points offline. Canary with 5% of traffic shows no change in resolution rate but 20% more escalations, because real queries are longer than the golden set. The offline set is updated with those queries.

### 7. CODE

```python
# run inside lab/ -- the offline half: seeded, versioned, gated
from evalharness import Dataset, Example, run_eval, Gate, evaluate_gates
ds = Dataset("toy", "golden", [Example(f"e{i}", f"{i}+{i}", str(2 * i)) for i in range(30)])
model = lambda x: str(2 * int(x.split('+')[0]))
res = run_eval(model, "m1", ds, seed=0)
print(evaluate_gates(res, [Gate("acc", "mean", min=0.95)]))
```

### 8. INPUT → PROCESS → OUTPUT

```
golden set -> offline score -> gate -> canary traffic -> online metrics -> ramp / rollback
```

### 9. ENTERPRISE USE CASE

Offline suites run in CI on every change; online experiments run in staged rollouts with automatic rollback.

### 10. AI ENGINEERING CONNECTION

LLM features need both: offline for iteration speed and safety checks, online for user value. Feedback from online logs feeds back into regression sets ([15.25 Regression datasets](15.25-regression-datasets.md)).

### 11. ADVANTAGES

- Offline: fast, safe, reproducible.
- Online: real distribution, real value.

### 12. LIMITATIONS

- Offline can be unrepresentative.
- Online needs traffic and risk tolerance and has confounders.

### 13. TRADE-OFFS

- Speed and safety (offline) vs realism (online).

### 14. COMMON MISTAKES

- Shipping on offline results alone.
- Online experiments with no guardrail metrics.
- Not feeding online failures back into offline sets.

### 15. PERFORMANCE / COST CONSIDERATIONS

Offline cost is compute; online cost is user exposure and engineering time.

### 16. SECURITY CONSIDERATIONS

Online logs contain user data: apply privacy controls before turning them into evaluation sets ([15.20 Privacy evaluation](15.20-privacy-evaluation.md)).

### 17. INTERVIEW EXPLANATION

Offline evaluation tests on fixed data before release; online evaluation measures live behaviour through canaries and experiments. Offline is cheap and repeatable but may mismatch reality; online is real but slow and risky. I gate on offline, ramp with online guardrails and recycle online failures into regression datasets.

### 18. RAPID-FIRE ANSWER

Offline = safe and fast; online = real; use both and loop failures back.
