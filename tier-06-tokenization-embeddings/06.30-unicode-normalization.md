# 6.30 Unicode normalization

**Metadata** — Tier: 6 · Phase: 2 · Priority: High · Difficulty: Beginner · Interview: High · Hands-on: High
Prerequisites: [6.1 Text preprocessing](06.01-text-preprocessing.md), [6.4 Byte tokenization](06.04-byte-tokenization.md) · Leads to: [6.27 Tokenizer training](06.27-tokenizer-training.md), [6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)

> **In plain words**
> The same visible text can be stored as different Unicode code-point sequences: "é" can be one character or `e` + a combining accent. **Unicode normalization** rewrites text into one canonical form so equal-looking strings become identical *before* tokenizing. Without it the same word gets different token ids; with the wrong form (NFKC) you may lose information. It does **not** fix look-alike characters from different scripts.

**You need first:** [6.1 Text preprocessing](06.01-text-preprocessing.md), [6.4 Byte tokenization](06.04-byte-tokenization.md).

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| NFC | compose: use single code points where possible |
| NFD | decompose: base letter + combining marks |
| NFKC / NFKD | also fold 'compatibility' characters (ligatures, full-width): lossy |
| combining mark | an accent stored as a separate code point |
| confusables | look-alike characters, e.g. Latin a and Cyrillic а |
| canonical equivalence | different code points meaning exactly the same text |

### 1. What is it?

Unicode normalization converts text to a canonical form so that canonically or compatibly equivalent strings have identical code point sequences (NFC, NFD, NFKC, NFKD).

### 2. Why does it exist?

The same visible text can have different code point and byte sequences: `é` can be U+00E9 or `e` + U+0301. Without normalization these map to different tokens.

### 3. Detailed explanation

| Form | Meaning | Typical use |
|---|---|---|
| NFC | compose where possible | default for most LLM pipelines' inputs |
| NFD | decompose | linguistic analysis |
| NFKC | also folds *compatibility* characters (`ﬁ`->`fi`, full-width->ASCII) | search / BERT-style cleanup; **lossy** |
| NFKD | NFKC but decomposed | rare |

Important limits: normalization handles *canonical/compatibility equivalence only*. It does **not** unify **confusables** from different scripts (Latin `a` U+0061 vs Cyrillic `а` U+0430): those need a separate confusables check (Unicode UTS #39, `REVIEW_REQUIRED`). Zero-width characters are not removed by normalization either.

Some tokenizer libraries normalize internally (e.g. SentencePiece rules, BERT's cleaning); know what *your* tokenizer does so your guardrails use a consistent view.

### 5. Simple example

Two photos of the same word taken from slightly different angles: they look the same to you but are different files to a computer, until you re-shoot them from a standard angle.

**By hand.** `"café"` typed with the single character U+00E9 has length 4. `"cafe\u0301"` (e + combining acute) has length 5. They look identical but `==` is False and a tokenizer would produce different ids. After NFC both become the 4-character form. NFKC additionally turns the ligature `ﬁ` into `fi` (lossy: you cannot tell afterwards that the ligature was there).

### 6. Technical example

A search index built on NFC text will miss a query typed from a keyboard that produces NFD (common with some macOS file names).

### 7. Code

**① By hand (plain Python).** The same word in two Unicode forms.

```python
import unicodedata

a, b = "café", "cafe\u0301"
print("looks identical, equal?", a == b, "  lengths:", len(a), len(b))
print("after NFC equal?", unicodedata.normalize("NFC", b) == a)
print("bytes:", len(a.encode()), len(b.encode()))
```

```text
looks identical, equal? False   lengths: 4 5
after NFC equal? True
bytes: 5 6
```

**② With NumPy.** What normalization does and does not do, in a table.

```python
import unicodedata

tests = {"accent forms": "cafe\u0301", "ligature": "\ufb01ne", "full-width": "\uff21\uff22\uff23", "Cyrillic a": "\u0430"}
print(f"{'case':<14}{'NFC':>8}{'NFKC':>8}   changed by NFKC?")
for name, s in tests.items():
    nfc, nfkc = unicodedata.normalize("NFC", s), unicodedata.normalize("NFKC", s)
    print(f"{name:<14}{nfc!r:>8}{nfkc!r:>8}   {nfkc != s}")
print("Cyrillic а is still not the Latin a after NFKC:", unicodedata.normalize("NFKC", "\u0430") != "a")
```

```text
case               NFC    NFKC   changed by NFKC?
accent forms    'café'  'café'   True
ligature         'ﬁne'  'fine'   True
full-width       'ＡＢＣ'   'ABC'   True
Cyrillic a         'а'     'а'   False
Cyrillic а is still not the Latin a after NFKC: True
```

### 9. Enterprise use case

Enterprise search and RAG pipelines normalize at ingestion *and* at query time with the same function and version.

### 10. AI engineering connection

Changes token counts and IDs, so it must match the tokenizer's training assumptions; part of train/serve consistency ([6.1 Text preprocessing](06.01-text-preprocessing.md)).

### 11. Advantages

Canonical text; fewer spurious vocabulary splits; more reliable matching.

### 12. Limitations

NFKC is lossy (can change code, math, ligatures); does not fix confusables or zero-width characters.

### 13. Trade-offs

Robust matching versus fidelity to the original text.

### 14. Common mistakes

- NFKC on code or math.
- Normalizing at index time but not at query time.
- Assuming normalization defeats homoglyph attacks.
- Forgetting that some tokenizers normalize internally.

### 15. Performance / cost

Linear time; negligible.

### 16. Security

Normalize *before* keyword/guardrail checks, then additionally strip zero-width characters and check confusables; know the differences between your filter's view and the model tokenizer's view.

</details>

### 17. Interview explanation

*"Unicode normalization gives equivalent strings identical code points: NFC composes, NFD decomposes, NFKC also folds compatibility characters but is lossy. I normalize before tokenizing and before safety filters, and I don't rely on it for cross-script lookalikes."*

### 18. Rapid-fire answer

Canonicalize equivalent Unicode (NFC default; NFKC lossy) before tokenization.
