### 1. WHAT IS IT?

Unicode normalization converts text to a canonical form so that canonically or compatibly equivalent strings have identical code point sequences (NFC, NFD, NFKC, NFKD).

### 2. WHY DOES IT EXIST?

The same visible text can have different code point and byte sequences: `é` can be U+00E9 or `e` + U+0301. Without normalization these map to different tokens.

### 3. DETAILED EXPLANATION

| Form | Meaning | Typical use |
|---|---|---|
| NFC | compose where possible | default for most LLM pipelines' inputs |
| NFD | decompose | linguistic analysis |
| NFKC | also folds *compatibility* characters (`ﬁ`->`fi`, full-width->ASCII) | search / BERT-style cleanup; **lossy** |
| NFKD | NFKC but decomposed | rare |

Important limits: normalization handles *canonical/compatibility equivalence only*. It does **not** unify **confusables** from different scripts (Latin `a` U+0061 vs Cyrillic `а` U+0430): those need a separate confusables check (Unicode UTS #39, `REVIEW_REQUIRED`). Zero-width characters are not removed by normalization either.

Some tokenizer libraries normalize internally (e.g. SentencePiece rules, BERT's cleaning); know what *your* tokenizer does so your guardrails use a consistent view.

### 5. SIMPLE EXAMPLE

Two photos of the same word taken from slightly different angles: they look the same to you but are different files to a computer, until you re-shoot them from a standard angle.

### 6. TECHNICAL EXAMPLE

A search index built on NFC text will miss a query typed from a keyboard that produces NFD (common with some macOS file names).

### 7. CODE

```python
import unicodedata
a, b = "café", "cafe\u0301"
print(a == b, len(a), len(b))                              # False 4 5
print(unicodedata.normalize("NFC", b) == a)                # True
print(unicodedata.normalize("NFKC", "\ufb01ne"))           # 'fine' (ligature expanded; lossy)
print("a" == "\u0430")                                    # False: Cyrillic a is NOT fixed by normalization
print(unicodedata.normalize("NFKC", "\u0430") == "a")     # False
```


### 9. ENTERPRISE USE CASE

Enterprise search and RAG pipelines normalize at ingestion *and* at query time with the same function and version.

### 10. AI ENGINEERING CONNECTION

Changes token counts and IDs, so it must match the tokenizer's training assumptions; part of train/serve consistency ([6.1 Text preprocessing](06.01-text-preprocessing.md)).

### 11. ADVANTAGES

Canonical text; fewer spurious vocabulary splits; more reliable matching.

### 12. LIMITATIONS

NFKC is lossy (can change code, math, ligatures); does not fix confusables or zero-width characters.

### 13. TRADE-OFFS

Robust matching versus fidelity to the original text.

### 14. COMMON MISTAKES

- NFKC on code or math.
- Normalizing at index time but not at query time.
- Assuming normalization defeats homoglyph attacks.
- Forgetting that some tokenizers normalize internally.

### 15. PERFORMANCE / COST CONSIDERATIONS

Linear time; negligible.

### 16. SECURITY CONSIDERATIONS

Normalize *before* keyword/guardrail checks, then additionally strip zero-width characters and check confusables; know the differences between your filter's view and the model tokenizer's view.

### 17. INTERVIEW EXPLANATION

*"Unicode normalization gives equivalent strings identical code points: NFC composes, NFD decomposes, NFKC also folds compatibility characters but is lossy. I normalize before tokenizing and before safety filters, and I don't rely on it for cross-script lookalikes."*

### 18. RAPID-FIRE ANSWER

Canonicalize equivalent Unicode (NFC default; NFKC lossy) before tokenization.
