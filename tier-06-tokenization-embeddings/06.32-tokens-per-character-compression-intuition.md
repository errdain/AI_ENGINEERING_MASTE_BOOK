### 1. WHAT IS IT?

Tokens-per-character (and its inverse, characters-per-token) is the intuition for how much text a token holds: roughly 4 characters or three-quarters of an English word per token for common English prose on modern tokenizers (`REVIEW_REQUIRED`).

### 2. WHY DOES IT EXIST?

You need a quick mental estimate to budget prompts, chunk documents and forecast cost before running a tokenizer.

### 3. DETAILED EXPLANATION

Rules of thumb (all `REVIEW_REQUIRED` and tokenizer-dependent): English prose ~4 chars/token, ~0.75 words/token; code and non-English text usually worse (more tokens per character); numbers, URLs and random identifiers can approach 1 token per 1-3 characters. UTF-8 bytes per token is the best cross-language yardstick ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)).

**Compression intuition:** a tokenizer is a *compressor over the model's alphabet*: each merge replaces a frequent multi-symbol sequence with one symbol. Text similar to the training corpus compresses well; unfamiliar text does not, which is why random strings and unusual scripts are expensive.

### 4. HOW DOES IT WORK?

Estimate `tokens ~ chars / c` with `c` measured on *your* text and tokenizer; then add safety margin; verify with the real tokenizer.

### 5. SIMPLE EXAMPLE

Typing shorthand: common phrases take one stroke, rare words take many.

### 6. TECHNICAL EXAMPLE

A 500-character chunk is ~125 English tokens at 4 chars/token but could be 500+ for dense IDs or non-Latin text.

### 7. CODE

```python
# run inside lab/
from mini_bpe import ByteBPE, compression_ratio
tok = ByteBPE.train("low lower lowest newer newest wider widest " * 30, 40)
familiar = "lowest newest widest " * 5
random_like = "qzxjkvwpy " * 10
for name, s in [("familiar", familiar), ("random-like", random_like)]:
    print(name, round(len(tok.encode(s)) / len(s), 2), "tokens/char")
```

### 8. INPUT → PROCESS → OUTPUT

```
chars ÷ (chars/token) ≈ tokens ──► budget check ──► verify with real tokenizer
```

### 9. ENTERPRISE USE CASE

Capacity plans and quotes use chars/token estimates per language, validated on sampled traffic.

### 10. AI ENGINEERING CONNECTION

Underlies quick checks of context fit and cost; not a replacement for exact counting.

### 11. ADVANTAGES

Fast mental estimation.

### 12. LIMITATIONS

Approximate; varies by tokenizer, language, domain; wrong for IDs/numbers/code.

### 13. TRADE-OFFS

Speed of estimation versus accuracy.

### 14. COMMON MISTAKES

- Using 4 chars/token for non-English text.
- Chunking by characters for hard token limits.
- Quoting these ratios without 'it depends'.

### 15. PERFORMANCE / COST CONSIDERATIONS

Underestimating tokens risks truncation errors and cost overruns; add margins.

### 16. SECURITY CONSIDERATIONS

Don't use character length as a limit for untrusted inputs; cap tokens.

### 17. INTERVIEW EXPLANATION

*"For English prose, roughly four characters or three-quarters of a word per token, but it varies by tokenizer, and code, numbers and non-Latin scripts are worse. I use it for estimates and count with the real tokenizer for limits."*

### 18. RAPID-FIRE ANSWER

~4 chars/token for English; worse elsewhere; always verify.
