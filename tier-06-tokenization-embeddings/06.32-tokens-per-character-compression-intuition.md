# 6.32 Tokens-per-character / compression intuition

**Metadata** — Tier: 6 · Phase: 2 · Priority: High · Difficulty: Beginner · Interview: High · Hands-on: Medium
Prerequisites: [6.31 Tokenization efficiency](06.31-tokenization-efficiency.md) · Leads to: cost estimation, RAG chunking (Tier 20)

> **In plain words**
> A useful mental model: a tokenizer is a **compressor** built from the training text. Text that looks like its training data compresses well (about 4 characters, or three-quarters of a word, per token for English); unusual text (random strings, rare scripts, URLs, long identifiers) compresses badly. Rules of thumb let you estimate token counts and costs quickly, but they are tokenizer-specific.

### 1. What is it?

Tokens-per-character (and its inverse, characters-per-token) is the intuition for how much text a token holds: roughly 4 characters or three-quarters of an English word per token for common English prose on modern tokenizers (`REVIEW_REQUIRED`).

### 2. Why does it exist?

You need a quick mental estimate to budget prompts, chunk documents and forecast cost before running a tokenizer.

### 3. Detailed explanation

Rules of thumb (all `REVIEW_REQUIRED` and tokenizer-dependent): English prose ~4 chars/token, ~0.75 words/token; code and non-English text usually worse (more tokens per character); numbers, URLs and random identifiers can approach 1 token per 1-3 characters. UTF-8 bytes per token is the best cross-language yardstick ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)).

**Compression intuition:** a tokenizer is a *compressor over the model's alphabet*: each merge replaces a frequent multi-symbol sequence with one symbol. Text similar to the training corpus compresses well; unfamiliar text does not, which is why random strings and unusual scripts are expensive.

### 4. How does it work?

Estimate `tokens ~ chars / c` with `c` measured on *your* text and tokenizer; then add safety margin; verify with the real tokenizer.

### 5. Simple example

Typing shorthand: common phrases take one stroke, rare words take many.

**By hand.** A 1,000-word English article ≈ 1,000 / 0.75 ≈ 1,333 tokens. A 2,000-character API reply ≈ 2,000 / 4 = 500 tokens. A 36-character UUID may cost 15–25 tokens (≈ 1.5–2.4 chars/token). Budget with a safety margin and count exactly with the model's own tokenizer when it matters.

### 6. Technical example

A 500-character chunk is ~125 English tokens at 4 chars/token but could be 500+ for dense IDs or non-Latin text.

### 7. Code

**① By hand (plain Python).** Quick estimators.

```python
def estimate_tokens(chars=None, words=None):
    if chars is not None:
        return round(chars / 4)
    return round(words / 0.75)

print("1,000 words ≈", estimate_tokens(words=1000), "tokens")
print("2,000 characters ≈", estimate_tokens(chars=2000), "tokens")
print("context of 8,192 tokens holds ≈", round(8192 * 0.75), "English words")
```

```text
1,000 words ≈ 1333 tokens
2,000 characters ≈ 500 tokens
context of 8,192 tokens holds ≈ 6144 English words
```

**② With NumPy.** Familiar versus unfamiliar text with a simulated vocabulary of frequent chunks.

```python
import numpy as np

vocab = ["the ", "ing ", "tion", "and ", " of ", "ent", "er "]       # frequent chunks a tokenizer might have learned
def tokens(s):
    i, n = 0, 0
    while i < len(s):
        hit = next((v for v in sorted(vocab, key=len, reverse=True) if s.startswith(v, i)), None)
        i += len(hit) if hit else 1; n += 1
    return n

rng = np.random.default_rng(0)
familiar = "the tion and of ing the ent er " * 10
random_like = "".join(rng.choice(list("qzxjkvwpy"), 90))
for name, s in (("familiar", familiar), ("random-like", random_like)):
    print(f"{name:<12}: {len(s)} characters -> {tokens(s)} tokens ({len(s) / tokens(s):.1f} chars/token)")
```

```text
familiar    : 310 characters -> 120 tokens (2.6 chars/token)
random-like : 90 characters -> 90 tokens (1.0 chars/token)
```

### 9. Enterprise use case

Capacity plans and quotes use chars/token estimates per language, validated on sampled traffic.

### 10. AI engineering connection

Underlies quick checks of context fit and cost; not a replacement for exact counting.

### 11. Advantages

Fast mental estimation.

### 12. Limitations

Approximate; varies by tokenizer, language, domain; wrong for IDs/numbers/code.

### 13. Trade-offs

Speed of estimation versus accuracy.

### 14. Common mistakes

- Using 4 chars/token for non-English text.
- Chunking by characters for hard token limits.
- Quoting these ratios without 'it depends'.

### 15. Performance / cost

Underestimating tokens risks truncation errors and cost overruns; add margins.

### 16. Security

Don't use character length as a limit for untrusted inputs; cap tokens.
