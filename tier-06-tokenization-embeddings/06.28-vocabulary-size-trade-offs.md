# 6.28 Vocabulary-size trade-offs

**Metadata** — Tier: 6 · Phase: 2 · Priority: Critical · Difficulty: Intermediate · Interview: Very high · Hands-on: High
Prerequisites: [6.18 Embedding matrix](06.18-embedding-matrix.md), [6.19 Embedding dimensions](06.19-embedding-dimensions.md), [6.5 Subword tokenization](06.05-subword-tokenization.md) · Leads to: [6.31 Tokenization efficiency](06.31-tokenization-efficiency.md), [6.32 Tokens-per-character / compression intuition](06.32-tokens-per-character-compression-intuition.md)

> **In plain words**
> Choosing the **vocabulary size** is a trade-off. A bigger vocabulary packs more text into each token (shorter sequences, cheaper attention, more text per context window, lower per-character API cost) but makes the embedding table and the output layer bigger and leaves rare tokens with few training examples. The gain from each extra merge shrinks, so there is a sweet spot.

**You need first:** [6.18 Embedding matrix](06.18-embedding-matrix.md), [6.19 Embedding dimensions](06.19-embedding-dimensions.md), [6.5 Subword tokenization](06.05-subword-tokenization.md).

|---|---|

### 1. What is it?

Vocabulary-size trade-offs are the balance between a larger vocabulary (shorter token sequences) and a larger embedding table and output softmax, plus less training signal per rare token.

### 2. Why does it exist?

Vocabulary size V is the main design knob of a tokenizer; it moves cost between sequence length and parameters.

### 3. Detailed explanation

**Larger V:** more characters per token (shorter sequences, cheaper attention, lower latency, more text per context window, lower per-character API cost), **but** a bigger embedding table and output projection (`V*d` each, unless tied), a bigger softmax per step, and rarer tokens that get few training updates.

**Smaller V:** longer sequences, smaller layers, better coverage per token. Compression gains show **diminishing returns** as V grows (each extra merge helps less than the previous one). Multilingual models need more V to avoid overpaying in non-English languages ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)). Typical ranges (`REVIEW_REQUIRED`): ~30k (BERT/Llama 2/T5-class) to >100k (recent large models).

### 4. How does it work?

Move V, d and document length in [explore: `vocab_tradeoff.html`](interactive/vocab_tradeoff.html).

### 5. Simple example

A phrasebook: more phrases make sentences shorter to say, but the book is heavier and the rare phrases are rarely practised.

**By hand.** At `d = 4,096`, `V = 32,000` means `131 million` parameters in the input table (and the same again in the output layer unless tied); `V = 128,000` means `524 million`. If the bigger vocabulary shortens a document by 15%, attention work falls by roughly `1 − 0.85² ≈ 28%`, while 4× more table parameters must be stored and learned.

### 6. Technical example

V = 128,000, d = 4,096: 524 M embedding parameters (and the same again if the output head is untied) - versus 131 M at V = 32,000.

### 7. Code

**① By hand (plain Python).** Cost of the table versus the saving in sequence length.

```python
d = 4096
for V, saving in ((32_000, 0.0), (64_000, 0.07), (128_000, 0.15)):
    table = V * d / 1e6
    attention = 1 - (1 - saving) ** 2
    print(f"V = {V:>7,}: table {table:7.1f}M params   sequence {saving:4.0%} shorter -> attention work {attention:4.0%} lower")
```

```text
V =  32,000: table   131.1M params   sequence   0% shorter -> attention work   0% lower
V =  64,000: table   262.1M params   sequence   7% shorter -> attention work  14% lower
V = 128,000: table   524.3M params   sequence  15% shorter -> attention work  28% lower
```

**② With NumPy.** The price side: the output layer does V multiplications per position.

```python
import numpy as np

d, tokens_per_step = 4096, 8192
for V in (32_000, 128_000, 256_000):
    flops = 2 * tokens_per_step * d * V                                 # logits for every position
    print(f"V = {V:>7,}: output-layer cost {flops / 1e12:6.2f} TFLOPs per 8,192-token step;  logits tensor {tokens_per_step * V * 2 / 1e9:5.2f} GB in 16-bit")
```

```text
V =  32,000: output-layer cost   2.15 TFLOPs per 8,192-token step;  logits tensor  0.52 GB in 16-bit
V = 128,000: output-layer cost   8.59 TFLOPs per 8,192-token step;  logits tensor  2.10 GB in 16-bit
V = 256,000: output-layer cost  17.18 TFLOPs per 8,192-token step;  logits tensor  4.19 GB in 16-bit
```

**③ With the tier library.** Measured with the tier's BPE on a word-frequency corpus: gain per extra merge shrinks.

```python
import sys
import numpy as np
sys.path.insert(0, "lab")
from mini_bpe import ByteBPE, compression_ratio

rng = np.random.default_rng(0)
syllables = ["ka", "to", "ri", "men", "sol", "ver", "lin", "dor", "pa", "qui", "an", "est", "ing", "tion", "er", "al"]
words = ["".join(rng.choice(syllables, size=rng.integers(1, 4))) for _ in range(300)]
p = 1 / np.arange(1, 301); p /= p.sum()                                  # Zipf-like word frequencies
text = " ".join(rng.choice(words, size=3000, p=p))
prev_m, prev_r = 0, 1.0
for m in (10, 20, 40, 80, 160, 320):
    r = compression_ratio(ByteBPE.train(text, m), text)
    print(f"{m:>3} merges: {r:4.2f} bytes/token   gain per extra merge {(r - prev_r) / (m - prev_m):.4f}")
    prev_m, prev_r = m, r
```

```text
 10 merges: 1.56 bytes/token   gain per extra merge 0.0560
 20 merges: 2.16 bytes/token   gain per extra merge 0.0604
 40 merges: 3.44 bytes/token   gain per extra merge 0.0636
 80 merges: 4.61 bytes/token   gain per extra merge 0.0293
160 merges: 5.63 bytes/token   gain per extra merge 0.0127
320 merges: 6.17 bytes/token   gain per extra merge 0.0034
```

### 9. Enterprise use case

A multilingual assistant measures cost per language across candidate tokenizers; moving from 32k to 128k+ vocabularies is often justified by non-English savings (`REVIEW_REQUIRED` for specific numbers).

### 10. AI engineering connection

Affects softmax cost per generated token, KV-cache length per document, and training data coverage per token.

### 11. Advantages

Tuning V can cut sequence length (cost) at modest parameter cost.

### 12. Limitations

Gains saturate; large V undertrains rare tokens; changing V later is expensive.

### 13. Trade-offs

Sequence length versus parameter/softmax cost and rare-token quality.

### 14. Common mistakes

- Maximizing V without checking undertrained tokens.
- Ignoring the untied output head in parameter counts.
- Comparing V across models without considering d.

### 15. Performance / cost

Output softmax is `O(V*d)` per generated token; embedding memory `V*d` bytes-per-param.

### 16. Security

Rare/undertrained tokens are associated with glitch behaviours; audit low-frequency tokens.

</details>

### 17. Interview explanation

*"Why not a huge vocabulary? A bigger vocabulary compresses text and shortens sequences, but the embedding table and softmax grow linearly, rare tokens are undertrained, and returns diminish. Why not bytes only? Sequences get 3-4x longer for non-ASCII text and attention cost is quadratic."*

### 18. Rapid-fire answer

Bigger V: shorter sequences but larger embedding/softmax and rarer tokens.
