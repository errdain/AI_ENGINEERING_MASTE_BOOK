# 6.26 Token vs semantic embeddings

**Metadata** — Tier: 6 · Phase: 2 · Priority: Critical · Difficulty: Beginner · Interview: Very high · Hands-on: High
Prerequisites: [6.17 Token embedding](06.17-token-embedding.md), [6.18 Embedding matrix](06.18-embedding-matrix.md) · Leads to: Tier 20 (RAG/retrieval); [Tier 8](../tier-08-transformer-architecture/README.md)

> **In plain words**
> Two things are called "embeddings". A **token embedding** is a row of the model's first-layer table: static, one per token, internal to the model. A **semantic (sentence) embedding** is one vector for a whole text, produced by a trained encoder and used for search and retrieval. Averaging token embeddings gives only a weak, order-blind sentence vector.

**You need first:** [6.17 Token embedding](06.17-token-embedding.md), [6.18 Embedding matrix](06.18-embedding-matrix.md).

> **Figure 6.26-1 — Token embeddings versus semantic embeddings**

> *How to read it:* the left half (lookup) is the first layer of every language model. The right half (encoder + pooling) is a trained model whose output vector represents the whole text and can be compared with cosine similarity.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| token embedding | a static vector per token from the input table |
| semantic embedding | a context-aware vector for a whole text |
| pooling | combining token vectors into one (mean, CLS, last token) |
| cosine similarity | angle-based similarity between two vectors |
| vector database | stores semantic embeddings for search |
| bag of embeddings | order-blind average of token vectors |

### 1. What is it?

Token (input) embeddings are static per-token vectors looked up from a table; semantic embeddings are vectors for a whole text produced by a trained encoder and used for similarity search.

### 2. Why does it exist?

The word 'embedding' covers two different things; confusing them is a common source of errors in RAG and retrieval systems.

### 3. Detailed explanation

| | Token (input) embedding | Semantic (sentence/document) embedding |
|---|---|---|
| What | row of `E`, one per token | one vector for a whole text |
| Context-aware | **no** (static at input) | **yes** (encodes the full text) |
| Used for | first layer of an LLM | search, clustering, RAG retrieval |
| Produced by | table lookup | forward pass of an encoder model, then pooling (mean, CLS, last-token; `REVIEW_REQUIRED` per model) |
| Compared with | not directly useful | cosine similarity / dot product |

A vector database stores the right-hand kind. The left-hand kind is an internal parameter block of a model and does not give meaningful sentence similarity on its own (averaging them is a weak baseline).

### 4. How does it work?

Semantic: text -> tokenizer -> transformer layers -> pooled vector. Token: id -> row lookup.

### 5. Simple example

A dictionary entry for a word (token embedding) vs a one-paragraph summary card for a whole document (semantic embedding).

**By hand.** Token vectors for ids 1, 2, 3 averaged give the same sentence vector whether the sentence is `[1, 2, 3]` or `[3, 2, 1]`: "dog bites man" and "man bites dog" collapse to one vector. A trained encoder produces different vectors because each token's representation depends on the others and on the order.

### 6. Technical example

Two sentences using 'bank' differently get the same input token vector but different semantic embeddings.

### 7. Code

**① By hand (plain Python).** The bag-of-embeddings problem in plain Python.

```python
E = {1: [1.0, 0.0], 2: [0.0, 1.0], 3: [2.0, 2.0]}
mean = lambda ids: [sum(E[i][c] for i in ids) / len(ids) for c in range(2)]
print("[1, 2, 3] ->", mean([1, 2, 3]))
print("[3, 2, 1] ->", mean([3, 2, 1]), "(identical: order and context are ignored)")
```

```text
[1, 2, 3] -> [1.0, 1.0]
[3, 2, 1] -> [1.0, 1.0] (identical: order and context are ignored)
```

**② With NumPy.** Cosine similarity between semantic vectors, and the bag-of-embeddings baseline.

```python
import numpy as np

rng = np.random.default_rng(0)
E = rng.normal(size=(10, 4))
bag = lambda ids: E[ids].mean(0)
cos = lambda a, b: float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
print("same words, other order:", np.allclose(bag([1, 2, 3]), bag([3, 2, 1])))
print("cosine of two different sentences' bags:", round(cos(bag([1, 2, 3]), bag([4, 5, 6])), 2))
```

```text
same words, other order: True
cosine of two different sentences' bags: -0.23
```

**③ With PyTorch.** A tiny trained 'encoder' (a GRU) is order-sensitive where the bag is not.

```python
import torch

torch.manual_seed(0)
emb = torch.nn.Embedding(10, 8)
gru = torch.nn.GRU(8, 8, batch_first=True)
a, b = torch.tensor([[1, 2, 3]]), torch.tensor([[3, 2, 1]])
bag = lambda x: emb(x).mean(1)
enc = lambda x: gru(emb(x))[1][0]                                   # last hidden state as the sentence vector
print("bag of embeddings identical for both orders:", torch.allclose(bag(a), bag(b)))
print("encoder output identical for both orders   :", torch.allclose(enc(a), enc(b)))
```

```text
bag of embeddings identical for both orders: True
encoder output identical for both orders   : False
```

**Lab excerpt** (from the tier's `lab/`, as originally authored; run inside the `lab/` folder):

```python
import numpy as np
rng = np.random.default_rng(0)
E = rng.normal(size=(10, 4))                    # token table (V=10, d=4)
sent_a, sent_b = [1, 2, 3], [3, 2, 1]
bag = lambda ids: E[ids].mean(0)                # naive 'sentence vector' from token embeddings
print(np.allclose(bag(sent_a), bag(sent_b)))    # True: order & context ignored -> why we need trained encoders
```

### 8. Input → Process → Output

```
text ──tokenizer──► ids ──E──► token vectors (static)
text ──encoder + pooling──► ONE semantic vector ──► vector DB / cosine search
```

### 9. Enterprise use case

RAG systems embed chunks with a semantic encoder; the chunk size must be set in that encoder's *tokens*.

### 10. AI engineering connection

Foundation for retrieval (Tier 20) and for understanding what the first LLM layer does.

### 11. Advantages

Clear separation of concepts avoids bugs in retrieval systems.

### 12. Limitations

Token embeddings are context-free; semantic embeddings depend on the specific encoder and are not interchangeable between models.

### 13. Trade-offs

Semantic embeddings cost a forward pass; token embeddings cost a lookup.

### 14. Common mistakes

- Averaging token embeddings as 'sentence embeddings'.
- Mixing vectors from different embedding models in one index.
- Exceeding the encoder's max input tokens (silent truncation).

### 15. Performance / cost

Encoding cost ~ model forward pass per chunk; lookup is O(1).

### 16. Security

Embeddings can leak information about their source text (inversion attacks, `REVIEW_REQUIRED`); treat vector stores as sensitive data.

</details>

### 17. Interview explanation

*"Token embeddings are a lookup table at the model's input and are context-free. Semantic embeddings are produced by running a whole text through an encoder and pooling; they're what vector search uses."*

### 18. Rapid-fire answer

Token embedding = table row; semantic embedding = pooled encoder output for a whole text.

```python
import numpy as np

rng = np.random.default_rng(1)
E = rng.normal(size=(20, 6))
bag = lambda ids: E[ids].mean(0)
cos = lambda a, b: float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
s1, s2 = [1, 2, 3, 4], [1, 2, 3, 9]
s3 = [10, 11, 12, 13]

```

```text

```

The bag does capture word overlap, which is why it is a (weak) baseline; what it cannot capture is order or meaning that depends on context.
