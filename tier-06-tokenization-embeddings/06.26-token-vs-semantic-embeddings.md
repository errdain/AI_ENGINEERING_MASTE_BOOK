## 6.26 Token vs semantic embeddings

### 1. WHAT IS IT?

Token (input) embeddings are static per-token vectors looked up from a table; semantic embeddings are vectors for a whole text produced by a trained encoder and used for similarity search.

### 2. WHY DOES IT EXIST?

The word 'embedding' covers two different things; confusing them is a common source of errors in RAG and retrieval systems.

### 3. DETAILED EXPLANATION

| | Token (input) embedding | Semantic (sentence/document) embedding |
|---|---|---|
| What | row of `E`, one per token | one vector for a whole text |
| Context-aware | **no** (static at input) | **yes** (encodes the full text) |
| Used for | first layer of an LLM | search, clustering, RAG retrieval |
| Produced by | table lookup | forward pass of an encoder model, then pooling (mean, CLS, last-token; `REVIEW_REQUIRED` per model) |
| Compared with | not directly useful | cosine similarity / dot product |

A vector database stores the right-hand kind. The left-hand kind is an internal parameter block of a model and does not give meaningful sentence similarity on its own (averaging them is a weak baseline).

### 4. HOW DOES IT WORK?

Semantic: text -> tokenizer -> transformer layers -> pooled vector. Token: id -> row lookup.

### 5. SIMPLE EXAMPLE

A dictionary entry for a word (token embedding) vs a one-paragraph summary card for a whole document (semantic embedding).

### 6. TECHNICAL EXAMPLE

Two sentences using 'bank' differently get the same input token vector but different semantic embeddings.

### 7. CODE

```python
import numpy as np
rng = np.random.default_rng(0)
E = rng.normal(size=(10, 4))                    # token table (V=10, d=4)
sent_a, sent_b = [1, 2, 3], [3, 2, 1]
bag = lambda ids: E[ids].mean(0)                # naive 'sentence vector' from token embeddings
print(np.allclose(bag(sent_a), bag(sent_b)))    # True: order & context ignored -> why we need trained encoders
```

### 8. INPUT → PROCESS → OUTPUT

```
text ──tokenizer──► ids ──E──► token vectors (static)
text ──encoder + pooling──► ONE semantic vector ──► vector DB / cosine search
```

### 9. ENTERPRISE USE CASE

RAG systems embed chunks with a semantic encoder; the chunk size must be set in that encoder's *tokens*.

### 10. AI ENGINEERING CONNECTION

Foundation for retrieval (Tier 20) and for understanding what the first LLM layer does.

### 11. ADVANTAGES

Clear separation of concepts avoids bugs in retrieval systems.

### 12. LIMITATIONS

Token embeddings are context-free; semantic embeddings depend on the specific encoder and are not interchangeable between models.

### 13. TRADE-OFFS

Semantic embeddings cost a forward pass; token embeddings cost a lookup.

### 14. COMMON MISTAKES

- Averaging token embeddings as 'sentence embeddings'.
- Mixing vectors from different embedding models in one index.
- Exceeding the encoder's max input tokens (silent truncation).

### 15. PERFORMANCE / COST CONSIDERATIONS

Encoding cost ~ model forward pass per chunk; lookup is O(1).

### 16. SECURITY CONSIDERATIONS

Embeddings can leak information about their source text (inversion attacks, `REVIEW_REQUIRED`); treat vector stores as sensitive data.

### 17. INTERVIEW EXPLANATION

*"Token embeddings are a lookup table at the model's input and are context-free. Semantic embeddings are produced by running a whole text through an encoder and pooling; they're what vector search uses."*

### 18. RAPID-FIRE ANSWER

Token embedding = table row; semantic embedding = pooled encoder output for a whole text.
