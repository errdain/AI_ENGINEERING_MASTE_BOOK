# 6.27 Tokenizer training

Prerequisites: [6.12 BPE](06.12-bpe.md), [6.15 Unigram LM tokenizer](06.15-unigram-lm-tokenizer.md), [6.1 Text preprocessing](06.01-text-preprocessing.md), [6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md) · Leads to: [6.31 Tokenization efficiency](06.31-tokenization-efficiency.md), [Tier 9](../tier-09-foundation-model-pretraining/README.md) (pre-training)

> **In plain words**
> **Tokenizer training** is the offline job of learning the vocabulary (merges or probabilities) from a corpus, then freezing and versioning it with the model. The corpus decides what gets cheap: a tokenizer trained on English compresses English well and code or Hindi badly. Choices made here (normalization, digits, whitespace, special tokens, size) are permanent properties of the model.

### 1. What is it?

Tokenizer training is the offline process of learning a tokenizer's vocabulary (and merges/probabilities) from a corpus, then freezing and versioning it as part of the model artifact.

### 2. Why does it exist?

The tokenizer determines cost, context fit, fairness across languages and downstream quality; a vocabulary learned on unrepresentative text is permanently inefficient for the real workload.

### 3. Detailed explanation

**Checklist (any algorithm):**

1. **Corpus.** Representative of production: languages, code, domain terms, numbers, URLs; deduplicate and sample deliberately (mix ratios shape vocabulary allocation per language).
2. **Normalize** ([6.30 Unicode normalization](06.30-unicode-normalization.md)) and choose **pre-tokenization** ([6.1 Text preprocessing](06.01-text-preprocessing.md)): digits split individually or grouped? whitespace/indentation kept? regex splits?
3. **Algorithm and size.** BPE ([6.12 BPE](06.12-bpe.md)), WordPiece ([6.13 WordPiece](06.13-wordpiece.md)), Unigram ([6.15 Unigram LM tokenizer](06.15-unigram-lm-tokenizer.md)); target vocab size per [6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md).
4. **Reserve special tokens** ([6.8 UNK](06.08-unk.md)-[6.11 EOS](06.11-eos.md), chat markers) and byte fallback ([6.29 Byte fallback](06.29-byte-fallback.md)) decisions.
5. **Train**, then **measure**: bytes/token or tokens/char and fertility per language/domain ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)), fragmentation of numbers/URLs/code, UNK rate, round-trip on random Unicode.
6. **Freeze and version** the tokenizer files; test that `decode(encode(x)) == x`; ship with the model.

Because the tokenizer must exist *before* model pre-training and cannot be changed afterwards without effectively retraining embeddings, this step deserves real engineering care.

### 5. Simple example

Writing a phrasebook: you pick the phrases to include by listening to the conversations you will actually have; a phrasebook compiled from the wrong conversations wastes pages.

**By hand.** Train two tokenizers with 40 merges, one on English sentences, one on Python code. Test each on both texts. Expected pattern: each compresses its *own* domain better (more bytes per token) than the other's. If your users write code but you trained on prose, every `def` and indentation will cost extra tokens.

### 6. Technical example

Training on English-only text gives few merges for Hindi, so Hindi costs several times more tokens (Figure 8); adding Hindi data to the tokenizer corpus before training fixes that (the model then also needs Hindi data).

### 7. Code

**① By hand (plain Python).** How much does a corpus-specific merge save? Count pairs in two corpora.

```python
from collections import Counter

def top_pair(text):
    pairs = Counter(zip(text, text[1:]))
    return pairs.most_common(1)[0]

english = "the cat sat on the mat and the dog ran to the park " * 40
code = "def add(a, b):\n    return a + b\n" * 40
print("most frequent adjacent pair in English text:", top_pair(english))
print("most frequent adjacent pair in code        :", top_pair(code))
```

```text
most frequent adjacent pair in English text: ((' ', 't'), 199)
most frequent adjacent pair in code        : ((' ', ' '), 120)
```

**② With NumPy.** Coverage: how much of new text is made of pieces seen in training?

```python
import numpy as np

train = "the cat sat on the mat and the dog ran to the park " * 40
words_train = set(train.split())
tests = {"similar text": "the dog sat on the park", "other domain": "gradient descent minimizes the loss"}
for name, t in tests.items():
    ws = t.split()
    print(f"{name:<14}: {np.mean([w in words_train for w in ws]):.0%} of words seen in the training corpus")
```

```text
similar text  : 100% of words seen in the training corpus
other domain  : 20% of words seen in the training corpus
```

**③ With the tier library.** Train two tokenizers and compare them across domains.

```python
import sys
sys.path.insert(0, "lab")
from mini_bpe import ByteBPE, compression_ratio

english = "the cat sat on the mat and the dog ran to the park " * 40
code = "def add(a, b):\n    return a + b\n" * 40

for name, tok in (("trained on English", t_en), ("trained on code", t_code)):
    print(f"{name:<19}-> English {compression_ratio(tok, english):5.2f} bytes/token | code {compression_ratio(tok, code):5.2f}")
```

```text
trained on English -> English  3.91 bytes/token | code  1.03
trained on code    -> English  1.02 bytes/token | code  4.56
```

### 9. Enterprise use case

A bank training a domain LLM builds a tokenizer on its mix of English documents, tabular text, account numbers and code; it audits how IBANs and amounts tokenize before committing.

### 10. AI engineering connection

Pre-training, continued pre-training and fine-tuning all depend on the tokenizer; vocabulary extension for new domains requires embedding resizing and training ([6.6 Vocabulary](06.06-vocabulary.md)).

### 11. Advantages

Right-sized vocabulary for your data lowers cost and improves quality.

### 12. Limitations

Frozen afterwards; sensitive to corpus mix; hard to evaluate before training the model.

### 13. Trade-offs

Domain-specific tokenizer (efficient) versus reusing a public tokenizer (compatibility with existing weights and tooling).

### 14. Common mistakes

- Training on unrepresentative data.
- Not reserving special tokens.
- Not testing round-trip on edge-case Unicode.
- Not versioning the tokenizer.
- Evaluating only on English.

### 15. Performance / cost

Training time grows with corpus and vocab size; efficiency gains compound across every token ever processed.

### 16. Security

Training corpora can leak secrets into vocabulary entries (long unique strings become tokens); deduplicate and filter secrets/PII before training; glitch tokens come from corpus artifacts.

</details>

### 20. Hands-on exercise

Run the snippet; then add a third corpus (a non-English text) and build the 3x3 compression matrix.

<details>
<summary>Show a solution</summary>

```python
import sys
sys.path.insert(0, "lab")
from mini_bpe import ByteBPE, compression_ratio

mixed = ("the cat sat on the mat " * 30) + ("def f(x):\n    return x\n" * 30)
english_only = "the cat sat on the mat " * 60
code_only = "def f(x):\n    return x\n" * 60
english_probe = "the cat sat on the mat " * 5
code_probe = "def f(x):\n    return x\n" * 5
for name, corpus in (("mixed corpus", mixed), ("English only", english_only)):
    tok = ByteBPE.train(corpus, 30)
    print(f"{name:<13}: English {compression_ratio(tok, english_probe):5.2f}   code {compression_ratio(tok, code_probe):5.2f} bytes/token")
```

```text
mixed corpus : English  3.71   code  5.48 bytes/token
English only : English  3.71   code  1.00 bytes/token
```

Mixing domains in the training corpus gives decent compression on both; training on one domain leaves the other poorly served.
