# 6.8 UNK

**Metadata** — Tier: 6 · Phase: 2 · Priority: Medium · Difficulty: Beginner · Interview: Medium · Hands-on: Low
Prerequisites: [6.3 Word tokenization](06.03-word-tokenization.md), [6.6 Vocabulary](06.06-vocabulary.md) · Leads to: [6.29 Byte fallback](06.29-byte-fallback.md), [6.4 Byte tokenization](06.04-byte-tokenization.md)

> **In plain words**
> `<UNK>` ("unknown") is the special token that stands for **anything the vocabulary cannot represent**. Using it throws away what the input was. Word-level and some WordPiece tokenizers need it; byte-level BPE and byte fallback make it unnecessary, which is a main reason modern tokenizers use bytes.

**You need first:** [6.3 Word tokenization](06.03-word-tokenization.md), [6.6 Vocabulary](06.06-vocabulary.md).

### 1. What is it?

`<UNK>` is the special token that stands for any input the vocabulary cannot represent.

### 2. Why does it exist?

Closed-vocabulary tokenizers (word-level, BERT's WordPiece in some cases) need a catch-all so that unseen text still maps to *some* ID.

### 3. Detailed explanation

In word-level and some WordPiece setups, an unmatched piece (or even the whole word, in BERT's WordPiece implementation) becomes `[UNK]`, which discards all information about what the input was. Byte-level BPE ([6.4 Byte tokenization](06.04-byte-tokenization.md)) and byte fallback ([6.29 Byte fallback](06.29-byte-fallback.md)) make `<UNK>` unnecessary or very rare, which is a major reason they dominate.

Metric: *UNK rate* (fraction of tokens that are UNK) on a representative sample is a quick tokenizer-quality check.

### 4. How does it work?

During encoding, if no vocabulary entry matches, emit the UNK ID. During decoding UNK cannot be inverted (information lost).

### 5. Simple example

A stamp reading 'unreadable' on every smudged word in a document: you know something was there, not what.

**By hand.** WordPiece vocabulary `{un, ##happi, ##ness}`. "unhappiness" → `un | ##happi | ##ness` (all known). "unzzz" → after `un`, no piece matches `zzz`, so (in BERT's implementation) the *whole word* becomes `[UNK]`. The model cannot distinguish "unzzz" from "unqqq" or from any other unknown word.

### 6. Technical example

BERT-style `wordpiece_encode` (see [`lab/tokenizer_extras.py`](lab/tokenizer_extras.py)) returns `['[UNK]']` for a word it cannot cover.

### 7. Code

**① By hand (plain Python).** Count how often UNK appears for a word vocabulary.

```python
vocab = {"the", "cat", "sat", "on", "mat"}
sentence = "the cat sat on the sofa near the window".split()
tokens = [w if w in vocab else "<UNK>" for w in sentence]
print(tokens)
print("UNK rate:", round(tokens.count("<UNK>") / len(tokens), 2))
```

```text
['the', 'cat', 'sat', 'on', 'the', '<UNK>', '<UNK>', 'the', '<UNK>']
UNK rate: 0.33
```

**② With NumPy.** UNK rate falls as the vocabulary grows, but never reaches zero for words.

```python
import numpy as np

rng = np.random.default_rng(0)
ranks = np.arange(1, 100_001)
p = 1 / ranks; p /= p.sum()
text = rng.choice(ranks, size=100_000, p=p)                    # Zipf-like word stream
for V in (1_000, 10_000, 50_000, 100_000):
    print(f"vocabulary of the {V:>7,} most frequent words: UNK rate {np.mean(text > V):.3f}")
```

```text
vocabulary of the   1,000 most frequent words: UNK rate 0.380
vocabulary of the  10,000 most frequent words: UNK rate 0.188
vocabulary of the  50,000 most frequent words: UNK rate 0.058
vocabulary of the 100,000 most frequent words: UNK rate 0.000
```

### 9. Enterprise use case

Teams monitor UNK rate by language/domain to detect vocabulary drift (e.g. new product names) before accuracy drops.

### 10. AI engineering connection

A reason retrieval encoders and classifiers with closed vocabularies degrade on new entities, and why generative LLMs use byte-capable tokenizers.

### 11. Advantages

Simple catch-all; keeps IDs valid for any input.

### 12. Limitations

Lossy and non-invertible; one UNK id for everything; hides important rare entities.

### 13. Trade-offs

Smaller vocabulary and simpler tokenizer versus information loss.

### 14. Common mistakes

- Ignoring UNK rate.
- Assuming every tokenizer has UNK (byte-level ones often do not emit it).
- Training a model to *predict* UNK as if it were a word.

### 15. Performance / cost

No runtime cost; the cost is accuracy loss on affected inputs.

### 16. Security

Attackers can pad inputs with rare characters that become UNK to blur content from classifiers; prefer byte-capable tokenizers for safety filters.

</details>

### 17. Interview explanation

*"UNK is the placeholder for out-of-vocabulary input. It loses information, which is why modern tokenizers use a byte base or byte fallback so that nothing is ever unknown."*

### 18. Rapid-fire answer

Catch-all for unseen input; lossy; mostly obsolete with byte-level tokenizers.

### 20. Hands-on exercise

Compute the UNK rate of the word tokenizer from 6.3 on a held-out sentence set.

<details>
<summary>Show a solution</summary>

```python
vocab = {"i", "love", "the", "cat"}
for sentence in ("i love the cat", "i love the kitten", "j adore the cat"):
    words = sentence.split()
    unk = sum(w not in vocab for w in words)
    print(f"{sentence!r:<22} UNK rate {unk / len(words):.2f}")
```

```text
'i love the cat'       UNK rate 0.00
'i love the kitten'    UNK rate 0.25
'j adore the cat'      UNK rate 0.50
```
