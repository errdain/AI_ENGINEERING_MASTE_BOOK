# 6.2 Character tokenization

**Metadata** — Tier: 6 · Phase: 2 · Priority: Medium · Difficulty: Beginner · Interview: Medium · Hands-on: Medium
Prerequisites: [6.1 Text preprocessing](06.01-text-preprocessing.md) · Leads to: [6.3 Word tokenization](06.03-word-tokenization.md), [6.4 Byte tokenization](06.04-byte-tokenization.md), [6.5 Subword tokenization](06.05-subword-tokenization.md)

> **In plain words**
> **Character tokenization** gives every character its own token. "unhappiness" becomes `u n h a p p i n e s s`: 11 tokens. The vocabulary is tiny and nothing is ever unknown, but sequences are long and the model has to learn spelling and meaning from scratch.

**You need first:** [6.1 Text preprocessing](06.01-text-preprocessing.md).

### 1. What is it?

Character tokenization treats every Unicode character (code point) as one token.

### 2. Why does it exist?

It is the simplest answer to "how do I turn text into IDs without ever meeting an unknown word?" and the baseline against which word and subword schemes are judged.

### 3. Detailed explanation

The vocabulary is the set of characters seen in training: tens for English letters, a few thousand for common CJK, and up to ~150k code points if you cover all of Unicode (`REVIEW_REQUIRED` exact count by Unicode version). Out-of-vocabulary words disappear because every word is spelled with known characters.

The costs are on the sequence side: roughly one token per character, so a 1,000-word document becomes ~5,000-6,000 tokens. Since attention cost grows with sequence length squared ([Tier 7](../tier-07-attention/README.md)), long sequences are expensive, and the model must *learn spelling to meaning* from scratch for every word.

### 4. How does it work?

Split the string into code points; map each to its index in a fixed table; decode by joining characters.

### 5. Simple example

Spelling a word letter by letter over the phone: always possible, but slow.

**By hand.** A 1,000-word English document has about 6,000 characters (including spaces). Character tokens: ~6,000. Attention compares every token with every other, so cost grows with the square: `6,000² = 36 million` pairs, versus about `1,300² = 1.7 million` for a typical sub-word tokenizer that makes ~1,300 tokens out of the same text, roughly 20× less work.

### 6. Technical example

Character-level models appear in research on spelling/morphology and in some OCR or speech-adjacent pipelines; mainstream LLMs use subwords ([6.5 Subword tokenization](06.05-subword-tokenization.md)) or bytes ([6.4 Byte tokenization](06.04-byte-tokenization.md)) instead.

### 7. Code

**① By hand (plain Python).** Build the vocabulary from the text and encode/decode by hand.

```python
text = "unhappiness"
vocab = {ch: i for i, ch in enumerate(sorted(set(text)))}
ids = [vocab[c] for c in text]
inverse = {i: c for c, i in vocab.items()}
print("vocabulary:", vocab)
print("ids:", ids)
print("decoded:", "".join(inverse[i] for i in ids), "   tokens:", len(ids), "for", len(text), "characters")
```

```text
vocabulary: {'a': 0, 'e': 1, 'h': 2, 'i': 3, 'n': 4, 'p': 5, 's': 6, 'u': 7}
ids: [7, 4, 2, 0, 5, 5, 3, 4, 1, 6, 6]
decoded: unhappiness    tokens: 11 for 11 characters
```

**② With NumPy.** The cost side: attention work grows with the square of the sequence length.

```python
import numpy as np

doc_chars = 6000
for name, n_tokens in (("characters", doc_chars), ("sub-words (~4.6 chars per token)", int(doc_chars / 4.6)), ("words (~1 per 6 chars)", doc_chars // 6)):
    print(f"{name:<34}{n_tokens:>6,} tokens   attention pairs {n_tokens ** 2:>12,}")
print("ratio of attention work, characters vs sub-words:", round((doc_chars / (doc_chars / 4.6)) ** 2, 1), "x")
```

```text
characters                         6,000 tokens   attention pairs   36,000,000
sub-words (~4.6 chars per token)   1,304 tokens   attention pairs    1,700,416
words (~1 per 6 chars)             1,000 tokens   attention pairs    1,000,000
ratio of attention work, characters vs sub-words: 21.2 x
```

**③ With PyTorch.** A character model's first layer is a tiny embedding table: one row per character.

```python
import torch

text = "unhappiness"
chars = sorted(set(text))
ids = torch.tensor([chars.index(c) for c in text])
torch.manual_seed(0)
table = torch.nn.Embedding(len(chars), 4)
print("embedding table parameters:", table.weight.numel(), "  (vocabulary", len(chars), "x 4 dimensions)")
print("vectors for the whole word:", tuple(table(ids).shape), "  -> one vector per character")
print("a 50,000-word vocabulary with 4 dimensions would need", 50_000 * 4, "parameters just for the table")
```

```text
embedding table parameters: 32   (vocabulary 8 x 4 dimensions)
vectors for the whole word: (11, 4)   -> one vector per character
a 50,000-word vocabulary with 4 dimensions would need 200000 parameters just for the table
```

### 9. Enterprise use case

Rarely used alone in production LLM serving; sometimes used as a fallback layer or for tasks where spelling matters (typo-robust search, name matching).

### 10. AI engineering connection

Shows the vocabulary-vs-length trade-off in its purest form, which motivates subwords ([6.5 Subword tokenization](06.05-subword-tokenization.md)) and the vocabulary-size analysis in [6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md).

### 11. Advantages

Tiny vocabulary; no OOV words; trivial to implement; robust to typos.

### 12. Limitations

Very long sequences; high attention and latency cost; weak use of context window; unseen *characters* (new emoji, rare scripts) still need a fallback ([6.29 Byte fallback](06.29-byte-fallback.md)).

### 13. Trade-offs

Small embedding table and no OOV versus long sequences and harder learning of word-level meaning.

### 14. Common mistakes

- Assuming `len(str)` equals the number of tokens of *any other* tokenizer.
- Forgetting that one visible glyph can be several code points ([6.30 Unicode normalization](06.30-unicode-normalization.md)).

### 15. Performance / cost

Tokens per input ~ characters; context-window and per-token billing costs are highest of all schemes. See [6.31 Tokenization efficiency](06.31-tokenization-efficiency.md).

### 16. Security

A tiny closed alphabet is easy to audit, but homoglyphs (visually identical code points) are distinct tokens and can evade filters; normalize first ([6.30 Unicode normalization](06.30-unicode-normalization.md)).

</details>

### 17. Interview explanation

*"Character tokenization gives a tiny vocabulary and no unknown words, but sequences are as long as the text, which makes attention expensive and forces the model to learn words from letters. That is why we moved to subwords."*

### 18. Rapid-fire answer

One token per character: no OOV, but long sequences.
