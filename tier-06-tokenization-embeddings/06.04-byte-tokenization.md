# 6.4 Byte tokenization

**Metadata** — Tier: 6 · Phase: 2 · Priority: High · Difficulty: Intermediate · Interview: High · Hands-on: Medium
Prerequisites: [6.1 Text preprocessing](06.01-text-preprocessing.md); UTF-8 basics · Leads to: [6.12 BPE](06.12-bpe.md), [6.29 Byte fallback](06.29-byte-fallback.md), [6.30 Unicode normalization](06.30-unicode-normalization.md)

> **In plain words**
> **Byte tokenization** works on the 256 possible values of a byte in UTF-8 instead of on characters. Any text in any language (English, Hindi, emoji) is just a list of bytes, so the base vocabulary is exactly 256 and nothing is ever unknown. The price: non-English characters take 2, 3 or 4 bytes each, so those languages produce longer sequences.

**You need first:** [6.1 Text preprocessing](06.01-text-preprocessing.md); UTF-8 basics.

### 1. What is it?

Byte tokenization operates on the 256 possible UTF-8 byte values, so every string, in any script, is representable with a vocabulary of exactly 256 base symbols.

### 2. Why does it exist?

It eliminates the unknown-token problem by construction and removes the need for language-specific character tables. Byte-level BPE (GPT-2 and many successors) starts from this base and learns merges on top ([6.12 BPE](06.12-bpe.md)).

### 3. Detailed explanation

UTF-8 encodes ASCII in 1 byte, most Latin accented letters in 2, most Indic and CJK characters in 3, and emoji in 4. So a byte-level tokenizer needs 1x, 2x, 3x or 4x as many base symbols for the same visible character.

Pure bytes make sequences long (see Figure 8: the right panel shows how a BPE trained only on English fragments Hindi and Japanese far more than English). Merges learned on representative data shorten common sequences; unrepresented scripts stay close to raw bytes. That asymmetry is a **fairness and cost** issue ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)).

Byte-level BPE vs byte fallback ([6.29 Byte fallback](06.29-byte-fallback.md)): in byte-level BPE the *base* alphabet is bytes; in byte fallback a normal subword vocabulary is kept and bytes are used only for characters not in it.

### 4. How does it work?

`text.encode('utf-8')` yields bytes; each byte is a token ID (plus an offset for special tokens in the lab); decoding concatenates bytes and decodes UTF-8.

### 5. Simple example

Writing every message in Morse code: any message is possible with two symbols, but some languages take far longer to send.

**By hand.** `é` is the code point 233, which UTF-8 stores as two bytes `195 169`. `日` takes three bytes (`230 151 165`), `🙂` four (`240 159 153 130`). So the string "é日🙂" has 3 characters but 2 + 3 + 4 = 9 bytes, and a pure byte tokenizer makes 9 tokens from it.

### 6. Technical example

GPT-2-style byte-level BPE maps each byte to a printable Unicode stand-in character purely for storage convenience; the lab skips that detail and uses raw bytes with ID = byte + 4 (4 reserved specials).

### 7. Code

**① By hand (plain Python).** Encode a string to bytes with Python and look at the lengths.

```python
for ch in ("a", "é", "日", "🙂"):
    b = ch.encode("utf-8")
    print(f"{ch!r:>6}: code point {ord(ch):>6}   UTF-8 bytes {list(b)}  ({len(b)} byte{'s' if len(b) > 1 else ''})")
s = "é日🙂"
print("characters:", len(s), "  bytes (tokens for a pure byte tokenizer):", len(s.encode()))
```

```text
   'a': code point     97   UTF-8 bytes [97]  (1 byte)
   'é': code point    233   UTF-8 bytes [195, 169]  (2 bytes)
   '日': code point  26085   UTF-8 bytes [230, 151, 165]  (3 bytes)
   '🙂': code point 128578   UTF-8 bytes [240, 159, 153, 130]  (4 bytes)
characters: 3   bytes (tokens for a pure byte tokenizer): 9
```

**② With NumPy.** Bytes as an array of ids; tokens per character for different scripts.

```python
import numpy as np

samples = {"English": "tokenization", "French": "déjà vu à Noël", "Hindi": "नमस्ते दुनिया", "Japanese": "こんにちは世界"}
for name, s in samples.items():
    ids = np.frombuffer(s.encode(), dtype=np.uint8)
    print(f"{name:<9}: {len(s):>2} characters -> {ids.size:>2} byte tokens   ({ids.size / len(s):.1f} tokens per character)")
```

```text
English  : 12 characters -> 12 byte tokens   (1.0 tokens per character)
French   : 14 characters -> 18 byte tokens   (1.3 tokens per character)
Hindi    : 13 characters -> 37 byte tokens   (2.8 tokens per character)
Japanese :  7 characters -> 21 byte tokens   (3.0 tokens per character)
```

**③ With the tier library.** The tier's tokenizer with zero merges is a pure byte tokenizer, and it round-trips anything.

```python
import sys

ids = tok.encode(text)
print(len(text), "characters ->", len(ids), "tokens")
print("lossless round trip:", tok.decode(ids) == text)
print("vocabulary size:", tok.vocab_size, "(4 special tokens + 256 bytes)")
```

```text
11 characters -> 21 tokens
lossless round trip: True
vocabulary size: 260 (4 special tokens + 256 bytes)
```

### 9. Enterprise use case

Byte-level tokenization is the reason a production system can accept arbitrary user input (names, emoji, mixed scripts) without an unknown-token failure path.

### 10. AI engineering connection

Foundation of byte-level BPE ([6.12 BPE](06.12-bpe.md)); its non-English cost asymmetry feeds multilingual pricing and context-budget decisions ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)).

### 11. Advantages

No UNK ever; 256-entry base vocabulary; language-agnostic; exact round-trip.

### 12. Limitations

Long sequences for non-Latin scripts (2-4x); individual bytes carry little meaning; malformed byte sequences produced by a model can fail UTF-8 decoding (the lab replaces them).

### 13. Trade-offs

Universal coverage and tiny base vocabulary versus longer sequences; merges recover compression only where training data was.

### 14. Common mistakes

- Assuming 1 character = 1 byte.
- Slicing token sequences in the middle of a multi-byte character and decoding the half (invalid UTF-8).
- Quoting English compression ratios for other scripts.

### 15. Performance / cost

Tokens per character for Hindi/Japanese can be several times English with an English-trained vocabulary (toy figure measured; real ratios `REVIEW_REQUIRED` per tokenizer).

### 16. Security

Any byte sequence is valid input, including invalid UTF-8 and overlong encodings; decode defensively and cap input by *tokens*.

### 17. Interview explanation

*"Byte tokenization uses the 256 UTF-8 byte values as the base alphabet, so nothing is ever unknown. The cost is that non-Latin text needs 2-4 bytes per character unless merges have been learned for it, so sequences get longer and more expensive for those users."*

### 18. Rapid-fire answer

Base alphabet of 256 bytes: no UNK, but non-Latin text costs 2-4x tokens before merges.
