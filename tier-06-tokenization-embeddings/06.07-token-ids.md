# 6.7 Token IDs

**Metadata** — Tier: 6 · Phase: 2 · Priority: High · Difficulty: Beginner · Interview: High · Hands-on: Medium
Prerequisites: [6.6 Vocabulary](06.06-vocabulary.md) · Leads to: [6.17 Token embedding](06.17-token-embedding.md), [6.18 Embedding matrix](06.18-embedding-matrix.md)

> **In plain words**
> **Token ids** are the integers a tokenizer produces: each one is simply the *position* of a token in the vocabulary. They carry **no meaning of their own** (id 500 is not "near" id 501); the model uses an id only to pick a row of the embedding table. Feeding ids into a network as if they were numbers is a classic beginner bug.

**You need first:** [6.6 Vocabulary](06.06-vocabulary.md).

**Words you'll meet on this page**

| Word | What it means here |
|---|---|

### 1. What is it?

Token IDs are the integers a tokenizer outputs: each is simply the index of a token in the vocabulary, used to select a row of the embedding matrix.

### 2. Why does it exist?

Neural networks consume numbers, not strings; an integer index is the cheapest unambiguous way to refer to a vocabulary entry.

### 3. Detailed explanation

IDs carry **no semantic or ordinal meaning**: ID 500 is not 'close to' ID 501. The first layer treats an ID as a categorical value and looks up a learnable vector ([6.17 Token embedding](06.17-token-embedding.md)). A common beginner error is feeding IDs into a model as if they were numeric features.

IDs are *model-specific*. The same text produces different IDs under different tokenizers, and an ID is meaningful only together with the matching checkpoint.

### 4. How does it work?

`encode(text) -> list[int]`; `decode(list[int]) -> text`. Special-token IDs are conventionally low (the lab reserves 0-3: PAD, BOS, EOS, UNK; real models vary).

### 5. Simple example

Seat numbers in a theatre: seat 12 is not 'more' than seat 11 in any meaningful way; it is just a location.

**By hand.** Vocabulary `[the, cat, sat]` → ids 0, 1, 2. Embedding table (3 × 2) `[[0.1, 0.4], [0.9, 0.2], [0.5, 0.5]]`. The sentence "the sat" is ids `[0, 2]`, and the network receives rows 0 and 2: `[[0.1, 0.4], [0.5, 0.5]]`. The numbers 0 and 2 themselves never reach the network.

### 6. Technical example

Embedding lookup `E[ids]` turns an int tensor of shape `(batch, seq)` into floats of shape `(batch, seq, d)`.

### 7. Code

**① By hand (plain Python).** Ids as addresses: the lookup is just indexing.

```python
table = [[0.1, 0.4], [0.9, 0.2], [0.5, 0.5]]       # rows for: the, cat, sat
ids = [0, 2]
print("rows the network sees:", [table[i] for i in ids])
print("id arithmetic is meaningless: id 1 + id 1 =", 1 + 1, "-> that is the token", ["the", "cat", "sat"][2], "(sat), not 'two cats'")
```

```text
rows the network sees: [[0.1, 0.4], [0.5, 0.5]]
id arithmetic is meaningless: id 1 + id 1 = 2 -> that is the token sat (sat), not 'two cats'
```

**② With NumPy.** Why ids must not be used as numeric features: compare an id feature with embedding rows.

```python
import numpy as np

rng = np.random.default_rng(0)
E = rng.normal(size=(5, 3))
ids = np.array([0, 2, 4])
print("ids as numbers:", ids, " -> pretends token 2 is 'between' tokens 0 and 4")
print("embedding rows:\n", E[ids].round(2))
print("distance between rows 0 and 4:", round(float(np.linalg.norm(E[0] - E[4])), 2), "  between rows 0 and 1:", round(float(np.linalg.norm(E[0] - E[1])), 2), "(learned, not ordered)")
```

```text
ids as numbers: [0 2 4]  -> pretends token 2 is 'between' tokens 0 and 4
embedding rows:
 [[ 0.13 -0.13  0.64]
 [ 1.3   0.95 -0.7 ]
 [-2.33 -0.22 -1.25]]
distance between rows 0 and 4: 3.09   between rows 0 and 1: 0.49 (learned, not ordered)
```

### 9. Enterprise use case

Logging IDs (not just text) is essential for debugging prompt-length and truncation problems; some teams store tokenizer version with every logged request.

### 10. AI engineering connection

Everything downstream (embedding lookup, loss on next-token IDs, logprobs, logit bias) is in ID space.

### 11. Advantages

Compact; fast to batch; exact.

### 12. Limitations

Not human-readable; meaningless outside the model/tokenizer pair; carry no similarity structure.

### 13. Trade-offs

Dense integer IDs are efficient but require a lookup table to be interpretable.

### 14. Common mistakes

- Treating IDs as numeric features.
- Assuming IDs are stable across tokenizer versions.
- Off-by-one errors from special-token offsets.

### 15. Performance / cost

int32/int64 tensors; negligible versus activation memory, but batching dominates through padding ([6.9 PAD](06.09-pad.md)).

### 16. Security

Logit-bias and token-ban features operate on IDs: ban lists must be built with the target tokenizer, and variants (`' word'` vs `'word'`) are different IDs.
