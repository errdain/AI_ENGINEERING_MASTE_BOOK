### 1. WHAT IS IT?

Token IDs are the integers a tokenizer outputs: each is simply the index of a token in the vocabulary, used to select a row of the embedding matrix.

### 2. WHY DOES IT EXIST?

Neural networks consume numbers, not strings; an integer index is the cheapest unambiguous way to refer to a vocabulary entry.

### 3. DETAILED EXPLANATION

IDs carry **no semantic or ordinal meaning**: ID 500 is not 'close to' ID 501. The first layer treats an ID as a categorical value and looks up a learnable vector ([6.17 Token embedding](06.17-token-embedding.md)). A common beginner error is feeding IDs into a model as if they were numeric features.

IDs are *model-specific*. The same text produces different IDs under different tokenizers, and an ID is meaningful only together with the matching checkpoint.

### 4. HOW DOES IT WORK?

`encode(text) -> list[int]`; `decode(list[int]) -> text`. Special-token IDs are conventionally low (the lab reserves 0-3: PAD, BOS, EOS, UNK; real models vary).

### 5. SIMPLE EXAMPLE

Seat numbers in a theatre: seat 12 is not 'more' than seat 11 in any meaningful way; it is just a location.

### 6. TECHNICAL EXAMPLE

Embedding lookup `E[ids]` turns an int tensor of shape `(batch, seq)` into floats of shape `(batch, seq, d)`.

### 7. CODE

```python
# run inside lab/
import numpy as np
from mini_bpe import ByteBPE
from positional import embedding_lookup
tok = ByteBPE.train("low lower lowest " * 20, 8)
ids = tok.encode("low lowest")
E = np.random.default_rng(0).normal(size=(tok.vocab_size, 4))
print(ids, embedding_lookup(E, ids).shape)    # (n_tokens, 4)
```

### 8. INPUT → PROCESS → OUTPUT

```
"low" ──tokenizer──► [264] ──E[264]──► vector in R^d
```

### 9. ENTERPRISE USE CASE

Logging IDs (not just text) is essential for debugging prompt-length and truncation problems; some teams store tokenizer version with every logged request.

### 10. AI ENGINEERING CONNECTION

Everything downstream (embedding lookup, loss on next-token IDs, logprobs, logit bias) is in ID space.

### 11. ADVANTAGES

Compact; fast to batch; exact.

### 12. LIMITATIONS

Not human-readable; meaningless outside the model/tokenizer pair; carry no similarity structure.

### 13. TRADE-OFFS

Dense integer IDs are efficient but require a lookup table to be interpretable.

### 14. COMMON MISTAKES

- Treating IDs as numeric features.
- Assuming IDs are stable across tokenizer versions.
- Off-by-one errors from special-token offsets.

### 15. PERFORMANCE / COST CONSIDERATIONS

int32/int64 tensors; negligible versus activation memory, but batching dominates through padding ([6.9 PAD](06.09-pad.md)).

### 16. SECURITY CONSIDERATIONS

Logit-bias and token-ban features operate on IDs: ban lists must be built with the target tokenizer, and variants (`' word'` vs `'word'`) are different IDs.

### 17. INTERVIEW EXPLANATION

*"A token ID is just the index into the vocabulary and therefore into the embedding matrix. It has no numeric meaning, and it is only valid with its own tokenizer and checkpoint."*

### 18. RAPID-FIRE ANSWER

Index of a token in the vocabulary; selects an embedding row.
