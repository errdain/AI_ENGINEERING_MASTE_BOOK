# 6.19 Embedding dimensions

**Metadata** — Tier: 6 · Phase: 2 · Priority: High · Difficulty: Beginner · Interview: High · Hands-on: Medium
Prerequisites: [6.18 Embedding matrix](06.18-embedding-matrix.md) · Leads to: [6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md), [Tier 8](../tier-08-transformer-architecture/README.md)

> **In plain words**
> The **embedding dimension** `d` (also called the model width, `d_model`) is the length of each token's vector and the width of the "highway" that every layer reads from and writes to. A bigger `d` lets the model hold more information per token but costs more everywhere: the embedding table grows like `V·d`, each layer's weights roughly like `d²`.

**You need first:** [6.18 Embedding matrix](06.18-embedding-matrix.md).

### 1. What is it?

The embedding dimension `d` (the model width, `d_model`) is the length of each token vector and the width of the residual stream that every layer reads and writes.

### 2. Why does it exist?

It sets the representational capacity per token and drives parameters and memory throughout the network.

### 3. Detailed explanation

`d` affects: embedding table `V*d`; per-layer weights (roughly proportional to `d^2`); activation memory; KV-cache size per token (Tier 11). Typical values: hundreds (small encoders; BERT-base uses 768), thousands (7B-class models commonly 4096), >10k for the largest (`REVIEW_REQUIRED` per model).

Bigger `d` is not free: more compute, more memory, and returns diminish without more data and layers (scaling laws, Tier 9).

### 4. How does it work?

Choose `d` (and heads: `d_model = n_heads * d_head`) at architecture time; it cannot change after pre-training without retraining.

### 5. Simple example

The number of fields on each token's index card: more fields can describe more, but cost more to store and read.

**By hand.** Doubling the width from 4,096 to 8,192 multiplies each layer's matrix sizes by `(8192/4096)² = 4`, the embedding table by 2, and the per-token KV-cache by 2. A 7B-class model has d ≈ 4,096; the table alone with `V = 32,000` has `131 million` parameters.

### 6. Technical example

Doubling `d` roughly quadruples per-layer parameters but only doubles the embedding table.

### 7. Code

**① By hand (plain Python).** Scaling arithmetic in plain Python.

```python
V, d = 32_000, 4096
print(f"embedding table: {V * d / 1e6:.0f}M parameters, {V * d * 2 / 1e9:.2f} GB in fp16")
for new_d in (2048, 4096, 8192):
    print(f"d = {new_d:>5}: per-layer weights scale by {(new_d / d) ** 2:5.2f}x, embedding table by {new_d / d:4.2f}x")
```

```text
embedding table: 131M parameters, 0.26 GB in fp16
d =  2048: per-layer weights scale by  0.25x, embedding table by 0.50x
d =  4096: per-layer weights scale by  1.00x, embedding table by 1.00x
d =  8192: per-layer weights scale by  4.00x, embedding table by 2.00x
```

**② With NumPy.** Parameters of a Transformer block as a function of d (attention 4d² + MLP 8d²).

```python
for d in (256, 768, 1024, 4096, 8192):
    block = 4 * d * d + 8 * d * d                             # attention projections + 4x-wide MLP
    print(f"d = {d:>5}: ~{block / 1e6:8.1f} million parameters per block")
```

```text
d =   256: ~     0.8 million parameters per block
d =   768: ~     7.1 million parameters per block
d =  1024: ~    12.6 million parameters per block
d =  4096: ~   201.3 million parameters per block
d =  8192: ~   805.3 million parameters per block
```

**③ With PyTorch.** Counting real parameters of a toy block at two widths.

```python
import torch

def block(d):
    return torch.nn.Sequential(torch.nn.Linear(d, 4 * d), torch.nn.GELU(), torch.nn.Linear(4 * d, d))

a, b = (sum(p.numel() for p in block(d).parameters()) for d in (128, 256))
print("MLP parameters at d = 128:", a, "  at d = 256:", b, "  ratio:", round(b / a, 2), "(~4x)")
```

```text
MLP parameters at d = 128: 131712   at d = 256: 525568   ratio: 3.99 (~4x)
```

### 9. Enterprise use case

Model-size selection (small d for edge, large d for quality) is a cost/latency decision.

### 10. AI engineering connection

Determines compatibility: embeddings from models of different d cannot be mixed without projection.

### 11. Advantages

Controls capacity.

### 12. Limitations

Memory and compute cost; needs matching data/depth.

### 13. Trade-offs

Capacity versus cost and latency.

### 14. Common mistakes

- Assuming a bigger d always means better quality.
- Mixing embeddings of different dimensions.
- Odd head dimension with RoPE ([6.24 RoPE](06.24-rope.md)).

### 15. Performance / cost

Memory ∝ d for activations and KV cache; compute ∝ d^2 per layer.

### 16. Security

No special security issue; larger embedding dims in vector stores increase storage and may influence membership-inference surface (`REVIEW_REQUIRED`).
