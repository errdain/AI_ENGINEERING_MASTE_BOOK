> **In plain words**
> **Byte-pair encoding (BPE)** builds a vocabulary by **repeatedly gluing together the two symbols that appear side by side most often**. Start from single bytes or characters; merge the commonest pair into a new symbol; repeat until the vocabulary is the size you want.
> Frequent words end up as one token, rare words as a few pieces, and (with a byte base) nothing is ever "unknown". It is the tokenizer behind most GPT-style models.

**You need first:** [6.4 Byte tokenization](06.04-byte-tokenization.md), [6.5 Subword tokenization](06.05-subword-tokenization.md), [6.6 Vocabulary](06.06-vocabulary.md).

### 1. What is it?

Byte-Pair Encoding (BPE) builds a subword vocabulary bottom-up: start from base symbols (bytes or characters) and repeatedly merge the most frequent adjacent pair into a new symbol until the vocabulary reaches a target size.

### 2. Why does it exist?

Frequency-driven merging yields frequent words as single tokens and rare words as pieces, with a bounded vocabulary and (with a byte base) no unknown tokens. BPE originated as a data-compression algorithm and was adapted for NMT subwords, then popularized for GPT-style models as byte-level BPE (`REVIEW_REQUIRED` for exact citation years).

### 3. Detailed explanation

**Training** (greedy, frequency-based):

1. Pre-tokenize the corpus ([6.1 Text preprocessing](06.01-text-preprocessing.md)) and count word frequencies. Each word is a sequence of base symbols.
2. Count every adjacent pair across the corpus, weighted by word frequency.
3. Merge the most frequent pair into a new symbol; record it as merge number *k*.
4. Repeat until the vocabulary hits the target size (or no pair occurs twice).

**Encoding** applies the learned merges **in the order learned**: an earlier merge has higher priority. Applying them in a different order would give different tokens than the model was trained with. **Decoding** concatenates the bytes of each token and decodes UTF-8, so it is lossless.

The result is a table of merges, and the vocabulary is `base symbols + one entry per merge + specials`. In the lab: `vocab_size = 4 + 256 + num_merges`.

**Worked example** (lab output for `"low low low low low lower lower newest newest newest"` with 6 merges): `l+o`, `lo+w`, `' '+low`, `' '+n`, `e+s`, `e+w`. Encoding `"lowest newest"` then yields `low | es | t | ' n' | ew | es | t`: the familiar stem `low` is whole, the suffix is assembled from the pieces that were frequent in training.

**Byte-level BPE** uses the 256 bytes as base ([6.4 Byte tokenization](06.04-byte-tokenization.md)); GPT-2 additionally remaps bytes to printable stand-in characters and uses a regex pre-tokenizer (`REVIEW_REQUIRED` for details).

**Variants.** *BPE-dropout* randomly skips merges during training of the *model* to regularize; *SentencePiece-BPE* ([6.14 SentencePiece](06.14-sentencepiece.md)) learns BPE directly on raw text with `▁` for whitespace.

### 4. How does it work?

Try different texts and merge counts in [explore: `bpe_trainer.html`](interactive/bpe_trainer.html).

```
corpus counts ─► count adjacent pairs ─► pick max (ties: deterministic) ─► merge everywhere ─► repeat
```

### 5. Simple example

Imagine shorthand: if the pair 'th' appears constantly you invent one symbol for it; then if that symbol plus 'e' appears constantly, you invent one for 'the'. You keep inventing shorthand for whatever you write most.

**By hand.** Take the words `low` (×5), `lower` (×2), `newest` (×3) as bytes. The pair `l o` occurs 5 + 2 = 7 times, `o w` 7 times, `w e` 2 + 3 = 5 times, `e s` 3 times. Merge the first most frequent pair (ties are broken deterministically) → a new symbol `lo`; recount; the next most frequent pair is now `lo w` (7 times) → `low`. After two merges `low` is a single token and `lower` is `low` + `e` + `r`: the frequent word became one piece, the rarer word stayed in pieces.

### 6. Technical example

On the lab's small repetitive corpus, 80 merges already reach about 4.6 bytes per token on training-like text (run the snippet in 6.28), while an English-trained vocabulary applied to Hindi stays near one token per byte (see Figure 8). Production tokenizers use tens to hundreds of thousands of merges.

### 7. Code

**① By hand (plain Python).** Count pairs, merge the best one, repeat.

```python
from collections import Counter

words = Counter(["low"] * 5 + ["lower"] * 2 + ["newest"] * 3)
seqs = {w: list(w) for w in words}                        # each word as a list of characters
for step in range(1, 5):
    pairs = Counter()
    for w, s in seqs.items():
        for a, b in zip(s, s[1:]):
            pairs[a, b] += words[w]                       # weight each pair by how often its word occurs
    best = max(pairs.items(), key=lambda kv: (kv[1], kv[0]))[0]   # most frequent; ties broken alphabetically (a rule, not magic)
    for w, s in seqs.items():
        i, merged = 0, []
        while i < len(s):
            if i + 1 < len(s) and (s[i], s[i + 1]) == best:
                merged.append(s[i] + s[i + 1]); i += 2
            else:
                merged.append(s[i]); i += 1
        seqs[w] = merged
    print(f"merge {step}: {best[0]!r} + {best[1]!r} -> {best[0] + best[1]!r}   total tokens now: {sum(len(s) * words[w] for w, s in seqs.items())}")
print({w: s for w, s in seqs.items()})
```

```text
merge 1: 'o' + 'w' -> 'ow'   total tokens now: 36
merge 2: 'l' + 'ow' -> 'low'   total tokens now: 29
merge 3: 'w' + 'e' -> 'we'   total tokens now: 26
merge 4: 'we' + 's' -> 'wes'   total tokens now: 23
{'low': ['low'], 'lower': ['low', 'e', 'r'], 'newest': ['n', 'e', 'wes', 't']}
```

**② With NumPy.** The same counting with arrays of ids: each merge creates a new id.

```python
import numpy as np

text = "low low low low low lower lower newest newest newest"
ids = np.frombuffer(text.encode(), dtype=np.uint8).astype(np.int64)         # byte-level: the base alphabet is 0..255
next_id = 256
for step in range(4):
    pairs, counts = np.unique(np.stack([ids[:-1], ids[1:]], axis=1), axis=0, return_counts=True)
    keep = ~((pairs == 32).any(axis=1))                                      # never merge across spaces (a tiny pre-tokenizer)
    pairs, counts = pairs[keep], counts[keep]
    a, b = pairs[np.argmax(counts)]
    out, i = [], 0
    while i < len(ids):
        if i + 1 < len(ids) and ids[i] == a and ids[i + 1] == b:
            out.append(next_id); i += 2
        else:
            out.append(ids[i]); i += 1
    ids = np.array(out); print(f"merge {step + 1}: ({a}, {b}) -> {next_id}   sequence length {len(ids)}")
    next_id += 1
```

```text
merge 1: (108, 111) -> 256   sequence length 45
merge 2: (256, 119) -> 257   sequence length 38
merge 3: (101, 115) -> 258   sequence length 35
merge 4: (101, 119) -> 259   sequence length 32
```

**Lab excerpt** (from the tier's `lab/`, as originally authored; run inside the `lab/` folder):

```python
# run inside lab/ -- the core loop of ByteBPE.train, written out
from collections import Counter
from mini_bpe import pair_counts, merge_pair

words = Counter(["low"] * 5 + ["lower"] * 2 + ["newest"] * 3)
seqs = [list(w.encode()) for w in words]
weights = list(words.values())
merges = []
for k in range(4):
    counts = pair_counts(seqs, weights)                                   # 1. count pairs
    best = max(counts.items(), key=lambda kv: (kv[1], -kv[0][0], -kv[0][1]))[0]   # 2. most frequent (deterministic ties)
    new_id = 256 + k
    merges.append((best, new_id))
    seqs = [merge_pair(s, best, new_id) for s in seqs]                    # 3. merge everywhere
print(merges)

# the full tokenizer (train / encode / decode, round-trips any Unicode):
from mini_bpe import ByteBPE, compression_ratio
tok = ByteBPE.train("low lower lowest " * 30, num_merges=20)
assert tok.decode(tok.encode("naïve 日本語 🙂")) == "naïve 日本語 🙂"
print(round(compression_ratio(tok, "low lower lowest " * 30), 2), "bytes/token")
```

### 9. Enterprise use case

Every company fine-tuning or continuing to pre-train an open model for a new domain (legal, biomedical, code) decides whether the stock tokenizer is efficient on its text; domain-specific tokenizers are trained with the process in [6.27 Tokenizer training](06.27-tokenizer-training.md).

### 10. AI engineering connection

Defines the unit for context windows, billing, logprobs and the embedding table ([6.18 Embedding matrix](06.18-embedding-matrix.md)). Almost every modern LLM family uses a BPE variant (`REVIEW_REQUIRED` per model).

### 11. Advantages

No UNK with a byte base; tunable vocabulary size; deterministic; simple and fast; good compression on training-like text.

### 12. Limitations

Greedy and frequency-driven, not linguistically aware; numbers, rare scripts and code can fragment unevenly; tokenizer is **frozen** once the model is trained; training is sensitive to the corpus mix.

### 13. Trade-offs

More merges give shorter sequences but a bigger embedding/softmax and rarer undertrained tokens ([6.28 Vocabulary-size trade-offs](06.28-vocabulary-size-trade-offs.md)).

### 14. Common mistakes

- Training the tokenizer on data unlike deployment data.
- Changing the tokenizer without retraining the model.
- Forgetting that a leading space is part of the token (`"low"` != `" low"`).
- Comparing token counts between different tokenizers as if they were the same unit.
- Applying merges out of order.

### 15. Performance / cost

Providers bill per token, so tokenizer efficiency on *your* language/domain is a direct cost multiplier ([6.31 Tokenization efficiency](06.31-tokenization-efficiency.md)). Naive BPE training is O(merges x corpus); production trainers use incremental pair-count updates.

### 16. Security

Glitch tokens (rarely trained tokens) can produce unstable behaviour; untrusted text can inflate token counts (cost-DoS), so cap input *tokens*, not characters; never use token counts as a security boundary.

### 17. Interview explanation

*"BPE builds a vocabulary bottom-up: start from bytes, repeatedly merge the most frequent adjacent pair until you hit the vocab size. That gives frequent words as single tokens and rare words as pieces, with no unknown tokens. The trade-off is vocabulary size versus sequence length, and the tokenizer is fixed after training, so it has to match the model."*

### 18. Rapid-fire answer

Greedy frequency-based merges of adjacent symbols produce a subword vocabulary.
