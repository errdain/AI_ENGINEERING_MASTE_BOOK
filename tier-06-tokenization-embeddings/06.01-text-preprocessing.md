### 1. WHAT IS IT?

Text preprocessing is everything done to a raw string *before* the tokenizer's vocabulary is applied: Unicode normalization, optional case folding, whitespace/control-character cleanup, and **pre-tokenization** (splitting into word-like chunks so that merges or matches never cross word boundaries).

### 2. WHY DOES IT EXIST?

A tokenizer is a deterministic function from string to IDs, so two strings that *look* the same but differ in bytes get different IDs. Preprocessing makes the input canonical and decides which boundaries the tokenizer is allowed to learn across.

### 3. DETAILED EXPLANATION

Typical stages, in order:

1. **Decode** bytes to text with a known encoding (UTF-8) and decide how to treat invalid bytes.
2. **Normalize** Unicode ([6.30 Unicode normalization](06.30-unicode-normalization.md)).
3. **Clean** (strip control characters, collapse or *preserve* whitespace). Modern LLM tokenizers usually *preserve* whitespace, because code indentation and newlines carry meaning.
4. **Case handling.** Lower-casing shrinks the vocabulary (older BERT-style models) but destroys information for names, code and acronyms; most modern LLM tokenizers keep case.
5. **Pre-tokenize.** Split into chunks (on whitespace, punctuation, digits, or by a regex). GPT-2-style tokenizers attach the leading space to the next word, so `"low"` and `" low"` are different tokens.

The rule of thumb: *whatever you do at training time you must do identically at inference time.* Preprocessing is part of the tokenizer artifact (see [6.27 Tokenizer training](06.27-tokenizer-training.md)).

### 4. HOW DOES IT WORK?

```
raw bytes ──decode──► str ──normalize──► str ──clean/case──► str ──pre-tokenize──► chunks ──► tokenizer
```
The lab's `_pretokenize` in [`lab/mini_bpe.py`](lab/mini_bpe.py) implements the simplest version: split before each run of whitespace and keep it attached to the following word.

### 5. SIMPLE EXAMPLE

Before sorting a pile of mail you flatten every envelope, throw away the packaging and put it in a standard tray. Sorting (tokenizing) then works the same way every time.

### 6. TECHNICAL EXAMPLE

A RAG ingestion pipeline normalizes PDFs to NFC, strips zero-width characters, and then uses the *same* tokenizer (including its pre-tokenizer) that the downstream LLM uses to count tokens per chunk. If ingestion normalizes but the query path does not, a query containing `e` + combining accent will fail to match its indexed chunk.

### 7. CODE

```python
# run inside lab/  (cd lab && python this_file.py)
from mini_bpe import _pretokenize
print(_pretokenize("low lower  lowest"))   # ['low', ' lower', '  lowest']  <- whitespace stays attached to the following word
```
`_pretokenize` keeps every character (lossless). A *lossy* cleanup step (e.g. lower-casing) would make decoding unable to restore the original text.

### 8. INPUT → PROCESS → OUTPUT

```
"Héllo,  World"   ──► NFC ──► keep case ──► pre-tokenize ──► ["Héllo,", "  World"]   (lab-style: whitespace stays on next word)
```

### 9. ENTERPRISE USE CASE

A legal-search vendor standardizes all ingested contracts (NFC, de-hyphenation, whitespace policy) and stores the preprocessing version number with every index so that re-indexing is reproducible.

### 10. AI ENGINEERING CONNECTION

Preprocessing is part of the tokenizer, so it is frozen with the model (see [6.27 Tokenizer training](06.27-tokenizer-training.md)). It also decides how chat templates and special-token strings in user text are handled ([6.10 BOS](06.10-bos.md)).

### 11. ADVANTAGES

Smaller effective vocabulary; consistent IDs for equivalent text; prevents merges across word boundaries; cheap to run.

### 12. LIMITATIONS

Lossy steps (lower-casing, NFKC, accent stripping) cannot be undone; language-specific rules (e.g. no spaces in Chinese/Japanese) make whitespace pre-tokenization wrong for many scripts, which is why [6.14 SentencePiece](06.14-sentencepiece.md) treats whitespace as an ordinary symbol.

### 13. TRADE-OFFS

More aggressive cleaning means fewer vocabulary entries and more robustness, but lost information (case, formatting, code structure) and a harder train/serve contract.

### 14. COMMON MISTAKES

- Lower-casing a model that must preserve case (code, names, acronyms).
- Cleaning at training time but not at inference time (train/serve skew).
- Collapsing whitespace for code or YAML.
- Counting tokens on raw text when the model's pipeline would normalize first.

### 15. PERFORMANCE / COST CONSIDERATIONS

Preprocessing is O(n) in text length and negligible next to model cost, but regex pre-tokenizers on adversarial input can be slow (catastrophic backtracking) -- benchmark with long, odd inputs (`REVIEW_REQUIRED` for any specific library).

### 16. SECURITY CONSIDERATIONS

Preprocessing runs *before* guardrails: homoglyphs and zero-width characters can bypass keyword filters that run on un-normalized text. Normalize first, then filter. Never let user text be interpreted as control tokens ([6.10 BOS](06.10-bos.md)).

### 17. INTERVIEW EXPLANATION

*"Preprocessing makes text canonical before the tokenizer sees it: normalize Unicode, decide on case and whitespace, and pre-tokenize into chunks so merges stay inside words. It must be identical at training and inference time, because the tokenizer is frozen with the model."*

### 18. RAPID-FIRE ANSWER

Canonicalize text (normalize, clean, pre-split) before the vocabulary is applied.
