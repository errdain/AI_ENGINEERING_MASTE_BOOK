# 1.40 Floating-point precision

**Metadata** — Tier: 1 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: High · Hands-on: Very high
Prerequisites: 1.1, 1.4 · Leads to: 1.39, 1.44, mixed precision, quantization (Tier 11), GPU memory budgeting

### 1. What is it?
Real numbers are stored in a fixed number of bits as `±(1.mantissa) × 2^exponent` (IEEE 754). Only a finite set of values is representable; everything else is rounded.

| dtype | bits | exponent | mantissa | max | machine ε (≈ rel. precision) |
|---|---|---|---|---|---|
| float64 | 64 | 11 | 52 | ≈1.8×10³⁰⁸ | 2.2×10⁻¹⁶ |
| float32 | 32 | 8 | 23 | ≈3.4×10³⁸ | 1.19×10⁻⁷ |
| float16 | 16 | 5 | 10 | 65504 | ≈9.8×10⁻⁴ |
| bfloat16 | 16 | 8 | 7 | ≈3.4×10³⁸ | ≈7.8×10⁻³ |

(float64/32/16 constants are checked with `np.finfo`; the bfloat16 row is from the format definition; NumPy has no native bfloat16: REVIEW_REQUIRED against current PyTorch docs.)

### 2. Why does it matter?
Model memory, speed, and accuracy all depend on dtype. Halving precision halves memory and can double throughput on modern hardware, but introduces rounding and range problems that surface as NaNs or degraded quality.

### 3. Detailed explanation
- **Exponent bits set the range; mantissa bits set the precision.** fp16: tiny range (max 65504, overflows easily), moderate precision. bf16: fp32-like range, very coarse precision. This is why bf16 training rarely needs loss scaling while fp16 does.
- **Spacing grows with magnitude:** near 1 float32 spacing is ~1.2e-7, near 10⁸ it is 8. So `1e8 + 1` stays `1e8` in float32; float32 cannot count past 2²⁴ = 16,777,216 by adding 1 (tested).
- **Non-associativity:** `(a+b)+c ≠ a+(b+c)` in general; summation order changes results, so parallel reductions can differ run-to-run or device-to-device.
- **Decimal inexactness:** `0.1 + 0.2 ≠ 0.3` (error ~5e-17; tested). Never compare floats with `==`; use `np.isclose`/tolerances.
- **Special values:** `inf`, `-inf`, `NaN` (`NaN != NaN`), signed zero, subnormals (gradual underflow, often slow on CPUs and flushed to zero on GPUs).
- **Underflow:** `float16(1e-8) → 0` (tested). **Overflow:** `float16(70000) → inf` (tested).
- **Mixed precision recipe:** compute matmuls in fp16/bf16, keep **master weights and optimizer states in fp32**, accumulate sums in fp32, use **loss scaling** for fp16 so small gradients don't underflow.
- **Low-bit inference:** int8/int4/fp8 quantization maps weights to few levels with scale factors (Tier 11).
- Memory: parameters × bytes. A 7B-parameter model: ~28 GB (fp32), ~14 GB (fp16/bf16), ~3.5 GB (4-bit), weights only: excludes activations, KV cache, and optimizer states (Adam adds ~8 bytes/param in fp32 for two moments).

### 4. How does it work?
Rounding to nearest representable value after every operation; relative error per operation ≤ ε/2. Errors accumulate over long computations (thousands of layers/steps).

### 5. Simple example
A ruler marked only in whole millimetres: you can't record 0.3 mm; big numbers are measured with a coarser ruler.

### 6. Technical example
Summing 1000 values of 1.0 onto an fp32 accumulator holding 1e8 yields no change at all (each +1 is absorbed); accumulating in fp64 gives the right 1e8+1000 (tested).

### 7. Code
```python
import numpy as np
print(0.1 + 0.2 == 0.3, abs(0.1 + 0.2 - 0.3))            # False 5.5e-17
print(np.finfo(np.float32).eps, np.finfo(np.float16).max)  # 1.1920929e-07 65504.0
print(np.float32(16777216) + np.float32(1))               # 16777216.0 (+1 absorbed)
print(np.float16(70000.0), np.float16(1e-8))              # inf 0.0
```

### 8. Input → Process → Output
`real number → nearest representable float (dtype) → computation → rounding at each step`

### 9. Enterprise use case
GPU memory/cost planning, choosing dtype per workload (bf16 training, int8/fp8 serving), and reproducibility policies (fixed reduction order, deterministic kernels) for regulated settings.

### 10. AI engineering connection
Mixed-precision training, quantization (GPTQ/AWQ-style), KV-cache dtype, loss scaling, reproducibility across hardware, FP8 training research.

### 11. Advantages
Wide dynamic range with constant relative precision; hardware-accelerated.

### 12. Limitations
Finite precision, rounding error accumulation, non-associativity, limited range for fp16.

### 13. Trade-offs
float32 (safe) ↔ bf16 (range, coarse) ↔ fp16 (precise-ish, narrow range) ↔ int8/4 (compact, needs calibration). Pick by hardware support and task tolerance.

### 14. Common mistakes
Comparing floats with `==`; summing in low precision; fp16 without loss scaling; assuming results are bit-reproducible across GPUs; casting everything to bf16 including LayerNorm/softmax accumulations; forgetting optimizer-state memory.

### 15. Performance / cost
Lower precision → more FLOPs/s and less bandwidth, but verify quality on your eval set. Always measure memory (`parameters × bytes`) before provisioning.

### 16. Security
Reduced-precision differences can alter safety-classifier outputs near thresholds; re-run safety evals on the exact deployed dtype/quantization.

### 17. Interview explanation
"Floats store a sign, exponent and mantissa. The exponent gives range, the mantissa gives precision. fp16 has a narrow range so it overflows and needs loss scaling; bf16 keeps fp32's range with less precision, so it's easier for training. I keep master weights and accumulations in fp32 and compare floats with tolerances."

### 18. Rapid-fire
Exponent=range, mantissa=precision; fp16 max 65504; bf16 = fp32 range; accumulate in fp32; never `==`.
