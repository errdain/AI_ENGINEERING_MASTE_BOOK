# 1.44 Numerical overflow and underflow

**Metadata** — Tier: 1 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: Very high
Prerequisites: 1.40, 1.42 · Leads to: loss scaling, NaN debugging, mixed-precision training (Tier 4), quantization

### 1. What is it?
- **Overflow:** a result too large in magnitude for the dtype becomes `±inf` (floats) or wraps around (integers).
- **Underflow:** a result too close to zero becomes subnormal or exactly `0`.

### 2. Why does it matter?
Both are silent. `inf` and `0` propagate: `inf − inf = NaN`, `0 · inf = NaN`, `0/0 = NaN`, `log(0) = −inf`. One bad value can contaminate a whole training run through the gradient.

### 3. Detailed explanation
Representable limits (see 1.40): float16 max 65504 (smallest positive normal ≈ 6.1e-5), float32 max ≈ 3.4e38, float64 max ≈ 1.8e308. Verified: `float16(70000) → inf`, `float16(1e-8) → 0`, product of 400 values of 1e-3 → 0 in float64 (tested).

Typical sources in ML:
| Source | Symptom | Fix |
|---|---|---|
| `exp` of large logits (softmax) | `inf/inf = NaN` | subtract max / log-sum-exp (1.43) |
| Product of probabilities | underflow to 0 | work in log space (1.41) |
| Exploding activations/gradients | `inf` loss | normalization, clipping (1.15), lower LR |
| fp16 gradients too small | silent zeros | loss scaling; use bf16 |
| Division by zero / tiny variance | `inf`, NaN | add ε |
| `log(0)` | `−inf` | clip prob to `[ε, 1−ε]` or use fused stable op |
| Integer overflow (token counts, ids, int8 accumulation) | wraparound, negative numbers | wider dtype / explicit checks |
| Large offset accumulation | lost small increments (absorption) | higher-precision accumulators (1.40) |

Detection: `np.isfinite`, `torch.isnan(x).any()`, anomaly detection modes, gradient-norm logging, checks on loss every step. NumPy raises `RuntimeWarning` (can be promoted to errors with `np.errstate(all='raise')`); PyTorch usually propagates silently.

Gradual underflow (subnormals) keeps tiny numbers non-zero at reduced precision but is slow on some CPUs and flushed to zero on many GPUs.

Dynamic loss scaling (fp16): multiply the loss by a large factor `S` before backward, unscale gradients before the optimizer step; if an overflow (`inf`/NaN) is detected, skip the step and reduce `S`; periodically increase `S`.

### 4. How does it work?
Hardware sets exception flags and returns `inf`/`0` according to IEEE 754 rules; frameworks mostly ignore the flags unless asked.

### 5. Simple example
An odometer that rolls over after 99,999: integer overflow. A scale that can't register under 1 g: underflow.

### 6. Technical example
Attention with fp16 scores of magnitude 100 → `exp(100)=inf` → softmax = NaN → loss NaN. Subtracting the row max fixes it at no cost.

### 7. Code
```python
import numpy as np, warnings
warnings.simplefilter("ignore")
print(np.float16(70000.0), np.float16(1e-8))            # inf 0.0
print(np.prod(np.full(400, 1e-3)))                      # 0.0  (underflow)
print(np.int8(127) + np.int8(1))                        # -128 (wraparound)
print(np.inf - np.inf, 0 * np.inf)                      # nan nan
```
TESTED: float16 overflow/underflow, product underflow, finite results of stable alternatives (`test_log_space_avoids_underflow_of_probability_products`, `test_cross_entropy_on_extreme_logits_is_finite`). The int8 wraparound line is NOT_TESTED in the suite (NumPy scalar overflow behaviour/warnings are version-sensitive; REVIEW_REQUIRED).

### 8. Input → Process → Output
`operation → result outside dtype range → inf / 0 / wrap → NaN propagation downstream`

### 9. Enterprise use case
Training platforms gate checkpoints on finite loss and auto-restart from the last good checkpoint with reduced LR when NaNs appear.

### 10. AI engineering connection
Mixed precision, loss scaling, quantization (int8 accumulation in int32), attention kernels, normalization ε, gradient clipping, `logprobs` handling.

### 11. Advantages (of knowing)
Fast diagnosis of NaN/Inf failures; cheap prevention.

### 12. Limitations
Detection hooks add overhead; some stabilizations change numerics slightly (clipping, ε).

### 13. Trade-offs
Check every step (safe, slower) vs periodic checks (cheap, late detection); bf16 (range-safe) vs fp16 + scaling (more precision).

### 14. Common mistakes
Adding ε inside a `log` or `sqrt` that doesn't need it and biasing results; not checking inputs from users/data pipelines (NaN labels); ignoring warnings; clipping values to hide a bug.

### 15. Performance / cost
A NaN discovered 12 hours into a run wastes the GPU-hours; a per-step `isfinite` check costs microseconds.

### 16. Security
Crafted inputs with huge values or NaN can poison online-learning or retrieval scoring; validate numeric ranges at the API boundary.

### 17. Interview explanation
"Overflow means a value is too big for the dtype and becomes inf; underflow means it rounds to zero. Both propagate silently into NaNs. The usual fixes are log-space, subtracting the max in softmax, ε in denominators, gradient clipping, bf16 or loss scaling for fp16, and cheap isfinite checks on the loss."

### 18. Rapid-fire
Overflow→inf, underflow→0, inf−inf=NaN; use log space, max-shift, ε, clipping, loss scaling.
