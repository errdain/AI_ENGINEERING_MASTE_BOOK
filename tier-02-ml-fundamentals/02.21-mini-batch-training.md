# 2.21 Mini-batch training

**Metadata** — Tier: 2 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: Very high
Prerequisites: 2.20 · Leads to: 2.22–2.24 Epoch/batch/iteration, Tier 4 Batch size (4.13) and gradient accumulation (4.14)

> **In plain words**
> **Mini-batch training** updates the model using the average gradient of **a small group of examples** (typically 16–4,096) at a time: a compromise between "one example" (noisy) and "the whole dataset" (slow).
> It is how nearly all deep learning is trained, because graphics cards crunch groups of examples in parallel far more efficiently than one at a time. Like polling 32 people at a time instead of one, or the whole town.

**You need first:** 2.20 SGD.

> *How to read it:* with 1,050 examples and a batch size of 100, one pass over the data (one **epoch**) makes 10 full batches and one smaller last batch: 11 updates. If you drop that small last batch (`drop_last=True`) you get 10.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| mini-batch | a small random group of examples used for one update |
| batch size `B` | how many examples per mini-batch |
| iteration | one update step (one batch) |
| epoch | one full pass over the training data |
| `drop_last` | discard the last, smaller batch |
| gradient accumulation | add up gradients over several small batches to mimic a big one |
| linear scaling rule | scale the learning rate with the batch size (a starting heuristic) |

### 1. What is it?
Updating the parameters using the average gradient of a **small group (mini-batch) of examples**, typically 16–4,096, rather than one example or the whole dataset.

### 2. Why does it exist?
It balances gradient noise against computation, and it fits the hardware: GPUs process batches in parallel far more efficiently than single examples.

### 3. Detailed explanation
- **Gradient estimate:** `g_B = (1/B) Σ_{i∈B} ∇ℓᵢ` is unbiased with variance about `σ²/B`.
- **Trade-offs**
  - *Small `B`:* many noisy updates per epoch, little memory per step, helpful noise, poor hardware use.
  - *Large `B`:* a smooth gradient and good parallel efficiency, but fewer updates per epoch; it often needs a larger learning rate and warm-up, and can generalise worse if increased naively.
- **Diminishing returns:** once the noise is small compared with the true gradient, a bigger batch adds cost without proportional benefit.
- **Memory:** activation memory grows linearly with `B`. **Gradient accumulation** simulates a large batch by summing gradients over several small ones (Tier 4, 4.14).
- **The last partial batch:** with `n = 1050` and `B = 100` an epoch has 10 full batches and one of 50 (11 iterations); `drop_last=True` discards the partial one (10 iterations).
- **Batch composition:** random shuffling, stratification for rare classes, bucketing by length for sequences (to reduce padding waste).
- **Batch normalisation** couples the examples in a batch (Tier 3, 3.30): the batch size then affects model *behaviour*, not just optimisation.
- **Learning-rate coupling:** a common heuristic scales the learning rate with the batch size (linearly or by square root); treat it as a starting point to tune.

### 4. How does it work?
Shuffle the indices → slice them into batches → for each batch compute the loss, the gradient and the update → repeat every epoch.

### 5. Simple example
Polling 32 people at a time instead of one at a time or the whole town.

**Counting iterations.**

| `n` | `B` | iterations per epoch |
|---|---|---|
| 1,000 | 64 | 16 (15 full batches + one of 40) |
| 1,050 | 100 | 11 (or 10 with `drop_last`) |
| 1,000 | 1,000 | 1 (full batch) |
| 1,000 | 1 | 1,000 (pure SGD) |

### 6. Technical example
Fine-tuning with batch size 32, with sequences padded per batch; pretraining with a global batch of millions of tokens spread across many GPUs.

### 7. Code
**① By hand (plain Python).** Cut shuffled indices into batches.

```python
import math
import random

def batches(n, B, drop_last=False, seed=0):
    idx = list(range(n))
    random.Random(seed).shuffle(idx)
    out = [idx[i:i + B] for i in range(0, n, B)]
    return out[:-1] if drop_last and len(out[-1]) < B else out

sizes = [len(b) for b in batches(1050, 100)]
print("batch sizes:", sizes, " iterations:", len(sizes))
print("with drop_last:", len(batches(1050, 100, drop_last=True)), "iterations")
print("formula: ceil(1050/100) =", math.ceil(1050 / 100), "  floor(1050/100) =", 1050 // 100)
covered = sorted(i for b in batches(1050, 100) for i in b)
print("every example used exactly once per epoch:", covered == list(range(1050)))
```

```text
batch sizes: [100, 100, 100, 100, 100, 100, 100, 100, 100, 100, 50]  iterations: 11
with drop_last: 10 iterations
formula: ceil(1050/100) = 11   floor(1050/100) = 10
every example used exactly once per epoch: True
```

**② With NumPy.** The same final loss needs different numbers of updates for different batch sizes.

```python
import numpy as np

rng = np.random.default_rng(0)
X = rng.normal(0, 1, (1024, 3))
y = X @ np.array([2.0, -1.0, 0.5]) + 0.1 * rng.normal(0, 1, 1024)

def train(B, lr, epochs=5):
    w, updates = np.zeros(3), 0
    for _ in range(epochs):
        perm = rng.permutation(len(X))
        for i in range(0, len(X), B):
            idx = perm[i:i + B]
            w -= lr * 2 * X[idx].T @ (X[idx] @ w - y[idx]) / len(idx)
            updates += 1
    return updates, float(np.mean((X @ w - y) ** 2))

for B in (8, 32, 128, 512):
    updates, loss = train(B, lr=0.05)
    print(f"B = {B:>3}: updates {updates:>4}   loss after 5 epochs {loss:.4f}")
```

```text
B =   8: updates  640   loss after 5 epochs 0.0101
B =  32: updates  160   loss after 5 epochs 0.0100
B = 128: updates   40   loss after 5 epochs 0.0110
B = 512: updates   10   loss after 5 epochs 0.6440
```

**③ With PyTorch.** The `DataLoader` does the batching for you.

```python
import torch
from torch.utils.data import DataLoader, TensorDataset

data = TensorDataset(torch.arange(1050).float().unsqueeze(1), torch.zeros(1050))
loader = DataLoader(data, batch_size=100, shuffle=True)
print("batches per epoch:", len(loader), "  last batch size:", len(list(loader)[-1][0]))
loader = DataLoader(data, batch_size=100, shuffle=True, drop_last=True)
print("with drop_last   :", len(loader))
```

```text
with drop_last   : 10
```

### 9. Enterprise use case
Batch size drives throughput, cost and memory; teams tune it against GPU utilisation and convergence.

### 10. AI engineering connection
Token-based batch sizes in LLM training; per-device versus global batch; micro-batches in pipeline parallelism (Tier 4, 4.30–4.34).

### 11. Advantages
Efficient hardware use, tunable noise, and standard practice.

### 12. Limitations
An extra hyper-parameter coupled with the learning rate; batch-dependent layers; memory limits.

### 13. Trade-offs
Throughput and stability versus generalisation and update frequency.

### 14. Common mistakes
Changing the batch size without retuning the learning rate; evaluating with a different batch size while BatchNorm is in train mode; silently dropping data with `drop_last`; unshuffled data sorted by class.

### 15. Performance / cost
GPU utilisation usually rises with `B` until memory or bandwidth saturates; profile it.

### 16. Security
Batches built from mixed tenants can leak information through batch-dependent layers; avoid cross-tenant batches when training on private data.

</details>

### 17. Interview explanation
"Mini-batch training averages the gradient over a small group of examples, giving an unbiased estimate with variance falling like one over B, and it uses GPUs efficiently. I tune batch size against memory and throughput, retune the learning rate when I change it, and use gradient accumulation if memory is the limit."

### 18. Rapid-fire answer
Average the gradient over `B` examples: variance ~ `1/B`, parallel-efficient; retune the learning rate when `B` changes.

### 20. Hands-on exercise
**Goal:** compare batch sizes at a fixed, small number of updates, not a fixed number of epochs.

1. Use the NumPy training loop above.
2. Give every batch size exactly **20 updates**, and average over 20 random runs to smooth out luck.
3. Print the average loss for `B` = 1, 8, 32, 128, 512.

<details>
<summary>Show a solution</summary>

```python
import numpy as np

rng = np.random.default_rng(0)
X = rng.normal(0, 1, (1024, 3))
y = X @ np.array([2.0, -1.0, 0.5]) + 0.1 * rng.normal(0, 1, 1024)

def train(B, lr=0.05, updates=20, seed=0):
    r = np.random.default_rng(seed)
    w = np.zeros(3)
    for _ in range(updates):
        idx = r.integers(0, len(X), B)                          # a random batch each step
        w -= lr * 2 * X[idx].T @ (X[idx] @ w - y[idx]) / B
    return float(np.mean((X @ w - y) ** 2))

for B in (1, 8, 32, 128, 512):
    print(f"B = {B:>3}: average loss after 20 updates {np.mean([train(B, seed=s) for s in range(20)]):.4f}")
```

```text
B =   1: average loss after 20 updates 0.1387
B =   8: average loss after 20 updates 0.0832
B =  32: average loss after 20 updates 0.0839
B = 128: average loss after 20 updates 0.0861
B = 512: average loss after 20 updates 0.0863
```

Going from `B = 1` to `B = 8` helps a lot (much less noise), but going from 8 to 512 buys almost nothing per update while costing 64 times more computation per update: **diminishing returns**. At a fixed number of *epochs* the small batches also get many more updates, so which comparison is fair depends on your budget.
</details>
