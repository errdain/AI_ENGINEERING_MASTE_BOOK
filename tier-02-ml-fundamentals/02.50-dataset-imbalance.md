# 2.50 Dataset imbalance

**Metadata** — Tier: 2 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: High
Prerequisites: 2.45, 2.43, 1.34 · Leads to: 2.51 Metric selection, Tier 30 Evaluation datasets, Tier 31 Monitoring

### 1. What is it?
The **imbalance in the dataset itself and what it means for sampling, splits, evaluation and probability outputs**: the difference between the class proportions in your training/test data and in the real world.

### 2. Why does it exist?
Whenever the dataset's prevalence differs from production's (by design, via downsampling, or by drift), thresholds, precision and probabilities change even if the model's ranking ability does not.

### 3. Detailed explanation
*Scope note:* the frozen roadmap lists both 2.45 (Class imbalance) and 2.50 (Dataset imbalance). To avoid duplication, 2.45 covers metrics and training methods for rare classes; this concept covers dataset construction, evaluation-set design and prevalence/calibration effects. The Critic should confirm this split (REVIEW_REQUIRED).
- **Preserve prevalence in held-out sets** when you want production-like metrics; stratify splits (2.10, 2.44). If you deliberately oversample positives for the evaluation set (to measure recall reliably), **reweight** precision-type metrics to the production prevalence (`precision = TPR·π/(TPR·π + FPR·(1−π))`, 2.38).
- **Downsampling the majority class for training** (cheap, common) shifts the model's probabilities. Demonstration: train on a 50/50 downsample of data with 1.96% positives. Mean predicted probability on production-like data is **0.128** instead of 0.0196; ECE 0.108; precision at threshold 0.5 only 0.192.
- **Prior correction:** add `log(π_prod/(1−π_prod)) − log(π_train/(1−π_train))` to the logit. After correction mean predicted probability is 0.0205 (≈ 0.0196), ECE **0.001** and precision at 0.5 rises to **0.803**, with **AUC unchanged** (0.974): ranking is the same, only the probabilities and the threshold meaning change.
- **Minimum positives:** the number of positives, not total rows, determines evaluation precision. 20 positives → recall's standard error ≈ 10 points.
- **Collection bias:** positives found by an existing detector are not a random sample of all positives (selection bias); labeled data may exclude cases the old system never flagged.
- **Imbalance over time:** prevalence drifts (fraud waves, seasonal queries); monitor base rates and recalibrate (2.34, 2.43).
- **Evaluation-set construction for LLM systems:** golden sets over-represent hard and rare cases; report results by category, with weights reflecting production traffic (Tier 30).
- **Multiclass and multi-label:** long-tail label distributions need per-class reporting, minimum counts per class and stratification.

### 4. How does it work?
Estimate production prevalence → keep or reweight evaluation prevalence accordingly → if you resample for training, record the training prior and correct logits or recalibrate → monitor base rates.

### 5. Simple example
A taste test run only on spicy-food lovers will overestimate how many customers like spicy food.

### 6. Technical example
Fraud model trained on 50/50 data deployed where fraud is 0.2%: raw scores say 'high risk' for far too many cases until prior-corrected.

### 8. Input → Process → Output
`dataset prevalence ≠ production prevalence → shifted probabilities/precision → correct priors, reweight, monitor`

### 9. Enterprise use case
Evaluation reports state the prevalence used and give production-adjusted precision and expected alert volumes.

### 10. AI engineering connection
Judge/guardrail eval sets, RAG question mixes and routing datasets rarely match live traffic; reweight by category frequency.

### 11. Advantages
Cheap corrections restore calibrated, decision-ready outputs.

### 12. Limitations
Requires a reliable estimate of production prevalence; the correction assumes label shift (2.34), not covariate shift.

### 13. Trade-offs
Balanced training data trains faster and finds positives more easily but needs post-hoc correction.

### 14. Common mistakes
Quoting precision from a rebalanced test set as production precision; forgetting the training prior; evaluating with too few positives; stratifying training but not evaluation.

### 15. Performance / cost
Downsampling cuts training cost dramatically; correction is free.

### 16. Security
Rare positives in training data may include sensitive records: handle them carefully.

### 17. Interview explanation
"Dataset imbalance is about how the data's class proportions compare with the real world. If I downsample negatives for training, the model's probabilities are inflated, so I add the log-odds difference of the priors to the logit, which fixes calibration and the meaning of the threshold without changing AUC. For evaluation I either keep production prevalence or reweight precision."

### 18. Rapid-fire
Dataset prevalence ≠ production prevalence ⇒ prior-correct logits, reweight eval metrics; AUC unaffected.
