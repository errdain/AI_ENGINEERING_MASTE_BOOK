# 2.50 Dataset imbalance

**Metadata** — Tier: 2 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: High

> **In plain words**
> **Dataset imbalance** is about **the mismatch between the class proportions in your data and in the real world**. If you train on a 50/50 mix (by downsampling the common class) but fraud is 2% in production, the model's probabilities are **inflated**: it says "likely fraud" for far too many cases.
> The fix is simple and cheap: **correct the model's log-odds by the difference of the two base rates**. Ranking (AUC) doesn't change; the probabilities and the meaning of the threshold do.
> *(2.45 covers metrics and training tricks for rare classes; this page covers building and evaluating the dataset and fixing the probabilities.)*

**You need first:** 2.45 Class imbalance, 2.43 Calibration, 1.34 Bayes (base rates).

> **Figure 2.50-1 — train on a different mix, correct the probabilities**
>
> ```mermaid
> flowchart LR
>     P["production: 2% positives"] --> D["downsample negatives<br/>to train on 50/50"]
>     D --> M["model: probabilities too high"]
>     M --> C["prior correction:<br/>logit + log-odds(production) − log-odds(training)"]
>     C --> OK["calibrated probabilities,<br/>same ranking (AUC unchanged)"]
> ```
>
> *How to read it:* the model learned that "half of all cases are positive", so its probabilities are inflated for a world where 2% are. Adding a constant (the log-odds difference) to every logit repairs the numbers. Since adding a constant never changes the order of the scores, AUC stays the same.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| prevalence `π` / base rate | share of positives |
| training prior vs production prior | the prevalence in the training data vs in the real world |
| downsampling | dropping some majority-class examples |
| prior correction | shifting the logit by the log-odds ratio of priors |
| label shift | `P(y)` changes, `P(x|y)` stays |
| minimum positives | the number of positives limits evaluation precision |
| selection bias | positives found by an old detector aren't a random sample |

### 1. What is it?
The **imbalance in the dataset itself and what it means for sampling, splits, evaluation and probability outputs**: the difference between the class proportions in your training or test data and in the real world.

### 2. Why does it matter?
Whenever the dataset's prevalence differs from production's (by design, by downsampling, or through drift), thresholds, precision and probabilities change even though the model's ranking ability doesn't.

### 3. Detailed explanation
*Scope note:* the frozen roadmap lists both 2.45 (Class imbalance) and 2.50 (Dataset imbalance). To avoid duplication, 2.45 covers metrics and training methods for rare classes; this concept covers dataset construction, evaluation-set design and prevalence and calibration effects. The Critic should confirm this split (REVIEW_REQUIRED).

- **Preserve prevalence in held-out sets** when you want production-like metrics; stratify the splits (2.10, 2.44). If you deliberately oversample positives in the evaluation set (to measure recall reliably), **re-weight** precision-type metrics to the production prevalence: `precision = TPR·π / (TPR·π + FPR·(1 − π))` (2.38).
- **Downsampling the majority class for training** (cheap and common) shifts the model's probabilities. Train on a 50/50 downsample of data with about 2% positives and the mean predicted probability on production-like data is several times too high, calibration error is large, and precision at threshold 0.5 is poor.
- **Prior correction:** add `log(π_prod/(1 − π_prod)) − log(π_train/(1 − π_train))` to the logit. After the correction the mean predicted probability matches the real rate, calibration error is near zero and precision at 0.5 rises sharply, with **AUC unchanged**.
- **Minimum positives:** the number of *positives*, not total rows, decides how precisely you can evaluate. 20 positives gives a recall standard error of about 10 points.
- **Collection bias:** positives found by an existing detector are not a random sample of all positives; labelled data may exclude cases the old system never flagged.
- **Imbalance over time:** prevalence drifts (fraud waves, seasonal queries); monitor base rates and recalibrate (2.34, 2.43).
- **Evaluation sets for LLM systems:** golden sets over-represent hard and rare cases; report results by category, with weights reflecting production traffic (Tier 30).
- **Multiclass and multi-label:** long-tail label distributions need per-class reporting, minimum counts per class, and stratification.

### 4. How does it work?
Estimate the production prevalence → keep or re-weight the evaluation prevalence accordingly → if you resample for training, record the training prior and correct the logits or recalibrate → monitor base rates.

### 5. Simple example
A taste test run only among spicy-food lovers will overestimate how many customers like spicy food.

**Prior correction, by hand.** Training prior 50% (log-odds 0), production prior 2% (log-odds `ln(0.02/0.98) = −3.89`). A model output of 0.5 (logit 0) becomes logit `0 + (−3.89 − 0) = −3.89`, i.e. probability 0.02. And a model output of 0.9 (logit 2.20) becomes logit −1.69, i.e. probability 0.16. A "90% sure" in the balanced world is only 16% in the real world.

### 6. Technical example
A fraud model trained on 50/50 data and deployed where fraud is 0.2%: the raw scores say "high risk" for far too many cases until the prior is corrected.

### 7. Code
**① By hand (plain Python).** The correction on single numbers.

```python
import math

def logit(p): return math.log(p / (1 - p))
def sigmoid(z): return 1 / (1 + math.exp(-z))

pi_train, pi_prod = 0.5, 0.02
shift = logit(pi_prod) - logit(pi_train)
for raw in (0.5, 0.9, 0.99):
    print(f"model says {raw:.2f}  ->  production-corrected probability {sigmoid(logit(raw) + shift):.3f}")
print("positives in a 10,000-case day:", 10000 * pi_prod, "-> alerts at raw 0.5 would be far too many")
```

```text
model says 0.50  ->  production-corrected probability 0.020
model says 0.90  ->  production-corrected probability 0.155
model says 0.99  ->  production-corrected probability 0.669
positives in a 10,000-case day: 200.0 -> alerts at raw 0.5 would be far too many
```

**② With NumPy and scikit-learn.** The whole experiment: downsample, correct, compare.

```python
import numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import precision_score, roc_auc_score

rng = np.random.default_rng(0)
def data(n, pi=0.02):
    y = (rng.random(n) < pi).astype(int)
    return rng.normal(0, 1, (n, 4)) + 1.8 * y[:, None], y
Xtr, ytr = data(200000)
Xte, yte = data(200000)                                                # production-like test data

keep = np.r_[np.where(ytr == 1)[0], rng.choice(np.where(ytr == 0)[0], (ytr == 1).sum(), replace=False)]    # 50/50 downsample
model = LogisticRegression().fit(Xtr[keep], ytr[keep])
z = model.decision_function(Xte)
sigmoid = lambda a: 1 / (1 + np.exp(-a))
shift = np.log(0.02 / 0.98) - np.log(0.5 / 0.5)

def ece(y, p, bins=10):
    idx = np.minimum((p * bins).astype(int), bins - 1)
    return sum(abs(y[idx == b].mean() - p[idx == b].mean()) * (idx == b).mean() for b in range(bins) if (idx == b).any())

for name, p in (("raw (trained on 50/50)", sigmoid(z)), ("prior-corrected", sigmoid(z + shift))):
    print(f"{name:<24} mean probability {p.mean():.4f} (true rate {yte.mean():.4f})  ECE {ece(yte, p):.4f}  precision at 0.5 {precision_score(yte, p > 0.5, zero_division=0):.3f}  AUC {roc_auc_score(yte, p):.4f}")
```

```text
raw (trained on 50/50)   mean probability 0.0730 (true rate 0.0197)  ECE 0.0533  precision at 0.5 0.348  AUC 0.9946
prior-corrected          mean probability 0.0197 (true rate 0.0197)  ECE 0.0003  precision at 0.5 0.883  AUC 0.9946
```

**③ With NumPy.** How many positives do you need to evaluate recall?

```python
import numpy as np

rng = np.random.default_rng(0)
true_recall = 0.8
for positives in (20, 100, 500, 2000):
    estimates = rng.binomial(positives, true_recall, 20000) / positives
    print(f"{positives:>4} positives: measured recall varies by ±{estimates.std() * 100:.1f} points (standard error)")
```

```text
  20 positives: measured recall varies by ±8.9 points (standard error)
 100 positives: measured recall varies by ±4.0 points (standard error)
 500 positives: measured recall varies by ±1.8 points (standard error)
2000 positives: measured recall varies by ±0.9 points (standard error)
```

### 8. Input → Process → Output
`dataset prevalence ≠ production prevalence → shifted probabilities and precision → correct priors, re-weight, monitor`

### 9. Enterprise use case
Evaluation reports state the prevalence used and give production-adjusted precision and expected alert volumes.

### 10. AI engineering connection
Judge and guard-rail evaluation sets, RAG question mixes and routing datasets rarely match live traffic; re-weight by category frequency.

### 11. Advantages
Cheap corrections restore calibrated, decision-ready outputs.

### 12. Limitations
Needs a reliable estimate of the production prevalence; the correction assumes label shift (2.34), not covariate shift.

### 13. Trade-offs
Balanced training data trains faster and finds positives more easily but needs post-hoc correction.

### 14. Common mistakes
Quoting precision from a rebalanced test set as production precision; forgetting the training prior; evaluating with too few positives; stratifying the training split but not the evaluation split.

### 15. Performance / cost
Downsampling cuts training cost dramatically; the correction is free.

### 16. Security
Rare positives in training data may include sensitive records; handle them carefully.

### 17. Interview explanation
"Dataset imbalance is about how the data's class proportions compare with the real world. If I downsample negatives for training, the model's probabilities are inflated, so I add the log-odds difference of the priors to the logit, which fixes calibration and the meaning of the threshold without changing AUC. For evaluation I either keep production prevalence or re-weight precision."

### 18. Rapid-fire answer
Dataset prevalence ≠ production prevalence: prior-correct the logits, re-weight evaluation metrics; AUC is unaffected.

### 20. Hands-on exercise
**Goal:** turn a 50/50 evaluation set into a production-prevalence report.

1. On a 50/50 evaluation set the classifier has recall (TPR) 0.90 and false-positive rate (FPR) 0.04.
2. Production prevalence is 1% with 100,000 cases a day. Compute expected true alerts, false alerts and precision.

<details>
<summary>Show a solution</summary>

```python
tpr, fpr, prevalence, cases = 0.90, 0.04, 0.01, 100_000
positives = cases * prevalence
true_alerts = tpr * positives
false_alerts = fpr * (cases - positives)
print(f"expected true alerts per day : {true_alerts:.0f}")
print(f"expected false alerts per day: {false_alerts:.0f}")
print(f"production precision         : {true_alerts / (true_alerts + false_alerts):.3f}   (the 50/50 test set would have suggested {tpr / (tpr + fpr):.3f})")
```

```text
expected true alerts per day : 900
expected false alerts per day: 3960
production precision         : 0.185   (the 50/50 test set would have suggested 0.957)
```
