# 2.36 Hyperparameter tuning

**Metadata** — Tier: 2 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: Very high
Prerequisites: 2.35, 2.12, 2.44 · Leads to: Tier 4 experiment tracking, Tier 30 Evaluation

### 1. What is it?
The process of **searching for the hyperparameter values that give the best validation performance**, using grid search, random search, or smarter methods, under a compute budget.

### 2. Why does it exist?
Good settings can matter as much as the choice of algorithm; a systematic search beats guesswork and is reproducible.

### 3. Detailed explanation
- **Grid search:** try every combination on a grid. Simple but exponential in the number of hyperparameters and wasteful when only a few matter.
- **Random search:** sample configurations from distributions (log-uniform for rates). With the same budget it tries many *distinct* values of the important hyperparameter. Lab: objective dependent mostly on `lr`, budget 9 trials; a 3×3 grid tests only 3 learning rates, random search 9. Averaged over 300 objective instances the best value found is 0.057 (random) vs 0.168 (grid); random wins in 72% of instances.
- **Smarter methods:** Bayesian optimization (model the objective, pick promising configs), successive halving/Hyperband (stop poor trials early), population-based training. Use them when trials are expensive (REVIEW_REQUIRED: verify details when writing the library-specific section).
- **Use a validation protocol that matches data size:** a hold-out validation set for large data; k-fold cross-validation for small data (2.44); group/time-aware folds when needed (2.10).
- **Selection optimism:** the best of many candidates is biased upward. In the lab, 300 random classifiers on noise: best CV score 62.5% but 48.9% on 20,000 fresh points. **Nested cross-validation** (inner loop tunes, outer loop evaluates) or a final untouched test set gives an honest estimate (2.13).
- **Practical workflow:** (1) start from sensible defaults and a baseline (2.46); (2) tune the most influential knobs first (learning rate, regularization); (3) search coarse-to-fine; (4) fix seeds and log everything; (5) retrain the winner on train+validation; (6) evaluate on test once.
- **Budget awareness:** set a maximum number of trials/time; consider diminishing returns; prefer simplifying the model or improving data before long searches.
- **Reproducibility:** record data version, code version, hyperparameters, seeds, and environment.

### 4. How does it work?
Define space → choose method and budget → run trials (parallel if possible) → rank by validation metric (with variance across seeds/folds) → pick → confirm on the test set.

### 5. Simple example
Trying different oven settings, noting results, then narrowing in on the best, and having someone else taste the final cake.

### 6. Technical example
Random search over learning rate (log-uniform 1e-5…1e-2), weight decay, and warmup fraction with early stopping of poor runs; 40 trials on 4 GPUs.

### 8. Input → Process → Output
`search space → trials → validation scores → best config → retrain → test once`

### 9. Enterprise use case
Experiment-tracking platforms schedule trials, store configs and results, and enforce that final reports use untouched test data.

### 10. AI engineering connection
Tuning retrieval and generation settings against a development set; evaluating prompt variants with confidence intervals; LoRA hyperparameter sweeps.

### 11. Advantages
Systematic, parallelizable, auditable.

### 12. Limitations
Expensive; overfits the validation set if overused; results vary with seeds.

### 13. Trade-offs
More trials give higher expected best score but more selection optimism and cost.

### 14. Common mistakes
Tuning on the test set; reporting the best validation score as expected performance; huge searches on a tiny validation set; ignoring seed variance; grid search over many dimensions.

### 15. Performance / cost
Parallelize trials; use early stopping/successive halving; reuse cached features.

### 16. Security
Search logs may contain data identifiers; protect experiment stores. Cap compute spend with budgets.

### 17. Interview explanation
"I define a search space with log scales for rates, usually run random search because a few hyperparameters dominate, and evaluate with cross-validation or a validation set. Because the best of many trials is optimistic, I confirm the winner on an untouched test set or with nested CV, and I log seeds and configs for reproducibility."

### 18. Rapid-fire
Random > grid when few parameters matter; tune on validation; the best-of-many is optimistic, so confirm on a held-out test.
