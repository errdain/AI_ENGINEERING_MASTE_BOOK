# 2.35 Hyper-parameters

> **In plain words**
> **Hyper-parameters** are **the dials you set *before* training**: the learning rate, how many epochs, the batch size, the penalty strength, how deep a tree may grow. The model does **not** learn them.
> **Parameters** (the weights) are what the model learns. Hyper-parameters are the **oven temperature and baking time**: not part of the cake, but they decide how it turns out.

**You need first:** 2.18 Objective functions and 2.25 Learning rate.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| parameter | a value the model learns (a weight) |
| hyper-parameter | a setting chosen before training |
| search space | the allowed values for each hyper-parameter |
| log scale | spacing values by powers of 10 (1e-4, 1e-3, …) |
| configuration (config) | one full set of hyper-parameter values |
| default | a library's starting value |
| seed | the starting number for random choices |

### 1. What is it?
Settings that **control the learning process or the model's structure and are set before (not learned by) training**: learning rate, batch size, epochs, regularisation strength, tree depth, number of layers or units, `k` in k-means, the decision threshold, the chunk size in RAG.

### 2. Why does it exist?
The same algorithm with different hyper-parameters can underfit, overfit or diverge. They must be chosen deliberately.

### 3. Detailed explanation
- **Parameters versus hyper-parameters:** parameters (weights) are learned by optimisation; hyper-parameters are chosen by you and tuned (indirectly) using validation performance (2.12).
- **Groups:** *optimisation* (learning rate 2.25, batch size 2.21, epochs 2.22, optimiser, schedule), *regularisation* (λ, dropout rate, weight decay 2.32), *architecture or capacity* (depth, width, polynomial degree), *data and pipeline* (augmentation, class weights, scaling method, sequence length), *decision* (threshold, `k`).
- **Scales matter:** many are best searched on a **log scale** (learning rate 1e-5…1e-1, λ 1e-6…10). Others are categorical (optimiser type) or integers (depth).
- **Importance is uneven:** often one or two (typically the learning rate) dominate, which is why random search beats grid search (2.36).
- **Interactions:** learning rate and batch size, λ and model size, epochs and the learning-rate schedule.
- **Defaults are starting points,** tuned for typical conditions. Record the values used in every experiment, together with the seed and data version.
- **Not hyper-parameters:** the learned weights, activations and running statistics. **Prompt settings** in LLM applications (temperature, top-p, max tokens, number of examples, chunk size, top-k) behave like hyper-parameters and deserve the same discipline (Tiers 17, 20).
- **Choosing hyper-parameters leaks information from the validation set** (2.12); the final test estimate must remain untouched (2.13).

### 4. How does it work?
Define the search space with ranges and scales → choose a tuning method (2.36) → evaluate configurations on validation data → select → retrain → test once.

### 5. Simple example
The oven temperature and baking time: not part of the cake, but they decide how it turns out.

**One tiny model, three configurations.** Fit `y = 2x` with gradient descent on the loss `(w·x − y)²`; here `w` is the *parameter*, the learning rate and the number of steps are *hyper-parameters*:

| learning rate | steps | result |
|---|---|---|
| 0.001 | 20 | `w ≈ 0.08`: too little learning (underfit) |
| 0.1 | 20 | `w ≈ 1.98`: good |
| 1.2 | 20 | `w` explodes (diverged) |

### 6. Technical example
LoRA rank 16, learning rate 2e-4, 3 epochs, 3% warm-up and batch size 32 are the hyper-parameters of a fine-tune.

### 7. Code
**① By hand (plain Python).** The parameter is learned; the hyper-parameters are chosen.

```python
def fit(learning_rate, steps):                         # <- hyper-parameters
    w = 0.0                                            # <- the parameter, learned below
    for _ in range(steps):
        grad = 2 * (w * 1.0 - 2.0) * 1.0               # data: x = 1, y = 2, loss (w*x - y)^2
        w -= learning_rate * grad
    return w

for lr in (0.001, 0.1, 1.2):
    print(f"learning rate {lr:<5} 20 steps -> learned w = {fit(lr, 20):.4g}   (target 2)")
```

```text
learning rate 0.001 20 steps -> learned w = 0.0785   (target 2)
learning rate 0.1   20 steps -> learned w = 1.977   (target 2)
learning rate 1.2   20 steps -> learned w = -1671   (target 2)
```

**② With NumPy.** Why log scales: where do random samples fall?

```python
import numpy as np

rng = np.random.default_rng(0)
linear = rng.uniform(1e-5, 1e-1, 10000)                          # uniform in the raw value
log = 10 ** rng.uniform(-5, -1, 10000)                           # uniform in the exponent
for name, s in (("uniform", linear), ("log-uniform", log)):
    print(f"{name:<11}: share below 1e-3 = {np.mean(s < 1e-3):.3f}   share between 1e-5 and 1e-4 = {np.mean(s < 1e-4):.3f}")
```

```text
uniform    : share below 1e-3 = 0.009   share between 1e-5 and 1e-4 = 0.001
log-uniform: share below 1e-3 = 0.494   share between 1e-5 and 1e-4 = 0.237
```

**③ With PyTorch.** Hyper-parameters live in the optimiser and loader configuration.

```python
import torch

config = {"lr": 3e-4, "weight_decay": 0.01, "batch_size": 32, "epochs": 3}              # recorded for reproducibility
model = torch.nn.Linear(4, 1)
opt = torch.optim.AdamW(model.parameters(), lr=config["lr"], weight_decay=config["weight_decay"])
group = opt.param_groups[0]
print("optimiser settings:", {k: group[k] for k in ("lr", "weight_decay")})
print("number of learned parameters:", sum(p.numel() for p in model.parameters()), "(different thing entirely)")
```

```text
optimiser settings: {'lr': 0.0003, 'weight_decay': 0.01}
number of learned parameters: 5 (different thing entirely)
```

### 9. Enterprise use case
Configurations are stored as code or YAML with versioning, so any model can be reproduced and audited.

### 10. AI engineering connection
Temperature and top-p, retrieval top-k, chunk size and overlap, re-ranker depth, agent step limits: all are tunable hyper-parameters evaluated on a development set.

### 11. Advantages
Direct control of behaviour and cost.

### 12. Limitations
Many interacting settings; the search is expensive; results depend on data and seeds.

### 13. Trade-offs
Wider searches find better configurations but cost compute and risk overfitting the validation set.

### 14. Common mistakes
Tuning on the test set; searching rates on a linear scale; changing many settings at once; not recording configurations; trusting one seed's best result.

### 15. Performance / cost
Each trial is a full (or truncated) training run; budget with early-stopping rules.

### 16. Security
Settings like temperature and max tokens affect safety and cost exposure (Tier 32); cap user-controllable values.

</details>

### 17. Interview explanation
"Hyper-parameters are the settings I choose before training, like learning rate, batch size, regularisation strength and model size, as opposed to parameters that are learned. They usually act on a log scale, a few dominate, and I tune them against a validation set while keeping the test set untouched."

### 18. Rapid-fire answer
Pre-set controls (learning rate, batch size, λ, depth, threshold) tuned on validation; parameters are learned.

### 20. Hands-on exercise
**Goal:** make a validated, loggable configuration.

1. Write a small class (a `dataclass`) with `lr`, `batch_size`, `epochs`.
2. Add a check that rejects `lr <= 0`, `batch_size < 1` and `epochs < 1`.
3. Print a configuration, then try a bad one.

<details>
<summary>Show a solution</summary>

```python
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class Config:
    lr: float
    batch_size: int
    epochs: int

    def __post_init__(self):
        if self.lr <= 0 or self.batch_size < 1 or self.epochs < 1:
            raise ValueError(f"invalid configuration: {self}")

print("good:", asdict(Config(lr=3e-4, batch_size=32, epochs=3)))
try:
    Config(lr=-1, batch_size=32, epochs=3)
except ValueError as e:
    print("rejected:", e)
```

```text
good: {'lr': 0.0003, 'batch_size': 32, 'epochs': 3}
rejected: invalid configuration: Config(lr=-1, batch_size=32, epochs=3)
```

</details>
