# 2.33 Data leakage

**Metadata** — Tier: 2 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: Very high · Hands-on: Very high

> **In plain words**
> **Data leakage** is when **information that wouldn't be available at prediction time sneaks into training or model selection**, making your evaluation score unrealistically good. The model looks excellent in development and collapses in production.
> Like a student who saw the exam questions in advance: 100% on the test, nothing learned.
> **Golden rule:** if the model couldn't know it at prediction time, it must not know it at training time.

**You need first:** 2.10 Dataset construction, 2.11–2.13 (train / validation / test).

### 1. What is it?
When **information that would not be available at prediction time** enters training or model selection, making evaluation scores unrealistically good.

### 2. Why does it matter?
Leakage is one of the most common and costly ML failures: a model looks excellent in development and collapses in production.

### 3. Detailed explanation
**Main forms**
1. **Target leakage:** a feature that is a consequence or proxy of the label (for example "refund issued" when predicting fraud). With data that has *no* signal plus one label-derived feature, the test accuracy is 100% versus an honest 50%.
2. **Preprocessing / selection leakage:** using the whole dataset to fit scalers, impute, select features, tune thresholds or embeddings *before* splitting. With 1,000 pure-noise features, 60 examples and random labels, picking the 20 "best" features on all data and then cross-validating gives about 90% accuracy; picking them *inside* each training fold gives chance (about 50%). This is the "selection bias" trap.
3. **Temporal leakage:** random splits on time-dependent data let the model interpolate between neighbouring moments. A nearest-neighbour model on the time index of a random walk looks great under a random split and terrible under a forward-in-time split.
4. **Group / duplicate leakage:** the same user, document or near-duplicate appears on both sides (2.10).
5. **Benchmark contamination:** test items appear in (pre)training data (2.13).
6. **Tuning leakage:** repeated use of the test set to make decisions (2.12, 2.13).

**Detection:** implausibly high scores; a single feature with outsized importance; performance that vanishes on a later time slice; train/test overlap checks (IDs, hashes, fuzzy matching); ablating suspicious features.

**Prevention:** define the prediction time and allow only information from before it (point-in-time joins); **split first**, then fit all preprocessing on the training part only (pipelines, cross-validation *inside* folds); split by group or time; version and de-duplicate datasets; lock the test set; review features with domain experts.

**Leakage is not overfitting:** overfitting is fitting noise in the training data; leakage corrupts the *evaluation*, so the result is wrong whatever the model.

### 4. How does it work?
Walk the pipeline step by step and ask: "At prediction time, would I have this information? And was it computed using only training data?"

### 5. Simple example
A student who saw the exam questions in advance scores 100% but hasn't learned the subject.

**A leaky feature, by hand.** Predicting loan default with the column `collections_calls_made`. Calls are only made *after* a customer defaults. At training time the column perfectly separates defaulters; at prediction time (before any default) it is always zero. The model learns "calls → default" and is useless in production.

### 6. Technical example
Predicting hospital readmission using a "discharge summary" field that was written after the readmission decision; a RAG evaluation whose gold passages were included in the prompt template.

### 7. Code
**① By hand (plain Python).** Target leakage: a feature copied from the label.

```python
import random

random.seed(0)
rows = [(random.random(), random.randint(0, 1)) for _ in range(1000)]                 # the real feature carries no signal
data = [(x, y, y) for x, y in rows]                                                    # leaky column = the label itself
train, test = data[:700], data[700:]
honest = sum((x > 0.5) == bool(y) for x, y, _ in test) / len(test)
leaky = sum(bool(leak) == bool(y) for _, y, leak in test) / len(test)
print("honest model (real feature only):", round(honest, 3), "(chance)")
print("model using the leaky column    :", leaky, "(looks perfect, useless in production)")
```

```text
honest model (real feature only): 0.433 (chance)
model using the leaky column    : 1.0 (looks perfect, useless in production)
```

**② With NumPy and scikit-learn.** Feature selection before the split: leakage on pure noise.

```python
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
X = rng.normal(0, 1, (60, 1000))                          # 1,000 pure-noise features
y = rng.integers(0, 2, 60)                                # random labels: there is nothing to learn

X_leaky = SelectKBest(f_classif, k=20).fit_transform(X, y)                     # WRONG: selected using ALL the labels
print("selection BEFORE cross-validation (leaky):", round(cross_val_score(LogisticRegression(), X_leaky, y, cv=5).mean(), 3))

pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression())      # RIGHT: selected inside each training fold
print("selection INSIDE each fold (honest)      :", round(cross_val_score(pipe, X, y, cv=5).mean(), 3))
```

```text
selection BEFORE cross-validation (leaky): 0.833
selection INSIDE each fold (honest)      : 0.45
```

**③ With NumPy and scikit-learn.** Temporal leakage: random split versus forward-in-time split.

```python
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.neighbors import KNeighborsRegressor

rng = np.random.default_rng(0)
t = np.arange(400).reshape(-1, 1)
y = np.cumsum(rng.normal(0, 1, 400))                     # a random walk: each value is near its neighbours
model = KNeighborsRegressor(1)

Xa, Xb, ya, yb = train_test_split(t, y, test_size=0.25, random_state=0)
print("random split  MSE:", round(float(np.mean((model.fit(Xa, ya).predict(Xb) - yb) ** 2)), 2), "(looks great: neighbours leak)")
model.fit(t[:300], y[:300])
print("forward split MSE:", round(float(np.mean((model.predict(t[300:]) - y[300:]) ** 2)), 2), "(the honest, much worse, answer)")
```

```text
random split  MSE: 0.99 (looks great: neighbours leak)
forward split MSE: 9.41 (the honest, much worse, answer)
```

### 9. Enterprise use case
Feature stores with point-in-time correctness and CI checks for train/test overlap prevent leakage at scale.

### 10. AI engineering connection
Prompt tuning on the evaluation set, evaluation questions present in the retrieval corpus, test data inside fine-tuning sets, and LLM judges that see reference answers they should not.

### 11. Advantages
(Of understanding it) it is the fastest explanation of "too good to be true" results.

### 12. Limitations
Subtle leaks can pass reviews; no tool catches them all.

### 13. Trade-offs
Strict isolation costs data and engineering effort but protects credibility.

### 14. Common mistakes
Fitting scalers, PCA or encoders on all data; oversampling before splitting; random split of time series; features derived from post-outcome events; reusing validation for final reporting.

### 15. Performance / cost
Pipelines that recompute preprocessing per fold cost more compute: an acceptable price.

### 16. Security
"Leakage" can also mean data exfiltration (sensitive information flowing where it shouldn't): a different problem with the same word, so say which.

### 17. Interview explanation
"Data leakage is when information not available at prediction time reaches training or model selection, so the evaluation is too optimistic. The classic cases are target leakage, preprocessing or feature selection on the full dataset, and random splits on time-ordered or grouped data. I prevent it by splitting first, fitting everything inside the training fold, splitting by time or group, and being suspicious of results that look too good."

### 18. Rapid-fire answer
Information from outside the training/prediction-time boundary inflates scores; split first, fit inside folds, split by time or group.

### 20. Hands-on exercise
**Goal:** reproduce the honest score with a pipeline that includes scaling and selection.

1. Use 60 random-label examples with 1,000 noise features.
2. Build a pipeline: `StandardScaler` → `SelectKBest(k=20)` → `LogisticRegression`.
3. Cross-validate it (5 folds). Is the score near chance?

<details>
<summary>Show a solution</summary>

```python
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

rng = np.random.default_rng(0)
X, y = rng.normal(0, 1, (60, 1000)), rng.integers(0, 2, 60)
pipe = make_pipeline(StandardScaler(), SelectKBest(f_classif, k=20), LogisticRegression())
scores = [cross_val_score(pipe, X, y, cv=5).mean() for _ in range(1)]
print("honest cross-validated accuracy:", round(float(np.mean(scores)), 3), "(chance is 0.5)")
```

```text
honest cross-validated accuracy: 0.467 (chance is 0.5)
```
