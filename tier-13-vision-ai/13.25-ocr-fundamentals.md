### 1. WHAT IS IT?

OCR (optical character recognition) converts text in images into machine-readable characters, classically by detecting text regions, recognising each, and assembling reading order.

### 2. WHY DOES IT EXIST?

Huge amounts of enterprise information live in scans, photos and PDFs without a text layer.

### 3. DETAILED EXPLANATION

**Classic pipeline.** preprocess (deskew, denoise, binarize) -> text detection (boxes/polygons) -> recognition (crop -> string, often CNN/Transformer + CTC or attention decoder) -> layout/reading order -> post-processing (spell-check, dictionaries, regex).

**End-to-end alternatives.** OCR-free models read the image and output text/JSON directly (document VLMs, [13.28 Document-image understanding](13.28-document-image-understanding.md)).

**Metrics.** Character error rate (CER), word error rate (WER); field-level exact match for structured extraction.

**Hard cases.** Low resolution, handwriting, curved text, rotated pages, multilingual mixes, tables.

### 4. HOW DOES IT WORK?

Detect text boxes (a detection problem, [13.26 Object detection](13.26-object-detection.md)) -> crop and normalise height -> recognise sequence -> merge lines/paragraphs -> structured output.

### 5. SIMPLE EXAMPLE

Photograph a receipt; OCR returns lines of text with box coordinates.

### 6. TECHNICAL EXAMPLE

CER = (S + D + I) / N over characters (substitutions, deletions, insertions over reference length). Lab does not ship an OCR engine; the detection geometry (IoU/NMS) reused here is tested in `test_iou_known_values`, `test_nms`.

### 7. CODE

```python
# Character error rate via edit distance (small, self-contained)
def cer(ref, hyp):
    d = list(range(len(hyp) + 1))
    for i, r in enumerate(ref, 1):
        prev, d[0] = d[0], i
        for j, h in enumerate(hyp, 1):
            prev, d[j] = d[j], min(d[j] + 1, d[j - 1] + 1, prev + (r != h))
    return d[-1] / len(ref)
print(round(cer("total 23.40", "tota1 23.4O"), 3))   # 2 substitutions / 11 chars = 0.182
```

### 8. INPUT → PROCESS → OUTPUT

Input: page image. Process: detect, recognize, order. Output: text + coordinates (+ confidences).

### 9. ENTERPRISE USE CASE

Accounts payable: OCR invoices to ERP fields; low-confidence fields route to human review; metrics tracked per vendor template.

### 10. AI ENGINEERING CONNECTION

OCR output feeds RAG over documents (Tier 20); VLMs increasingly replace multi-stage OCR but cost more and can hallucinate characters.

### 11. ADVANTAGES

Deterministic, cheap, auditable per-stage.

### 12. LIMITATIONS

Error compounding, layout sensitivity, language/script coverage, handwriting.

### 13. TRADE-OFFS

Classic pipeline (cheap, auditable) vs VLM (flexible, costly, may hallucinate).

### 14. COMMON MISTAKES

Evaluating only on clean scans; ignoring confidence scores; dropping coordinates needed for audit; treating digits O/0, l/1 confusions as rare.

### 15. PERFORMANCE / COST CONSIDERATIONS

Resolution drives accuracy and latency; a 300 dpi page is large; batch pages.

### 16. SECURITY CONSIDERATIONS

Documents contain PII; keep processing in-region and redact logs; text in images can carry prompt injection into downstream LLMs.

### 17. INTERVIEW EXPLANATION

OCR reads text from images, classically in stages: preprocess, detect text regions, recognise each crop, then order and post-process. Metrics are CER/WER. Modern document VLMs do it end-to-end but can hallucinate characters, so I keep confidences, coordinates and human review for critical fields.

### 18. RAPID-FIRE ANSWER

Detect text regions, recognise characters, assemble reading order.
