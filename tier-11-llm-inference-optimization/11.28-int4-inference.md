### 1. WHAT IS IT?

**INT4 inference** stores weights in 4 bits (16 levels), typically with **group-wise** scales (e.g. groups of 32-128 weights), cutting weight memory about 4x versus FP16.

### 2. WHY DOES IT EXIST?

Local and edge deployment, and cheaper GPU serving, need models that fit in limited memory and decode quickly in a bandwidth-bound regime.

### 3. DETAILED EXPLANATION

- With qmax = 7 the step is ≈ 127/7 ≈ 18x coarser than INT8 over the same range, so a single scale per tensor is unusable; **group scales** are essential.
- Effective bits per weight = `4 + 16/g`: 4.5 for g = 32, 4.25 for g = 64.
- Smarter recipes reduce error: calibration-based rounding (GPTQ), activation-aware scaling (AWQ), and the GGUF "K-quants" family (`REVIEW_REQUIRED`; verify the current state and names).
- Two 4-bit values are packed per byte; kernels unpack on the fly.
- Lab toy: INT4 group-32 gives max logit change 0.158 and top-1 agreement 0.84 versus INT8's 0.97 — a toy, but it shows the accuracy cost is measurable.
[Quantization explorer](interactive/quantization_explorer.html): set bits=4 and vary group size and outlier magnitude.

### 4. HOW DOES IT WORK?

Same as [11.26 Quantization](11.26-quantization.md) with bits=4 and group size g; pack nibbles; kernels dequantize inside the matmul.

### 5. SIMPLE EXAMPLE

Paint-by-numbers with 16 colours instead of 256: fine for most pictures, but gradients show banding unless you pick the palette per region (groups).

### 6. TECHNICAL EXAMPLE

Run an 8B model on a laptop: ≈ 4.5 GB of weights at 4 bits (group 32) versus 16 GB at FP16. Llama-family models in GGUF Q4 variants are popular for this (`REVIEW_REQUIRED` for exact sizes/quality).

### 7. CODE

```python
# run from lab/
import torch
from quant import quant_error

torch.manual_seed(0)
w = torch.randn(256, 256)
for g in (None, 128, 64, 32, 16):
    e = quant_error(w, 4, group=g) if g else quant_error(w, 4)
    bits_eff = 4 + (16 / g if g else 0)
    print(f"group={g!s:5} eff_bits={bits_eff:5.2f} rmse={e['rmse']:.4f}")
```

### 8. INPUT → PROCESS → OUTPUT

```
FP16 ─► groups of g ─► per-group scale ─► 4-bit codes (packed 2/byte) ─► kernel dequant ─► matmul
```

### 9. ENTERPRISE USE CASE

Self-hosting teams quantize to 4 bits to halve GPU count, after A/B evaluating on their own tasks.

### 10. AI ENGINEERING CONNECTION

Basis of most laptop/edge LLM use ([11.29 GGUF](11.29-gguf.md)-[11.31 Ollama](11.31-ollama.md)) and of cost cuts ([11.45 Inference cost](11.45-inference-cost.md)).

### 11. ADVANTAGES

- ~4x smaller than FP16; fastest decode when kernels are good; enables local use.

### 12. LIMITATIONS

- Measurable accuracy loss; sensitive to recipe; harder for small models and reasoning/long-context tasks (`REVIEW_REQUIRED`).

### 13. TRADE-OFFS

Memory and speed vs accuracy; larger groups (cheaper) vs smaller groups (more accurate).

### 14. COMMON MISTAKES

- Using per-tensor scales. - Comparing a 4-bit big model to a FP16 small model without equal eval. - Ignoring KV cache, which may dominate memory at long context.

### 15. PERFORMANCE / COST CONSIDERATIONS

Decode traffic ~4x lower for weights; KV cache is unchanged unless separately quantized, so at long context gains shrink.

### 16. SECURITY CONSIDERATIONS

Third-party quantized models: verify source and hash; re-evaluate safety.

### 17. INTERVIEW EXPLANATION

"INT4 stores weights in 16 levels with a scale per small group, packing two per byte. Decode gets nearly 4x less weight traffic, so tokens come faster and larger models fit locally. The price is accuracy, which is why group scales and calibrated methods like GPTQ or AWQ exist, and why you always evaluate on your own tasks."

### 18. RAPID-FIRE ANSWER

INT4 = 16 levels, group scales, ~4x smaller than FP16, with measurable accuracy cost.
