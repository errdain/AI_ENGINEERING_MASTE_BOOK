### 1. WHAT IS IT?

The **KV cache** stores the key (K) and value (V) vectors that every layer computed for every previous token, so each decode step only computes Q/K/V for the *new* token and attends over the cached ones.

### 2. WHY DOES IT EXIST?

In a causal model, earlier tokens' K and V never change. Recomputing them every step would make per-step work grow with context length and total work O(T^2) in tokens processed. The cache turns that recomputation into memory.

### 3. DETAILED EXPLANATION

- **Why K and V but not Q.** The new token's query is needed only once; later tokens never query earlier tokens' queries, but they do attend to earlier keys and values.
- **Compute vs memory.** The cache converts compute into memory: per step you process one token and read the cache. At long context and large batch, *reading the KV cache* becomes a decode bottleneck alongside the weights.
- **Per sequence (and per beam).** Each sequence owns its cache; beam search needs one per beam ([11.9 Beam search](11.09-beam-search.md)).
- **Size.** `2 x layers x kv_heads x head_dim x tokens x bytes` ([11.17 KV-cache memory calculation](11.17-kv-cache-memory-calculation.md)); GQA/MQA (Tier 8) shrink `kv_heads`.
- **Lab.** `lab/tiny_gpt.py` keeps `(K, V)` per layer shaped `(batch, kv_heads, seq, head_dim)` and concatenates the new K/V each step. The test `test_kv_cache_logits_equal_full_recompute` proves cached incremental logits equal the full forward pass (atol 1e-5); other tests show cached and uncached greedy generation are identical and that the cache uses `n_kv_head`, not `n_head`.

### 4. HOW DOES IT WORK?

1. Prefill: compute K/V for all prompt tokens at every layer and store them.
2. Decode step: for the new token compute q, k, v per layer.
3. Append k, v to that layer's cache (concatenate along the sequence axis).
4. Attention: `softmax(q . K^T / sqrt(d)) . V` over all `S+1` cached positions (no mask needed for a single query at the end, but the position id must be `S`).
5. Pass the output upward; at the end return logits and the updated caches.

### 5. SIMPLE EXAMPLE

Meeting minutes: instead of re-reading the whole transcript before each new remark, you keep notes (K/V) of everything said and only add the new line.

### 6. TECHNICAL EXAMPLE

Measured in the lab: generating 128 tokens took about 146 ms with the cache vs 724 ms without (about 4.9x; 1.7x at 16 tokens, 2.4x at 64; CPU, 2 threads, noisy, relative only). Illustrative 7B-class shape: 128 KiB per token in fp16 with 8 KV heads ([11.17 KV-cache memory calculation](11.17-kv-cache-memory-calculation.md)).

### 7. CODE

```python
import torch
from tiny_gpt import TinyGPT, kv_cache_bytes

torch.manual_seed(0)
m = TinyGPT().eval()
ids = torch.arange(1, 13).unsqueeze(0)
with torch.no_grad():
    full, _ = m(ids)                                  # full forward
    pre, caches = m(ids[:, :-1])                      # prefill all but the last token
    step, caches = m(ids[:, -1:], caches)             # one incremental step with the cache
print(torch.allclose(full[0, -1], step[0, -1], atol=1e-5))   # True: same logits
print(kv_cache_bytes(caches), "bytes")
```

See [`lab/tiny_gpt.py`](lab/tiny_gpt.py) and the tests in [`lab/test_tier11.py`](lab/test_tier11.py).

### 8. INPUT → PROCESS → OUTPUT

```
token + cache(S tokens) -> Q.K^T over S+1 keys, append K/V -> logits + cache(S+1 tokens)
```

### 9. ENTERPRISE USE CASE

Long-document Q&A and multi-turn chat: KV memory, not weights, caps how many concurrent users one GPU serves.

### 10. AI ENGINEERING CONNECTION

Context length limits, prompt caching products, KV-cache quantization, GQA/MQA choices at model design time and long-context serving all revolve around the KV cache.

### 11. ADVANTAGES

Avoids recomputing the prefix; per-step compute is O(context) instead of re-running everything; enables streaming with low ITL.

### 12. LIMITATIONS

Memory grows linearly with context and batch; at long context decode time is partly KV-read-bound; fragmentation if allocated naively ([11.21 PagedAttention](11.21-pagedattention.md)).

### 13. TRADE-OFFS

Compute saved vs memory spent; fewer KV heads or lower KV precision save memory at some quality risk.

### 14. COMMON MISTAKES

- Wrong position ids on the incremental step (the lab test catches this).
- Causal-mask offset errors with a non-empty cache.
- Sharing one cache across beams or users.
- Ignoring that engines also need activation memory, workspace and fragmentation headroom.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cache size is the main limiter of concurrency ([11.44 GPU-memory budgeting](11.44-gpu-memory-budgeting.md)); KV quantization, GQA, paging and prefix caching ([11.18 Prefix caching](11.18-prefix-caching.md)) are the capacity levers.

### 16. SECURITY CONSIDERATIONS

KV memory must be isolated between tenants and cleared or reused safely: a bug that serves another user's cache leaks their prompt.

### 17. INTERVIEW EXPLANATION

"The KV cache stores each layer's keys and values for all previous tokens so that every decode step only computes the new token and attends to the stored ones. It turns quadratic recomputation into linear work, but its memory, two tensors per layer per token, grows with context and batch and usually limits how many users a GPU can serve."

### 18. RAPID-FIRE ANSWER

Cached per-layer K/V of past tokens so each step computes only one token; memory = 2 x layers x kv_heads x head_dim x tokens x bytes.
