### 1. WHAT IS IT?

**Throughput** is the amount of work completed per unit time — for LLM serving usually output tokens per second (system-wide) or requests per second.

### 2. WHY DOES IT EXIST?

It determines how many users a GPU can serve and the cost per token.

### 3. DETAILED EXPLANATION

- System throughput vs per-user speed ([11.15 Tokens per second](11.15-tokens-per-second.md)): batching raises the first and lowers the second.
- Rises with batch until compute-bound or KV-bound; falls off in practice when scheduling or memory pressure bites.
- Measure with a realistic prompt/output length mix; report together with latency percentiles.
![Batching](figures/07_batching_gantt.gif)

*Figure 7 — Look at how continuous batching keeps slots full while static batching idles waiting for the longest sequence; total tokens/s is higher with continuous batching.*

### 4. HOW DOES IT WORK?

tokens/s = batch_size × (1 / step_time). Step time rises slowly with batch while memory-bound, so throughput rises almost linearly.

### 5. SIMPLE EXAMPLE

A bus carrying 40 passengers per trip moves more people per hour than a car, though each person may wait for the full route.

### 6. TECHNICAL EXAMPLE

Lab scheduler: static makespan 269 ticks vs continuous 152 for 24 requests (toy; `lab/benchmark.py`) — about 1.8x throughput from scheduling alone.

### 7. CODE

```python
# run from lab/ : static vs continuous throughput in the toy simulator
import random
from scheduler import Req, simulate, metrics
rnd = random.Random(1)
reqs = [Req(i, i * 2, rnd.randint(10, 40), rnd.choice([5, 10, 40, 60])) for i in range(24)]
for mode in ("static", "continuous"):
    f, r, log = simulate(reqs, 600, 8, mode)
    print(mode, round(metrics(f, log)["throughput"], 2), "tokens/tick")
```

### 8. INPUT → PROCESS → OUTPUT

```
batch size ↑ ─► tokens/step ↑ ─► throughput ↑ (until ridge or KV limit) ─► latency ↑
```

### 9. ENTERPRISE USE CASE
