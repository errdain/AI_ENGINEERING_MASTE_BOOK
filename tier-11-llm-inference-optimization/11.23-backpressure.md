### 1. WHAT IS IT?

**Backpressure** is the signal an overloaded server sends upstream to slow down: bounded queues, HTTP 429/503 with `Retry-After`, and load shedding.

### 2. WHY DOES IT EXIST?

Without it an overloaded server's queue grows without bound, TTFT explodes for **everyone**, and clients time out while the server keeps computing answers nobody will read.

### 3. DETAILED EXPLANATION

- Bound every queue; reject early when full (fail fast beats failing slowly).
- Return 429 (rate limit) or 503 (overloaded) with `Retry-After`; clients should retry with exponential backoff **and jitter** to avoid retry storms.
- Shed low-priority traffic first; cancel generation when the client disconnects.
- Count *tokens*, not requests, when measuring load.
- Admission control ([11.24 Admission control](11.24-admission-control.md)) is the decision that creates the backpressure.

### 4. HOW DOES IT WORK?

Queue depth or estimated wait exceeds a threshold -> reject or defer with a retry hint -> client waits and retries with jitter.

### 5. SIMPLE EXAMPLE

A restaurant with a waiting list: when full, the host says "come back in 30 minutes" instead of seating people in the aisles.

### 6. TECHNICAL EXAMPLE

Lab: with 40 requests arriving one per tick, capacity 200 KV tokens, 4 slots, an unbounded queue finishes all 40 but with mean TTFT 137.5 ticks; a queue bounded at 5 rejects 27 and finishes 13 with mean TTFT 29.

### 7. CODE

```python
from scheduler import Req, simulate, metrics

reqs = [Req(rid=i, arrival=i, prompt=20, out=30) for i in range(40)]
for mq in (None, 5):
    f, rej, log = simulate(reqs, 200, max_batch=4, mode="continuous", max_queue=mq)
    print("max_queue", mq, "done", len(f), "rejected", len(rej), "mean TTFT", metrics(f, log)["mean_ttft"])
```

### 8. INPUT → PROCESS → OUTPUT

```
client -> gateway -> [bounded queue] --full--> 429/503 + Retry-After --> client backoff+jitter
```

### 9. ENTERPRISE USE CASE

LLM gateways return 429 to teams over quota and shed batch work during peaks.

### 10. AI ENGINEERING CONNECTION

Agent loops multiply request rates; the gateway must apply backpressure so one agent cannot starve others.

### 11. ADVANTAGES

Protects latency of admitted work; keeps queues bounded; surfaces overload quickly.

### 12. LIMITATIONS

Rejected requests need a client strategy; thresholds need tuning.

### 13. TRADE-OFFS

Rejecting some work (good) vs accepting everything and failing slowly (bad).

### 14. COMMON MISTAKES

Retrying immediately on 429 (retry storm); counting requests instead of tokens; no cancellation on disconnect.

### 15. PERFORMANCE / COST CONSIDERATIONS

Avoids wasted GPU time on requests whose clients have given up.

### 16. SECURITY CONSIDERATIONS

Quotas and limits are also abuse and denial-of-wallet controls; cap `max_tokens` server-side.

### 17. INTERVIEW EXPLANATION

"Backpressure tells callers to slow down when I'm saturated: bounded queues, 429s or 503s with Retry-After, and client backoff with jitter. Without it queues grow, latency explodes for everyone and the GPU wastes time on abandoned requests."

### 18. RAPID-FIRE ANSWER

Signal overload upstream (bounded queue, 429/503, Retry-After) so load is shed early.
