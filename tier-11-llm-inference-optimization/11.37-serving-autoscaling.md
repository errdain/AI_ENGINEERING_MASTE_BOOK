### 1. WHAT IS IT?

**Serving autoscaling** adds or removes model replicas automatically in response to load.

### 2. WHY DOES IT EXIST?

Traffic varies; fixed capacity is either overloaded at peak or wasteful at night. GPUs are expensive.

### 3. DETAILED EXPLANATION

- Scale on LLM-relevant signals: **queue depth / time-in-queue, tokens in flight, KV-cache utilization, p95 TTFT** — not CPU%; "GPU utilization" is a misleading signal (it reports kernel activity, not saturation of bandwidth or KV).
- Scale on tokens, not requests, because request sizes vary 100x.
- Cold starts ([11.38 Cold starts](11.38-cold-starts.md)) force you to scale *before* the peak: use predictive/scheduled scaling, a warm minimum, and scale-down delay.
- Spillover to hosted API as a pressure valve (data policy permitting).

### 4. HOW DOES IT WORK?

Metrics ─► autoscaler compares with targets ─► adds replicas (wait for warmup) / removes (drain in-flight streams) ─► gateway updates pool.

### 5. SIMPLE EXAMPLE

A taxi company dispatching more cars when waiting time grows, remembering each car takes 10 minutes to arrive.

### 6. TECHNICAL EXAMPLE

Target: p95 queue time < 500 ms (illustrative). Scale up when queue time stays above target for 1-2 minutes; minimum 2 warm replicas; scale down after 15 idle minutes with graceful drain.

### 7. CODE

```python
# Desired replicas from tokens-in-flight (toy HPA-style rule)
import math

def desired_replicas(tokens_in_flight: int, tokens_per_replica: int, current: int, min_r=1, max_r=16) -> int:
    want = math.ceil(tokens_in_flight / tokens_per_replica)
    return max(min_r, min(max_r, want))

print(desired_replicas(180_000, 40_000, 3))   # 5
```

### 8. INPUT → PROCESS → OUTPUT

```
tokens-in-flight, queue time ─► autoscaler ─► replica count ─► warm-up ─► ready ─► gateway
```

### 9. ENTERPRISE USE CASE

A platform team autoscales between 2 and 12 replicas by queue time, with a nightly scale-down and a hosted fallback.

### 10. AI ENGINEERING CONNECTION

Central to cost control ([11.45 Inference cost](11.45-inference-cost.md)) and reliability ([11.46 Serving reliability](11.46-serving-reliability.md)).

### 11. ADVANTAGES

- Matches cost to demand; handles spikes.

### 12. LIMITATIONS

- Slow scale-up (cold starts); thrashing; GPU quota limits.

### 13. TRADE-OFFS

Cost vs SLO risk; aggressive scale-down vs cold start penalties.

### 14. COMMON MISTAKES

- Autoscaling on CPU. - Ignoring cold start. - No max limit (cost explosion). - Killing replicas with active streams.

### 15. PERFORMANCE / COST CONSIDERATIONS

Warm minimum costs 24/7; scale-to-zero saves money but breaks interactive SLOs.

### 16. SECURITY CONSIDERATIONS

Autoscaler/IAM permissions must be least-privilege; cap max replicas to bound runaway cost from abuse.

### 17. INTERVIEW EXPLANATION

"I'd autoscale on queue time or tokens in flight, not CPU, keep a warm minimum because cold starts take minutes, and drain replicas before removing them. A max cap protects against runaway cost."

### 18. RAPID-FIRE ANSWER

Autoscale on queue/tokens/KV pressure with a warm floor and graceful drain.

### 19. INTERVIEW QUESTIONS

**Basic:** Why not CPU%? **Intermediate:** Why scale on tokens? **Advanced:** Design for a 5-minute cold start. **Scenario:** Spike doubles traffic in 1 minute — what protects users? (admission control, spillover, headroom.)
