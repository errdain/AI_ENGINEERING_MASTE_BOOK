### 1. WHAT IS IT?

**Quantization** stores (and sometimes computes) model numbers with fewer bits — for example INT8 or INT4 instead of FP16/BF16. **Weight-only** quantization compresses the weights and keeps activations in floating point; **weight+activation** schemes (and KV-cache quantization) also quantize activations/KV and need low-precision kernels.

### 2. WHY DOES IT EXIST?

Decode is bound by bytes read per token ([11.39 Memory bandwidth](11.39-memory-bandwidth.md)). Fewer bytes per weight means proportionally less traffic, a smaller footprint (fits on fewer or cheaper GPUs) and more room for KV cache ([11.44 GPU-memory budgeting](11.44-gpu-memory-budgeting.md)).

### 3. DETAILED EXPLANATION

- **Symmetric scheme:** `s = max|w| / (2^(b−1) − 1)`, `q = round(w / s)`, `ŵ = q · s`. For in-range values the rounding error is at most `s/2` (checked by the lab tests).
- **Granularity:** per-tensor (one scale), per-channel/row, or per-**group** of g weights (e.g. 32-128). Finer granularity isolates outliers but costs scale storage: effective bits ≈ `b + 16/g` when each group has an fp16 scale (4 + 16/32 = 4.5).
- **Why outliers matter:** one large weight inflates `max|w|`, hence `s`, hence the error of every other weight sharing that scale.
- **Post-training (PTQ) vs quantization-aware training (QAT):** PTQ quantizes a finished model (optionally with calibration data); QAT trains with simulated quantization. Methods such as GPTQ, AWQ and SmoothQuant refine PTQ — `REVIEW_REQUIRED`; verify the current state of each.
- **Speed is not automatic:** dequantize-on-the-fly kernels can erase the gain; real speedups need fused low-precision kernels.
[Open the quantization explorer](interactive/quantization_explorer.html): raise *outlier magnitude* with per-tensor scale, then shrink the group size.

### 4. HOW DOES IT WORK?

1. Choose granularity and bit-width.
2. Compute scale(s) from the weights (and, for some methods, calibration activations).
3. Round to integers and store `q` plus scales.
4. At inference, either dequantize inside the matmul kernel or use integer arithmetic.

### 5. SIMPLE EXAMPLE

Rounding prices to the nearest 10 cents is nearly invisible; rounding to the nearest dollar is visible. If one item costs $10,000 and you pick a single rounding rule from the biggest price, small prices all collapse — hence per-group rules.

### 6. TECHNICAL EXAMPLE

An 8B-parameter model needs ≈ 16 GB in FP16, ≈ 8 GB in INT8 and ≈ 4.5 GB in group-quantized INT4 (arithmetic, ignoring embeddings and overhead). On a memory-bandwidth-bound GPU the lower bound on ITL (weight bytes ÷ bandwidth) falls by roughly the same ratio. A 70B-class model drops from ≈ 140 GB to ≈ 35-40 GB at 4 bits, i.e. from multiple GPUs to one large GPU (`REVIEW_REQUIRED`: real files include embeddings, scales and higher-precision layers).

### 7. CODE

```python
# Lab code: lab/quant.py  (run from the lab/ directory)
import torch
from quant import quantize_sym, dequantize, quant_error

torch.manual_seed(0)
w = torch.randn(64, 128)
w[0, 0] = 40.0                                   # one outlier
for bits in (8, 4):
    t = quant_error(w, bits)                     # per-tensor scale
    r = quant_error(w, bits, dim=0)              # per-row scale
    g = quant_error(w, bits, group=32)           # group-wise scale
    print(bits, "rmse tensor/row/group:", round(t["rmse"], 4), round(r["rmse"], 4), round(g["rmse"], 4))
q, s = quantize_sym(w, 8, dim=0)
assert (w - dequantize(q, s)).abs().max() <= s.max() / 2 + 1e-6   # rounding error <= s/2
```

See [`lab/quant.py`](lab/quant.py) (`QLinear`, `quantize_model`) and its tests in [`lab/test_tier11.py`](lab/test_tier11.py).

### 8. INPUT → PROCESS → OUTPUT

```
FP16 weights ─► pick granularity/bits ─► scales + round ─► int tensors + scales ─► dequant in kernel ─► matmul
```

### 9. ENTERPRISE USE CASE

Fitting a 70B-class model on fewer GPUs, or an 8B model on a laptop, by cutting weights to 4-8 bits — always validated on the company's own evaluation set before rollout.

### 10. AI ENGINEERING CONNECTION

Quantization is the main lever behind local inference ([11.29 GGUF](11.29-gguf.md)-[11.31 Ollama](11.31-ollama.md)) and cost reduction ([11.45 Inference cost](11.45-inference-cost.md)). It is a deployment-time transformation: Tier 10 covers fine-tuning methods such as QLoRA that combine quantized base weights with trainable adapters.

### 11. ADVANTAGES

- 2-4x lower memory and weight traffic.
- Faster decode when kernels are efficient.
- More KV-cache room, hence higher concurrency.

### 12. LIMITATIONS

- Accuracy loss, task-dependent (long-context, reasoning and non-English often degrade first — `REVIEW_REQUIRED`).
- Outliers complicate activation quantization.
- Needs kernel support; not every hardware path accelerates every format.

### 13. TRADE-OFFS

Memory/speed/cost vs accuracy; per-tensor simplicity vs per-group accuracy; PTQ speed vs QAT quality.

### 14. COMMON MISTAKES

- Judging quality by perplexity alone.
- Per-tensor scales with outliers.
- Assuming 4x smaller means 4x faster.
- Quantizing without re-running safety and task evals.

### 15. PERFORMANCE / COST CONSIDERATIONS

Memory ≈ params × bits/8 (+ scales). Prefill is compute-bound, so weight-only quantization helps TTFT little; decode benefits most.

### 16. SECURITY CONSIDERATIONS

Quantized weights from untrusted sources are still untrusted binaries; verify checksums and prefer safe formats. Quantization can shift safety behavior; re-run red-team evals.

### 17. INTERVIEW EXPLANATION

"Quantization stores weights with fewer bits, using a scale per tensor, row or group. Because decode is limited by how many bytes it reads per token, 4-bit weights cut traffic by about 4x and let bigger models fit on smaller hardware. The cost is rounding error, which is worst when outliers inflate the scale, so we use group-wise scales and validate on our own evals."

### 18. RAPID-FIRE ANSWER

Fewer bits per weight means fewer bytes read per token and less memory, at the cost of rounding error; group scales limit the damage from outliers.
