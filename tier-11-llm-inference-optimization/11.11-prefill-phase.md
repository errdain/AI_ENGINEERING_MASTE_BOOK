### 1. WHAT IS IT?

**Prefill** is the first phase of generation: the model processes the entire prompt in **one parallel forward pass**, builds the KV cache for every prompt token and outputs the logits for the first generated token.

### 2. WHY DOES IT EXIST?

The prompt is known in advance, so unlike generation it can be processed in parallel. Doing it as one big pass is far faster than feeding the prompt token by token, and it fills the KV cache ([11.16 KV cache](11.16-kv-cache.md)) that decode will reuse.

### 3. DETAILED EXPLANATION

- Every prompt token is a row in a large matrix multiply, so the GPU is kept busy with FLOPs: prefill is typically **compute-bound** once the prompt is long enough (REVIEW_REQUIRED for short prompts, which can still be memory-bound).
- Cost grows roughly linearly with prompt length (weights x tokens) plus an attention term that grows quadratically with length (Tier 7).
- Prefill drives **TTFT** ([11.13 Time to first token (TTFT)](11.13-time-to-first-token-ttft.md)): TTFT = queue time + prefill time (+ network).
- Long prefills can stall decode steps of other users on the same GPU; *chunked prefill* splits long prompts so decoding continues (engine-specific, REVIEW_REQUIRED). **Prefix caching** ([11.18 Prefix caching](11.18-prefix-caching.md)) skips prefill for a shared prefix.

### 4. HOW DOES IT WORK?

1. Embed all `n` prompt tokens (+ positions).
2. For each layer: project Q/K/V for all `n` tokens; apply the causal mask; store K/V in the cache; run MLP.
3. Take the last position's hidden state, compute logits.
4. Hand the cache and first-token logits to the decode loop ([11.12 Decode phase](11.12-decode-phase.md)).

### 5. SIMPLE EXAMPLE

Reading a whole brief before answering questions: one long, focused read-through, after which each answer is quick.

### 6. TECHNICAL EXAMPLE

A RAG request with a 6,000-token prompt: prefill dominates TTFT; adding retrieved chunks lengthens prefill almost linearly.

### 7. CODE

```python
import torch
from tiny_gpt import TinyGPT, kv_cache_bytes

torch.manual_seed(0)
m = TinyGPT().eval()
prompt = torch.arange(1, 33).unsqueeze(0)          # 32 tokens at once
with torch.no_grad():
    logits, caches = m(prompt)                     # PREFILL
print(logits.shape, "cache bytes:", kv_cache_bytes(caches))   # logits for all 32 positions; only the last is used
```

See [`lab/tiny_gpt.py`](lab/tiny_gpt.py).

### 8. INPUT → PROCESS → OUTPUT

```
prompt (n tokens) --one parallel pass--> KV cache (n entries) + logits(last) --> first token
```

### 9. ENTERPRISE USE CASE

Capacity planning for RAG and agent workloads is mostly prefill planning: prompt length distributions set the TTFT SLO and the GPU count.

### 10. AI ENGINEERING CONNECTION

RAG (Tier 20) and long system prompts inflate prefill; prefix caching and prompt ordering (static first) cut it.

### 11. ADVANTAGES

Highly parallel and compute-efficient; one pass regardless of prompt length (within memory limits).

### 12. LIMITATIONS

Long prompts raise TTFT; prefill of long prompts blocks other work unless chunked; memory for activations grows with prompt length.

### 13. TRADE-OFFS

Short TTFT for one user vs interference with other users' decode steps (chunking trades TTFT against ITL jitter).

### 14. COMMON MISTAKES

Quoting TTFT without queue time; assuming prefill is memory-bound like decode; putting changing content (timestamps) at the front of the prompt, which defeats prefix caching.

### 15. PERFORMANCE / COST CONSIDERATIONS

Compute cost of prefill is paid once per request, scales with prompt tokens; hosted APIs bill input tokens separately (prices REVIEW_REQUIRED).

### 16. SECURITY CONSIDERATIONS

Prompts may contain secrets; do not share prefill caches across tenants without isolation ([11.18 Prefix caching](11.18-prefix-caching.md)).

### 17. INTERVIEW EXPLANATION

"Prefill is the first pass where the model reads the whole prompt in parallel and builds the KV cache. It's compute-heavy and sets time-to-first-token. After that, decode produces one token at a time. To cut TTFT I shorten or cache the prompt, or use faster compute; to improve ITL I look at memory bandwidth instead."

### 18. RAPID-FIRE ANSWER

Prefill = parallel pass over the prompt that builds the KV cache and yields the first token; compute-bound; determines TTFT.
