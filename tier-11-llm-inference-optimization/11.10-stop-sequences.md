### 1. WHAT IS IT?

**Stop sequences** are token-id sequences or strings (EOS, `"\n\nUser:"`, a closing brace or code fence) that end generation as soon as they appear.

### 2. WHY DOES IT EXIST?

Without them the model keeps going until the token cap, wasting time and money and producing text no one wanted.

### 3. DETAILED EXPLANATION

- Match on **tokens or decoded text across token boundaries**: a stop string may span two tokens.
- Streaming consumers must **hold back** text that could be the start of a stop string, and never emit the stop string itself.
- Always combine with `max_new_tokens`; log the **finish reason** (stop, length, error, cancelled).

### 4. HOW DOES IT WORK?

After each generated token, check whether the end of the output equals a stop sequence; if so, truncate and stop.

### 5. SIMPLE EXAMPLE

A "stop reading at the full stop" rule for an audio book.

### 6. TECHNICAL EXAMPLE

A chat template ends assistant turns with EOS; a legacy prompt format uses `"\n\nUser:"` as a stop so the model does not write the user's next line.

### 7. CODE

```python
from decoding import hit_stop_sequence

print(hit_stop_sequence([5, 7, 9], [[7, 9]]))     # True

def stream_with_stops(chunks, stops):
    """Yield text safely: hold back a tail that could start a stop string."""
    buf, keep = "", max(len(s) for s in stops) - 1
    for c in chunks:
        buf += c
        for s in stops:
            i = buf.find(s)
            if i != -1:
                yield buf[:i]; return          # cut at the stop string
        if len(buf) > keep:
            yield buf[:len(buf) - keep]; buf = buf[len(buf) - keep:]
    yield buf

print("".join(stream_with_stops(["Hel", "lo\n", "\nUs", "er: hi"], ["\n\nUser:"])))   # Hello
```

### 8. INPUT → PROCESS → OUTPUT

```
token stream -> check suffix vs stops -> (match) cut + finish_reason=stop  |  (no match) emit safe prefix
```

### 9. ENTERPRISE USE CASE

JSON-extraction pipelines stop at the closing brace; agent frameworks stop at tool-call delimiters.

### 10. AI ENGINEERING CONNECTION

Prompt formats and chat templates (Tier 10) rely on stop/EOS tokens; agents rely on clean stops to parse tool calls.

### 11. ADVANTAGES

Saves tokens, latency and cost; makes output parseable.

### 12. LIMITATIONS

String matching across token boundaries is easy to get wrong; a stop that never fires means rambling to the cap.

### 13. TRADE-OFFS

Early termination vs the risk of cutting legitimate text that contains the stop string.

### 14. COMMON MISTAKES

Not holding back partial matches while streaming; no token cap as backstop; not recording finish reasons so truncation goes unnoticed.

### 15. PERFORMANCE / COST CONSIDERATIONS

A missing stop is a direct cost leak: every extra token is paid for.

### 16. SECURITY CONSIDERATIONS

Hold-back bugs can leak system-prompt fragments to the user; user-controlled stop strings should be length-limited.

### 17. INTERVIEW EXPLANATION

"A stop sequence ends generation when a given token pattern shows up. The gotchas are matching across token boundaries, not streaming a half-matched stop string to the client, and always having a max-token cap and a finish-reason metric as a backstop."

### 18. RAPID-FIRE ANSWER

Strings/token patterns that end generation; pair with a token cap and finish-reason logging.
