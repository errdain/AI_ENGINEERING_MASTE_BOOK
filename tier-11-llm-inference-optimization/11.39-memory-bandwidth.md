### 1. WHAT IS IT?

**Memory bandwidth** is the rate (bytes/second) at which a processor can read from or write to its main memory (GPU HBM, CPU DRAM). For LLM decode it is the dominant performance limit.

### 2. WHY DOES IT EXIST?

Each decode step must read every weight (and the KV cache) from memory but does only ~2 FLOPs per weight per sequence. The arithmetic units wait for data.

### 3. DETAILED EXPLANATION

- **Lower bound on inter-token latency** (batch 1): `ITL ≥ (weight bytes + KV bytes read) ÷ bandwidth`. Example (illustrative, `REVIEW_REQUIRED`): 16 GB ÷ 2 TB/s = 8 ms → at most 125 tok/s per user.
- Hence quantization ([11.26 Quantization](11.26-quantization.md)) speeds decode; so do GQA/MQA and KV quantization (smaller KV reads).
- Peak bandwidth is rarely reached; real kernels achieve a fraction.
- CPUs: dual-channel DRAM gives tens of GB/s, so a 4.5 GB model yields about 10 tok/s (illustrative) — why local decode is slow without GPUs.
[Explore bandwidth and bytes/param](interactive/roofline_latency.html).

### 4. HOW DOES IT WORK?

Per step: read weights W from HBM → compute on a handful of tokens → write activations/KV. Time ≈ max(bytes/bandwidth, FLOPs/peak), usually the first term in decode.

### 5. SIMPLE EXAMPLE

A chef (compute) who is fast but must fetch every ingredient from a far-away pantry (memory): the trip, not the chopping, sets the pace.

### 6. TECHNICAL EXAMPLE

Same 8B FP16 model on two chips: 1 TB/s → ≥ 16 ms/token; 3 TB/s → ≥ 5.3 ms/token (illustrative). Bandwidth, not FLOPs, differentiates them for decode.

### 7. CODE

```python
def min_itl_ms(weight_gb: float, bandwidth_gb_s: float) -> float:
    """Lower bound on batch-1 decode latency per token (ignores KV reads and overhead)."""
    return weight_gb / bandwidth_gb_s * 1e3

print(min_itl_ms(16, 2000), "ms ->", 1000 / min_itl_ms(16, 2000), "tok/s")   # 8.0 ms -> 125 tok/s
print(min_itl_ms(4.5, 2000))                                                    # int4 weights: 2.25 ms
```

### 8. INPUT → PROCESS → OUTPUT

```
weights in HBM ─(bandwidth)─► compute units ─► one token per sequence per step
```

### 13. TRADE-OFFS

Spend on bandwidth (HBM) vs on FLOPs.

### 14. COMMON MISTAKES

- Buying FLOPs for a decode-bound workload. - Quoting peak bandwidth as achieved.

### 15. PERFORMANCE / COST CONSIDERATIONS

Latency floor and quantization gain both follow from bytes/bandwidth.

### 16. SECURITY CONSIDERATIONS

No direct security issue; note timing side channels from cache sharing are covered in [11.18 Prefix caching](11.18-prefix-caching.md).

### 17. INTERVIEW EXPLANATION

"Decode reads all the weights for each token but does little math per byte, so it's memory-bandwidth-bound. Time per token is at least weight bytes divided by bandwidth, which is why 4-bit weights and batching help."

### 18. RAPID-FIRE ANSWER

Decode is limited by bytes/bandwidth; ITL ≥ weight bytes ÷ bandwidth.
