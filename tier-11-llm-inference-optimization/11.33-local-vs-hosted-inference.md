### 1. WHAT IS IT?

**Local vs hosted inference** is the decision of running models on hardware you control (laptop, on-prem, your cloud GPUs) or calling a provider's API.

### 2. WHY DOES IT EXIST?

Cost, privacy, latency, control and capability all trade off; the choice is architectural, not ideological.

### 3. DETAILED EXPLANATION

| | Local / self-hosted | Hosted API |
|---|---|---|
| Data control | full | provider terms apply |
| Cost shape | fixed GPUs (capex or reserved) — cheap at high steady utilization | pay per token — cheap at low/spiky volume |
| Latency control | you tune it | provider's variability |
| Ops burden | you own scaling, upgrades, reliability | provider |
| Model choice | open-weight models only | proprietary frontier models |

Decide with **utilization × volume × data constraints**. A hybrid (self-host the steady base load, spill to hosted at peaks or for hard prompts) is common.

### 4. HOW DOES IT WORK?

1. Estimate tokens/day in and out. 2. Compute self-host cost per 1M tokens at realistic utilization ([11.45 Inference cost](11.45-inference-cost.md)). 3. Compare with hosted price (`REVIEW_REQUIRED`: changes often). 4. Add ops and risk cost. 5. Check data/regulatory constraints. 6. Pilot, measure, re-check quarterly.

### 5. SIMPLE EXAMPLE

Owning a car vs taking taxis: owning is cheap per trip if you drive daily, taxis win for occasional trips.

### 6. TECHNICAL EXAMPLE

A bank keeps customer data on-prem with a self-hosted model, and routes non-sensitive, hard reasoning prompts to a hosted frontier API with a gateway enforcing policy.

### 7. CODE

```python
# Break-even volume: self-host monthly fixed cost vs per-token hosted price (all inputs ASSUMED)
def breakeven_tokens_per_month(gpu_cost_month: float, hosted_per_m: float, selfhost_per_m_marginal: float = 0.0) -> float:
    """Tokens/month above which self-hosting is cheaper (in millions)."""
    return gpu_cost_month / (hosted_per_m - selfhost_per_m_marginal)

# $2.00/GPU-hour assumed -> ~ $1,460/month for one GPU; hosted at assumed $1 per 1M tokens
print(round(breakeven_tokens_per_month(2.0 * 730, 1.0), 0), "million tokens/month")   # 1460
```
Both prices are `REVIEW_REQUIRED` assumptions, not quotes; real analysis also needs utilization and ops cost.

volume + data rules + latency SLO ─► cost model ─► {hosted | self-host | hybrid} ─► pilot ─► monitor

### 9. ENTERPRISE USE CASE

Regulated industries (healthcare, finance, government) often self-host for data residency; startups usually begin hosted.

### 10. AI ENGINEERING CONNECTION

Gateway abstraction (OpenAI-compatible APIs) lets applications switch; evaluation parity is required before switching models.

### 11. ADVANTAGES

- Self-host: control, privacy, predictable cost at scale. Hosted: zero ops, frontier quality, elasticity.

### 12. LIMITATIONS

- Self-host: ops burden, capacity planning, weaker open models for some tasks. Hosted: data sharing, rate limits, price changes, vendor dependence.

### 13. TRADE-OFFS

Capex/fixed cost vs pay-per-use; control vs convenience; quality vs privacy.

### 14. COMMON MISTAKES

- Ignoring utilization and ops cost. - Comparing price without quality parity. - No fallback plan.

### 15. PERFORMANCE / COST CONSIDERATIONS

Utilization dominates self-host economics; hosted bills input and output tokens separately.

### 16. SECURITY CONSIDERATIONS

Review provider data-retention and training terms; self-hosting needs your own patching, authN/authZ and network isolation.

### 17. INTERVIEW EXPLANATION

"I'd decide using volume, utilization and data constraints. Hosted is cheap and quick at low or spiky volume and gives frontier models; self-hosting wins at high steady utilization or when data can't leave. Often a hybrid with a gateway is best, and I'd re-check the numbers quarterly."

### 18. RAPID-FIRE ANSWER

Hosted: no ops and pay-per-token; self-hosted: control and cheaper at high steady utilization; hybrid is common.
