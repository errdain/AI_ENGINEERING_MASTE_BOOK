### 1. WHAT IS IT?

**Repetition, frequency and presence penalties** lower the logits of tokens that already appeared in the output, to discourage loops and repeated phrasing.

### 2. WHY DOES IT EXIST?

Greedy and low-temperature decoding often fall into repetitive loops; penalties push the model to say something new.

### 3. DETAILED EXPLANATION

- **Repetition penalty** (CTRL-style): for tokens already seen, divide a positive logit (multiply a negative one) by a factor `> 1`.
- **Frequency penalty:** subtract `alpha x count` from the logit (grows with every occurrence).
- **Presence penalty:** subtract a flat `beta` once the token has been seen.
- The additive forms follow OpenAI-style definitions (REVIEW_REQUIRED per provider).
- Too strong a penalty makes the model avoid legitimately repeated tokens: names, JSON keys, code identifiers, punctuation.

[Try the penalty in the decoding explorer](interactive/decoding_explorer.html).

### 4. HOW DOES IT WORK?

Collect the generated token ids, count them, and edit the logit of each seen id before temperature and filters. The lab applies this first (see [11.3 Decoding overview](11.03-decoding-overview.md)).

### 5. SIMPLE EXAMPLE

A teacher who says "you already used that word, try another" every time you repeat yourself, even when repeating a name is correct.

### 6. TECHNICAL EXAMPLE

A summariser repeats one sentence until the token cap; a mild repetition penalty ends the loop. A code generator with a strong penalty starts renaming variables inconsistently.

### 7. CODE

```python
import torch
from decoding import repetition_penalty

z = torch.tensor([2.0, 1.0, -1.0, 0.5])
print(repetition_penalty(z, generated=[0, 2, 2], penalty=1.2, freq=0.1, presence=0.1))
```

See [`lab/decoding.py`](lab/decoding.py).

### 8. INPUT → PROCESS → OUTPUT

```
generated ids -> counts -> adjust logits of seen tokens -> (temperature/filters) -> sample
```

### 9. ENTERPRISE USE CASE

Used on open-ended generation features; avoided or kept minimal on code, JSON and tool calls.

### 10. AI ENGINEERING CONNECTION

Interacts with structured output: JSON keys must repeat, so heavy penalties can break parsing.

### 11. ADVANTAGES

Cheap loop breaker with no retraining.

### 12. LIMITATIONS

Penalises legitimate repeats; blunt (token-level, not semantic); parameters are provider-specific.

### 13. TRADE-OFFS

Less repetition vs the risk of breaking names and structured formats.

### 14. COMMON MISTAKES

Penalising with a large factor on code/JSON; assuming a number tuned on one provider transfers to another; counting prompt tokens when the API counts only generated ones (REVIEW_REQUIRED).

### 15. PERFORMANCE / COST CONSIDERATIONS

Negligible per-step cost.

### 16. SECURITY CONSIDERATIONS

Not a security control.

### 17. INTERVIEW EXPLANATION

"Repetition penalties lower the logits of tokens already used so the model doesn't loop. Frequency scales with how often a token appeared, presence is a one-time flat cut. They're blunt, so on code or JSON I keep them off or small because those formats repeat tokens legitimately."

### 18. RAPID-FIRE ANSWER

Lower seen-token logits (multiplicative or additive) to reduce loops, at the risk of hurting legitimate repetition.

### 19. INTERVIEW QUESTIONS

**Basic.** Why use a repetition penalty? **Intermediate.** Frequency vs presence penalty? **Advanced.** Why handle positive and negative logits differently in the CTRL form? (Dividing a negative logit would raise it.) **Scenario.** JSON output keys keep changing after a "less repetitive" tweak; cause?
