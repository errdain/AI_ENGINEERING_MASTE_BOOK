### 1. WHAT IS IT?

**Autoregressive inference** is how a decoder-only language model generates text: it models `P(x_t | x_<t)`, produces a distribution over the next token, picks one token with a decoding rule, appends it to the input, and repeats until a stop condition (EOS token, stop sequence, `max_new_tokens`).

### 2. WHY DOES IT EXIST?

Text is a sequence and each token depends on the ones before it. Factorising the joint probability as a product of next-token probabilities lets one network, trained with next-token prediction (Tier 9), generate arbitrary-length text. The price is that generation is **inherently sequential**: token *t+1* cannot be computed before token *t* is known.

### 3. DETAILED EXPLANATION

- **Training vs inference.** In training, all positions of a sequence are processed in parallel (teacher forcing, with a causal mask from Tier 7). In inference, the future tokens do not exist yet, so only the prompt can be processed in parallel; the output is produced one token per forward pass.
- **Latency model.** Output length `N` means `N` forward passes. End-to-end latency is roughly `TTFT + (N - 1) x ITL` ([11.13 Time to first token (TTFT)](11.13-time-to-first-token-ttft.md), [11.14 Inter-token latency](11.14-inter-token-latency.md)). You cannot parallelise across the tokens of one answer.
- **Two phases.** The first pass over the prompt is the *prefill* ([11.11 Prefill phase](11.11-prefill-phase.md)); every later pass is a *decode* step ([11.12 Decode phase](11.12-decode-phase.md)).
- **Why serving is hard.** Because each user's loop is sequential and memory-bound, serving systems exist mostly to interleave many users' loops on one GPU ([11.19 Batching](11.19-batching.md), [11.20 Continuous batching](11.20-continuous-batching.md)).

### 4. HOW DOES IT WORK?

1. Tokenise the prompt (Tier 6) into ids `x_1..x_n`.
2. **Prefill:** run the model on all `n` ids at once; keep the per-layer K/V ([11.16 KV cache](11.16-kv-cache.md)); take the logits at the *last* position only ([11.2 Logits](11.02-logits.md)).
3. Apply a decoding rule ([11.3 Decoding overview](11.03-decoding-overview.md)) to the logits to choose `x_{n+1}`.
4. **Decode:** feed only `x_{n+1}` (plus the cache) to the model, get the next logits, choose `x_{n+2}`.
5. Stop when a stop token/sequence appears ([11.10 Stop sequences](11.10-stop-sequences.md)) or the token cap is reached.

### 5. SIMPLE EXAMPLE

Predictive text on a phone: it suggests one word, you accept it, and only then can it suggest the next. It cannot write the last word of the sentence before the first.

### 6. TECHNICAL EXAMPLE

`lab/tiny_gpt.py` + `lab/decoding.py`: `generate` calls the model once on the whole prompt (prefill) and then once per new token with a single-id input and the cache. Measured on the lab model, generating 128 tokens with the cache took about 146 ms vs about 724 ms without (CPU, noisy, relative only, see the tier README results table).

### 7. CODE

Minimal loop (runs against `lab/`, see [`lab/decoding.py`](lab/decoding.py)):

```python
import torch
from tiny_gpt import TinyGPT

torch.manual_seed(0)
model = TinyGPT().eval()
ids = [1, 2, 3, 4]                                  # "prompt"
with torch.no_grad():
    logits, caches = model(torch.tensor([ids]))     # prefill: logits for EVERY prompt position
    for _ in range(5):
        nxt = int(logits[0, -1].argmax())           # greedy rule on the LAST position only
        ids.append(nxt)
        logits, caches = model(torch.tensor([[nxt]]), caches)   # decode: one token + cache
print(ids)
```

### 8. INPUT → PROCESS → OUTPUT

```
prompt ids --prefill--> KV cache + logits(last) --decoding rule--> token --append--> (feed back, 1 token) --> ... --> stop
```

### 9. ENTERPRISE USE CASE

Every chat, copilot and code-completion product is an autoregressive loop; capacity planning, SLOs (p95 TTFT / ITL) and per-token pricing all follow from its sequential nature.

### 10. AI ENGINEERING CONNECTION

Streaming UIs, token-based billing, reasoning models (long outputs mean long latency and cost), structured-output decoding and speculative decoding ([11.25 Speculative decoding](11.25-speculative-decoding.md)) are all consequences of or workarounds for this loop.

### 11. ADVANTAGES

Simple, flexible (any length, any stop rule), supports streaming (users see tokens as they are produced), one model serves many tasks.

### 12. LIMITATIONS

Per-token latency cannot be parallelised for a single request; long outputs are slow and costly; errors can compound because each sampled token conditions the next (exposure effects, REVIEW_REQUIRED on how strongly this matters in practice).

### 13. TRADE-OFFS

Sequential generation buys flexibility at the cost of speed. Non-autoregressive or diffusion-style text generation exists but is not the mainstream for LLMs (REVIEW_REQUIRED).

### 14. COMMON MISTAKES

- Assuming an output token costs the same time as an input token (output tokens are sequential and far more expensive in time).
- Forgetting that prefill yields logits for all prompt positions but only the last is used to generate.
- Re-running the full prefix every step (no KV cache), which makes generation quadratic in total work.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost scales with `output tokens x per-step time`. The per-step time is dominated by reading weights from memory ([11.39 Memory bandwidth](11.39-memory-bandwidth.md)); levers are batching, quantization, caching and speculative decoding.

### 16. SECURITY CONSIDERATIONS

Generation loops need a hard `max_new_tokens` cap enforced server-side; an uncapped loop is a denial-of-wallet vector. Exposing per-step logits through an API leaks information about the model.

### 17. INTERVIEW EXPLANATION

"An LLM generates text one token at a time. It runs the whole network, reads the probability distribution for the next token, picks one, appends it, and runs again. That is why the first token costs a big parallel pass over the prompt and every later token costs a smaller sequential pass. The trade-off is flexibility versus speed: we cannot parallelise across the tokens of one answer, so we batch across users instead."

### 18. RAPID-FIRE ANSWER

One forward pass per generated token; each token depends on the previous one, so output length sets latency.

### 19. INTERVIEW QUESTIONS

**Basic.** What does autoregressive mean? (Each token is predicted from all previous tokens.) Why is generation sequential? (The next input is the previous output.)

**Intermediate.** How is inference different from training in terms of parallelism? (Training parallelises over positions; inference only over the prompt.) What is the latency formula? (`TTFT + (N-1) x ITL`.)

**Advanced.** Why does the KV cache change the total work from quadratic to linear in the number of generated tokens? (Cached K/V of earlier tokens are never recomputed.)

**Scenario.** A product's answers got 3x longer after a prompt change; what happens to latency and cost? (Both grow roughly linearly with output tokens; check `max_tokens` and finish reasons.)
