### 1. WHAT IS IT?

A **cold start** is the delay before a newly started serving instance can answer its first request: node scheduling, pulling container and weights (tens of GB), loading into GPU memory, warming kernels and compiling graphs.

### 2. WHY DOES IT EXIST?

LLM weights are huge, so spin-up takes minutes rather than seconds, which affects autoscaling and incident recovery.

### 3. DETAILED EXPLANATION

- Components: GPU node provisioning, image pull, weight download, weight load to VRAM, CUDA graph/kernel warm-up (`REVIEW_REQUIRED` per engine), first-request effects.
- Load time ≈ weight bytes ÷ min(storage/network bandwidth, PCIe bandwidth): 16 GB at 2 GB/s ≈ 8 s from fast local NVMe, but minutes over a slow network (illustrative).
- Mitigations: warm minimum replicas, pre-pulled images, weights on local NVMe or shared cache, smaller/quantized weights, memory-mapped loading, scale ahead of demand, spillover.

### 4. HOW DOES IT WORK?

Schedule pod ─► pull image ─► fetch weights ─► load to GPU ─► warm-up ─► pass readiness ─► receive traffic.

### 5. SIMPLE EXAMPLE

Starting a cold oven: the food is ready quickly once it's hot, but heating takes time.

### 6. TECHNICAL EXAMPLE

A new replica needs 140 GB of weights over a 1 GB/s link: ≈ 140 s just to download, before loading (illustrative).

### 7. CODE

```python
def cold_start_seconds(weight_gb: float, link_gb_s: float, overhead_s: float = 30.0) -> float:
    """Rough lower bound: transfer time plus fixed overhead (scheduling, warm-up)."""
    return weight_gb / link_gb_s + overhead_s

print(cold_start_seconds(140, 1.0), cold_start_seconds(16, 2.0))   # 170.0 38.0
```

### 8. INPUT → PROCESS → OUTPUT

```
scale-up trigger ─► node ─► image ─► weights ─► GPU load ─► warm-up ─► READY
```

### 9. ENTERPRISE USE CASE

Services keep warm pools and image caches; batch jobs tolerate cold starts, interactive chat does not.

### 10. AI ENGINEERING CONNECTION

Constrains autoscaling policy ([11.37 Serving autoscaling](11.37-serving-autoscaling.md)) and recovery time in reliability planning ([11.46 Serving reliability](11.46-serving-reliability.md)).

### 11. ADVANTAGES

(Mitigations) Faster scale-out and recovery with caching and warm pools.

### 12. LIMITATIONS

Cold starts cannot be eliminated, only hidden; warm capacity costs money.

### 13. TRADE-OFFS

Cost of warm capacity vs latency risk; scale-to-zero savings vs first-request delay.

### 14. COMMON MISTAKES

- Ignoring cold start in scaling targets. - Readiness probe that passes before warm-up. - Pulling weights from the public internet at startup.

### 15. PERFORMANCE / COST CONSIDERATIONS

Idle warm replicas cost GPU-hours; measure time-to-ready as an SLO.

### 16. SECURITY CONSIDERATIONS

Weights must be fetched from trusted, access-controlled storage; pin digests.

### 17. INTERVIEW EXPLANATION

"Cold start is the minutes it takes a new replica to download and load tens of GB of weights and warm up. I'd keep a warm floor, cache weights locally, scale ahead of demand, and make readiness checks reflect a real generation."

### 18. RAPID-FIRE ANSWER

Cold start = scheduling + weight transfer + load + warm-up, often minutes; hide it with warm capacity.
