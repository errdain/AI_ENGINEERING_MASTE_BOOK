# 4.19 Mixed-precision training

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: Very high · Hands-on: High
Prerequisites: 4.16 FP32, 4.17 FP16, 4.18 BF16 · Leads to: 4.24 GPU memory, 4.34 FSDP/ZeRO

> **In plain words**
> **Mixed precision** means using **cheap 16-bit numbers where it is safe and 32-bit numbers where it matters**. The heavy matrix multiplications run in 16-bit (fast, half the memory). The sensitive parts (the master copy of the weights, sums, softmax, the loss) stay in 32-bit. You get most of the speed and memory savings with almost no loss in accuracy.

**You need first:** 4.16 FP32, 4.17 FP16, 4.18 BF16.

> **Figure 4.19-1 — which parts run in which precision**
>
> ```mermaid
> flowchart LR
>     M["FP32 master weights"] -->|"cast to 16-bit"| W["16-bit weights"]
>     W --> F["forward + backward<br/>matmuls in 16-bit"]
>     F --> G["16-bit gradients"]
>     G -->|"cast to FP32<br/>(+ unscale if FP16)"| U["FP32 optimizer update"]
>     U --> M
> ```
>
> *How to read it:* the loop on the left keeps the true weights in FP32. Each step makes a 16-bit copy for the fast math, then brings the gradients back to FP32 so the tiny update lands on the full-precision weights. In FP16 there is one extra step: loss scaling before backward and unscaling after (4.17).

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| master weights | the FP32 copy that receives the updates |
| autocast | automatic per-operation choice of precision |
| loss scaling | multiplying the loss so FP16 gradients do not underflow |
| `GradScaler` | PyTorch's dynamic loss scaler (FP16 only) |
| accumulate in FP32 | sums inside a matmul use more bits |
| unscale | divide gradients by the scale before clipping/stepping |
| skip step | ignore an update whose gradients had `inf`/NaN |

### 1. What is it?
Training with a mix of 16-bit and 32-bit formats: forward/backward matmuls in FP16 or BF16, with FP32 for master weights, optimizer state, and numerically sensitive operations (Micikevicius et al., 2017).

### 2. Why does it exist?
16-bit arithmetic is faster (tensor cores) and halves activation and gradient memory, but full 16-bit training loses small updates and can overflow. The mix keeps accuracy.

### 3. Detailed explanation
- **Why master weights?** A weight of 1.0 plus an update of 0.0001 stays 1.0 in FP16 (precision 0.001); in FP32 it becomes 1.0001. Updates accumulate only in FP32 (code ②).
- **Autocast** decides per operation: matmuls and convolutions go to 16-bit; softmax, log, normalization, losses and reductions stay FP32.
- **FP16 recipe:** `autocast(float16)` + `GradScaler`: scale the loss, backward, unscale, clip (4.15), step, update the scale. If any gradient is `inf`/NaN, skip the step and halve the scale.
- **BF16 recipe:** `autocast(bfloat16)`, no scaler.
- **Order with clipping and accumulation:** unscale first, then clip, then step; with accumulation, call the scaler once per optimizer step (4.14).
- **Memory saved:** activations (the biggest part for large batches) are halved; weights are stored twice (FP32 + 16-bit) so the *weights* part can even grow slightly (4.24).
- **Speed:** depends on hardware; tensor cores give large matmul speedups; small models may see none.
- **Checks:** compare the loss curve with the FP32 run on a short run; they should be close.
- **Pitfalls:** custom ops that produce `inf` in 16-bit; `exp` of big numbers; very small `ε` in normalization (1e-8 underflows in FP16, use 1e-5 or compute in FP32).
- **Newer variants:** FP8 training (Hopper-class GPUs) uses per-tensor scaling (REVIEW_REQUIRED).

### 4. How does it work?
Keep FP32 weights; per step cast to 16-bit, run forward/backward there, move gradients to FP32, update the FP32 weights.

### 5. Simple example
A chef who does rough chopping fast with a big knife (16-bit) but weighs the spices exactly on a precise scale (32-bit).

**By hand.** Master weight 1.0, update 0.0001 per step for 1,000 steps. FP32 master: `1.0 + 0.1 = 1.1`. Pure FP16: each addition rounds back to 1.0 → stays 1.0.

### 6. Technical example
A typical LLM step: `with torch.autocast("cuda", dtype=torch.bfloat16): loss = model(x, y)`; `loss.backward()`; clip; `optimizer.step()`.

### 7. Code
**① By hand (plain Python).** Dynamic loss scaling logic.

```python
scale, good_steps = 1024.0, 0
grads_per_step = [1e-3, 2e-3, float("inf"), 1e-3, 2e-3, 1e-3]       # step 3 overflowed in 16-bit
for i, g in enumerate(grads_per_step, 1):
    if g == float("inf"):
        scale /= 2; good_steps = 0                                    # skip the update, halve the scale
        print(f"step {i}: overflow -> skip the update, scale becomes {scale}")
    else:
        good_steps += 1
        print(f"step {i}: ok, update applied with gradient {g}")
```

```text
step 1: ok, update applied with gradient 0.001
step 2: ok, update applied with gradient 0.002
step 3: overflow -> skip the update, scale becomes 512.0
step 4: ok, update applied with gradient 0.001
step 5: ok, update applied with gradient 0.002
step 6: ok, update applied with gradient 0.001
```

**② With NumPy.** Why master weights matter: tiny updates vanish in 16-bit.

```python
import numpy as np

updates = 1000
w16 = np.float16(1.0)
w32 = np.float32(1.0)
for _ in range(updates):
    w16 = np.float16(w16 + np.float16(0.0001))                        # pure FP16 weights
    w32 = np.float32(w32 + np.float32(0.0001))                        # FP32 master weights
print(f"after {updates} updates of +0.0001:   FP16-only weight = {float(w16):.4f}   FP32 master weight = {float(w32):.4f}")
```

```text
after 1000 updates of +0.0001:   FP16-only weight = 1.0000   FP32 master weight = 1.1000
```

**③ With PyTorch.** An autocast training loop on CPU with BF16 (FP32 master weights, 16-bit activations).

```python
import torch

torch.manual_seed(0)
model = torch.nn.Sequential(torch.nn.Linear(16, 64), torch.nn.ReLU(), torch.nn.Linear(64, 1))
opt = torch.optim.AdamW(model.parameters(), lr=1e-2)
X = torch.randn(256, 16); y = X[:, :1] * 2

first = last = None
for step in range(60):
    opt.zero_grad()
    with torch.autocast("cpu", dtype=torch.bfloat16):
        pred = model(X)                                                # matmuls in bfloat16
    loss = torch.nn.functional.mse_loss(pred.float(), y)               # loss in float32
    loss.backward(); opt.step()
    first = first if first is not None else loss.item()
    last = loss.item()
print("activation dtype under autocast:", pred.dtype)
print("master weight dtype            :", model[0].weight.dtype)
print(f"loss {first:.3f} -> {last:.3f}")
scaler = torch.amp.GradScaler("cuda", enabled=torch.cuda.is_available())
print("GradScaler enabled (only needed for FP16 on a GPU):", scaler.is_enabled())
```

```text
activation dtype under autocast: torch.bfloat16
master weight dtype            : torch.float32
loss 4.158 -> 0.012
GradScaler enabled (only needed for FP16 on a GPU): False
```

### 9. Enterprise use case
Cuts GPU hours and memory for training and fine-tuning; a standard flag in every training framework.

### 10. AI engineering connection
All large-model training; combined with sharded optimizers (4.34) and checkpointing (4.41).

### 11. Advantages
Roughly 2× memory on activations, large speedups on tensor cores, near-FP32 accuracy.

### 12. Limitations
Complexity; potential NaNs; hardware-dependent speedups.

### 13. Trade-offs
FP16 (more precision, needs scaling) versus BF16 (simpler, coarser).

### 14. Common mistakes
Casting the whole model with `.half()` and training; clipping scaled gradients; stepping the scaler per micro-batch; computing the loss in 16-bit; using `ε = 1e-8` in FP16.

### 15. Performance / cost
Expect 1.5–3× throughput on suitable GPUs for large models (REVIEW_REQUIRED).

### 16. Security
No direct issue; numeric differences can change borderline model behaviour.

### 17. Interview explanation
"Mixed precision runs matmuls in 16-bit for speed and memory but keeps FP32 master weights, optimizer state and reductions. With FP16 I need dynamic loss scaling to avoid underflow; with BF16 the range is enough so I just use autocast. I unscale before clipping and verify the loss curve against FP32."

### 18. Rapid-fire answer
16-bit compute + FP32 master weights; FP16 needs loss scaling, BF16 doesn't; autocast keeps sensitive ops in FP32.
