# 4.23 CPU vs GPU

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: High
Prerequisites: 3.8 Weighted sum, 4.2 Forward pass · Leads to: 4.24 GPU memory, 4.25 Profiling, 4.30 Distributed training

> **In plain words**
> A **CPU** has a few very clever cores that do one thing after another quickly. A **GPU** has thousands of simpler cores that do **the same operation on a huge pile of numbers at once**. Neural networks are mostly big matrix multiplications, which are exactly that kind of work, so GPUs are far faster for training. But moving data between the two is slow, so you keep as much as possible on the GPU.

**You need first:** 3.8 Weighted sum, 4.2 Forward pass.

> *How to read it:* the CPU (top left) has a handful of cores with big caches, good for varied, sequential logic. The GPU (right) packs thousands of simple cores that run the same instruction on lots of data. Data must be copied from RAM to GPU memory first; that copy is a bottleneck to avoid in a training loop.

### 1. What is it?
Two kinds of processors. Training code picks a **device** and puts the model and data on it: `model.to("cuda")`.

### 2. Why does it exist?
Deep learning needs trillions of multiply-adds. A GPU performs them in parallel; a CPU performs far fewer at a time. The speed difference is often 10–100× for large matrices.

### 3. Detailed explanation
- **Matrix multiplication** is the workload: every output element is an independent dot product, so thousands can run simultaneously.
- **When the CPU wins:** tiny models and tiny batches (GPU launch overhead dominates), lots of branching logic, preprocessing (tokenization, image decoding), and small inference jobs.
- **Data movement:** copying between RAM and GPU memory is slow (PCIe is ~10–30× slower than GPU memory). Avoid per-step `.cpu()` / `.item()` calls, which also force the GPU to wait (4.25).
- **Device placement rules:** model and input tensors must be on the same device or PyTorch raises an error (code ③).
- **Choosing the device in code:** `"cuda"` if available, else `"mps"` (Apple), else `"cpu"`.
- **Asynchrony.** GPU kernels run asynchronously; timing code must synchronize (`torch.cuda.synchronize()`) or it measures nothing (4.25).
- **Vectorization on CPU too:** NumPy/PyTorch use optimized, SIMD, multi-threaded routines; a Python `for` loop is ~100× slower (code ②).
- **Other accelerators:** TPUs, NPUs, custom chips; same ideas, different software stacks.
- **Cost.** GPU-hours are the main training expense; utilization (the share of time the GPU is busy) is a key metric (4.25).
- **Multiple devices:** data parallel, tensor parallel, pipeline parallel (4.30–4.34).

### 4. How does it work?
Allocate tensors on a device; the framework launches the right kernels there; results stay on that device until you copy them.

### 5. Simple example
A single master chef (CPU) versus a kitchen of a thousand line cooks (GPU): the chef can cook any dish alone, but to make a thousand identical sandwiches the line wins, once the ingredients are on the counter.

**By hand.** A matrix product of two `1000×1000` matrices needs `2×1000³ = 2×10⁹` operations. A CPU doing ~10¹¹ per second takes ~20 ms; a GPU doing ~10¹⁴ per second takes ~20 µs (plus overhead).

### 6. Technical example
`device = "cuda" if torch.cuda.is_available() else "cpu"; model.to(device); batch = batch.to(device, non_blocking=True)`.

**② With NumPy.** Vectorized math versus a Python loop (the same idea as CPU versus GPU).

```python
import time
import numpy as np

n = 120
A, B = np.random.default_rng(0).normal(size=(2, n, n))

def loop_matmul(A, B):
    C = [[0.0] * n for _ in range(n)]
    for i in range(n):
        for j in range(n):
            C[i][j] = sum(A[i][k] * B[k][j] for k in range(n))
    return C

t = time.perf_counter(); C1 = loop_matmul(A.tolist(), B.tolist()); t_loop = time.perf_counter() - t
t = time.perf_counter(); C2 = A @ B; t_vec = time.perf_counter() - t
print("results agree:", np.allclose(np.array(C1), C2))
print("vectorized is at least 50x faster than the Python loop:", t_loop / t_vec > 50)
```

```text
results agree: True
vectorized is at least 50x faster than the Python loop: True
```

```python
import torch

device = "cuda" if torch.cuda.is_available() else ("mps" if torch.backends.mps.is_available() else "cpu")
print("cuda available:", torch.cuda.is_available(), "   cuda devices:", torch.cuda.device_count())

x = torch.randn(3, 4)
print("model and input on the same device -> output on:", model(x).device)
```

### 9. Enterprise use case
GPU capacity planning (type, count, utilization) drives training budgets; inference may run on cheaper accelerators or CPUs.

### 10. AI engineering connection
Model size is bounded by device memory (4.24); LLM serving optimizes GPU utilization with batching (Tier 11).

### 11. Advantages
GPUs: orders-of-magnitude speedup on dense math.

### 12. Limitations
Memory limits; transfer overhead; poor on branchy code; cost and availability.

### 13. Trade-offs
CPU: flexible, cheap, slow for big models. GPU: fast, expensive, memory-limited.

### 14. Common mistakes
Moving the model but not the data; `.item()` in the inner loop; timing GPU code without synchronizing; data loading on the main thread starving the GPU; tiny batches on a big GPU.

### 15. Performance / cost
Target high GPU utilization: overlap data loading (4.26), use larger batches, mixed precision (4.19).

### 16. Security
Shared GPUs can leak data through leftover memory or side channels; use isolation in multi-tenant settings.

</details>

### 17. Interview explanation
"Neural nets are dominated by matrix multiplications, which parallelize across thousands of GPU cores, so GPUs are far faster than CPUs for training. The costs are limited device memory and slow host-device transfers, so I keep data and the model on the device, avoid per-step synchronizing calls, and profile utilization."

### 18. Rapid-fire answer
GPU = thousands of simple cores for parallel matmul; CPU = few strong cores; keep data on-device; avoid `.item()` and copies in the loop.

### 20. Hands-on exercise
**Goal:** find where vectorization starts to pay off.

1. For sizes 128 and 1024 (and, for fun, 2) time a Python-loop dot product and `np.dot` over 2,000 repetitions.
2. Print the ratio for each size.

<details>
<summary>Show a solution</summary>

```python
import time
import numpy as np

rng = np.random.default_rng(0)
for n in (128, 1024):
    a, b = rng.normal(size=(2, n))
    al, bl = a.tolist(), b.tolist()
    t = time.perf_counter()
    for _ in range(2000):
        sum(x * y for x, y in zip(al, bl))
    t_loop = time.perf_counter() - t
    t = time.perf_counter()
    for _ in range(2000):
        np.dot(a, b)
    t_np = time.perf_counter() - t
    print(f"n = {n:>4}: numpy faster than the loop? {t_np < t_loop}")
```

```text
n =  128: numpy faster than the loop? True
n = 1024: numpy faster than the loop? True
```

For very small arrays (try n = 2) the call overhead can dominate and the answer may flip, which is the same reason small models don't benefit from a GPU.
</details>
