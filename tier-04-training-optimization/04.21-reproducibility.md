# 4.21 Reproducibility

> **In plain words**
> **Reproducibility** means that running the same training again gives the **same result**, or at least a result you can explain. It is harder than it sounds: randomness is everywhere (initial weights, data order, dropout), and even **adding the same numbers in a different order** can change the last digits. To reproduce a run you must fix the seeds, pin the software versions and record the configuration.

**You need first:** 4.20 Checkpoints.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| reproducible | same inputs and settings give the same outputs |
| deterministic | no randomness at all in the computation |
| seed | starting value of a random-number generator |
| run-to-run variance | differences between runs with different seeds |

### 1. What is it?
The ability to re-run an experiment and get the same (or statistically equivalent) result, via controlled randomness, pinned software and recorded configuration.

### 2. Why does it exist?
Without it you can't debug (a bug that disappears), compare (is model B really better than A, or just luckier?), audit, or hand work to a colleague.

### 3. Detailed explanation
- **Levels.** *Bit-exact* reproduction needs the same hardware, libraries, seeds and deterministic kernels. *Statistical* reproduction means the results agree within the normal seed-to-seed variation. Aim for the second; use the first when debugging.
- **Seed everything** that is random: Python, NumPy, PyTorch CPU and GPU, data-loader workers (4.22).
- **Non-associative floating-point:** `(a + b) + c ≠ a + (b + c)` in the last digits. Parallel reductions add in different orders on different runs or hardware (code ①②).
- **Non-deterministic GPU ops:** atomic adds in some kernels; `torch.use_deterministic_algorithms(True)` forces deterministic ones (some become slower or raise errors) (code ③).
- **Data order and augmentation** must be seeded and logged. A changed dataset version silently changes results.
- **Record:** code commit, config file, library versions (`pip freeze`), hardware, seed, data version (checkpoint metadata, 4.20).
- **Seed variance is a baseline.** Run 3–5 seeds and report mean ± spread; a 0.3-point "improvement" smaller than the spread is noise (2.20, 2.21).
- **Resume exactness.** Saving RNG states in the checkpoint lets a resumed run follow the same random stream (4.20).
- **Distributed training:** different world sizes change the reduction order and data sharding; exact reproduction across cluster sizes is usually not expected.
- **LLM sampling** adds more randomness (temperature, top-p); set a seed or temperature 0 for tests (Tier 11).

### 4. How does it work?
Fix the seeds; pin versions; request deterministic algorithms; log the config; compare runs by tolerance, not by `==`.

### 5. Simple example
A recipe that works only on Tuesdays: if you didn't write down the oven temperature and brand of flour, you can't bake it again.

**By hand.** Adding `0.1 + 0.2 + 0.3` left-to-right gives 0.6000000000000001; adding `0.3 + 0.2 + 0.1` gives 0.6. Same numbers, different order, different last digit.

### 7. Code
**① By hand (plain Python).** Order changes the last digits.

```python
a, b, c = 0.1, 0.2, 0.3
print("(0.1 + 0.2) + 0.3 =", (a + b) + c)
print("0.1 + (0.2 + 0.3) =", a + (b + c))

print("1e16 + 1 - 1e16 =", 1e16 + 1.0 - 1e16, "   1e16 - 1e16 + 1 =", 1e16 - 1e16 + 1.0, "(the 1 is lost in the first order)")
```

```text
(0.1 + 0.2) + 0.3 = 0.6000000000000001
0.1 + (0.2 + 0.3) = 0.6
1e16 + 1 - 1e16 = 0.0    1e16 - 1e16 + 1 = 1.0 (the 1 is lost in the first order)
```

**② With NumPy.** Seeds make randomness repeatable; summation order changes float32 results.

```python
import numpy as np

a = np.random.default_rng(42).normal(size=5)
b = np.random.default_rng(42).normal(size=5)
c = np.random.default_rng(43).normal(size=5)
print("same seed -> identical:", np.array_equal(a, b), "   different seed -> identical:", np.array_equal(a, c))

x = np.random.default_rng(0).normal(size=1_000_000).astype(np.float32)
s1 = x.sum()
s2 = x[np.random.default_rng(1).permutation(x.size)].sum()
print("float32 sum, original order vs shuffled:", s1, s2, "-> equal?", s1 == s2)
print("relative difference:", f"{abs(float(s1) - float(s2)) / abs(float(s1)):.1e}")
```

```text
same seed -> identical: True    different seed -> identical: False
float32 sum, original order vs shuffled: 998.57056 998.57074 -> equal? False
relative difference: 1.8e-07
```

**③ With PyTorch.** Same seed, same run; the deterministic switch.

```python
import torch

def run(seed):
    torch.manual_seed(seed)
    model = torch.nn.Sequential(torch.nn.Linear(4, 8), torch.nn.Dropout(0.3), torch.nn.Linear(8, 1))
    X = torch.randn(64, 4); y = X.sum(dim=1, keepdim=True)
    opt = torch.optim.SGD(model.parameters(), lr=0.05)
    for _ in range(50):
        opt.zero_grad(); torch.nn.functional.mse_loss(model(X), y).backward(); opt.step()
    return torch.nn.functional.mse_loss(model(X), y).item()

print("seed 7 twice :", run(7) == run(7), "(identical)")
print("seed 7 vs 8  :", run(7) == run(8), "(different)")
torch.use_deterministic_algorithms(True)
print("deterministic algorithms enabled:", torch.are_deterministic_algorithms_enabled())
```

```text
seed 7 twice : True (identical)
seed 7 vs 8  : False (different)
deterministic algorithms enabled: True
```

### 9. Enterprise use case
Regulated settings require being able to retrain a model and explain differences; reproducibility records support audits.

### 10. AI engineering connection
Experiment tracking, evaluation harnesses and regression tests for model changes all depend on controlled randomness.

### 11. Advantages
Debuggable, comparable, auditable.

### 12. Limitations
Exact reproducibility can cost speed; impossible across different hardware.

### 13. Trade-offs
Deterministic kernels versus throughput.

### 14. Common mistakes
Seeding only one library; comparing floats with `==`; ignoring data changes; judging models on a single seed; forgetting dataloader workers.

### 15. Performance / cost
Deterministic algorithms can slow training by tens of percent in some operations (REVIEW_REQUIRED).

### 16. Security
Logged configs and environment dumps may contain secrets; scrub them.

### 20. Hands-on exercise
**Goal:** measure seed-to-seed variation.

1. Train the code ③ model for seeds 0–9.
2. Print the mean and standard deviation of the final loss.
3. How large would an "improvement" need to be to stand out?

<details>
<summary>Show a solution</summary>

```python
import numpy as np
import torch

def run(seed):
    torch.manual_seed(seed)
    model = torch.nn.Sequential(torch.nn.Linear(4, 8), torch.nn.Dropout(0.3), torch.nn.Linear(8, 1))
    X = torch.randn(64, 4); y = X.sum(dim=1, keepdim=True)
    opt = torch.optim.SGD(model.parameters(), lr=0.05)
    for _ in range(50):
        opt.zero_grad(); torch.nn.functional.mse_loss(model(X), y).backward(); opt.step()
    return torch.nn.functional.mse_loss(model(X), y).item()

losses = np.array([run(s) for s in range(10)])
print(f"final loss over 10 seeds: mean {losses.mean():.3f}, std {losses.std():.3f}, range {losses.min():.3f}-{losses.max():.3f}")
print(f"differences smaller than about {2 * losses.std():.3f} are not distinguishable from noise")
```

```text
final loss over 10 seeds: mean 0.380, std 0.142, range 0.197-0.649
differences smaller than about 0.284 are not distinguishable from noise
```
