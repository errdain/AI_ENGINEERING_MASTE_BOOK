# 4.39 Loss debugging

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: Very high · Hands-on: Very high
Prerequisites: 4.35 Training curves, 4.36 Validation curves, 4.37 Gradient monitoring · Leads to: Tier 15 experiment practice

> **In plain words**
> When a model does not learn, the cause is usually not the fancy architecture but a **small bug**: wrong labels, a missing `zero_grad`, a bad learning rate, data and labels misaligned. **Loss debugging** is a short list of **cheap tests** that find these bugs quickly: check the starting loss, make the model **overfit one tiny batch**, check that the **labels are right**, and change **one thing at a time**. Run these before spending GPU days.

**You need first:** 4.35 Training curves, 4.36 Validation curves, 4.37 Gradient monitoring.

> **Figure 4.39-1 — the debugging ladder**
>
> ```mermaid
> flowchart TB
>     A["1. initial loss ≈ ln K ?"] --> B["2. overfit ONE batch to ~0 ?"]
>     B --> C["3. gradients flow to every layer?"]
>     C --> D["4. labels / data aligned? (look at samples)"]
>     D --> E["5. learning rate sweep"]
>     E --> F["6. add complexity back, one change at a time"]
> ```
>
> *How to read it:* work top to bottom; stop at the first step that fails, because later steps can't succeed until it does. Step 2 is the most powerful: a correct pipeline can always memorize 8 examples. If it can't, there is a bug, not a lack of capacity.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| sanity check | a quick test whose answer you already know |
| overfit a batch | train on a handful of examples until the loss is ≈ 0 |
| `ln K` | expected starting cross-entropy for K balanced classes |
| label alignment | each input is paired with its own label |
| ablation | remove or change one component to see its effect |
| baseline | a trivial model to compare with |
| shuffled-label test | training on random labels as a control |

### 1. What is it?
A systematic checklist for finding why a loss is high, flat, noisy or wrong, based on small, fast experiments (Karpathy's "recipe for training neural networks" popularized several of these; REVIEW_REQUIRED).

### 2. Why does it exist?
Neural-network bugs rarely crash. The code runs and produces a bad number. Without a checklist, people tune hyperparameters for days around a data bug.

### 3. Detailed explanation
1. **Check the starting loss.** With K balanced classes it should be about `ln K` (4.3). Much higher → bad initialization or label/logit mismatch; much lower → leakage or labels visible in the input.
2. **Overfit a tiny batch** (say 8 examples, no regularization, no augmentation). Loss should go to ≈ 0 within a few hundred steps. If not: a bug in the loss, the labels, the optimizer, the learning rate, or `zero_grad`/`step` (4.1).
3. **Verify gradients** reach every layer and parameters are in the optimizer (4.37, 4.29).
4. **Look at the data.** Print and view samples with their labels; check shapes, dtypes, normalization and that shuffling keeps inputs and labels together.
5. **Check the label pipeline.** Labels off by one, mapped to wrong classes, or all the same (class imbalance → loss stuck at the prior).
6. **Shuffle test:** train on random labels; the loss should stay near chance on held-out data. If it magically improves, there is leakage.
7. **Learning-rate sweep** over orders of magnitude (4.35).
8. **Compare to a baseline:** predict the majority class or use a linear model. The network must beat it.
9. **Regularization on last:** add dropout, weight decay, augmentation only after step 2 works.
10. **Change one thing at a time**, and keep notes; fix the seed (4.22) so differences are real.
11. **Loss goes down but the metric doesn't:** the loss may not match the metric, or the validation set differs (4.36).
12. **Train/eval mismatch:** forgetting `eval()` or normalizing differently at test time.
13. **Mixed precision problems:** compare with FP32 (4.38).

### 4. How does it work?
Use small experiments with known outcomes to localize the failure: data, model, loss, optimization, or evaluation.

### 5. Simple example
Debugging a car that won't start: check the battery (starting loss), then try a short test drive in a parking lot (overfit one batch), before changing the engine.

**By hand.** 10 classes → expected starting loss `ln 10 = 2.30`. If you see 11.5 the output scale is wrong (huge logits); if you see 0.1, the labels may be leaking.

### 6. Technical example
Fine-tuning an LLM and the loss never drops below 4: tokenization of the labels is shifted by one position, so the model is asked to predict the wrong token.

### 7. Code
**① By hand (plain Python).** The expected starting loss, and what bad values mean.

```python
import math

for K in (2, 10, 1000):
    print(f"{K:>4} classes: expected starting loss ln K = {math.log(K):.3f}")

def read_start(loss, K):
    expected = math.log(K)
    if loss > 2 * expected:
        return "far above ln K: output scale or labels are wrong"
    if loss < 0.5 * expected:
        return "far below ln K: labels may leak into the inputs"
    return "close to ln K: fine"

for observed in (11.5, 2.3, 0.1):
    print(f"observed {observed}: {read_start(observed, 10)}")
```

```text
   2 classes: expected starting loss ln K = 0.693
  10 classes: expected starting loss ln K = 2.303
1000 classes: expected starting loss ln K = 6.908
observed 11.5: far above ln K: output scale or labels are wrong
observed 2.3: close to ln K: fine
observed 0.1: far below ln K: labels may leak into the inputs
```

**② With NumPy.** The shuffled-label control: no pattern, no learning.

```python
import numpy as np

rng = np.random.default_rng(0)
X = rng.normal(size=(2000, 5))
y_true = (X[:, 0] + X[:, 1] > 0).astype(float)
y_random = rng.permutation(y_true)
split = 1000

def fit_eval(y):
    A = np.c_[X, np.ones(len(X))]
    w = np.linalg.lstsq(A[:split], y[:split], rcond=None)[0]
    return ((A[split:] @ w > 0.5) == y[split:]).mean()

print("held-out accuracy with real labels    :", round(fit_eval(y_true), 3))
print("held-out accuracy with shuffled labels:", round(fit_eval(y_random), 3), "(about 0.5: nothing to learn)")
```

```text
held-out accuracy with real labels    : 0.975
held-out accuracy with shuffled labels: 0.499 (about 0.5: nothing to learn)
```

**③ With PyTorch.** Overfit one batch, with a working loop and three classic bugs.

```python
import torch
from torch import nn

def run(bug=None, steps=300):
    torch.manual_seed(0)
    X = torch.randn(8, 10); y = torch.randint(0, 3, (8,))
    net = nn.Sequential(nn.Linear(10, 32), nn.ReLU(), nn.Linear(32, 3))
    opt = torch.optim.Adam(net.parameters(), lr=1e-2 if bug != "lr" else 1e-8)
    for _ in range(steps):
        if bug != "zero_grad":
            opt.zero_grad()
        out = net(X)
        if bug == "softmax_first":
            out = torch.softmax(out, dim=1)
        loss = nn.functional.cross_entropy(out, y)
        if bug == "no_backward":
            pass
        else:
            loss.backward()
        opt.step()
    return loss.item()

for bug in (None, "lr", "no_backward", "softmax_first"):
    print(f"{str(bug or 'correct pipeline'):<17}: loss on the single batch after 300 steps = {run(bug):.4f}")
```

```text
correct pipeline : loss on the single batch after 300 steps = 0.0002
lr               : loss on the single batch after 300 steps = 1.0772
no_backward      : loss on the single batch after 300 steps = 1.0772
softmax_first    : loss on the single batch after 300 steps = 0.5515
```

### 9. Enterprise use case
A written debugging protocol shortens incident time on stalled training jobs and prevents wasted compute.

### 10. AI engineering connection
Fine-tuning and RLHF pipelines have many data/label alignment steps where off-by-one and masking bugs hide.

### 11. Advantages
Cheap, systematic, finds most bugs.

### 12. Limitations
Doesn't tell you whether the architecture is best; some failures are subtle (data quality).

### 13. Trade-offs
Time spent on checks versus time on blind tuning: checks win.

### 14. Common mistakes
Tuning the architecture before overfitting one batch; changing many things at once; trusting validation without looking at data; leaving regularization on while testing overfit; not fixing seeds.

### 15. Performance / cost
Run checks on tiny data on CPU in seconds.

### 16. Security
Debug prints of real data can expose sensitive records; use synthetic samples when possible.

### 20. Hands-on exercise
**Goal:** find an off-by-one label bug.

1. Create inputs where the class is `x₀ > 0` (2 classes).
2. Train a small network with the correct labels and with labels shifted by one example (`y.roll(1)`).
3. Compare the final accuracy.

<details>
<summary>Show a solution</summary>

```python
import torch
from torch import nn

def train(shift):
    torch.manual_seed(0)
    X = torch.randn(1000, 4); y = (X[:, 0] > 0).long()
    if shift:
        y = y.roll(1)                                                # labels misaligned by one example
    net = nn.Sequential(nn.Linear(4, 16), nn.ReLU(), nn.Linear(16, 2))
    opt = torch.optim.Adam(net.parameters(), lr=0.02)
    for _ in range(200):
        opt.zero_grad(); nn.functional.cross_entropy(net(X), y).backward(); opt.step()
    return (net(X).argmax(1) == y).float().mean().item()

print(f"correct labels   : accuracy {train(False):.2f}")
print(f"labels shifted   : accuracy {train(True):.2f}  (far below 1.0: the inputs and labels no longer belong together, so the network can only partly memorize)")
```

```text
correct labels   : accuracy 1.00
labels shifted   : accuracy 0.60  (far below 1.0: the inputs and labels no longer belong together, so the network can only partly memorize)
```
