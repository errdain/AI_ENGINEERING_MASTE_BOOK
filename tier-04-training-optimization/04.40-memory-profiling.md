# 4.40 Memory profiling

**Metadata** — Tier: 4 · Phase: 1 · Priority: P1 · Difficulty: 3/5 · Interview: High · Hands-on: High
Prerequisites: 4.24 GPU memory, 4.25 Profiling · Leads to: 4.41 Gradient checkpointing

> **In plain words**
> 4.24 taught you to *estimate* memory with arithmetic. **Memory profiling** *measures* what actually happens: how much memory is used at each moment, which operation allocates it, and **whether memory keeps growing** step after step (a leak). The most common leak in PyTorch is keeping the loss tensor (with its whole graph) instead of its number.

**You need first:** 4.24 GPU memory, 4.25 Profiling.

> **Figure 4.40-1 — memory over one training step**
>
> ```mermaid
> flowchart LR
>     A["start: weights"] --> B["forward: activations pile up ↑"]
>     B --> C["backward: gradients appear,<br/>activations freed ↓"]
>     C --> D["optimizer step:<br/>state allocated (first step) ↑"]
>     D --> E["zero_grad: gradients freed ↓"]
> ```
>
> *How to read it:* memory rises through the forward pass, reaches its **peak** near the start of backward, falls as activations are consumed, and has a second bump at the first optimizer step. The *peak* is what causes out-of-memory errors, not the average.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| peak memory | the highest usage during a step |
| allocated / reserved | memory in use / memory held by the allocator |
| memory leak | usage that grows every step |
| snapshot | a recorded list of live allocations |
| `tracemalloc` | Python's built-in memory tracer |
| `profile_memory` | PyTorch profiler option to record tensor memory |
| retain | a reference that keeps a graph alive |

### 1. What is it?
Recording memory use over time and by operation, using `torch.cuda.memory_*` (GPU), `torch.profiler(profile_memory=True)`, or `tracemalloc` (CPU/Python).

### 2. Why does it exist?
OOM errors, slow fragmentation and creeping leaks are hard to diagnose by estimation. Measurements show which tensors or stages dominate.

### 3. Detailed explanation
- **GPU counters:** `torch.cuda.memory_allocated()` (now), `max_memory_allocated()` (peak), `memory_reserved()` (held by the caching allocator), `reset_peak_memory_stats()`. `torch.cuda.memory_summary()` prints a table.
- **Memory snapshots:** `torch.cuda.memory._record_memory_history()` and `_dump_snapshot` produce a timeline you can inspect in a viewer to see which Python line allocated each block (REVIEW_REQUIRED: API names change).
- **Profiler:** `torch.profiler.profile(profile_memory=True)` reports per-operator memory (works on CPU too; code ③).
- **The classic leak:** appending `loss` (a tensor with `grad_fn`) to a list keeps each step's graph alive; use `loss.item()` or `loss.detach()` (code ③).
- **Other leaks:** accumulating activations in a list, hooks that keep references, caching tensors in globals, growing Python containers, un-freed CUDA graphs.
- **Peak vs steady:** compare memory after step 1, 2 and 10. The first step is higher (lazy optimizer state, cuDNN workspaces); after that it should be flat.
- **Fragmentation:** `reserved` far above `allocated` may mean fragmentation; setting `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` can help (REVIEW_REQUIRED).
- **Tools:** `nvidia-smi` (whole process), `torch.cuda.mem_get_info()`, TensorBoard profiler memory view, Memray/tracemalloc for CPU Python memory.
- **Reduce:** smaller micro-batch, accumulation (4.14), BF16 (4.18), checkpointing (4.41), sharding (4.34), freeing references, `del` and `set_to_none`.
- **Measure at realistic sizes.** Small tests hide the scaling.
- **Peak occurs in a specific place;** find it before optimizing.

### 4. How does it work?
Reset peak counters, run N steps, read allocated/peak, repeat across stages and batch sizes; use a profiler/snapshot to attribute memory to operations.

### 5. Simple example
A bathtub with the tap running (activations) and the drain opening later (backward). The overflow happens at the highest water level, and a slow drip that never drains (a leak) overflows it eventually.

**By hand.** A list of 1,000 retained 4 MB graphs would use 4 GB; storing `loss.item()` instead keeps 1,000 floats (8 KB).

### 6. Technical example
Print `torch.cuda.max_memory_allocated() / 1e9` after the first step and after step 100; if it grows, something is retained.

### 7. Code
**① By hand (plain Python).** Python-level memory tracing with `tracemalloc`.

```python
import tracemalloc

tracemalloc.start()
leaky = []
for i in range(5):
    leaky.append([0.0] * 100_000)                                     # each list ~0.8 MB
    current, peak = tracemalloc.get_traced_memory()
    print(f"after {i + 1} appends: {current / 1e6:.1f} MB")
tracemalloc.stop()
print("memory grows linearly while the list keeps references -> a leak pattern")
```

```text
after 1 appends: 0.8 MB
after 2 appends: 1.6 MB
after 3 appends: 2.4 MB
after 4 appends: 3.2 MB
after 5 appends: 4.0 MB
memory grows linearly while the list keeps references -> a leak pattern
```

**② With NumPy.** Array memory and views.

```python
import numpy as np

a = np.zeros((1000, 1000), dtype=np.float32)
print("array bytes:", a.nbytes / 1e6, "MB")
view = a[:500]
print("a view shares memory:", np.shares_memory(a, view), "  its nbytes (logical):", view.nbytes / 1e6, "MB")
copy = a[:500].copy()
print("a copy does not share:", not np.shares_memory(a, copy))
print("float16 version:", a.astype(np.float16).nbytes / 1e6, "MB")
```

```text
array bytes: 4.0 MB
a view shares memory: True   its nbytes (logical): 2.0 MB
a copy does not share: True
float16 version: 2.0 MB
```

**③ With PyTorch.** The loss-tensor leak, and the profiler's memory view.

```python
import torch
from torch import nn
from torch.profiler import profile, ProfilerActivity

torch.manual_seed(0)
net = nn.Sequential(nn.Linear(256, 256), nn.ReLU(), nn.Linear(256, 1))
X, y = torch.randn(64, 256), torch.randn(64, 1)

history_bad, history_good = [], []
for _ in range(5):
    loss = nn.functional.mse_loss(net(X), y)
    history_bad.append(loss)                                          # keeps the graph (and activations) alive
    history_good.append(loss.item())                                  # keeps just a number
print("stored object (bad) :", type(history_bad[0]).__name__, "with grad_fn:", history_bad[0].grad_fn is not None)
print("stored object (good):", type(history_good[0]).__name__)

with profile(activities=[ProfilerActivity.CPU], profile_memory=True) as prof:
    nn.functional.mse_loss(net(X), y).backward()
top = sorted(prof.key_averages(), key=lambda r: r.self_cpu_memory_usage, reverse=True)[0]
print("the operator allocating the most memory is a matrix multiply or related op:", any(k in top.key for k in ("mm", "linear", "addmm", "relu", "mse", "empty")))
```

```text
stored object (bad) : Tensor with grad_fn: True
stored object (good): float
the operator allocating the most memory is a matrix multiply or related op: True
```

### 9. Enterprise use case
Memory regression tests (peak memory per config) prevent jobs from silently starting to OOM after code changes.

### 10. AI engineering connection
Choosing parallelism, batch size and checkpointing for LLM runs depends on measured peaks, not estimates.

### 11. Advantages
Pinpoints leaks and the real peak; guides which fix to apply.

### 12. Limitations
Overhead; tools differ per backend; snapshot APIs change.

### 13. Trade-offs
Detailed history uses memory itself; record only a few steps.

### 14. Common mistakes
Looking at `nvidia-smi` instead of allocated/peak; measuring only the first step; confusing reserved with used; storing tensors with graphs; calling `empty_cache()` to "fix" a leak.

### 15. Performance / cost
Disable detailed recording in production.

### 16. Security
Memory dumps may contain data; handle them as sensitive.

### 17. Interview explanation
"I measure peak allocated memory per step, compare step 1 against later steps to detect leaks, and use the profiler or memory snapshots to attribute allocations. The classic PyTorch leak is storing the loss tensor, which retains the graph; I store loss.item(). To reduce peaks I use smaller micro-batches, BF16, checkpointing or sharding."

### 18. Rapid-fire answer
Measure peak (`max_memory_allocated`), compare across steps for leaks, profile by op/snapshot; store `.item()`; reduce with accumulation, bf16, checkpointing, sharding.

### 20. Hands-on exercise
**Goal:** show that the graph is what costs memory.

1. Store 5 losses as tensors versus as floats (code ③).
2. Count how many tensors are kept alive by the first approach by checking `loss.grad_fn.next_functions` depth.

<details>
<summary>Show a solution</summary>

```python
import torch
from torch import nn

net = nn.Sequential(nn.Linear(8, 8), nn.ReLU(), nn.Linear(8, 1))
loss = nn.functional.mse_loss(net(torch.randn(4, 8)), torch.randn(4, 1))

def graph_size(fn, seen=None):
    seen = seen if seen is not None else set()
    if fn is None or fn in seen:
        return len(seen)
    seen.add(fn)
    for nxt, _ in fn.next_functions:
        graph_size(nxt, seen)
    return len(seen)

print("operations kept alive by holding the loss tensor:", graph_size(loss.grad_fn))
print("operations kept alive by holding loss.item():     0")
```

```text
operations kept alive by holding the loss tensor: 10
operations kept alive by holding loss.item():     0
```

</details>
