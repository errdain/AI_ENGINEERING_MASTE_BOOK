# 4.24 GPU memory

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: Very high · Hands-on: High
Prerequisites: 4.16–4.19 Number formats, 4.8 Adam · Leads to: 4.34 FSDP/ZeRO, 4.40 Memory profiling, 4.41 Gradient checkpointing

> **In plain words**
> Training runs out of GPU memory ("CUDA out of memory") more often than anything else. The memory goes to **four things**: the **weights**, their **gradients**, the **optimizer's extra numbers** (Adam keeps two per weight), and the **activations** saved for the backward pass. You can estimate each with simple arithmetic *before* you run, and then pick the right fix: smaller batch, 16-bit numbers, accumulation, checkpointing or sharding.

**You need first:** 4.16–4.19 (bytes per number), 4.8 Adam.

> **Figure 4.24-1 — where training memory goes**
>
> ```mermaid
> flowchart TB
>     T["GPU memory during training"] --> W["weights<br/>P × bytes"]
>     T --> G["gradients<br/>P × bytes"]
>     T --> O["optimizer state<br/>Adam: 2 × P × 4 bytes"]
>     T --> A["activations<br/>∝ batch × sequence × layers"]
>     T --> X["temporary buffers,<br/>CUDA context, fragmentation"]
> ```
>
> *How to read it:* the first three boxes depend only on the number of parameters `P`. Activations grow with the batch size, sequence length and depth and often dominate for large batches. The last box is overhead you can only measure.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| `P` | number of parameters |
| optimizer state | extra tensors the optimizer keeps (Adam: `m` and `v`) |
| activations | intermediate outputs saved for backward |
| OOM | out of memory |
| peak memory | the highest usage during a step |
| fragmentation | free memory split into unusable pieces |
| `max_memory_allocated` | PyTorch's peak-memory counter (GPU) |

### 1. What is it?
The accounting of what occupies device memory in training, and the tools to reduce it.

### 2. Why does it exist?
GPUs have limited memory (for example 24–80 GB). A model that "fits" for inference may be 4–16× too big to train because of gradients, optimizer state and activations.

### 3. Detailed explanation
Per parameter, with mixed precision and Adam (4.19, 4.8):

| item | bytes per parameter |
|---|---|
| 16-bit weights (working copy) | 2 |
| 16-bit gradients | 2 |
| FP32 master weights | 4 |
| FP32 Adam `m` and `v` | 8 |
| **total (excluding activations)** | **16** |

So a 7B-parameter model needs about **112 GB** before activations; a 1B model about 16 GB (code ①).
- **Pure FP32 + Adam:** `4 + 4 + 8 = 16` bytes per parameter too. Mixed precision doesn't shrink this part (4.19); it shrinks activations.
- **Inference only:** just the weights (2 bytes per parameter in 16-bit; 0.5 in 4-bit quantization).
- **Activations** are roughly `layers × batch × sequence × hidden × a constant` numbers; the constant depends on the architecture (REVIEW_REQUIRED). They are halved by 16-bit and removed (recomputed) by checkpointing (4.41).
- **Fixes, in order of ease:** smaller micro-batch + accumulation (4.14); BF16 (4.18); gradient checkpointing (4.41); 8-bit optimizers; sharding the states across GPUs (FSDP/ZeRO, 4.34); LoRA (train few parameters); offloading to CPU.
- **Peak vs steady:** memory spikes during backward and at the first optimizer step (state allocated lazily).
- **Fragmentation and caching:** PyTorch caches memory; `reserved` is higher than `allocated`.
- **Measure:** `torch.cuda.max_memory_allocated()`, the memory profiler (4.40), `nvidia-smi`.
- **KV cache** adds memory in inference (Tier 11).

### 4. How does it work?
Sum the four categories; compare with the device memory; reduce the biggest term.

### 5. Simple example
Packing a suitcase: clothes (weights), their duplicates for the trip home (gradients), the packing list notes (optimizer state), and whatever you buy during the trip (activations).

**By hand.** 1B parameters: weights 2 GB (16-bit) + gradients 2 GB + master 4 GB + Adam 8 GB = **16 GB**, before activations.

### 6. Technical example
Fine-tuning a 7B model with LoRA: base weights frozen in 16-bit (14 GB), tiny adapters trained (a few hundred MB of states), so it fits in a 24 GB GPU (REVIEW_REQUIRED: illustrative).

### 7. Code
**① By hand (plain Python).** A memory calculator.

```python
def training_gb(params, weight_bytes=2, grad_bytes=2, master_bytes=4, adam_bytes=8):
    return params * (weight_bytes + grad_bytes + master_bytes + adam_bytes) / 1e9

for name, p in (("125M", 125e6), ("1B", 1e9), ("7B", 7e9), ("70B", 70e9)):
    print(f"{name:>5} parameters: {training_gb(p):8.1f} GB for weights+grads+optimizer (no activations)   inference in 16-bit: {p * 2 / 1e9:6.1f} GB")
```

```text
 125M parameters:      2.0 GB for weights+grads+optimizer (no activations)   inference in 16-bit:    0.2 GB
   1B parameters:     16.0 GB for weights+grads+optimizer (no activations)   inference in 16-bit:    2.0 GB
   7B parameters:    112.0 GB for weights+grads+optimizer (no activations)   inference in 16-bit:   14.0 GB
  70B parameters:   1120.0 GB for weights+grads+optimizer (no activations)   inference in 16-bit:  140.0 GB
```

**② With NumPy.** Bytes per array and the activation count of a small network.

```python
import numpy as np

batch, hidden, layers = 32, 1024, 24
act = np.zeros((batch, hidden), dtype=np.float32)
print("one activation tensor:", act.nbytes / 1e3, "KB")
per_example = layers * hidden * 4 * 10                                # ~10 saved tensors per layer, a rough rule
print(f"~{batch * per_example / 1e6:.1f} MB of activations for batch {batch} (rough rule), {64 * per_example / 1e6:.1f} MB for batch 64")
print("doubling the batch doubles activations:", 64 * per_example == 2 * batch * per_example)
```

```text
one activation tensor: 131.072 KB
~31.5 MB of activations for batch 32 (rough rule), 62.9 MB for batch 64
doubling the batch doubles activations: True
```

**③ With PyTorch.** Measure parameters and optimizer state on a real model.

```python
import torch

model = torch.nn.Sequential(torch.nn.Linear(512, 2048), torch.nn.ReLU(), torch.nn.Linear(2048, 512))
P = sum(p.numel() for p in model.parameters())
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
model(torch.randn(8, 512)).sum().backward(); opt.step()                # creates the optimizer state
state = sum(t.numel() for s in opt.state.values() for t in s.values() if torch.is_tensor(t) and t.dim() > 0)
print(f"parameters: {P:,}   optimizer state numbers: {state:,}  (= {state / P:.0f} x the parameters)")
print(f"FP32 bytes: weights {P * 4 / 1e6:.1f} MB, gradients {P * 4 / 1e6:.1f} MB, Adam state {state * 4 / 1e6:.1f} MB")
print("GPU memory counters (torch.cuda.max_memory_allocated) need a GPU; CUDA available here:", torch.cuda.is_available())
```

```text
parameters: 2,099,712   optimizer state numbers: 4,199,424  (= 2 x the parameters)
FP32 bytes: weights 8.4 MB, gradients 8.4 MB, Adam state 16.8 MB
GPU memory counters (torch.cuda.max_memory_allocated) need a GPU; CUDA available here: False
```

### 9. Enterprise use case
Memory arithmetic determines GPU type, count, and whether a project is feasible, long before purchase.

### 10. AI engineering connection
LoRA/QLoRA, quantization and sharding exist because of this table.

### 11. Advantages
Predictable arithmetic; guides cheap fixes.

### 12. Limitations
Activation sizes depend on the architecture; real usage includes overhead.

### 13. Trade-offs
Every saving costs something: compute (checkpointing), precision (quantization), complexity (sharding).

### 14. Common mistakes
Forgetting optimizer state and gradients; estimating from inference size; ignoring fragmentation; assuming larger GPUs fix a leak (holding `loss` tensors); measuring after `empty_cache`.

### 15. Performance / cost
Memory fragmentation and allocator settings can cost tens of percent of capacity.

### 16. Security
Memory not zeroed between jobs may leak data in shared environments.

### 20. Hands-on exercise
**Goal:** how big a model fits on a 24 GB GPU?

1. Using 16 bytes/parameter for training and 2 bytes/parameter for inference, compute the largest parameter count for each (ignore activations and overhead).
2. Repeat for 80 GB.

<details>
<summary>Show a solution</summary>

```python
for gb in (24, 80):
    train = gb * 1e9 / 16
    infer = gb * 1e9 / 2
    print(f"{gb} GB: full training up to ~{train / 1e9:.1f}B parameters, 16-bit inference up to ~{infer / 1e9:.0f}B parameters")
```

```text
24 GB: full training up to ~1.5B parameters, 16-bit inference up to ~12B parameters
80 GB: full training up to ~5.0B parameters, 16-bit inference up to ~40B parameters
```

In practice the limits are lower because of activations and overhead.
