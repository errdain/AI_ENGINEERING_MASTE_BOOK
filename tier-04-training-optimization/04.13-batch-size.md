# 4.13 Batch size

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: High
Prerequisites: 4.6 SGD, 4.10 Scheduling · Leads to: 4.14 Gradient accumulation, 4.24 GPU memory, 4.31 Data parallelism

> **In plain words**
> The **batch size** is how many examples you use for each update. Small batches give noisy but cheap steps; large batches give smooth, accurate gradients but fewer steps per epoch and more memory.
> A rule of thumb: when you multiply the batch size by `k`, multiply the learning rate by about `k` (up to a point), and warm up.

**You need first:** 4.6 SGD, 4.10 Learning-rate scheduling.

> *How to read it:* the gradient noise falls like `1/√B` (code ②). With 10,000 examples a batch of 10 gives 1,000 steps per epoch, a batch of 1,000 only 10. The best choice balances hardware efficiency, noise and the number of updates.

### 1. What is it?
The number of training examples (or tokens) combined into one gradient estimate and one optimizer step.

### 2. Why does it exist?
It is the knob between statistical efficiency (more accurate gradients) and hardware efficiency (parallelism, memory). The hardware prefers large batches; the optimizer often prefers many updates.

### 3. Detailed explanation
- **Noise.** The standard deviation of the batch gradient falls like `1/√B` (4.6).
- **Steps per epoch** = `N / B`. Fewer steps with larger batches means a longer epoch-to-epoch trajectory is not simply faster.
- **Linear scaling rule.** For SGD, if you multiply `B` by `k`, multiplying the learning rate by `k` often keeps the training curve (per epoch) similar, up to a limit, with warm-up (Goyal et al., 2017; REVIEW_REQUIRED). For Adam a square-root scaling is often used (REVIEW_REQUIRED).
- **Critical batch size.** Beyond some size, extra examples give diminishing returns: the gradient is already accurate (REVIEW_REQUIRED).
- **Generalization.** Very large batches sometimes generalize worse ("generalization gap") unless the learning rate and regularization are retuned (REVIEW_REQUIRED).
- **Memory.** Activations scale linearly with `B` (and sequence length) (4.24). If `B` doesn't fit, use accumulation (4.14) or checkpointing (4.41).
- **Hardware efficiency.** GPUs are underused at tiny batches; throughput rises then saturates.
- **LLMs** are described in tokens per batch (for example 0.5M–4M tokens): `B × sequence length`.
- **BatchNorm** needs reasonably large per-device batches (3.30).
- **Loss reduction** should be `mean`, so the scale does not depend on `B` (4.3).
- **Batch size schedules** (start small, grow) exist (REVIEW_REQUIRED).

### 4. How does it work?
Pick `B`; each step averages the gradient over `B` examples. Scale lr (and warm-up) accordingly.

### 5. Simple example
Polling opinions: asking 5 people gives a quick but shaky estimate; asking 5,000 is steady but slow and expensive.

**By hand.** 10,000 examples. `B = 10` → 1,000 steps/epoch; `B = 100` → 100 steps/epoch; `B = 1,000` → 10 steps/epoch.

### 6. Technical example
GPT-3-scale training used batch sizes of millions of tokens, increasing during training (REVIEW_REQUIRED: published schedules).

### 7. Code
**① By hand (plain Python).** Steps per epoch and the scaled learning rate.

```python
N, base_lr, base_B = 10_000, 0.1, 100
for B in (10, 100, 1000):
    print(f"B = {B:>4}: steps per epoch = {N // B:>4}   linearly scaled lr = {base_lr * B / base_B:.3f}   sqrt-scaled lr = {base_lr * (B / base_B) ** 0.5:.3f}")
```

```text
B = 1000: steps per epoch =   10   linearly scaled lr = 1.000   sqrt-scaled lr = 0.316
```

**② With NumPy.** Gradient noise against batch size.

```python
import numpy as np

rng = np.random.default_rng(0)
X = rng.normal(0, 1, 20000)
y = 2 * X + rng.normal(0, 1, 20000)
per_example = 2 * (0.0 * X - y) * X                                  # gradient of each example at w = 0
print("true gradient:", round(per_example.mean(), 3))
for B in (1, 4, 16, 64, 256):
    est = [per_example[rng.choice(20000, B)].mean() for _ in range(3000)]
    print(f"B = {B:>3}: noise (std) = {np.std(est):.3f}    1/sqrt(B) scaling predicts {np.std(per_example) / B ** 0.5:.3f}")
```

```text
true gradient: -3.975
B =   1: noise (std) = 5.828    1/sqrt(B) scaling predicts 5.928
B =   4: noise (std) = 2.910    1/sqrt(B) scaling predicts 2.964
B =  16: noise (std) = 1.538    1/sqrt(B) scaling predicts 1.482
B =  64: noise (std) = 0.752    1/sqrt(B) scaling predicts 0.741
B = 256: noise (std) = 0.362    1/sqrt(B) scaling predicts 0.370
```

**③ With PyTorch.** The same data, different batch sizes, the same number of epochs.

```python
import torch

def train(B, lr, epochs=5):
    torch.manual_seed(0)
    X = torch.randn(2000, 1); y = 3 * X + 1 + 0.3 * torch.randn_like(X)
    model = torch.nn.Linear(1, 1)
    opt = torch.optim.SGD(model.parameters(), lr=lr)
    steps = 0
    for _ in range(epochs):
        order = torch.randperm(2000)
        for i in range(0, 2000, B):
            idx = order[i:i + B]
            opt.zero_grad(); torch.nn.functional.mse_loss(model(X[idx]), y[idx]).backward(); opt.step(); steps += 1
    return steps, torch.nn.functional.mse_loss(model(X), y).item()

for B, lr in ((10, 0.01), (100, 0.01), (100, 0.1), (1000, 0.01), (1000, 0.1)):
    steps, loss = train(B, lr)
    print(f"batch {B:>4}, lr {lr:<5}: {steps:>4} steps, final loss {loss:.3f}")
```

```text
batch   10, lr 0.01 : 1000 steps, final loss 0.084
batch  100, lr 0.01 :  100 steps, final loss 0.203
batch  100, lr 0.1  :  100 steps, final loss 0.084
batch 1000, lr 0.01 :   10 steps, final loss 5.508
batch 1000, lr 0.1  :   10 steps, final loss 0.159
```

### 8. Input → Process → Output
`B examples → averaged gradient (noise ∝ 1/√B) → one update`

### 9. Enterprise use case
Batch size is set by hardware (memory, interconnect) and budget; tokens per batch is a headline training parameter.

### 10. AI engineering connection
LLM recipes list global batch in tokens; fine-tuning uses small batches with accumulation.

### 11. Advantages
Lets you trade noise against throughput.

### 12. Limitations
Memory-bound; interacts with lr, BatchNorm, generalization.

### 13. Trade-offs
Small batches: noise, regularization, more updates. Large batches: speed through parallelism, smoother curves.

### 14. Common mistakes
Changing batch size without touching the learning rate; `sum` reduction; comparing runs at the same number of steps instead of the same number of examples; tiny per-device batches with BatchNorm.

### 15. Performance / cost
Find the largest batch that fits memory and keeps the device busy.

### 16. Security
No direct issue.

### 17. Interview explanation
"Batch size trades gradient noise, which falls like 1/√B, against hardware throughput and the number of updates. When I scale it I rescale the learning rate (linear for SGD, often square-root for Adam), lengthen warm-up, and use gradient accumulation when the batch does not fit in memory."

### 18. Rapid-fire answer
Larger `B`: less noise, fewer steps, more memory; scale lr with `B` and warm up; use accumulation to emulate large batches.

```python
import torch

def final_loss(B, lr, epochs=3):
    torch.manual_seed(0)
    X = torch.randn(2000, 1); y = 3 * X + 1 + 0.3 * torch.randn_like(X)
    model = torch.nn.Linear(1, 1)
    opt = torch.optim.SGD(model.parameters(), lr=lr)
    for _ in range(epochs):
        order = torch.randperm(2000)
        for i in range(0, 2000, B):
            idx = order[i:i + B]
            opt.zero_grad(); torch.nn.functional.mse_loss(model(X[idx]), y[idx]).backward(); opt.step()

for B, lr in ((10, 0.02), (50, 0.045), (250, 0.1)):
    print(f"batch {B:>3}, lr {lr}: loss after 3 epochs = {final_loss(B, lr):.3f}")
```
