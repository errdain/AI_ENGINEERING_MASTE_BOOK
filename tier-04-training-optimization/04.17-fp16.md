# 4.17 FP16 (half precision)

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: High · Hands-on: High
Prerequisites: 4.16 FP32 · Leads to: 4.18 BF16, 4.19 Mixed precision

> **In plain words**
> **FP16** uses **16 bits** per number, half of FP32. That halves memory and speeds things up on GPUs. The price: a **narrow range**. Numbers above **65,504** overflow to infinity, and very small numbers (below about 6×10⁻⁸) become **zero**. Small gradients can silently vanish. That is why FP16 training needs **loss scaling** (4.19).

**You need first:** 4.16 FP32.

| overflow | a number too large becomes `inf` |
| underflow | a number too small becomes 0 |

| loss scaling | multiply the loss so gradients stay in range |

| `GradScaler` | PyTorch's dynamic loss scaler |

### 1. What is it?
IEEE half precision: 5 exponent bits, 10 fraction bits. Max 65,504; smallest normal 6.1×10⁻⁵; epsilon 9.8×10⁻⁴ (about 3 decimal digits).

### 2. Why does it exist?
Half the memory and bandwidth, and 2–8× faster matrix math on tensor cores, compared with FP32.

### 3. Detailed explanation
- **Overflow:** activations or logits above 65,504 become `inf`; then `nan` follows (4.38). Softmax and large sums are typical offenders; compute them in FP32.
- **Underflow:** gradients are often tiny (1e-8 and below). In FP16 they flush to 0, so those weights stop learning. **Loss scaling** multiplies the loss by a large factor (for example 1024 or 65536) before `backward()` so gradients are larger, then divides before the update (code ③).
- **Dynamic loss scaling:** if an `inf` appears, skip the step and halve the scale; after many good steps, double it (`GradScaler`).
- **Precision:** only ~3 digits; small updates to large weights vanish (`1.0 + 0.0001 == 1.0`). This is why mixed precision keeps FP32 master weights.
- **Where it is used:** inference (widely), and mixed-precision training on older GPUs. Modern LLM training prefers BF16 (4.18).
- **Casting:** `tensor.half()` or `.to(torch.float16)`.
- **Accumulation in matmul** is usually done in FP32 inside the hardware even when inputs are FP16.
- **Numerical landmines:** `exp`, `log`, `softmax`, normalization statistics, and reductions need FP32.

### 4. How does it work?
Same layout as FP32 with fewer bits: a 5-bit exponent limits the range; a 10-bit fraction limits the precision.

### 5. Simple example
A small suitcase: light and fast to carry, but long items don't fit (overflow) and tiny items fall through the holes (underflow).

**By hand.** 70,000 does not fit (max 65,504) → `inf`. 0.00000001 (1e-8) is below the smallest subnormal (≈6×10⁻⁸) → 0. And `1 + 0.0004` rounds to 1.0 because the gap near 1 is ≈ 0.00098.

### 6. Technical example
`torch.autocast("cuda", dtype=torch.float16)` plus `torch.cuda.amp.GradScaler()` in the loop.

### 7. Code
**① By hand (plain Python).** What 16-bit storage does to numbers (via `struct`'s `e` format).

```python
import struct

def to_fp16(x):
    return struct.unpack("e", struct.pack("e", x))[0]

for x in (3.14159265, 1.0001, 70000.0 - 5000.0, 1e-5, 1e-8):
    try:
        print(f"{x!r:>14} -> {to_fp16(x)!r}")
    except OverflowError:
        print(f"{x!r:>14} -> overflow")
try:
    to_fp16(70000.0)
except OverflowError:
    print("70000.0 cannot be stored in FP16 (max 65504)")
```

```text
    3.14159265 -> 3.140625
        1.0001 -> 1.0
       65000.0 -> 64992.0
         1e-05 -> 1.0013580322265625e-05
         1e-08 -> 0.0
70000.0 cannot be stored in FP16 (max 65504)
```

```python
import numpy as np

info = np.finfo(np.float16)

print("float16(60000) * 2:", np.float16(60000) * np.float16(2), "(overflow)")
```


**③ With PyTorch.** Loss scaling rescues a tiny gradient.

```python
import torch

w = torch.nn.Parameter(torch.tensor([1.0], dtype=torch.float32))
x = torch.tensor([1e-4], dtype=torch.float16)
for scale in (1.0, 1024.0):
    w.grad = None
    out = (w.half() * x)                                             # forward in FP16
    loss = (out * 1e-4).sum() * scale                                 # a very small loss -> tiny gradient
    loss.backward()
    g = w.grad.item() / scale                                         # unscale before using the gradient
    print(f"loss scale {scale:>6}: gradient seen = {w.grad.item():.3e}   after unscaling = {g:.3e}   true value = 1e-08")
```

```text
loss scale    1.0: gradient seen = 0.000e+00   after unscaling = 0.000e+00   true value = 1e-08
loss scale 1024.0: gradient seen = 1.025e-05   after unscaling = 1.001e-08   true value = 1e-08
```

### 9. Enterprise use case
FP16 inference halves serving memory and speeds latency with minor accuracy loss for most models.

### 10. AI engineering connection
Half-precision checkpoints (`.half()`) are the typical format for released models; some quantized formats start from FP16 weights.

### 11. Advantages
Half the memory and bandwidth; fast tensor-core math.

### 12. Limitations
Narrow range, low precision; needs loss scaling; prone to NaNs.

### 13. Trade-offs
Speed and memory versus numerical risk; BF16 (4.18) trades precision for safety.

### 14. Common mistakes
Training fully in FP16 without master weights; softmax or layer norm in FP16; no loss scaling; ignoring `inf` checks; casting large constants to FP16.

### 15. Performance / cost
Up to ~2× less memory traffic, multiple× matmul speed on tensor cores.

### 16. Security
Quantization-induced numeric changes can alter model behaviour in edge cases; re-evaluate safety tests after casting.

</details>

### 17. Interview explanation
"FP16 has a 5-bit exponent and 10-bit fraction, so its maximum is 65,504 and its smallest values flush to zero. For training I keep FP32 master weights, run matmuls in FP16, and use dynamic loss scaling to stop small gradients underflowing. On newer hardware I prefer BF16."

### 18. Rapid-fire answer
16 bits: 1/5/10; max 65,504; underflow below ~6e-8; needs loss scaling and FP32 master weights.

```python
import numpy as np

n = 1

```
