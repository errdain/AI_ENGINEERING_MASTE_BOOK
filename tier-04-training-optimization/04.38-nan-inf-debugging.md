# 4.38 NaN / Inf debugging

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: Very high · Hands-on: Very high
Prerequisites: 1.43 Stable softmax, 1.44 Overflow/underflow, 4.17 FP16 · Leads to: 4.39 Loss debugging

> **In plain words**
> **`NaN`** ("not a number") and **`inf`** (infinity) are what the computer produces when a calculation breaks: dividing by zero, taking the log of zero, `exp` of a huge number, or a gradient that grew without limit. **Once a single NaN appears it spreads to every number it touches**, so the whole model becomes NaN within a step. Debugging means finding the **first** place it appears and the operation that created it.

**You need first:** 1.43 Stable softmax, 1.44 Overflow/underflow, 4.17 FP16.

> **Figure 4.38-1 — where NaNs come from and how they spread**
>
> ```mermaid
> flowchart LR
>     S1["log(0), 0/0, sqrt(−1)"] --> N["first NaN / inf"]
>     S2["exp(large), fp16 overflow"] --> N
>     S3["exploding gradients, lr too high"] --> N
>     S4["bad data: NaN in the input"] --> N
>     N --> P["propagates through<br/>every operation"]
>     P --> D["loss = NaN,<br/>all weights NaN after step"]
> ```
>
> *How to read it:* four families of sources lead to a first bad number; after that, every operation that touches it returns NaN. So the clue is *when* and *where* the first one appeared, not the final NaN loss.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| NaN | result of an undefined operation (0/0, inf − inf) |
| inf | result of overflow or division by a tiny number |
| propagate | NaN contaminates everything it touches |
| anomaly detection | PyTorch mode that names the operation that produced NaN |
| `isfinite` | test that a tensor has no NaN/inf |

### 1. What is it?
Finding and fixing the numeric failure that makes the loss, gradients or weights non-finite.

### 2. Why does it exist?
NaNs silently destroy long, expensive runs. Fast diagnosis saves days of compute.

### 3. Detailed explanation
- **Typical sources:**
  1. `log` of 0 or negative: use `log_softmax`/`cross_entropy` fused versions or add `ε` (1.43–1.44).
  2. `exp` of large numbers in naive softmax/sigmoid; subtract the max.
  3. Division by zero in normalization (add `ε`; in FP16 use `1e-5`, not `1e-8`).
  4. Learning rate too high → exploding values (3.26, 4.15).
  5. FP16 overflow (> 65,504) or missing loss scaling (4.17, 4.19).
  6. Bad data: NaN/inf in inputs, empty batches, division by an empty count.
  7. Custom ops with zero gradients at singular points (`sqrt(0)`, `x**0.5` at 0).
- **Strategy:**
  1. *Reproduce quickly:* fixed seed, fewer steps, same batch (4.21–4.22).
  2. *Check the data:* `torch.isfinite(batch).all()`.
  3. *Bisect:* is the loss NaN **before** backward (forward problem) or are the gradients NaN (backward problem)?
  4. *Use anomaly detection:* `torch.autograd.set_detect_anomaly(True)` raises at the backward op that produced NaN (slow, debugging only).
  5. *Add forward hooks* that check each module's output for non-finite values and name the first culprit (code ③).
  6. *Lower precision issues:* retry in FP32; if it disappears, it was range.
  7. *Mitigate:* gradient clipping (4.15), warm-up (4.11), lower lr, stable losses, `ε` constants.
- **Skipping bad steps:** some loops skip an update if the gradient norm is non-finite (as `GradScaler` does) and log it.
- **Don't hide it:** `nan_to_num` can mask a real bug; use it only knowingly.
- **Checkpoints:** restart from the last good checkpoint with a lower lr and a fix; keep several (4.20).

### 4. How does it work?
Detect the first non-finite value (data, forward, loss, backward), identify the operation, fix the cause (stability, scale, data).

### 5. Simple example
A contaminated ingredient in a recipe: one bad egg spoils everything it touches; the trick is to find which ingredient, not to taste the final dish.

**By hand.** `log(0) = −inf`; `−inf × 0 = NaN`; `NaN + 5 = NaN`. One bad value becomes NaN everywhere downstream.

### 6. Technical example
`torch.autograd.set_detect_anomaly(True)` pinpoints that `LogBackward` produced NaN: the loss used `log(softmax(x))` instead of `log_softmax(x)`.

### 7. Code
**① By hand (plain Python).** The rules of NaN and inf.

```python
import math

inf = float("inf")
print("1e308 * 10        =", 1e308 * 10)
print("inf - inf         =", inf - inf)
print("0 * inf           =", 0 * inf)
print("nan == nan        =", float("nan") == float("nan"), "  (use math.isnan)")
print("nan + 5           =", float("nan") + 5)
try:
    math.log(0)
except ValueError:
    print("math.log(0)       -> ValueError (math domain error)")
```

```text

inf - inf         = nan
0 * inf           = nan
nan == nan        = False   (use math.isnan)
nan + 5           = nan
math.log(0)       -> ValueError (math domain error)
```

**② With NumPy.** Naive versus stable softmax and log-softmax.

```python
import numpy as np

x = np.array([1000.0, 1001.0, 1002.0])
with np.errstate(all="ignore"):
    naive = np.exp(x) / np.exp(x).sum()
print("naive softmax    :", naive)
shifted = x - x.max()
stable = np.exp(shifted) / np.exp(shifted).sum()
print("stable softmax   :", stable.round(4))
print("stable log-softmax:", (shifted - np.log(np.exp(shifted).sum())).round(4))
with np.errstate(all="ignore"):
    print("log(softmax) of a very unlikely class:", np.log(np.exp(np.array([0.0, -2000.0])) / np.exp(np.array([0.0, -2000.0])).sum()))
```

```text
naive softmax    : [nan nan nan]
stable softmax   : [0.09   0.2447 0.6652]
stable log-softmax: [-2.4076 -1.4076 -0.4076]
log(softmax) of a very unlikely class: [  0. -inf]
```

**③ With PyTorch.** Find the first module that produces a non-finite value, and anomaly detection.

```python
import torch
from torch import nn

torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Linear(8, 8), nn.Sigmoid(), nn.Linear(8, 1))
with torch.no_grad():
    net[2].weight.fill_(3e38)                                           # simulate a corrupted / exploded layer

first_bad = []
def check(module, inputs, output):
    if not torch.isfinite(output).all() and not first_bad:
        first_bad.append(module.__class__.__name__ + " #" + str(list(net).index(module)))
for m in net:
    m.register_forward_hook(check)
out = net(torch.randn(3, 4))
print("final output is finite:", torch.isfinite(out).all().item(), "(the sigmoid squashed the infinity!)")
print("but the first non-finite module output came from:", first_bad)

x = torch.tensor([0.0], requires_grad=True)
try:
    with torch.autograd.detect_anomaly():
        (torch.sqrt(x) * 0.0).sum().backward()
except RuntimeError as e:
    print("anomaly detection caught:", str(e).split(" returned")[0])
```

```text
final output is finite: True (the sigmoid squashed the infinity!)
but the first non-finite module output came from: ['Linear #2']
anomaly detection caught: Function 'SqrtBackward0'
```

<summary><b>Beyond the basics (sections 9–16)</b> — real-world use, limits, mistakes. Skip on a first read.</summary>

### 9. Enterprise use case
Automatic NaN detection with run restart from a checkpoint is standard in long training jobs.

### 10. AI engineering connection
Large-scale training uses NaN/inf checks, loss-spike handling, bf16, and clipping; custom kernels need stability review.

### 11. Advantages
Systematic debugging saves compute.

### 12. Limitations
Anomaly mode is slow; the true source can be far upstream of where NaN is noticed.

### 13. Trade-offs
Checking every tensor costs time; check at module boundaries or every N steps.

### 14. Common mistakes
Looking only at the final loss; masking with `nan_to_num`; `==` comparison with NaN; trusting FP16 without scaling; fixing by lowering lr without finding the cause.

### 15. Performance / cost
Anomaly mode and per-module checks should be off in production runs.

### 16. Security
Adversarial inputs can trigger NaN/inf (denial of service); validate inputs.

</details>

### 17. Interview explanation
"A NaN spreads to everything it touches, so I find the first occurrence: check inputs with isfinite, add forward hooks to find the first non-finite module output, use anomaly detection for the backward op, and retry in FP32 to rule out range. The usual culprits are log(0), unstable softmax, missing epsilon, too-high learning rate or FP16 overflow; the fixes are fused stable losses, epsilon, clipping, warm-up and BF16."

```python
import torch

x = torch.tensor([[0.0, -200.0]])
target = torch.tensor([1])
naive = -torch.log(torch.softmax(x, dim=1))[0, 1]
stable = torch.nn.functional.cross_entropy(x, target)
print("-log(softmax(x))[1]       =", naive.item(), "  (probability underflowed to 0 -> inf)")
print("cross_entropy (fused)     =", stable.item())
```
