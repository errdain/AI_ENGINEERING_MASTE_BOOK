# 4.14 Gradient accumulation

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 2/5 · Interview: High · Hands-on: Very high
Prerequisites: 4.4 Backward pass, 4.13 Batch size · Leads to: 4.24 GPU memory, 4.31 Data parallelism

> **In plain words**
> **Gradient accumulation** lets you train with a **big batch on a small GPU**. Instead of one big batch, you run several small **micro-batches**, let their gradients **add up** in `.grad`, and only then take **one** optimizer step. The result is the same update as the big batch, but you only needed memory for the small one.
> Like carrying 100 bricks in 4 trips of 25 and building only after the last trip.

**You need first:** 4.4 Backward pass (gradients add up), 4.13 Batch size.

> **Figure 4.14-1 — four micro-batches, one update**
>
> ```mermaid
> flowchart LR
>     M1["micro-batch 1<br/>forward + backward"] --> A["gradients add<br/>in .grad"]
>     M2["micro-batch 2"] --> A
>     M3["micro-batch 3"] --> A
>     M4["micro-batch 4"] --> A
>     A --> S["optimizer.step()<br/>then zero_grad()"]
> ```
>
> *How to read it:* each micro-batch does a normal forward and backward, but we **skip `step()` and `zero_grad()`** until the 4th. Because `.grad` accumulates, after four micro-batches it holds the sum of their gradients. With each loss divided by 4 this equals the gradient of the mean over the whole big batch.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| micro-batch | the small batch that fits in memory |
| accumulation steps `k` | number of micro-batches per optimizer step |
| effective (global) batch | `micro-batch × k` (× devices) |
| loss scaling by `1/k` | keeps the average equal to the big-batch mean |
| optimizer step | one real update of the weights |
| `no_sync` | skip gradient communication on non-final micro-steps (distributed) |

### 1. What is it?
Running several forward/backward passes before one optimizer step, relying on `.grad` accumulating, to emulate a larger batch.

### 2. Why does it exist?
Activations scale with the batch size (4.24). If the batch you want does not fit in memory, accumulation gives the same gradient with memory for only a micro-batch.

### 3. Detailed explanation
- **The recipe:** for each micro-batch compute `loss / k`, call `backward()`; every `k`-th micro-batch call `step()` then `zero_grad()` (code ③).
- **Why divide by `k`?** The mean over `k·m` examples equals the average of `k` micro-batch means. Without the division the gradient is `k` times too large.
- **Exact equality** holds for losses that are plain averages of per-example terms. **BatchNorm** statistics are per micro-batch, so results differ (3.30). Dropout masks differ per micro-batch, which is fine.
- **Token-weighted losses.** With variable-length sequences, average over *tokens* across the whole effective batch, not over micro-batch means, or short micro-batches get too much weight (4.3).
- **Cost:** the same compute per example; fewer, bigger optimizer steps; slightly more Python overhead; lower memory.
- **Counting steps.** Schedulers, warm-up and logging count *optimizer* steps, not micro-batches (4.11).
- **Gradient clipping** goes after the last micro-batch, before `step()` (4.15).
- **Distributed training:** synchronize gradients only on the last micro-step (`no_sync`) to avoid wasted communication (4.31).
- **Mixed precision:** use one `GradScaler` update per optimizer step (4.19).

### 4. How does it work?
Zero the gradients once. Loop over `k` micro-batches doing forward, `loss/k`, backward. Then step and zero again.

### 5. Simple example
Carrying 100 bricks in four trips of 25, stacking them in one pile, and building only after the fourth trip.

**By hand.** Gradients of four micro-batches `[2, 4, 6, 8]` (each already a mean). Big-batch mean = 5. Accumulate `loss/4` each: `0.5 + 1 + 1.5 + 2 = 5`.

### 6. Technical example
Fine-tuning a 7B model with micro-batch 1, accumulation 32 → effective batch 32 on one GPU (REVIEW_REQUIRED: illustrative).

### 7. Code
**① By hand (plain Python).** Averages of averages.

```python
micro_grads = [2.0, 4.0, 6.0, 8.0]            # gradient (a mean) of four equal-size micro-batches
k = len(micro_grads)
accumulated = 0.0
for g in micro_grads:
    accumulated += g / k                       # backward on loss / k
print("accumulated gradient:", accumulated, "   big-batch mean:", sum(micro_grads) / k)
print("forgetting the division by k gives:", sum(micro_grads), "(k times too big)")
```

```text
accumulated gradient: 5.0    big-batch mean: 5.0
forgetting the division by k gives: 20.0 (k times too big)
```

**② With NumPy.** The same equality on a real regression gradient.

```python
import numpy as np

rng = np.random.default_rng(0)
X, y, w = rng.normal(0, 1, (64, 5)), rng.normal(0, 1, 64), rng.normal(0, 1, 5)
grad = lambda Xb, yb: 2 * Xb.T @ (Xb @ w - yb) / len(yb)

big = grad(X, y)
acc = sum(grad(X[i:i + 16], y[i:i + 16]) / 4 for i in range(0, 64, 16))
print("big batch  :", big.round(5))
print("accumulated:", acc.round(5))
print("max difference:", f"{np.abs(big - acc).max():.1e}")
```

```text
big batch  : [-0.76038 -1.58446 -1.97493 -1.41599 -2.97499]
accumulated: [-0.76038 -1.58446 -1.97493 -1.41599 -2.97499]
max difference: 6.7e-16
```

**③ With PyTorch.** The loop, and the memory-saving evidence: same weights after one effective step.

```python
import torch

def make():
    torch.manual_seed(0)
    return torch.nn.Linear(8, 1)

torch.manual_seed(1)
X, y = torch.randn(64, 8), torch.randn(64, 1)

big = make(); opt = torch.optim.SGD(big.parameters(), lr=0.1)
opt.zero_grad(); torch.nn.functional.mse_loss(big(X), y).backward(); opt.step()          # one batch of 64

acc = make(); opt = torch.optim.SGD(acc.parameters(), lr=0.1)
k = 4
opt.zero_grad()
for i in range(k):                                                                         # four micro-batches of 16
    xb, yb = X[i * 16:(i + 1) * 16], y[i * 16:(i + 1) * 16]
    (torch.nn.functional.mse_loss(acc(xb), yb) / k).backward()
opt.step()                                                                                  # a single update
print("weights equal after one effective step:", torch.allclose(big.weight, acc.weight, atol=1e-6))
print("largest weight difference:", f"{(big.weight - acc.weight).abs().max().item():.1e}")
```

```text
weights equal after one effective step: True
largest weight difference: 3.0e-08
```

### 8. Input → Process → Output
`k micro-batches → summed (÷k) gradients → one step ≈ big-batch step`

<summary><b>Beyond the basics (sections 9–16)</b> — real-world use, limits, mistakes. Skip on a first read.</summary>

### 9. Enterprise use case
Lets teams fine-tune large models on modest hardware by simulating large batches.

### 10. AI engineering connection
Standard in LLM fine-tuning (LoRA, QLoRA) and in large pre-training combined with data parallelism.

### 11. Advantages
Large effective batches with small memory; trivial to implement.

### 12. Limitations
Does not speed training; BatchNorm mismatch; variable-length loss weighting.

### 13. Trade-offs
More accumulation means more memory saved but more sequential work.

### 14. Common mistakes
Forgetting `/k`; stepping the scheduler every micro-batch; clipping each micro-batch instead of after accumulation; calling `zero_grad` every micro-batch; averaging per-micro-batch means for token losses.

### 15. Performance / cost
Overlap data loading; in distributed training skip gradient sync on non-final micro-steps.

### 16. Security
No direct issue.

</details>

### 17. Interview explanation
"Gradient accumulation sums gradients over k micro-batches, each loss divided by k, and then takes one optimizer step, so I get the gradient of a k-times-larger batch with the memory of a small one. I count scheduler steps per optimizer step and clip after the last micro-batch."

### 18. Rapid-fire answer
`loss/k` → `backward` ×k → `step` → `zero_grad`; same as a k-times batch; saves memory, not time.

### 20. Hands-on exercise
**Goal:** see the BatchNorm exception.

1. Build `Linear(8, 8) → BatchNorm1d(8) → Linear(8, 1)`.
2. Compute the gradient of the first layer's weight for one batch of 64, and as 4 accumulated micro-batches of 16.
3. Are they equal?

<details>
<summary>Show a solution</summary>

```python
import torch

torch.manual_seed(0)
net = torch.nn.Sequential(torch.nn.Linear(8, 8), torch.nn.BatchNorm1d(8), torch.nn.Linear(8, 1))
X, y = torch.randn(64, 8), torch.randn(64, 1)
mse = torch.nn.functional.mse_loss

net.zero_grad(); mse(net(X), y).backward()
big = net[0].weight.grad.clone()

net.zero_grad()
for i in range(4):
    (mse(net(X[i * 16:(i + 1) * 16]), y[i * 16:(i + 1) * 16]) / 4).backward()
print("equal:", torch.allclose(big, net[0].weight.grad, atol=1e-5))
print("largest difference:", f"{(big - net[0].weight.grad).abs().max().item():.1e}")
```

```text
equal: False
largest difference: 2.0e-01
```

BatchNorm normalizes with each micro-batch's own statistics, so the two computations are different functions.
</details>
