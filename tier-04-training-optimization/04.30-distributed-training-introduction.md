# 4.30 Distributed training: introduction

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: High · Hands-on: Medium
Prerequisites: 4.13 Batch size, 4.24 GPU memory · Leads to: 4.31 Data parallelism, 4.32 Tensor parallelism, 4.33 Pipeline parallelism, 4.34 FSDP/ZeRO

> **In plain words**
> One GPU is often **too slow** (the job would take months) or **too small** (the model does not fit). **Distributed training** splits the work across several GPUs or machines. There are two basic reasons and a few basic ways: split the **data** (every GPU holds the whole model, sees different examples), or split the **model** (each GPU holds a piece). The price is **communication**: GPUs must exchange numbers, and that can become the bottleneck.

**You need first:** 4.13 Batch size, 4.24 GPU memory.

### 1. What is it?
Training one model with multiple processes, each usually bound to one device, that coordinate through collective communication.

### 2. Why does it exist?
(1) **Speed:** more devices process more data per second. (2) **Capacity:** models and their training state exceed one device's memory (4.24).

### 3. Detailed explanation
- **Vocabulary:** a *process* per GPU; each has a *rank* (0…N−1); together the *world size* N. Launched with `torchrun`.
- **Communication primitives:** *broadcast* (rank 0 sends to all), *all-reduce* (sum across ranks, everyone gets the sum), *all-gather* (collect pieces from all), *reduce-scatter* (sum and give each rank a piece).
- **Data parallelism (DDP):** the same model on each GPU; each sees a different mini-batch; gradients are averaged with all-reduce; all replicas stay identical (4.31).
- **Sharded data parallelism (FSDP/ZeRO):** split parameters, gradients, optimizer state across GPUs; gather what a layer needs just in time (4.34).
- **Model parallelism:** tensor parallel splits matrix multiplies across GPUs (4.32); pipeline parallel puts different layers on different GPUs and streams micro-batches through (4.33).
- **Scaling cost:** compute shrinks per GPU, communication does not. Efficiency drops as N grows or when the interconnect is slow (inside a node NVLink is fast; between nodes it is slower).
- **Global batch** = per-GPU batch × N × accumulation steps; adjust the learning rate and warm-up (4.13).
- **Failures:** more machines means more failures; checkpoint often (4.20).
- **Reproducibility** across different world sizes is not exact (4.21).
- **Debugging:** start on one GPU, then two; deadlocks usually mean ranks diverged in control flow.
- **Alternatives:** use a bigger GPU, quantization, LoRA, or smaller batches before going distributed.

### 4. How does it work?
Launch N processes; each builds the model and gets a data shard; they synchronize through collectives at defined points (gradients, parameters).

### 5. Simple example
Grading 1,000 exams with 4 teachers: each takes 250 exams (data parallel); at the end they add up their tallies (all-reduce). Alternatively, one exam is so large that the teachers split its pages (model parallel).

**By hand.** One GPU processes 1,000 examples/s. 8 GPUs with perfect scaling: 8,000/s. With 85% efficiency: 6,800/s.

### 6. Technical example
`torchrun --nproc_per_node=8 train.py` with `DistributedDataParallel` or FSDP wrapping the model.

### 7. Code
**① By hand (plain Python).** Simulate an all-reduce across four "ranks".

```python
grads_per_rank = [[1.0, 2.0], [3.0, 2.0], [5.0, 2.0], [7.0, 2.0]]     # each rank's local gradient
n = len(grads_per_rank)
summed = [sum(g[i] for g in grads_per_rank) for i in range(2)]
averaged = [s / n for s in summed]
print("all-reduce (average):", averaged)
print("every rank now holds:", [averaged for _ in range(n)][0], "-> replicas stay identical after the update")
```

```text
all-reduce (average): [4.0, 2.0]
every rank now holds: [4.0, 2.0] -> replicas stay identical after the update
```

**② With NumPy.** Why the average of micro-batch gradients equals the big-batch gradient.

```python
import numpy as np

rng = np.random.default_rng(0)
X, y, w = rng.normal(size=(64, 3)), rng.normal(size=64), rng.normal(size=3)
grad = lambda Xb, yb: 2 * Xb.T @ (Xb @ w - yb) / len(yb)
shards = np.array_split(np.arange(64), 4)                              # 4 "GPUs", 16 examples each
local = [grad(X[s], y[s]) for s in shards]
print("average of the 4 local gradients equals the full-batch gradient:", np.allclose(np.mean(local, axis=0), grad(X, y)))

for n_gpus, eff in ((1, 1.0), (8, 0.95), (64, 0.85), (512, 0.6)):
    print(f"{n_gpus:>4} GPUs at {eff:.0%} efficiency -> {n_gpus * eff:6.1f}x single-GPU speed")
```

```text
average of the 4 local gradients equals the full-batch gradient: True
   1 GPUs at 100% efficiency ->    1.0x single-GPU speed
   8 GPUs at 95% efficiency ->    7.6x single-GPU speed
  64 GPUs at 85% efficiency ->   54.4x single-GPU speed
 512 GPUs at 60% efficiency ->  307.2x single-GPU speed
```

**③ With PyTorch.** Run a real two-process job on the CPU (gloo backend) and all-reduce.

```python
import torch
import torch.distributed as dist
import torch.multiprocessing as mp
import os, tempfile

def worker(rank, world_size, path):
    dist.init_process_group("gloo", init_method=f"file://{path}", rank=rank, world_size=world_size)
    t = torch.tensor([float(rank + 1)])                                # rank 0 has 1.0, rank 1 has 2.0
    dist.all_reduce(t, op=dist.ReduceOp.SUM)
    if rank == 0:
        print(f"world size {dist.get_world_size()}: after all-reduce every rank holds", t.item())
    dist.destroy_process_group()

path = os.path.join(tempfile.mkdtemp(), "rendezvous")
mp.start_processes(worker, args=(2, path), nprocs=2, start_method="fork")
```

```text
world size 2: after all-reduce every rank holds 3.0
```

### 9. Enterprise use case
Cluster scheduling, cost per GPU-hour, interconnect choice and checkpoint/restart policy drive training budgets.

### 10. AI engineering connection
All frontier LLMs are trained with combinations of data, tensor, pipeline and sharded parallelism.

### 11. Advantages
Faster training; trains models that do not fit on one device.

### 12. Limitations
Communication overhead; complexity; failure handling; non-exact reproducibility.

### 13. Trade-offs
More GPUs reduce time but cost more in communication and money; sometimes a smaller model on one GPU is better.

### 14. Common mistakes
Going distributed too early; forgetting to scale the learning rate; saving checkpoints from every rank; data shards that overlap; ranks that take different code paths (deadlock).

### 15. Performance / cost
Overlap communication with computation; keep tensor parallelism within a node; use bucketed all-reduce.

### 16. Security
Multi-tenant clusters need network isolation; gradient communication can expose data in federated setups.

</details>

### 17. Interview explanation
"Distributed training uses multiple processes, one per GPU, that coordinate with collectives. Data parallelism replicates the model and averages gradients with all-reduce; sharding splits optimizer state, gradients and parameters; tensor and pipeline parallelism split the model itself. The trade-off is communication cost, which limits scaling efficiency."

### 18. Rapid-fire answer
Processes with ranks and a world size; collectives (all-reduce, all-gather); data / sharded / tensor / pipeline parallelism; communication limits scaling.

### 20. Hands-on exercise
**Goal:** simulate the cost of communication.

1. Compute time per step is 100 ms on one GPU for a batch of 32.
2. With N GPUs the compute per GPU stays 100 ms (each gets 32 examples), and an all-reduce adds `5 ms × log2(N)`.
3. Compute throughput (examples/s) and efficiency for N = 1, 2, 8, 64.

<details>
<summary>Show a solution</summary>

```python
import math

base = 32 / 0.100                                                   # examples per second on one GPU
for n in (1, 2, 8, 64):
    step = 0.100 + 0.005 * math.log2(n)
    throughput = n * 32 / step
    print(f"{n:>3} GPUs: {throughput:8.0f} examples/s   efficiency {throughput / (n * base):.0%}")
```

```text
  1 GPUs:      320 examples/s   efficiency 100%
  2 GPUs:      610 examples/s   efficiency 95%
  8 GPUs:     2226 examples/s   efficiency 87%
 64 GPUs:    15754 examples/s   efficiency 77%
```
