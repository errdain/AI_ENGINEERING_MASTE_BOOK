# 4.25 Profiling

**Metadata** — Tier: 4 · Phase: 1 · Priority: P0 · Difficulty: 3/5 · Interview: High · Hands-on: Very high

> **In plain words**
> **Profiling** means **measuring where the time goes** in your training step before trying to make it faster. Guessing is usually wrong: the slow part is often the data loading, a hidden synchronization, or a tiny operation repeated thousands of times, not the big matrix multiplication you suspected.
> The rule: measure, change one thing, measure again.

**You need first:** 4.1 Training loop, 4.23 CPU vs GPU.

> **Figure 4.25-1 — a step split into phases**
>
> ```mermaid
> flowchart LR
>     D["data loading"] --> F["forward"]
>     F --> B["backward"]
>     B --> O["optimizer step"]
>     O --> L["logging / checkpoint"]
> ```
>
> *How to read it:* time each box separately. If the GPU waits for the data box, a faster model will not help; if backward dominates, look at the model; if the last box is big, you are logging or saving too often.

**Words you'll meet on this page**

| Word | What it means here |
|---|---|
| profiler | tool that records how long each operation takes |
| bottleneck | the slowest stage, which limits overall speed |
| wall time | real elapsed time |
| warm-up iterations | first steps that include one-off setup costs |
| synchronize | wait for GPU work to finish before reading the clock |
| utilization | the share of time the device is busy |
| FLOPs / MFU | operations per second / share of the hardware's peak achieved |

### 1. What is it?
Measuring time (and memory) per operation or per phase of the training step, with timers or `torch.profiler`.

### 2. Why does it exist?
Cost and iteration speed. A 20% speed-up on a month-long run saves six days. But optimizing the wrong part saves nothing.

### 3. Detailed explanation
- **Start simple:** time the phases of a step with `time.perf_counter()` (code ①). Drop the first few iterations (warm-up, compilation, caching).
- **GPU timing caveat.** GPU kernels run asynchronously; call `torch.cuda.synchronize()` before reading the clock or use CUDA events, otherwise you time only the launch.
- **`torch.profiler`** records every operator on CPU and GPU, memory use and a timeline you can open in TensorBoard or Chrome (code ③).
- **Typical findings:** (1) data loader too slow, GPU idle (4.26); (2) a hidden `.item()` or `.cpu()` forcing synchronization; (3) many tiny operations (launch overhead) that fusion or `torch.compile` could merge; (4) too small a batch; (5) slow logging.
- **Utilization:** `nvidia-smi` shows GPU use; consistently below ~80% suggests an input or Python bottleneck.
- **MFU (model FLOPs utilization):** achieved FLOPs ÷ the hardware's peak. LLM training reports 30–60% as good (REVIEW_REQUIRED).
- **FLOP counting by hand:** a dense layer costs `2·in·out` per example forward; backward ≈ 2× that (3.20). Compare with the measured time.
- **Profile at realistic sizes:** a toy batch hides the real bottleneck.
- **Change one thing at a time** and keep the measurement script.
- **Don't profile with the profiler on all the time:** it adds overhead.

### 4. How does it work?
Wrap regions of the loop in timers or run a profiler for a few steps; read the sorted table of operators.

### 5. Simple example
A road trip log: how long driving, how long at gas stations, how long in traffic. If most time is traffic, a faster car will not help.

**By hand.** A step takes 100 ms: data 60, forward 15, backward 20, optimizer 5. The bottleneck is data (60%); making the model twice as fast saves only 17 ms.

### 6. Technical example
`with torch.profiler.profile(activities=[CPU, CUDA], schedule=torch.profiler.schedule(wait=1, warmup=1, active=3)) as prof:` around a few training steps.

### 7. Code
**① By hand (plain Python).** A phase timer; the share of each phase.

```python
import time

class Timer:
    def __init__(self):
        self.t = {}
    def phase(self, name, fn):
        start = time.perf_counter(); out = fn(); self.t[name] = self.t.get(name, 0) + time.perf_counter() - start
        return out

timer = Timer()
for _ in range(5):
    timer.phase("data", lambda: sum(i * i for i in range(300000)))     # pretend slow data loading
    timer.phase("compute", lambda: sum(i for i in range(30000)))      # pretend fast compute
slowest = max(timer.t, key=timer.t.get)
print("slowest phase:", slowest)
print("data loading takes more than compute:", timer.t["data"] > timer.t["compute"])
```

```text
slowest phase: data
data loading takes more than compute: True
```

**② With NumPy.** FLOP counting and arithmetic intensity (no timing needed).

```python
layers = [(784, 512), (512, 256), (256, 10)]
batch = 128
forward_flops = sum(2 * i * o for i, o in layers) * batch
total_flops = 3 * forward_flops                                        # forward + backward (about 2x forward)
params = sum(i * o + o for i, o in layers)
print(f"parameters: {params:,}")
print(f"forward FLOPs per step: {forward_flops:,}   whole step (about 3x): {total_flops:,}")
print(f"at 1e11 FLOP/s a CPU would need about {total_flops / 1e11 * 1000:.1f} ms per step; at 1e13 FLOP/s about {total_flops / 1e13 * 1000:.2f} ms")
```

```text
parameters: 535,818
forward FLOPs per step: 136,970,240   whole step (about 3x): 410,910,720
at 1e11 FLOP/s a CPU would need about 4.1 ms per step; at 1e13 FLOP/s about 0.04 ms
```

**③ With PyTorch.** The built-in profiler finds the matrix multiplications.

```python
import torch
from torch.profiler import profile, ProfilerActivity

torch.manual_seed(0)
model = torch.nn.Sequential(torch.nn.Linear(512, 1024), torch.nn.ReLU(), torch.nn.Linear(1024, 10))
opt = torch.optim.SGD(model.parameters(), lr=0.01)
X, y = torch.randn(256, 512), torch.randint(0, 10, (256,))

with profile(activities=[ProfilerActivity.CPU]) as prof:
    for _ in range(3):
        opt.zero_grad()
        torch.nn.functional.cross_entropy(model(X), y).backward()
        opt.step()
rows = sorted(prof.key_averages(), key=lambda r: r.self_cpu_time_total, reverse=True)[:6]
names = [r.key for r in rows]
print("a matrix-multiply operator is among the 6 most expensive:", any("mm" in n for n in names))
print("operators recorded include the optimizer and loss:", any("cross_entropy" in n or "nll" in n or "log_softmax" in n for n in [r.key for r in prof.key_averages()]))
```

```text
a matrix-multiply operator is among the 6 most expensive: True
operators recorded include the optimizer and loss: True
```

### 9. Enterprise use case
Profiling guides the purchase and tuning of expensive clusters; a 10% efficiency gain pays for engineering time.

### 10. AI engineering connection
Kernel fusion, FlashAttention, `torch.compile` and data-pipeline work all start from a profile.

### 11. Advantages
Replaces guesses with data.

### 12. Limitations
Overhead of profiling; results depend on hardware and sizes; GPU async makes naive timing wrong.

### 13. Trade-offs
Detailed traces are large; sample a few steps.

### 14. Common mistakes
Timing the first iteration; not synchronizing the GPU; profiling a toy size; changing several things at once; optimizing before measuring.

### 15. Performance / cost
Keep profiling out of production runs, or sample rarely.

### 16. Security
Traces can reveal model structure and shapes; treat them as internal.

### 17. Interview explanation
"I profile before optimizing: time each phase (data, forward, backward, optimizer), skip warm-up steps, synchronize the GPU before reading the clock, and use torch.profiler to see operator times. Common wins are fixing a slow data loader, removing `.item()` syncs, increasing batch size and fusing small ops."

### 18. Rapid-fire answer
Measure phases, skip warm-up, synchronize GPU timing, use `torch.profiler`; look for data-loading stalls, syncs, tiny kernels; check utilization/MFU.

### 20. Hands-on exercise
**Goal:** find the bottleneck of a toy pipeline and the benefit of fixing it.

1. A "data" step takes `sum(range(200000))`, a "model" step takes `sum(range(50000))`.
2. Measure each over 20 repetitions and compute the shares.
3. If the data step were made 4× faster, what fraction of time would the whole step save?

<details>
<summary>Show a solution</summary>

```python
import time

def timed(fn, reps=20):
    start = time.perf_counter()
    for _ in range(reps):
        fn()
    return time.perf_counter() - start

data = timed(lambda: sum(range(200000)))
model = timed(lambda: sum(range(50000)))
total = data + model
print("data is the larger share:", data > model, "   data share is over 60%:", data / total > 0.6)
saved = data * (1 - 1 / 4) / total
print("4x faster data step would save more than half of the step time:", saved > 0.5)
```

```text
data is the larger share: True    data share is over 60%: True
4x faster data step would save more than half of the step time: True
```

</details>
