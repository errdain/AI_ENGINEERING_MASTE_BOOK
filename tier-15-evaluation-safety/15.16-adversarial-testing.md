### 1. WHAT IS IT?

Adversarial testing deliberately searches for inputs that make the model fail (wrong answer, policy violation, leak), rather than sampling typical inputs.

### 2. WHY DOES IT EXIST?

Typical-input evaluation underestimates worst-case behaviour; attackers choose worst cases.

### 3. DETAILED EXPLANATION

Approaches: hand-crafted attack prompts, templates (role-play, encoding, instruction override), automated search (mutating prompts, using another model as attacker), perturbation search (typos or tokens that flip the output), and data-poisoning or backdoor probes (REVIEW_REQUIRED, advanced).

Metrics: **attack success rate (ASR)** = successful attacks / attempts, minimum-perturbation to flip, per-attack-family ASR. Always report the attack budget; ASR is only meaningful with it, and a lower ASR against a fixed attack set does not prove safety (attackers adapt). Human red teams (""[15.24 Red teaming](15.24-red-teaming.md)"") complement automated search. Tier 32 owns guardrail design and attack taxonomies.

### 4. HOW DOES IT WORK?

Define threat model and goal -> generate/mutate attacks -> run -> judge success (human-verified for safety) -> add successful attacks to regression sets ([15.25 Regression datasets](15.25-regression-datasets.md)).

### 5. SIMPLE EXAMPLE

A locksmith testing your lock by trying to pick it, not by turning the key normally.

### 6. TECHNICAL EXAMPLE

Mutate a refusal-triggering prompt 50 ways; 4 slip through: ASR 8% at budget 50. Add the 4 to the regression set.

### 7. CODE

```python
# run inside lab/ -- ASR bookkeeping with a CI
import numpy as np
from metrics import wilson_interval
success = np.array([1] * 4 + [0] * 46)
print("ASR", success.mean(), "95% CI", tuple(round(v, 3) for v in wilson_interval(int(success.sum()), len(success))))
```

### 8. INPUT → PROCESS → OUTPUT

```
threat model -> attack generator -> target model -> success judge -> ASR + new regression cases
```

### 9. ENTERPRISE USE CASE

Security and trust teams run scheduled adversarial suites and treat new successful attacks as incidents.

### 10. AI ENGINEERING CONNECTION

Foundation for Tier 32 prompt-injection and guardrail testing.

### 11. ADVANTAGES

- Finds worst-case failures.

### 12. LIMITATIONS

- Never exhaustive; depends on attacker creativity and budget.

### 13. TRADE-OFFS

- Automation scale vs human creativity.

### 14. COMMON MISTAKES

- Reporting ASR without budget.
- Fixing only the exact attacks found.

### 15. PERFORMANCE / COST CONSIDERATIONS

Search is compute-heavy; human red teaming is expensive.

### 16. SECURITY CONSIDERATIONS

Handle attack corpora as sensitive: they are a recipe collection; restrict access.

### 17. INTERVIEW EXPLANATION

Adversarial testing searches for failure-inducing inputs under a threat model. I report attack success rate with the attack budget and CI, verify successes by humans for safety, and feed them into regression datasets; I never claim robustness from a fixed attack list alone.

### 18. RAPID-FIRE ANSWER

Search for failures; ASR with budget; feed back into regressions.

### 19. INTERVIEW QUESTIONS

- **Basic:** Define ASR.
- **Intermediate:** Why is a low ASR not proof of safety?
- **Advanced:** How would you automate attack generation?
- **Scenario:** A new jailbreak spreads publicly; what is your process?
