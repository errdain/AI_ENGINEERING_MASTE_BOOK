### 1. WHAT IS IT?

Foundation-model evaluation is the practice of measuring what a general-purpose model can and cannot do, how reliably, and how safely. It is hard because the model has no single task, no single correct answer and no fixed input distribution.

### 2. WHY DOES IT EXIST?

Classic ML had one task and one test set; one number summarised quality. A foundation model is used for thousands of tasks nobody listed in advance, so the evaluation question changes from 'is it accurate?' to 'is it good enough, for whom, at what risk, compared with what?'. This concept explains why the later concepts in the tier are needed at all.

### 3. DETAILED EXPLANATION

Six recurring difficulties, each of which later concepts address:

1. **Open-ended outputs.** Free text has many acceptable answers; exact match under-counts, overlap metrics reward the wrong things, so we need rubrics, human review and judges ([15.27 Human evaluation](15.27-human-evaluation.md), [15.28 LLM-as-judge concepts and limitations](15.28-llm-as-judge-concepts-and-limitations.md)).
2. **Unbounded input space.** You cannot enumerate prompts; coverage comes from sampling and slicing ([15.6 Benchmark design](15.06-benchmark-design.md), [15.15 Robustness](15.15-robustness.md)).
3. **Contamination.** Public benchmarks may be in the training data, so a high score may be recall, not skill ([15.21 Memorization/data-leakage evaluation](15.21-memorization-data-leakage-evaluation.md)).
4. **Metric-goal gap.** Benchmarks are proxies; optimising them (Goodhart's law) breaks the proxy.
5. **Stochasticity and sensitivity.** Sampling, prompt wording and few-shot order change scores; one run is an anecdote ([15.29 Evaluation reproducibility](15.29-evaluation-reproducibility.md)).
6. **Safety is a tail property.** Average quality can be excellent while rare failures are catastrophic ([15.22 Model safety](15.22-model-safety.md), [15.24 Red teaming](15.24-red-teaming.md)).

Evaluation is also a moving target: the model, the prompt, the data and the user population all change, so evaluation must be versioned and repeatable ([15.30 Evaluation versioning](15.30-evaluation-versioning.md)).

### 4. HOW DOES IT WORK?

Treat evaluation as an engineered measurement system: define the question, choose or build a dataset, choose a scorer, run it reproducibly, attach uncertainty, and turn the result into a decision (gate). The tier follows exactly that order.

### 5. SIMPLE EXAMPLE

Judging a new employee by one multiple-choice test would be silly: you would also want to see real work samples, references, behaviour under pressure, and how they do after a month. A foundation model is that employee, hired for every role at once.

### 6. TECHNICAL EXAMPLE

Two models score 71.0 and 72.5 on a 300-question benchmark. A 95% interval on each is roughly +/-5 points, so the ranking is not established ([15.6 Benchmark design](15.06-benchmark-design.md)). Re-running with a different prompt template changes both numbers by several points. A reported 'win' of this kind is noise.

### 7. CODE

```python
# run inside lab/ -- how wide is the uncertainty on a score from only n examples?
from metrics import wilson_interval
for n in (50, 300, 3000):
    lo, hi = wilson_interval(round(0.72 * n), n)
    print(f"n={n:5d}: accuracy 0.72, 95% CI [{lo:.3f}, {hi:.3f}] (width {hi - lo:.3f})")
```

### 8. INPUT → PROCESS → OUTPUT

```
model + prompts + (noisy) scorer
   -> scores on a finite sample
   -> uncertainty (CI) + slices + failure analysis
   -> decision (ship / hold / fix)
```

### 9. ENTERPRISE USE CASE

A product team cannot ship on 'it feels better'. They keep a versioned evaluation suite, run it on every model or prompt change and store the results so that a regression can be traced to a change.

### 10. AI ENGINEERING CONNECTION

Every LLM application inherits these difficulties. RAG adds retrieval and groundedness questions ([15.14 Groundedness](15.14-groundedness.md)); agents add multi-step trajectories (later tiers). Tier 30 generalises this tier's foundations to application-level evaluation.

### 11. ADVANTAGES

- Naming the difficulties early prevents false confidence.
- Gives a checklist for reviewing any reported benchmark result.

### 12. LIMITATIONS

- A list of difficulties is not a method; the rest of the tier supplies methods.
- Some difficulties (what 'good' means) are value judgements, not engineering problems.

### 13. TRADE-OFFS

- Rigour vs speed: stronger evaluation costs data, compute and reviewer time.
- Breadth (many tasks) vs depth (reliable score per task).

### 14. COMMON MISTAKES

- Reporting a single number without an interval.
- Treating a public leaderboard as the ground truth for your use case.
- Evaluating once at launch and never again.

### 15. PERFORMANCE / COST CONSIDERATIONS

Evaluation compute scales with (models x prompts x samples). Cheap automatic checks run on every change; expensive human or judge-based reviews run on a smaller, targeted set.

### 16. SECURITY CONSIDERATIONS

An evaluation set that leaks into training silently invalidates results; keep held-out sets private and access-controlled ([15.21 Memorization/data-leakage evaluation](15.21-memorization-data-leakage-evaluation.md)).

### 17. INTERVIEW EXPLANATION

Foundation models do many tasks with free-form outputs, so no single metric captures quality. Scores come from finite samples, may be contaminated, and are sensitive to prompts and sampling. Good practice is to define the question, use sliced and uncertainty-aware metrics, combine automatic, judge and human review, version everything and decide with explicit gates.

### 18. RAPID-FIRE ANSWER

Open-ended outputs, unbounded inputs, contamination, proxy metrics, stochasticity, tail risk: so measure with uncertainty, slices and gates, not one number.

### 19. INTERVIEW QUESTIONS

- **Basic:** Why is evaluating an LLM harder than evaluating a spam classifier?
- **Intermediate:** Name three reasons a benchmark score may not predict production quality.
- **Advanced:** How would you tell whether a 1.5-point benchmark gain is real?
- **Scenario:** Your vendor says model B beats model A by 2 points on a public benchmark. What do you ask before switching?
