### 1. WHAT IS IT?

Task-specific evaluation scores a model on the concrete task it will perform (classification, extraction, summarisation, QA, code, tool use) with a metric suited to that task.

### 2. WHY DOES IT EXIST?

General benchmarks do not tell you whether the model extracts invoice totals correctly. The task defines inputs, outputs and what counts as correct.

### 3. DETAILED EXPLANATION

| Task type | Typical scorer |
|---|---|
| Classification | accuracy, precision/recall/F1 ([15.9 Accuracy](15.09-accuracy.md), [15.10 Precision/recall/F1 in model evaluation](15.10-precision-recall-f1-in-model-evaluation.md)) |
| Extraction | exact match, token-level F1 |
| Generation (summary, rewrite) | rubric or judge ([15.28 LLM-as-judge concepts and limitations](15.28-llm-as-judge-concepts-and-limitations.md)), human ([15.27 Human evaluation](15.27-human-evaluation.md)), plus faithfulness ([15.14 Groundedness](15.14-groundedness.md)) |
| Code | unit tests (pass rate) |
| Retrieval-augmented QA | answer correctness + groundedness + citation accuracy |
| Safety-critical | per-class recall, worst-slice score |

Pick a **primary** metric tied to the decision and a few **guardrail** metrics (cost, latency, safety). Report per slice.

### 4. HOW DOES IT WORK?

Write 20-50 realistic examples first, define correctness, build the scorer, validate the scorer against human labels, then scale the set.

### 5. SIMPLE EXAMPLE

Testing a translator by asking them to translate your contracts, not by general trivia.

### 6. TECHNICAL EXAMPLE

Invoice extraction: score each field by exact match after normalisation; also report per-field recall so a rare field is not hidden by the average.

### 7. CODE

```python
# run inside lab/ -- two task scorers shipped with the harness
from evalharness import exact_match, token_f1
print(exact_match("Paris.", "paris"))                    # 1.0 after normalisation
print(round(token_f1("the capital is Paris", "Paris is the capital"), 2))   # 1.0 bag-of-words
```

### 8. INPUT → PROCESS → OUTPUT

```
task spec -> examples + references -> scorer (validated) -> per-slice metrics -> decision
```

### 9. ENTERPRISE USE CASE

Each AI feature owns a task-specific suite in CI; the platform team owns shared harness code.

### 10. AI ENGINEERING CONNECTION

Task evaluation is the unit of Tier 30 application evaluation (RAG, agents).

### 11. ADVANTAGES

- Directly tied to value.
- Scorers can be exact.

### 12. LIMITATIONS

- Requires labelled data.
- Task suites do not reveal unrelated failures.

### 13. TRADE-OFFS

- Specificity vs generality.

### 14. COMMON MISTAKES

- Using BLEU-like overlap as a proxy for quality without validation.
- Skipping scorer validation.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost: labelling plus runs; start small.

### 16. SECURITY CONSIDERATIONS

Task data often contains customer data: anonymise first ([15.20 Privacy evaluation](15.20-privacy-evaluation.md)).

### 17. INTERVIEW EXPLANATION

Task-specific evaluation uses realistic inputs and a scorer matched to the task: exact match/F1 for extraction, unit tests for code, rubrics or judges for generation. I define a primary metric and guardrails, validate the scorer against humans and report per slice.

### 18. RAPID-FIRE ANSWER

Real task, right scorer, validated, sliced.

### 19. INTERVIEW QUESTIONS

- **Basic:** Why not just use public benchmarks?
- **Intermediate:** How would you evaluate summarisation?
- **Advanced:** How do you validate an automatic scorer?
- **Scenario:** Extraction accuracy is 95% but customers complain; what slice analysis do you run?

### 20. HANDS-ON EXERCISE

Build a 20-item extraction dataset and score a regex 'model' with exact match and token F1.
