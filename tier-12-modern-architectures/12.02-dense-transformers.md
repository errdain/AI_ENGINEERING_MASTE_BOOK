### 1. WHAT IS IT?

A **dense** Transformer uses *all* of its parameters for every token: every layer's attention and FFN weights participate in each forward pass. Parameters = active parameters.

### 2. WHY DOES IT EXIST?

Dense models are the baseline: simple to train, easy to shard, predictable latency. Sparse/MoE models are defined against them.

### 3. DETAILED EXPLANATION

Parameter count of a bias-free decoder layer (hand-checkable, implemented in [`lab/arch_matrix.py`](lab/arch_matrix.py) and its tests): attention `d·H·d_h + 2·d·H_kv·d_h + H·d_h·d`, gated FFN `3·d·d_ff`, norms `2d`. Add embeddings `V·d` (and an untied output head `V·d`). Parameter counting in full is owned by [Tier 8 Transformer Architecture](../tier-08-transformer-architecture/README.md).

Per-token decode FLOPs ≈ 2 × (matmul parameters) + attention term `4·n·H·d_h` per layer for context `n`.

### 4. HOW DOES IT WORK?

1. Count parameters from the config. 2. Weights memory = params × bytes. 3. FLOPs/token ≈ 2 × params (+ attention term). 4. KV cache from `H_kv` (see [12.7 Grouped-Query Attention (GQA) in modern models](12.07-grouped-query-attention-gqa-in-modern-models.md)).

### 5. SIMPLE EXAMPLE

A restaurant where every cook works on every dish: simple coordination, but doubling the menu doubles the labour.

### 6. TECHNICAL EXAMPLE

Llama-2-7B-shaped config (d=4096, 32 layers, 32 heads, d_ff=11008, V=32000, untied): the lab computes ~6.74 B parameters (REVIEW_REQUIRED against the model card).

### 7. CODE

```python
import sys; sys.path.insert(0, "lab")
import arch_matrix as am
s = am.PRESETS["Llama-2-7B-shape (case study)"]
print(am.total_params(s)/1e9, am.active_params(s) == am.total_params(s))   # ~6.74 True
print(am.flops_per_token(s, 8192)/1e9, "GFLOPs/token @ 8k")
```

### 8. INPUT → PROCESS → OUTPUT

```
config (d, L, H, H_kv, d_ff, V) → count params → weights GiB, GFLOPs/token, KV KiB/token
```

### 9. ENTERPRISE USE CASE

Capacity planning: weights GiB decides how many GPUs a replica needs; GFLOPs/token decides throughput.

### 10. AI ENGINEERING CONNECTION

Dense models are the default for fine-tuning (Tier 10) and the reference point for quantization (Tier 11).

### 11. ADVANTAGES

Simple; best-understood scaling behaviour (Tier 9); all parameters train every step.

### 12. LIMITATIONS

Compute grows linearly with parameters, so capacity and cost are coupled.

### 13. TRADE-OFFS

Dense gives predictable latency; MoE decouples capacity from compute at the price of memory and complexity.

### 14. COMMON MISTAKES

Quoting parameter counts that include or exclude embeddings inconsistently; comparing dense and MoE totals as if equal.

### 15. PERFORMANCE / COST CONSIDERATIONS

FLOPs/token ≈ 2·N; memory ≈ 2 bytes × N in bf16 plus KV cache.

### 16. SECURITY CONSIDERATIONS

Larger dense models memorise more training data; apply data-governance rules from Tier 9.

### 17. INTERVIEW EXPLANATION

*"Dense means every parameter is used for every token, so total and active parameters coincide and compute per token is about twice the parameter count."*

### 18. RAPID-FIRE ANSWER

Dense: all weights active every token; cost ≈ 2·params FLOPs.
