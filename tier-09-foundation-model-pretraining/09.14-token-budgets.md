### 1. WHAT IS IT?

**D = number of training tokens**, counting repeats: `D = steps x batch_size x context_length`. The token budget is the amount of data the run will consume, and it is bounded by the **unique tokens remaining after the whole pipeline**.

### 2. WHY DOES IT EXIST?

Token count, together with parameters N, sets compute (`6ND`, [9.15](09.15-compute-budgets.md)) and quality (scaling laws, [9.20](09.20-scaling-laws.md)). You must decide D before launching, and know whether you actually have that many unique tokens.

### 3. DETAILED EXPLANATION

The pipeline is a **funnel**: the final token count is the product of every stage's survival rate, so small per-stage changes compound. With the default rates of [data_funnel.html](interactive/data_funnel.html) (8%, 30%, 10%, 15%, 25%, 0.3% dropped) the yield is about **37%**, so you need roughly 2.7x as many raw documents as final documents. (An earlier draft of this chapter quoted 16%; the page's defaults compute to 0.92 x 0.70 x 0.90 x 0.85 x 0.75 x 0.997 = 0.368.)

Token budget, tokenizer and epochs are coupled: a different tokenizer changes how many tokens the same text is ([Tier 6](../tier-06-tokenization-embeddings/README.md)), and a budget above unique tokens means repeated epochs ([9.6](09.06-data-mixture-design.md)).

### 4. HOW DOES IT WORK?

1. Estimate raw tokens available. 2. Multiply by per-stage survival to get unique final tokens `U`. 3. Decide target `D` from the compute plan ([9.21](09.21-compute-data-model-scaling-trade-offs.md)). 4. Epochs = `D / U`. 5. If epochs are too high, collect more data, change mixture, or reduce D.

### 5. SIMPLE EXAMPLE

A school year of 180 lessons: you can repeat a lesson a few times, but not 40 times.

### 6. TECHNICAL EXAMPLE

Lab: `tokens_seen = 200 x 16 x 64 = 204,800`, about 3.6 passes over the ~57k-token training stream. That is far too many epochs for a real run; it is fine for a toy whose purpose is to exercise machinery.

### 7. CODE

```python
# Token budget arithmetic (standalone).
def unique_tokens(raw_docs: float, tokens_per_doc: float, survival: list[float]) -> float:
    u = raw_docs * tokens_per_doc
    for s in survival:
        u *= s
    return u

def epochs(budget_tokens: float, unique: float) -> float:
    return budget_tokens / unique

u = unique_tokens(500e6, 1200, [0.92, 0.70, 0.90, 0.85, 0.75, 0.997])
print(f"unique tokens {u:.3e}, epochs for a 1e12 budget {epochs(1e12, u):.2f}")

steps, batch, ctx = 200, 16, 64                       # the lab run
print("lab tokens seen:", steps * batch * ctx)
```

### 8. INPUT → PROCESS → OUTPUT

```
raw docs x tokens/doc x stage survival -> unique tokens U -> D (target) / U = epochs -> go / no-go
```

### 9. ENTERPRISE USE CASE

For a continued-pretraining proposal, compute unique in-domain tokens after cleaning and dedup first; many enterprise corpora turn out to be tens of billions of tokens or fewer, which limits what model size is sensible.

### 10. AI ENGINEERING CONNECTION

Context length, tokenizer fertility and training tokens all appear on model cards; "trained on N tokens" is the D of the scaling-law picture. Inference-time token costs ([Tier 11](../tier-11-llm-inference-optimization/README.md)) use the same tokens.

### 11. ADVANTAGES

- Makes data needs concrete and comparable across plans.
- Exposes data walls before spending compute.

### 12. LIMITATIONS

- Token counts are tokenizer-dependent; comparisons across tokenizers need care (use bits-per-byte for loss, [9.31](09.31-pretraining-evaluation.md)).
- Tokens are not equally valuable (quality varies).

### 13. TRADE-OFFS

Quality filtering and dedup lower D; accepting more repetition raises D but with diminishing returns; synthetic data adds D with its own risks.

### 14. COMMON MISTAKES

- Counting raw tokens instead of unique post-pipeline tokens.
- Ignoring that D includes repeats.
- Comparing token counts across different tokenizers.

### 15. PERFORMANCE / COST CONSIDERATIONS

Storage for raw + intermediate + final shards is several times the final size. Throughput planning needs tokens/sec per accelerator and the dataloader's ability to keep up.

### 16. SECURITY CONSIDERATIONS

A tight token budget tempts teams to relax filters (licensing, PII, contamination); keep policy checks as hard gates, not as budget variables.

### 17. INTERVIEW EXPLANATION

"The token budget is the number of training tokens including repeats, steps times batch times context. It's bounded by the unique tokens left after the pipeline, which is a product of stage survival rates, so I'd compute that first, then check epochs for the target budget. If the budget needs many epochs, the data, not the compute, is the bottleneck."

### 18. RAPID-FIRE ANSWER

`D = steps x batch x context`, limited by unique post-pipeline tokens; epochs = D / unique.
