### 1. WHAT IS IT?

Keeping tokens spread across experts during MoE pretraining, via an **auxiliary balancing loss** and a **capacity factor**.

### 2. WHY DOES IT EXIST?

Left alone, a router tends to **collapse**: a few experts get most tokens, get trained more, get better and attract still more tokens (rich-get-richer); the others become dead parameters. Hardware also suffers: a hot expert is a straggler. A capacity factor caps tokens per expert; **overflow tokens are dropped** (they skip the layer via the residual) or re-routed.

### 3. DETAILED EXPLANATION

**Switch-style auxiliary loss:** `L_aux = E · Σᵢ fᵢ · Pᵢ`, where `fᵢ` is the fraction of tokens whose *top-1* expert is *i* (hard, non-differentiable) and `Pᵢ` is the mean router *probability* for expert *i* (differentiable). For a perfectly uniform load and uniform probabilities, `fᵢ = Pᵢ = 1/E` and `L_aux = 1`. When `f = P` it equals `E·ΣPᵢ² ≥ 1` (Cauchy-Schwarz) and grows as the load concentrates. (An earlier draft of this chapter called `L_aux ≥ 1` a general bound; it is only exact for that matched case, though `f` and `P` are strongly correlated in practice, since top-1 selects the largest probability. The lab test checks `L_aux ≥ 1` in its specific setting.) It is added to the task loss with a small weight (lab default 0.01); the gradient flows through `Pᵢ`, pushing probability mass away from over-used experts.

### 4. HOW DOES IT WORK?

1. Per batch compute `fᵢ` (top-1 counts / tokens) and `Pᵢ` (mean router probabilities). 2. `L_aux = E Σ fᵢ Pᵢ`. 3. `loss_total = task_loss + w · L_aux`. 4. Capacity: `cap = capacity_factor · tokens·k / E`; tokens beyond `cap` for an expert are dropped or re-routed. 5. Log per-expert load and drop rate every step.

### 5. SIMPLE EXAMPLE

A supermarket with 8 checkouts where everyone queues at checkout 1: the manager (aux loss) nudges customers to other lanes, and a maximum queue length (capacity) sends overflow customers away.

### 6. TECHNICAL EXAMPLE

With 4 experts, top-2 and a skewed start, no balancing leaves two experts nearly idle; a weight of 0.5 in the GIF experiment moves the load towards 25% each. Too large a weight forces uniformity even where specialisation would help.

### 7. CODE

```python
# Run from lab/: the Switch-style auxiliary loss, by hand and from the layer.
import torch, torch.nn.functional as F
from model import MoEFFN

torch.manual_seed(0)
moe = MoEFFN(d=16, n_exp=4, top_k=2)
x = torch.randn(1, 64, 16)
moe(x)
flat = x.reshape(-1, 16)
probs = F.softmax(moe.router(flat), -1)
f = F.one_hot(probs.argmax(-1), 4).float().mean(0)            # top-1 load fraction
manual = 4 * (f * probs.mean(0)).sum()
print(float(manual), float(moe.aux_loss))                      # equal
uniform = torch.full((4,), 0.25); print(4 * (uniform * uniform).sum())   # exactly 1.0 for a uniform router
```

Source: [`lab/model.py`](lab/model.py) (`MoEFFN`).

### 8. INPUT → PROCESS → OUTPUT

```
router probs + top-1 assignments -> f_i, P_i -> L_aux = E·Σ f_i P_i -> total loss; capacity cap -> keep / drop overflow tokens
```

### 9. ENTERPRISE USE CASE

Training dashboards for MoE runs show per-expert token share, drop rate and router entropy per layer; alerts fire when any expert's share falls below a floor or the drop rate rises.

### 10. AI ENGINEERING CONNECTION

Balanced experts determine how well expert parallelism scales in both training and serving ([Tier 11](../tier-11-llm-inference-optimization/README.md)); collapse wastes parameters and quietly lowers quality.

### 11. ADVANTAGES

- Prevents collapse and keeps all experts useful.
- Reduces stragglers and improves hardware utilisation.

### 12. LIMITATIONS

- The auxiliary loss interferes with the task objective (routing quality) if over-weighted.
- Capacity limits drop tokens, which hurts quality and creates train/inference mismatch.

### 13. TRADE-OFFS

Large balancing weight: uniform but possibly worse routing (experts forced to share tokens they should not). Small weight: collapse. Capacity factor up: fewer drops but more padding/compute.

### 14. COMMON MISTAKES

- Judging MoE only by loss and never logging per-expert load.
- Comparing an MoE and a dense model at equal *total* parameters instead of equal active parameters or FLOPs.
- Ignoring that MoE inference needs all experts in memory.

### 15. PERFORMANCE / COST CONSIDERATIONS

Balanced load maximises MFU; drops waste forward compute. Expert-parallel all-to-all cost depends on balance across ranks, not only across experts.

### 16. SECURITY CONSIDERATIONS

Adversarial or unusually clustered inputs can skew load and cause drops for co-batched requests; consider per-tenant isolation or capacity headroom (`REVIEW_REQUIRED`).

### 17. INTERVIEW EXPLANATION

"A router picks top-k experts per token so compute stays low while parameters grow. Without a counterweight it collapses onto a few experts, so we add an auxiliary loss — fraction of tokens routed to each expert times mean router probability, summed over experts and scaled by E — that is minimal when load is uniform, plus a capacity factor to bound the hottest expert. I'd monitor per-expert load and drop rate throughout the run."

### 18. RAPID-FIRE ANSWER

The aux loss `E·Σ fᵢPᵢ` keeps the router from collapsing; capacity bounds the hottest expert.
