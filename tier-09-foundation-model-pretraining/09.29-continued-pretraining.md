### 1. WHAT IS IT?

Resuming the *same* next-token objective from an existing base checkpoint on new data: more tokens, a new language, longer context, or fresher knowledge.

### 2. WHY DOES IT EXIST?

Training from scratch repeats most of the cost. Starting from a strong base and adding data is far cheaper than a new pretraining run, and it keeps general ability while gaining the new capability.

### 3. DETAILED EXPLANATION

Key engineering points:

- Restart with a **short warmup and a lower peak LR** than the original: re-warming to the original peak can cause a loss bump.
- **Mix in replay data** from the original distribution to limit **catastrophic forgetting** (Tier 10 covers forgetting).
- Keep the **tokenizer fixed**; changing it needs embedding surgery and retraining.
- Evaluate **old and new** capabilities ([9.31](09.31-pretraining-evaluation.md)).

Exact recipes (LR re-warming, replay fractions) are empirical (`REVIEW_REQUIRED`).

![LR schedule](figures/12_lr_schedule.png)

*Figure 12 — A warmup + cosine schedule; in continued pretraining you start a *new*, shorter schedule from the base checkpoint (shorter warmup, lower peak), shown here as the short-warmup curve.*

In the lab, `train(..., resume=True)` with a larger `cfg.steps` continues from `latest.pt`; true continued pretraining starts a *new* run from the weights with a new, shorter schedule on a new corpus (Exercise below).

### 4. HOW DOES IT WORK?

1. Load base weights (optimizer state optional; usually re-initialised). 2. Prepare new data plus a replay slice of old data. 3. Define a new schedule: short warmup, peak LR lower than the original, decay. 4. Train. 5. Evaluate on old-capability and new-capability sets. 6. Compare forgetting with and without replay.

### 5. SIMPLE EXAMPLE

A surgeon learning a new technique: keeps practising the old operations a little each week (replay) while adding the new one, and doesn't retrain from medical school.

### 6. TECHNICAL EXAMPLE

Train 100 steps on wiki+web only, then start a *new* run from that checkpoint on code-heavy data with warmup 5 and LR x0.3, with and without 20% replay, and measure validation loss on the old wiki/web validation set: replay should reduce forgetting.

### 7. CODE

```python
# Run from lab/: load a base checkpoint and define the NEW, gentler schedule for continued pretraining (about 10 s).
import tempfile
from pathlib import Path
import run_lab
from model import ModelConfig
from pretrain import TrainConfig, train, load_checkpoint, lr_at

tok, tr, va, _ = run_lab.prepare()
mc = ModelConfig(vocab_size=tok.vocab_size)
base_dir = tempfile.mkdtemp()
train(TrainConfig(steps=60, eval_every=10**6, ckpt_every=60, model=mc), tr, va, base_dir)

ck = load_checkpoint(Path(base_dir) / "latest.pt")                 # keys: model, opt, step, config, history
cont = TrainConfig(steps=40, lr=1e-3, warmup=5, model=mc)          # lower peak LR (base used 3e-3), short warmup
print("base step:", ck["step"], "| new schedule:", [round(lr_at(s, cont), 5) for s in (0, 4, 5, 20, 39)])
```

The lab's `train` has no "init from weights" argument; adding one (load `ck["model"]`, ignore `ck["opt"]`, reset `step=0`) is a small exercise (below).

### 8. INPUT → PROCESS → OUTPUT

```
base checkpoint + new data (+ replay) -> new short schedule (lower peak LR) -> updated checkpoint -> old/new evals (forgetting check)
```

### 9. ENTERPRISE USE CASE

Extending an open base model to a new language or to a company's internal code and documents, with replay of general data and regression tests on the original capabilities.

### 10. AI ENGINEERING CONNECTION

Most "custom base models" in practice are continued-pretrained open models. It sits between fine-tuning ([Tier 10](../tier-10-fine-tuning-alignment/README.md)) and full pretraining, and the RAG-vs-adaptation decision ([9.30](09.30-domain-adaptive-pretraining.md)).

### 11. ADVANTAGES

- Far cheaper than training from scratch.
- Adds knowledge/skills/context length while keeping general ability.

### 12. LIMITATIONS

- Forgetting and loss bumps if LR/replay are mis-set.
- Cannot change the tokenizer or architecture cheaply.
- Knowledge is baked into weights (not deletable per document).

### 13. TRADE-OFFS

Higher LR adapts faster but forgets more; more replay protects old skills but slows learning the new domain; more new tokens help the target but cost compute.

### 14. COMMON MISTAKES

- Re-warming to the original peak LR.
- No replay data, no regression suite.
- Changing the tokenizer mid-stream.
- Evaluating only the new domain.

### 15. PERFORMANCE / COST CONSIDERATIONS

Cost ≈ `6 N D_new` (see [9.15](09.15-compute-budgets.md)), usually a small fraction of the original budget; plus evaluation of old capabilities.

### 16. SECURITY CONSIDERATIONS

Anything in the new corpus can be memorised and regurgitated; apply access-control-aware filtering, PII/secret scrubbing and membership-inference review first. Verify the base checkpoint's provenance and format (no pickle from untrusted sources).

### 17. INTERVIEW EXPLANATION

"Continued pretraining resumes next-token training from a base checkpoint on new data. I'd use a short warmup and a lower peak learning rate than the original, mix in replay from the original distribution to limit forgetting, keep the tokenizer fixed, and evaluate old and new capabilities. It's much cheaper than starting over, but the knowledge is baked in."

### 18. RAPID-FIRE ANSWER

Resume pretraining from a base checkpoint on new data with a lower LR, short warmup and replay.
