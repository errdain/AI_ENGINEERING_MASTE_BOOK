### 1. WHAT IS IT?

Pretraining a model whose feed-forward blocks are replaced by **E expert FFNs plus a router**; each token is processed by only its **top-k** experts. *Architecture of MoE blocks is taught in Tier 12; here: what changes during pretraining.*

### 2. WHY DOES IT EXIST?

Total parameters (capacity, knowledge) grow with E, while compute per token stays about that of **k** experts. Sparse models can reach lower loss at the same *training compute* than dense ones, at the price of larger memory footprint, all-to-all communication and trickier optimisation (`REVIEW_REQUIRED` for quantitative claims).

### 3. DETAILED EXPLANATION

**Total vs active parameters.** The `6ND` rule uses the *active* parameter count for FLOPs, while memory scales with *total* parameters. An 8-expert, top-2 layer has about 2 experts' worth of FFN compute per token but 8 experts' worth of memory. Comparing an MoE and a dense model at equal *total* parameters is a category error; compare at equal active parameters or equal FLOPs.

Pretraining-specific issues: routing must be learned jointly with the experts ([9.26](09.26-expert-routing.md)); the router tends to collapse without a balancing loss ([9.27](09.27-load-balancing.md)); training can be less stable ([9.28](09.28-training-stability.md)); expert parallelism needs all-to-all token dispatch ([9.23](09.23-distributed-pretraining.md)).

Lab: `model.MoEFFN` (token-choice, top-k, 4 experts in the demo); `python run_lab.py --moe 4` trains it end to end: **327,552** total parameters vs **128,512** dense (the extra are inactive-per-token expert weights).

### 4. HOW DOES IT WORK?

Per MoE layer: (1) router scores each token; (2) top-k experts chosen and gate weights renormalised; (3) each expert processes its tokens; (4) outputs combined by gate weights; (5) an auxiliary balancing loss is added to the task loss; (6) in distributed training tokens are exchanged between GPUs hosting different experts (all-to-all).

### 5. SIMPLE EXAMPLE

A hospital with many specialists: each patient sees two relevant specialists, not all of them. The hospital knows more than any visit uses, but it needs a building big enough for every specialist.

### 6. TECHNICAL EXAMPLE

In the lab, a 4-expert, top-2 MoE run reaches validation loss ≈ 0.82 vs ≈ 0.96 for the dense model in the same steps. Single seed, templated toy data: **not** evidence that MoE is better in general.

### 7. CODE

```python
# Run from lab/: total vs active parameters of the lab's dense and MoE models.
from model import ModelConfig, TinyLM

dense = TinyLM(ModelConfig(vocab_size=380))
moe = TinyLM(ModelConfig(vocab_size=380, moe_experts=4, moe_top_k=2))
print("dense total:", dense.num_params(), " moe total:", moe.num_params())   # 128,512 vs 327,552
# FFN params per expert = 2 * d * 4d + biases; active per token ~ top_k experts of E.
d = 64; per_expert = 2 * d * 4 * d + 4 * d + d
print("per expert:", per_expert, "-> active FFN params per MoE layer per token:", 2 * per_expert, "of", 4 * per_expert)
```

Source: [`lab/model.py`](lab/model.py) (`MoEFFN`).

### 8. INPUT → PROCESS → OUTPUT

```
token hidden states -> router -> top-k experts -> weighted sum of expert outputs -> next layer;   aux loss -> total loss
```

### 9. ENTERPRISE USE CASE

Serving organisations choose MoE for quality-per-FLOP but must budget memory for *all* experts and handle expert-parallel communication; pretraining one is a large-cluster project.

### 10. AI ENGINEERING CONNECTION

Many recent open and closed LLMs are reported to be MoE (`REVIEW_REQUIRED` per model). Model cards list *total* and *active* parameters; inference ([Tier 11](../tier-11-llm-inference-optimization/README.md)) needs all experts in memory even though few are active per token.

### 11. ADVANTAGES

- More capacity per training and inference FLOP.
- Naturally specialised experts (to some degree).

### 12. LIMITATIONS

- Larger memory footprint and all-to-all communication.
- Routing instability, expert collapse and token dropping under capacity limits.
- Harder to fine-tune and serve efficiently at small batch sizes.

### 13. TRADE-OFFS

Quality per FLOP vs memory and complexity; more, smaller experts (finer specialisation) vs routing overhead; strong balancing (uniform load) vs routing quality.

### 14. COMMON MISTAKES

- Judging MoE only by loss and never logging per-expert load.
- Comparing MoE and dense at equal total parameters.
- Ignoring that MoE inference needs all experts in memory.
- Using total parameters in `6ND`.

### 15. PERFORMANCE / COST CONSIDERATIONS

Training FLOPs use active parameters; communication (all-to-all) and load imbalance reduce MFU; capacity factor trades dropped tokens for padding compute ([9.27](09.27-load-balancing.md)).

### 16. SECURITY CONSIDERATIONS

Routing can be adversarially manipulated to overload experts (a denial-of-service style risk in shared batches; `REVIEW_REQUIRED`). Treat routing statistics as monitored production signals.

### 17. INTERVIEW EXPLANATION

"An MoE layer replaces the FFN with many experts and a router that picks the top-k per token, so total parameters grow while compute per token stays at about k experts. The 6ND rule uses active parameters; memory uses total. The pretraining-specific issues are router collapse, which we counter with a balancing loss, communication from all-to-all dispatch, and trickier stability."

### 18. RAPID-FIRE ANSWER

MoE = many experts, few active per token: more parameters, similar FLOPs, more memory and routing complexity.
